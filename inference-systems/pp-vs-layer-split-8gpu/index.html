单机 8 卡：PP2 还是 LayerSplit —— 以 6000D 为例的选型

2026-11-16 SGLang v0.5.23 PP · LayerSplit · PD 读源码 + 推导

你给的两个候选里，TP8 + LayerSplit 在单机 8 卡上不是一个可部署的配置 —— 不是性能问题，是它根本起不来。把这条排除之后，真正的三选一是 TP8 unified、TP4×PP2 unified、PD 4+4（prefill 侧带 LayerSplit）， 而它们的差别可以算成一张每卡 KV 容量的账。

TL;DR · 四条

  • TP8 + LayerSplit 需要 16 卡：LayerSplit 只存在于 PD 的 prefill worker， 而 prefill 与 decode 的 TP 拓扑必须对齐 —— TP8 prefill 就是 8 卡，再加 8 卡 decode。 8 卡机上想用 LayerSplit，只能切成 4+4。
  • PP2 把每卡 KV 砍半（容量 ×1.97），PD 4+4 不会。 PD 把一半卡让给 prefill，decode 侧仍是 L 层/卡 —— 换来的是 TTFT 隔离， 代价是 decode 算力减半。
  • 6000D 上第一个会炸的是后端：SM120/SM121 + GLM DSA + FP8 KV 只允许 flashinfer_sparse_mla（默认）或 triton_sparse_mla（prefill）， --dsa-prefill-backend trtllm 会被直接拒绝 —— 所以 B300 那份 e2e 配方照抄不过来。
  • 默认就选 TP8 unified；只有当你已经因为显存跑不到目标并发、且长上下文占主导时， 才上 TP4×PP2；LayerSplit 留给「prefill 与 decode 本来就分机」的场景。
术语约定
  • LayerSplit = --enable-dsa-cache-layer-split；PP = pipeline parallel（--pp-size）； CP = --attn-cp-size（attention context parallel，嵌在 TP 世界内）；PD = prefill/decode 分离。
  • 6000D 按 SM120（sm_120） 处理 —— 这不是猜的，源码里 SM120/SM121 是 GLM DSA + FP8 KV 的 一等分支（kernels/ops/attention/flash_mla_sm120.py:698-722）。
  • 行号对应 v0.5.23。所有容量数字都是公式推导，未做运行时实测； 互连带宽按你自己的机器填（本页不给 6000D 的带宽断言）。

01先把 TP8 + LayerSplit 排除掉

三层约束串起来，它在 8 卡上就自动不成立了。每一层都是源码里的一条 raise，不是建议。

1
LayerSplit 只允许出现在 PD 的 prefill worker 上 arg_groups/model_hook.py:365-380 —— disaggregation_mode != "prefill" 时， decode 与非 PD 两条分支各有一个 raise
2
因此一个开 LayerSplit 的部署必然还有一个 decode worker doc 原话：decode 侧通过 PD 传输拿到完整分片（prefill_cp.mdx:92）
3
而 PD 两端的「有效 TP 宽度」必须对得上 判据是 prefill 的 attn_tp_size × attn_cp_size 等于 decode 的 attn_tp_size； 对不上直接 RuntimeError（disaggregation/common/conn.py:1376-1388）—— CP 只改变这个乘积的分解方式，不改变它的值
4
于是 TP8 prefill 需要 8 卡 decode → 合计 16 卡 8 卡机上唯一能容纳的 PD 切法是 prefill 4 + decode 4

还有一条更硬的：LayerSplit 要求 --pp-size 1（model_hook.py:402-408）。 所以 PP 和 LayerSplit 在配置层面就是互斥的 —— 你问的「PP 还是 LayerSplit」不是二选一的性能题， 而是先被一条断言判掉一半。

反过来读这条结论更有用：LayerSplit 的设计前提是「prefill 和 decode 已经是两拨机器」。 它在那种场景下才有意义 —— prefill 机的 KV 是纯成本（算完就传走）， 用 LayerSplit 把它压到 1/S，代价是每读一层远程层要广播一整层。 单机 unified 部署里，prefill 用的 KV 就是 decode 要用的 KV，压它没有额外收益。

02真正可比的三张牌

记 L = 层数，b = 每 token 每层的 KV 字节（MLA latent + DSA index-K）， V = 每卡留给 KV 的显存，S = attn_cp_size。 在 MLA 后端下 KV 在 TP 组内是复制的（这就是全部问题的起点）， 所以「每卡持有几层」直接决定能装多少 token。

配置每卡持有层数可容纳 token相对容量（vs A）额外通信
A · TP8 unified L V / (L·b) 1.00× all-reduce（本来就有）
B · TP4 × PP2 unified ⌈L/2⌉ V / (⌈L/2⌉·b) ≈ 1.97× stage 边界 P2P（hidden states，量小）+ bubble
C · PD 4+4，prefill 带 LayerSplit(S=4) decode L ／ prefill ⌈L/4⌉+1 decode V/(L·b) 1.00×（decode 侧） prefill 侧每层广播一整层 + mooncake 传输

第三、四列是这张表的关键。**PP2 拿到的是近乎两倍的 token 容量，而 PD 4+4 一点也没多** —— 它只是把 4 张卡从 decode 挪给了 prefill。所以除非你的瓶颈确实在 prefill（长 prompt、TTFT 主导）， 否则 PD 4+4 是净亏：decode 算力减半，容量不变，还多一套 mooncake 与故障面。

三张牌的拓扑（每格一卡）

A · TP8：全卡同层，KV 8 份复制，容量 1×
B · stage0：layers [0, ⌈L/2⌉)B · stage1：layers [⌈L/2⌉, L)
C · prefill TP4×CP4 + LayerSplitC · decode TP4（完整 L 层）

036000D 特有的两个坑

3.1 DSA 后端：trtllm 在这块卡上被拒绝

LayerSplit 的 e2e 用例跑在 B300 上，用的是 --dsa-prefill-backend trtllm。 照抄到 SM120 上会在启动阶段直接失败：

GLM DSA with FP8 KV cache on NVIDIA SM120/SM121 supports only
flashinfer_sparse_mla (default) or triton_sparse_mla (prefill), but got ['trtllm'].

kernels/ops/attention/flash_mla_sm120.py:712-722； 自动选择在 arg_groups/overrides.py:641-654（is_glm_sm12_fp8 分支）。

所以 6000D 上的正确做法是完全不写 --dsa-prefill-backend， 让它落到 flashinfer_sparse_mla；只有在已经确认过的组合里才显式指定 triton_sparse_mla 作为 prefill 替代。这不是调优项，是「不写才对」。

3.2 无 NVLink 时，LayerSplit 的通信形状和 PP 差两个数量级

这个差别决定了同样的显存收益该买哪一张牌：

每次传输的字节随什么增长能否被计算盖住
PP2 的 stage 边界 hidden states：tokens × hidden × dtype（每 chunk 一次） chunk 大小 能，异步 P2P + 双流重叠
LayerSplit 的远程层读 整层 buffer：(size + page_size) × b（每个远程层一次） 整个 KV 池的容量，与 batch 命中多少页无关 只能靠「提前一层」预取，深度 1

第二行那个「随容量增长」是这条路径最反直觉的地方：你把池子撑得越大，每次前向的广播量越大。 在 NVLink 机上这没关系（几十 GB 的广播摊到几百毫秒的 prefill 里只有几个百分点）； 在 PCIe 直连的机器上，它会和层计算时间正面竞争 —— 而预取深度只有 1 层， 一旦单层广播时间超过单层计算时间，就再也盖不住了。

所以判断方法很朴素：测一次「一层 buffer 的 all-broadcast 时间」和「一层 prefill 的计算时间」， 前者必须明显小于后者。下面的计算器把这两个量并列出来。

04决策规则

你的瓶颈选理由
还没到显存墙 A · TP8 unified 没有 bubble、没有 PD 故障面、没有 mooncake 依赖；先把 TP8 跑满再谈切分
长上下文 / 高并发把 KV 顶爆 B · TP4 × PP2 每卡层数减半 → 容量 ×1.97；代价是 (pp−1)/(m+pp−1) 的 bubble 与 stage 边界 P2P
TTFT 主导（长 prompt、RAG、agent）且 decode 负载轻 C · PD 4+4 + LayerSplit prefill 侧 KV 压到 ⌈L/4⌉+1 层，CP4 换 TTFT；但要接受 decode 只剩 4 卡
已经有第二台机器 PD 8+8 + LayerSplit 这才是这个特性的目标场景：prefill 侧 TP8×CP8，每卡 ⌈L/8⌉+1 层

补一条 PP2 的调优口径（文档 pipeline_parallelism.mdx 给的）： PP 的 bubble 主要来自 stage 间耗时不均，--enable-dynamic-chunking 就是为此存在的， 它按拟合出来的二次模型动态缩 chunk，SGLANG_DYNAMIC_CHUNKING_SMOOTH_FACTOR 默认 0.75。 层数除不尽时把多的那层放在高 PP rank（SGLANG_PP_LAYER_PARTITION）， 文档给的例子是 15,15,15,16 优于 16,15,15,15。

06两条可执行命令

B · TP4 × PP2（unified，8 卡全用上）

python -m sglang.launch_server \
  --model-path <你的 GLM-DSA 权重> \
  --tp 4 --pp 2 \
  --kv-cache-dtype fp8_e4m3 \
  --mem-fraction-static 0.85 \
  --chunked-prefill-size 8192 \
  --enable-dynamic-chunking \
  --speculative-algorithm EAGLE --speculative-num-steps 3 \
  --speculative-eagle-topk 1 --speculative-num-draft-tokens 4

不写 --dsa-prefill-backend：SM120 上它会自动落到 flashinfer_sparse_mla。--enable-dynamic-chunking 是给 PP bubble 用的， PP1 时不需要。EAGLE 的 steps/topk 是保守起点，按你的命中率再调。

C · PD 4+4（prefill 带 LayerSplit）

# ── prefill：TP4 × CP4 + LayerSplit，4 卡 ──
python -m sglang.launch_server \
  --model-path <你的 GLM-DSA 权重> \
  --tp 4 --attn-cp-size 4 \
  --enable-prefill-cp --cp-strategy interleave \
  --enable-dsa-cache-layer-split \
  --kv-cache-dtype fp8_e4m3 \
  --disaggregation-mode prefill \
  --disaggregation-transfer-backend mooncake \
  --base-gpu-id 0 --port 30000

# ── decode：TP4，4 卡，收完整分片 ──
python -m sglang.launch_server \
  --model-path <你的 GLM-DSA 权重> \
  --tp 4 \
  --kv-cache-dtype fp8_e4m3 \
  --disaggregation-mode decode \
  --base-gpu-id 4 --port 30001

07最容易踩的四个坑

GLM DSA with FP8 KV cache on NVIDIA SM120/SM121 supports only flashinfer_sparse_mla (default) or triton_sparse_mla (prefill), but got ['trtllm'].

kernels/ops/attention/flash_mla_sm120.py:712-722 · 后端门

  1. 从 B300 的 e2e 配方照抄 --dsa-prefill-backend trtllm 就会撞上这条。
  2. 删掉这个参数即可 —— 默认值就是对的。

--enable-dsa-cache-layer-split is not supported with pipeline parallelism (pp_size > 1) yet.

arg_groups/model_hook.py:402-408 · PP 门

  1. 想「PP2 再加 LayerSplit」是拿不到双份收益的，两者互斥。
  2. 8 卡上要么 PP2（unified），要么 4+4 PD + LayerSplit。

--enable-dsa-cache-layer-split is only supported on PD prefill workers. Non-PD workers also run decode and require ordinary local decode cache semantics.

arg_groups/model_hook.py:376-380 · PD 角色门

  1. unified 部署（不写 --disaggregation-mode）时触发。
  2. 根因不是性能而是语义：非 owner rank 上没有完整 cache，而 decode 每步都要全层 KV。

（无报错，但 prefill 比预期慢，且随 KV 池变大而变慢）

LayerSplit 广播语义 · 容量与广播量同向增长

  1. 远程层读广播的是整层 buffer（size + page_size 行），不是本批次命中的页。
  2. 所以把 max_total_num_tokens 调大，prefill 的每层广播时间会同步变大。
  3. 诊断：对比「一层 buffer 的 broadcast 时间」与「一层 prefill 计算时间」，前者不显著小于后者就是盖不住了。

08常见误解

「PP 和 LayerSplit 都是按层切，可以叠加。」
不行，而且理由很直接：pp_size > 1 时 LayerSplit 直接 raise。 两者的相似只停留在「都跟 layer 有关」—— PP 切计算图（每层权重只在一个 stage）， LayerSplit 切KV 归属（每层权重仍然处处都有）。
「8 卡上 TP8 比 TP4×PP2 省显存。」
反了。PP2 让每张卡只放一半的层，KV 容量接近翻倍； TP8 每张卡都要放全部 L 层。PP2 的代价是 pipeline bubble 和 stage 边界 P2P， 不是显存。
「PD 4+4 因为 prefill 侧有 LayerSplit，所以整体容量变大。」
没有。决定并发的是 decode 侧的 KV 容量，而 decode 侧是普通 TP4、每卡 L 层 —— 和 TP8 unified 完全一样。PD 换来的是 TTFT 隔离，付出的是 decode 算力减半。
「CP 也会把 KV 摊到各 rank 上。」
CP 切的是 token（interleave/zigzag），不是层。每个 CP rank 仍然持有全部层的 KV， 只是处理的 token 少。真要摊层，必须显式开 LayerSplit。

09自测

Q1 · 为什么 PD 4+4 的容量和 TP8 一样，却少了 4 张卡的算力？
因为 KV 容量由「单卡持有几层」决定，而 PD 两侧都是普通 TP。 prefill 侧虽然有 LayerSplit（每卡 ⌈L/4⌉+1 层），但 prefill 的 KV 是过路的 —— 算完就经 mooncake 传走，不承载并发。承载并发的是 decode 侧的 radix cache， 它每卡 L 层，和 TP8 一模一样。 所以 PD 4+4 是用一半算力换「prefill 不打断 decode」。
Q2 · PP2 的 bubble 到底多大？什么时候可以忽略？
粗略 (pp−1)/(m+pp−1)，m 是同时在飞的微批次数。 pp=2、m=4 时约 20%；m=8 时约 11%。这不是纯浪费 —— 它意味着 stage0 在等 stage1 时可以用别的请求填， 所以连续批处理下实际损失通常小于这个数。但一旦 --chunked-prefill-size 设得很大、 单 chunk 就吃满一个 stage，bubble 会向 50% 靠近。这就是 --enable-dynamic-chunking 的用武之地。
Q3 · 如果我已经有第二台机器，8+8 怎么配？
prefill 侧 --tp 8 --attn-cp-size 8 --enable-prefill-cp --cp-strategy interleave --enable-dsa-cache-layer-split --disaggregation-mode prefill --disaggregation-transfer-backend mooncake， 每卡 ⌈L/8⌉+1 层（L=61 时是 9 层，占 14.8%）；decode 侧 --tp 8 普通。 这才是 LayerSplit 的目标形态：prefill 的 KV 从「纯成本」压到 1/S， 而广播走的是机器内 NVLink 域 —— 前提是那台机器确实有 NVLink 域。
Q4 · 6000D 上能不能开 --enable-dp-attention 来代替 PP？
方向不同：DP attention 让每个 DP 组各自处理不同请求、attention 权重按组切， 它不减少每卡持有的层数，所以不解决 KV 容量。它是为了去掉 attention 的 TP 通信， 不是为了让 KV 变小。想要容量只有两条路：少放层（PP / LayerSplit）或不复制（那是另一套机制）。
