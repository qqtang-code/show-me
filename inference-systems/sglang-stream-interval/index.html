--stream-interval 为什么在长输出场景有提升

2026-09-24SGLangstreamingSSE净室微基准

这个 flag 的表面作用是「少发几次」，但真正被它砍掉的是默认非增量流式路径里的一个 O(T²)：每一个流式事件都要搬运「截至当前的全部输出」，事件数又正比于输出长度。间隔 N 把事件数除以 N，于是二次项也除以 N —— 输出越长，被除掉的绝对值越大，这就是长输出有感、短输出无感的全部原因。

结论 代码里只有一个判定点 一个事件走五段路 每块都在搬运整个前缀 总代价是二次的 什么时候无效 建议

01结论

TL;DR

  • 唯一的作用点：调度器在 accept() 里决定「这一 step 要不要把这条请求的输出推给下游」。stream_interval = N > 1 时条件变成 len(output_ids) % N == 1 —— 首个 token 仍然立刻发出（TTFT 不变），之后每 N 个 token 发一次。
  • 真正的杠杆不是「少发几次」，而是默认（非增量）流式路径下每个事件都要重建并搬运完整前缀：tokenizer manager 里 state.get_text() 是 O(t) 的字符串重建，/generate 的 SSE 块里带着完整 text + 完整 output_ids。事件数 × 每事件 O(t) ⇒ 总量 O(T²)。
  • 所以收益与 T 成正比：间隔 2 恒定砍掉约 50%（实测 1.93–2.10×），而 512 token 时单请求只有 7 ms 的可砍量、8192 token 时有 1451 ms。长输出的绝对值才够大，才能在 tok/s 上看见。
  • 你 9 月那轮 stream-interval 4 无效是同一个机制的结果：batch 仅 2–3 条、单步 3.7 ms 的 kernel-bound decode 里，流式管线本来就不是瓶颈，砍掉一半的「不是瓶颈的那部分」等于没砍。

02代码里只有一个判定点

整个 flag 在源码里只被真正消费一次，而且不在 scheduler.py 里（scheduler.py:352 存了个 self.stream_interval 但没人用，是个残留字段）。生效点是 managers/scheduler_components/output_streamer.py 里组装流式负载的那个累加器：

# output_streamer.py:345-363 · _GenerationStreamAccumulator.accept()
if req.finished():
    should_output = True          # 最后一块一定发
elif req.stream:
    stream_interval = req.sampling_params.stream_interval or self.default_stream_interval
    should_output = (len(req.output_ids) % stream_interval == 1
                     if stream_interval > 1 else
                     len(req.output_ids) % stream_interval == 0)
    if should_output:
        should_output &= not req.check_match_stop_str_prefix()
else:
    # 非流式请求完全不受 --stream-interval 影响
    should_output = (len(req.output_ids) % self.default_force_stream_interval == 0)

为什么会有「每个块都带完整前缀」这种设计？看 output_streamer.py:379 和 tokenizer_manager.py:2055 的注释就清楚了：中间块把自己的 text 写成 None，由 _wait_one_response 在交付前统一补上 —— 原意是躲开「在 _handle_batch_output 里每 step 重建字符串」的 O(n²)。但补的地点仍然在每个事件上（_wait_one_response 是逐事件 yield 的），所以 O(n²) 只是换了个函数，并没有消失。SGLang 后来加的 --incremental-streaming-output 才是真正去掉它的那个开关（见文末）。

04每块都在搬运整个前缀

把 /generate 的流式块真实序列化一遍（T=4096、interval=1），就能看到「面积」是怎么堆出来的：横轴是这块发出时已经生成了多少 token，纵轴是这一块的字节数。曲线是直线，所以累加量是三角形面积 —— 二次。

每块 SSE 都背着整个前缀

一块 hairline = 每 128 token 抽样一次的真实序列化字节数 · 面积 = 一次请求的 SSE 总量 · 输出长度 4096 token
HAIRLINE AREA · F3 · 净室微基准 · ORJSON 3.11

读法

  • 块的大小 ≈ 13.1 B × t：t 是「已经生成了多少 token」。第 128 个 token 那块 1.9 KB，第 4096 个那块 53.5 KB。
  • 53.5 KB 里 28.7 KB（53.6%）是 output_ids 数组 —— 客户端做吞吐统计根本用不到，但它跟着每一块重发一次。
  • 把 4096 块加起来 = 105 MiB，一条请求。这就是「面积」的含义。
  • 间隔 2 不会让每块变小：每块依旧背着完整前缀，只是块数减半 → 面积减半。

05总代价是二次的

把服务端（get_text + orjson.dumps）和客户端（json.loads）的 CPU 时间实测出来，横轴是输出长度、纵轴是单请求的流式管线开销。每把输出长度翻一倍，开销涨 3.9 倍 —— 二次项主导的标志。

翻倍输出长度，开销涨 3.9 倍

单请求流式管线 CPU 时间（服务端重建+序列化 / 客户端解析）· 实心点 = 1 / 2 / 4 三个间隔 · 横轴每格 ×2
HAIRLINE LINE · F2 · 净室微基准 · ORJSON 3.11

读法

  • 512 token 时三条线几乎重合（7.4 / 3.6 / 1.9 ms），间隔在这里几乎无可砍。
  • 8192 token 时拉到 1451 / 732 / 363 ms —— 同一份数据的四倍差距。
  • 间隔 2 的收益是恒定的 50%（全区间 1.93–2.10×），与 T 无关；变的是它的绝对值。
  • 换成字节看更直白：单请求 1.7 → 417.9 MiB，翻 16 倍输出换来 246 倍流量。

放大到并发：128 并发 × 4096 token，单跑就是 13.4 GiB 的 SSE 字节和约 44 s 的客户端 CPU（341.6 ms × 128）。这些时间不与 GPU 重叠——它们趴在同一个单线程事件循环和同一条网络路径上。这就是「长输出 + 高并发」被流式管线吃掉的那一块。

06什么时候无效：把它和你的实测对上

同一个 flag 在两种场景下结论相反，机制上完全自洽：

条件有提升无提升
客户端模式 流式（SSE）—— 事件真实存在 非流式：走 FORCE_STREAM_INTERVAL，默认已经是 50，该 flag 完全不参与
输出长度 数千 token：二次项长起来了，可砍的绝对量大 几十~几百 token：每请求只有几 ms，砍半也看不见
并发 高并发：128 条请求的字节量与解析量压满 CPU / 网络 低并发（如 batch 2–3）：总量本来就小
瓶颈位置 瓶颈在流式管线（TM / HTTP / 客户端 CPU 或网络） 瓶颈在 GPU：单步 3.7 ms 的 kernel-bound decode 主导，流式开销本来就不在关键路径上

你自己的两轮数据正好落在这张表的两端。9.11–9.14 那一轮 num-continuous-decode-steps 8 + stream-interval 4 + scheduler-recv-interval 2 拿到 7,166.7 / 7,167.1 tok/s（<0.1%），当时记录的原因是「decode 是 kernel-bound：单步约 3.7 ms、batch 仅 2–3 条，成本由 40 层固定 per-step 工作决定，与 batch 大小几乎无关」—— 落在右下格：batch 只有 2–3 条，每个事件的负载极小，而 3.7 ms/step 的 GPU 时间不受影响，所以砍掉一半的流式开销等于没砍。而长输出 + 高并发的场景落在左上格，同一个 flag 就会给你两位数百分比。判据不是「这个 flag 有没有用」，而是「流式管线的 CPU 与字节量占墙钟时间的比例」。

07建议

手段做什么代价 / 注意
--stream-interval N 事件数 ÷N，二次项 ÷N。TTFT 不变（首 token 仍立即发）。长输出流式基准建议从 2 起步，试到 4。 chunk 粒度变粗，逐 token 的 ITL 曲线被平滑掉。测 tok/s 不受影响（bench 客户端按 completion_tokens 差分摊 ITL），但看首字后抖动会失真。
--incremental-streaming-output 真正去掉二次项：块里只带 delta，不再重建完整文本。同样条件下微基准 37×（105 MiB → 1 MiB）。 语义变了：text 是增量而非累计值。SGLang 自带的 bench 客户端在 /generate 上直接 generated_text = data["text"]，用这个 flag 跑会只留最后一段（吞吐数字仍对，文本内容不对）。接自家客户端才建议开。
--batch-notify-size 默认 16：攒够 16 条才 set event 唤醒一次事件循环，压掉 asyncio 唤醒开销。已经默认开着，高并发下可以再调大。 唤醒延迟增加，与间隔是同一类取舍，叠加时注意总延迟。
客户端侧 基准压测想量纯 GPU 能力时用 --disable-stream：服务端回到 FORCE_STREAM_INTERVAL=50，流式管线开销基本消失。 拿不到 TTFT / ITL。要测首字延迟就必须用流式，那时再配 --stream-interval。
