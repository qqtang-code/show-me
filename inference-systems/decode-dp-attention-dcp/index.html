DCP 与 DPAttention：
TP8×DCP4 与 TP16×attnDP4 两条 1M 路线

同样把上下文做到 1M，两种形态用的是完全不同的算术：一个把序列按位置切给更多 rank，一个把请求分进多个独立池。下面按这两套真实配置讲清原理、代价和容量公式。

TL;DR · 两条路都到 1M，但代价完全不同

  • DPAttention 是请求维度的并行：attn_tp_size = tp/d/attn_cp，每个 DP 组有自己的 scheduler 和 KV pool；DCP 是上下文维度的并行：同一请求的主 KV 按 slot%c 分给组内不同 rank。
  • TP8×DCP4：8 卡单节点，每 rank 269,952 行 × DCP4 = 逻辑 1,079,808 tokens，纯 GPU、无 host 分层，实测完成 1,048,188+384 的真实 1M 请求。
  • TP16×attnDP4：16 卡双节点，4 个独立池。每池 480K×host3 = 1,440,000（DCP1）或 600K×DCP2 = 1,200,000，两种都实测完成过 1M。
  • DCP 不减少核心 attention FLOPs：gathered Q heads ×c、本地 KV ÷c，乘积不变；它换的是主 KV 副本数和单请求上下文容量。
  • 最容易被忽略的代价：DSA index-K 不随 DCP 分片，所以 TP8×DCP4 的 index-K 仍是 8 份全历史；而 TP16×attnDP4 靠 host 分层拿容量，同一份 1M 请求在每个 rank 的 host 上各存一份。

01两套 1M 形态

一句话：TP8×DCP4 用“位置分片”把 4 个 rank 拼成一个更长的逻辑序列；TP16×attnDP4 用“请求分池”把并发拆成 4 份，再靠 host 分层或组内 DCP 把单个池抬到 1M。

维度A · TP8 × DCP4B · TP16 × attnDP4
部署单节点 8 卡；TP8 × PP1 × DCP4 × attnDP1双节点 16 卡；TP16 × PP1 × attnDP4 × attnTP4，DCP1 或 DCP2
请求归属全部 8 rank 协同处理同一批请求（attnDP1）请求只进入其中一个 DP 组（4 rank）
1M 的来源每 rank 269,952 物理行 × DCP4 = 1,079,808每池 4 rank：480,000 × 3（--hisparse-config host_to_device_ratio=3）或 600,000 × 2（DCP2）
逻辑 target 容量1,079,808 tokens1,440,000 / 1,200,000 tokens（单池）
主 KV 副本因子attnTP/c = 8/4 = 24/1 = 4（DCP1）或 4/2 = 2（DCP2）
每 rank KV16.4481 GiB（全 GPU，含 draft）26.5946 GiB GPU + 72.3424 GiB host（DCP1+host3）
1M 实测HTTP 200，1,048,188 in + 384 out，85.86 s（bs=1 graph）GLM：8×C1、每池 2 条、DP0–3 全覆盖；Hy4：同尺寸约 90 s
推测解码NEXTN 3 steps / 4 draftEAGLE 或 NEXTN 3/4
为什么这两种能到 1M：1M 需要 ≥1,048,576 个逻辑 target 位置。TP8×DCP4 把 4 个 rank 的位置拼起来，物理行只要 269,952 就够；TP16×attnDP4 的单个池只有 4 个 rank，DCP1 时物理行必须靠 host 扩 3 倍，或开 DCP2 让组内再分一次。
与 stock SGLang 的差异（重要）：arg_groups/model_overrides/deepseek_v2.py: _dsa_dcp_overrides() 在 dcp_size > 1 时对 DSA 模型直接抛错："DSA DCP does not support PD disaggregation." 和 "DSA DCP does not support HiSparse or HiCache."；PD 解码端 disaggregation/common/conn.py 还要求 "PD decode DCP currently requires prefill attention CP=1"。所以 B1（DCP1 + HiSparse）是 stock 允许的组合（dcp_size≤1 时 guard 直接返回），而 A（DCP4）与 B2（DCP2）在 PD 部署里都必须先去掉这些 guard——它们跑在带 overlay 的构建上，不是 stock 行为。

02具体机制

A 形态：DCP 把位置切给 4 个 rank

1
写入：token 位置 p 只写到 p % 4 对应的 rank，局部行号 p // 4。逻辑 page 变成 64×4=256 token。
2
取 Q：每 rank 本地 8 个 head（64/8），要么 DCP all-gather Q 到 32 个 head，要么用 dcp_replicate_q_proj 直接算 full-head。
3
局部 attention：32 个 gathered head × 本地 1/4 的 KV，产出 partial output + LSE。
4
归并：组内 a2a 交换 partial output + FP32 LSE，Triton log-sum-exp 合并，回到本 rank 的 8 个 head。
5
无 DP 交换：attnDP1 时 num_dp_ranks = dp_size × attn_dp_size = 1，layer boundary 的 move_rows() 只在布局确有 ATTN_DP 差异时才插 gather，所以没有跨 DP 的 hidden gather/scatter。每层 DCP 侧仍是两次集合通信：Q all-gather（开 dcp_replicate_q_proj 可省）+ partial output/LSE 的 a2a。
owner(slot) = slot % 4
local_row   = slot // 4
logical page = 64 × 4 = 256 tokens

每 rank：8 local heads → 32 gathered heads × (1/4 KV) → partial + LSE
        → a2a 归并 → 8 heads  ← 主 KV 只存 1/4，但存 2 份（两个 DCP 组）

B 形态：DPAttention 把请求分进 4 个池

1
路由：请求进入某个 DP 组的 scheduler，只由该组 4 个 rank 处理；其他组不复制这份 KV。
2
attention：组内按 attnTP4 切 head，每 rank 16 个 head；DCP1 时本组完整 KV 在 4 个 rank 各一份。
3
FFN/MoE：四个组的 token 重新聚合到完整 TP16 上算 FFN/MoE，再散回各 DP 组。
4
同步：MLPSyncBatchInfo 同步 token 数、forward mode、graph eligibility；最慢的组拖关键路径。
5
容量：每池独立，DCP1 时靠 host 分层扩到 3×；或组内开 DCP2 再乘 2。

源码：managers/data_parallel_controller.py、layers/dp_attention.py、scheduler_components/dp_attn.py、models/deepseek_v2.py 的 parallel_group="attn_tp"。

两者是独立旋钮

A 是 DP1+DCP4，B 的 DCP1 变体是 DP4+DCP1，B 的 DCP2 变体是 DP4+DCP2。组合时先按请求分 DP，再在组内按位置做 DCP；DCP 不跨 DP 组共享 KV，也不替代 MoE 前的 DP gather/combine。

03对推理行为的影响

核心账：(Hq/t × c) × (S/c) = Hq×S/t。DCP 理想情况下不减少每 rank 的核心 attention FLOPs，改变的是 KV ownership、kernel 形状和容量。

维度A · TP8 × DCP4B · TP16 × attnDP4
每 rank Q heads8 → gathered 3216（DCP1）；DCP2 时 16 → 32
每 rank 主 KV 位置S/4S（DCP1）或 S/2（DCP2）
核心 attention FLOPs不变（heads×c、KV÷c 相抵）不变；DCP2 同理
每层集合通信DCP：Q gather（可选）+ partial output/LSE a2a；无跨 DP 交换DP：hidden gather + reduce-scatter；DCP2 再加 partial/LSE
同步面单 scheduler，无 DP 组间 skew4 个 scheduler，慢组会拖全局；EAGLE 下 graph 投票需一致
KV 副本主 KV 2 份；index-K 8 份（不分片）主 KV 4 份（DCP1）或 2 份（DCP2）；index-K 4 份
单请求 1M 占用15.1994 GiB/rank（8 卡合计约 121.6 GiB）3.491 GiB GPU + 52.6759 GiB host（4 卡合计约 14.0 + 210.7 GiB）
1M 并发1（1,079,808 只够一条）每池 1 条，四池共 4 条
不要写成“DCP 更快”：A 的收益是纯 GPU 里塞进 1M，代价是 index-K 8 份全历史和每层 LSE 归并；B 的收益是 4 个独立池与更大的聚合容量，代价是跨 DP 通信、host 带宽和 4 份 KV 复制。两者都是容量路线，不是算力路线。

Prefill 与 Decode 分开看

  • Prefill：两套 D 侧都不做长 Prefill。P 侧 CP4 负责把 prompt 算完；A 走 CP0-only 传输后按 DCP4 重排，B 按普通 MLA 传输。
  • Decode：A 每层多一次 DCP 归并、少一半 KV 读取；B 每层多一次跨 DP 交换、KV 读全量。
  • 长输出：A 的 LSE 归并随 token 数线性增长但与被读历史无关；B 的 DP 交换随 batch 增长，KV 读取随上下文增长。
  • 小 batch：A 只有 1 个 scheduler，max_running_requests=1 时几乎无调度收益；B 天然支持 4 组并发，但单条长请求只占 1 组，其余组空转。

05三条 1M 算术

三条路径都越过了 1M 门槛，但余量和机制不同：TP8×DCP4 只多出 3.0%，TP16×attnDP4 的 DCP2 变体多出 14.5%，DCP1+host3 多出 37.3%。

读图

  • TP8×DCP4：269,952 × 4 = 1,079,808，只比门槛高 31,232（3.0%），一条 1M 请求就基本占满。

自测

为什么 TP8×DCP4 只需要 269,952 行就能到 1M？
因为 4 个 DCP rank 各持 1/4 位置，逻辑长度 = 4 × 269,952 = 1,079,808。若是 DCP1，同样行数只有 269,952。
为什么 TP16×attnDP4 不能只靠 DPAttention 到 1M？
DPAttention 把容量拆成 4 个独立池，单池仍是 480,000 行；单个 1M 请求只能落在一个池里，所以还要 host ratio 3 或组内 DCP2 把单池抬过 1M。
DCP4 是不是把 attention 计算也降成 1/4？
不是。gathered Q heads 变成 4 倍、本地 KV 变成 1/4，核心 FLOPs 乘积不变；省的是一半主 KV 副本和读取量，多的是 Q 准备与 LSE 归并。
