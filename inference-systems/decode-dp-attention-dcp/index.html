把上下文做到 1M：
DCP、DPAttention 与 HiSparse 的三种切法

单请求 1M 上下文是一个硬指标：逻辑 target 位置必须 ≥ 1,048,576。三条路都在这个数字上做乘法，但乘的对象不同——乘位置分片宽度、乘请求池数量、乘 host 分层倍数。下面把三种形态的原理、容量算术和代价放在一起。

术语保留 rank / group / scheduler / KV pool / target / draft / partial output / LSE / hot set。事实源码或日志；推导由公式计算；实测保存的历史结果；未确认证据不足。

TL;DR · 同一个 1M，三种乘法

  • 三条路的分野是「逻辑容量 = 物理行 × 什么」。 DCP 乘位置分片宽度 c；DPAttention 把容量拆成 d 个独立池；HiSparse 乘 host/device 倍数 r。
  • DCP 是上下文维度。owner(slot)=slot%c、local_row=slot//c。gathered Q heads ×c 与本地 KV ÷c 相抵，核心 attention FLOPs 不变，换的是主 KV 副本数与单请求容量。
  • DPAttention 是请求维度。attn_tp = tp/d/attn_cp，每池独立 scheduler 与 KV pool。它单独不足以上 1M：单池仍是 480K 行，必须叠加 host 分层或组内 DCP。
  • HiSparse 是层级维度。GPU 只留每请求热集，逻辑池 = 设备池 × ratio。代价是每个 rank 在 host 上各存一份全量、以及页交换带宽。
  • 最容易漏的代价：DSA index-K 不随 DCP 分片（全历史每 rank 一份），也不随热集缩小（覆盖整个逻辑池）。所以 DCP 的显存收益小于「主 KV ÷ c」，HiSparse 的 index 也按逻辑池计费。

02具体机制

A · DCP 把位置切给 4 个 rank

1
写入：token 位置 p 只写到 p % 4 对应的 rank，局部行号 p // 4；逻辑 page 变成 64×4=256 token。
2
取 Q：每 rank 本地 8 个 head（64/8），要么 DCP all-gather Q 到 32 个，要么用 dcp_replicate_q_proj 直接算 full-head。
3
局部 attention：32 个 gathered head × 本地 1/4 的 KV，产出 partial output + LSE。
4
归并：组内 a2a 交换 partial output + FP32 LSE，Triton log-sum-exp 合并，回到本 rank 的 8 个 head。
5
无 DP 交换：attnDP1 时 num_dp_ranks=1，layer boundary 不会插 ATTN_DP 的 gather。但每层 DCP 侧仍是两次集合通信：Q gather（可省）+ partial/LSE a2a。
owner(slot) = slot % 4
local_row   = slot // 4
logical page = 64 × 4 = 256 tokens

8 local heads → 32 gathered heads × (1/4 KV) → partial + LSE → a2a → 8 heads
主 KV：每 rank 只存 1/4，但存 2 份（两个 DCP 组）

B · DPAttention 把请求分进 4 个池

1
路由：请求进入某个 DP 组的 scheduler，只由该组 4 个 rank 处理；其他组不复制这份 KV。
2
attention：组内按 attnTP4 切 head（每 rank 16 个）；DCP1 时本组完整 KV 在 4 个 rank 各一份。
3
FFN/MoE：四个组的 token 重新聚合到完整 TP16 上算 FFN/MoE，再散回各 DP 组。
4
同步：MLPSyncBatchInfo 同步 token 数、forward mode、graph eligibility；最慢的组拖关键路径。
5
容量：单池 480,000 行 < 1M，所以再加一层——host 分层 3×（B1）或组内 DCP2（B2）。

C · HiSparse 把历史挪到 host

1
双分配器：HiSparseTokenToKVPoolAllocator 同时维护 logical allocator（size_full = 132,096×16 = 2,113,536）与 device allocator（132,096），并保存 logical→device 映射。
2
热集：每请求在 GPU 只保留 24,576 个 token 的位置（device_buffer_size），长序列其余页留在 host。
3
每步取页：DSA top-k 选出要读的页后 swap_in_selected_pages() 把命中页搬进 GPU 热集，淘汰按 LRU。
4
index 也放大：index_buf_size = size × host_to_device_ratio，所以 index-K 的 GPU 地址空间同样覆盖整个逻辑池。
5
成本：DCP1 + attnTP8 ⇒ 每 rank 一份全量，8 个 rank 在 host 各存一份；页交换与 host 带宽直接进 TPOT。
logical_allocator: size_full = N × 16 = 2,113,536
device_allocator : size_hisparse = N = 132,096
每请求 GPU 热集 = 24,576 + page reserve

逻辑容量 = N × 16 = 2,113,536  →  可驻留 2 条 1M 请求

三者能叠加吗

可以，但两条约束先卡住。DCP 与 attnDP 正交（B2 就是 DP4+DCP2）；DCP 与 HiSparse 在 stock 里互斥，要同时用必须改 _dsa_dcp_overrides()；dcp_size 又不能与 prefill CP 同进程。所以现实组合是：A = DP1+DCP4、B1 = DP4+DCP1+HiSparse(3)、B2 = DP4+DCP2、C = DP1+DCP1+HiSparse(16)。

03对推理行为的影响

核心账：(Hq/t × c) × (S/c) = Hq×S/t。DCP 理想情况下不减少每 rank 的核心 attention FLOPs，改变的是 KV ownership、kernel 形状与容量；HiSparse 则把「读多少 KV」变成「搬多少页」。

维度A · TP8 × DCP4B · TP16 × attnDP4C · TP8 + HiSparse
每 rank Q heads8 → gathered 3216；DCP2 时 16 → 328（DCP1）
每 rank 主 KVS/4S 或 S/2S 的副本，GPU 只留热集
每层集合通信Q gather + partial/LSE a2a；无跨 DP 交换跨 DP hidden gather + reduce-scatter（+DCP2 归并）无（DCP1/DP1）；有 host↔device 页搬运
关键路径LSE 归并每层都在DP 组间同步 + MoE页换入 I/O + host 带宽
KV 副本主 2 份，index 8 份主 4 或 2 份，index 4 份主 8 份，index 8 份（含 host）
1M 并发1每池 1，共 42
主要风险index 8 份；每层归并4 份复制；DP 长尾host 带宽；热集命中率；页搬运抖动
不要写成「DCP 更快」或「HiSparse 更省」：三条路都是容量路线。A 用纯 GPU 换 1M，代价是 index 副本与每层归并；B 用多池换并发，代价是跨 DP 通信与复制；C 用 host 换逻辑容量，代价是页交换带宽。同样的 1M 请求，A 占 15.2 GiB/rank 显存、C 只占 3.88 GiB 显存但要 52.7 GiB host。

Prefill 与 Decode 分开看

  • Prefill：三条路的 D 侧都不做长 Prefill。P 侧 CP4 算完 prompt；A 走 CP0-only 传输后按 DCP4 重排，B/C 按普通 MLA 传输。DCP 不影响 Prefill 计算本身。
  • Decode：A 每层多一次归并、少读 3/4 主 KV；B 每层多一次跨 DP 交换、读全量 KV；C 读的是热集，命中之外要等页搬运。
  • 长输出：A 的归并随 token 数线性增长但与被读历史无关；C 的历史越长，页命中率与换入延迟越主导 TPOT。
  • 小 batch：A、C 只有一个 scheduler，max_running_requests=1 时没有调度收益；B 天然 4 组并发，但单条长请求只占 1 组。

04容量公式与四个算例

每层每 token 的字节数

m = 512(FP8 latent) + (512/128)×4(scale) + 64×2(BF16 RoPE) = 656 B
i = 128(FP8 index-K) + 4(FP32 scale) = 132 B

target 主 KV = 78 × m = 51,168 B / token / rank
target index = 21 × i =  2,772 B / token / rank
NEXTN draft  = m + i  =    788 B / token / rank

通用式

Target main  = (N + 64) × 78m
Ibuf         = (N + 64) × c − 64      # 未开 host 分层时
Pidx         = floor((Ibuf + 65) / 64)
Target index = Pidx × 64 × 21i
Draft        = (cN + 64) × m  +  floor((cN+65)/64) × 64 × i

逻辑容量   = c × N            # DCP
           = N × r            # HiSparse（r = host_to_device_ratio）
主 KV 副本 = attn_tp_size / c
1M 门槛    = 1,048,576

HiSparse 形态下 index 覆盖整个逻辑池：index_buf_size = N × r，所以 index 字节随 r 增长而不是随 device 池。

自测

为什么 A 只要 269,952 行就到 1M，而 C 要 132,096 行？
A 有 4 个 DCP rank 各持 1/4 位置，逻辑 = 4×269,952；C 是 DCP1，单 rank 物理行只有 132,096，靠 host 16 倍放大到 2,113,536。两者乘法对象不同：一个是 c，一个是 r。
为什么 TP16×attnDP4 不能只靠 DPAttention 到 1M？
DPAttention 把容量拆成 4 个独立池，单池仍是 480,000 行；单个 1M 请求只能落在一个池里，所以还要 host ratio 3 或组内 DCP2 把单池抬过 1M。
三条路里谁最省显存，代价是什么？
C 的 GPU 每 rank 只 11.85 GiB、单条 1M 请求只占 3.88 GiB 显存，但它要在 host 上每 rank 存一份全量（106.18 GiB），并把页交换放上关键路径。
