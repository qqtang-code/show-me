TL;DR · 先纠正四个常见误读

  • D 侧 = PD 分离里的 Decode 角色。 DPAttention 按请求拆 scheduler/KV 池；DCP 按 token 位置拆 target 主 KV。Prefill CP4 是另一件事。
  • 两套 D 侧都是 TP16 × attnDP4 × attnTP4，但 GLM 系列是 DCP1，Hy 系列 r15 是 DCP2。不能把 Hy 的 DCP2 公式或收益套到 GLM 上。
  • Hy DCP2 的主 KV 副本数是 2，不是 1。 attnTP4 内有两个 DCP pair；index-K 和 NEXTN draft 仍是 4 份。
  • 核心 attention FLOPs 不因 DCP 自动下降。 gathered Q heads ×c、本地 KV ÷c；新增 Q 准备、partial output + LSE 归并、page remap 和同步。最确定的收益是容量，不是“必然更快”。

02具体工作机制

DPAttention：请求和 KV 池分开，FFN 仍走完整 TP

1
请求路由：请求进入某个 DP scheduler；本组 attnTP4 只处理本组请求。其他 DP 组不复制该请求的 KV。
2
attention：Q_B/KV_B/O projection 按 attnTP4 切 head；DCP1 时本组完整 latent KV 在 4 rank 各一份。
3
attention output：attnTP 内完成 partial sum；o_proj.reduce_results=False 只表示归约交给 layer boundary，并非不需要归约。
4
FFN/MoE：DP gather 把四个组的 token 重新送入完整 TP16 的 FFN/MoE，再 reduce-scatter 回 DP-local 行。
5
同步：MLPSyncBatchInfo 同步 token 数、forward mode 和 graph eligibility；无请求组可构造 idle batch，慢组会影响整组关键路径。

源码：managers/data_parallel_controller.py；scheduler_components/dp_attn.py；layers/dp_attention.py；models/deepseek_v2.py 中 parallel_group="attn_tp"。MAX_LEN、SUM_LEN、gatherv 是不同分支，不能统一写成 all-gather。

GLM unified 的 DP 通信特化：SGLANG_PD_D_HIERARCHY_MAX_ROWS=4 时，满足全 TP16、连续 BF16、宽度 6144、输入 1–4 行且输出为 16 倍的 AllGather 会先跨节点 pair [r,r+8]，再做节点内 8-rank 集合通信并重排；ReduceScatter 反向执行，未命中回退通用 NCCL。它优化 DP 激活交换，不是 DCP，也不改变 KV owner。实现见 Git a405481e:runtime/glm53_pd_d_hierarchy/patches/01-d-hierarchy.patch 与镜像哈希对账。

DCP：owner rule、局部 attention、LSE 合并

独立可组合：GLM 的 DP4+DCP1、代码允许的 DP1+DCP>1、Hy 的 DP4+DCP2 说明两者并非互为前提。组合时先按请求分 DP，再在每组 attnTP 内按位置分片；DCP 不跨 DP 组共享 KV，也不替代 MoE 的 DP gather/combine。

owner(slot) = slot % dcp_size
local_row   = slot // dcp_size
logical_page = physical_page × dcp_size

P → D:  send_kvcache_dcp / build_dcp_token_transfer_plan
D:     Q projection → 可选 Q all-gather
       gathered Q × 本地 KV shard → partial output + LSE
       single-owner learnable sink（Hy）
       a2a output+LSE → Triton LSE combine
       V correction / o_proj / 后续 MoE 边界
  • layers/dcp/layout.py 用 indices[r::c] // c 选择并折叠 owner 的物理行；dsa_dcp.py 重写并压缩 page table。
  • layers/dcp/comm.py: dcp_a2a_lse_reduce() 把 output 与 FP32 LSE 打包进一次 all_to_all_single，随后本地 Triton combine；ag_rs 是另一条路径。stock 每 rank packed buffer 为 B×H×(D+2)×e：t=4、Hq=64、D=512、BF16 时 DCP2 为 B×32,896 B，DCP4 为 B×65,792 B；这不是 r15 自定义 kernel 的已验证线上流量。
  • DSATokenToKVPool 的 target index-K 地址空间随 c 增长，仍覆盖全历史；NEXTN 在 is_nextn and use_dsa 时固定 dcp_size=1。
  • Hy 的 CP0 持完整 Prefill KV，P→D 时直接做 full→DCP relayout；decode 不需要每层广播全量 KV。

03对推理行为的影响

核心账：(Hq/t × c) × (S/c) = Hq×S/t。DCP 理想情况下不减少每 rank 的核心 attention FLOPs，只改变 ownership 和 kernel 形状。DSA 下把 S 换成 K=min(S,2048) 仍近似成立；indexer 全历史扫描和 remap 另算。

Prefill 与 Decode 分别看什么

维度DPAttentionDCP
长输入 Prefill / TTFT当前 P 侧 attnDP1，不改变 P 的 CP4 计算；D 侧主要影响传输布局与 metadata。P→D 需 relayout，但不改变 P 的计算。Hy r6→r15 TTFT 约 10.13→10.16s，未体现收益。
Decode 计算均衡时本地 batch ÷4、heads ×4，理想总量不变；C1 时其他 DP 组可能空闲。核心 FLOPs 不自动下降；Q 复制路径增加约 c 倍 Q projection，并增加 partial/LSE 与 remap。
kernel 效率4→16 heads/rank 可能改善 tile；同时权重复制、权重复读和小 batch 成本增加。16→32 heads/rank 可能改善形状，但短序列/小 batch 可能被集合通信和 combine 抵消。
通信与同步attnTP 组缩小，但增加 DP gather/combine 与全局 scheduler 同步，慢组拖长关键路径。每层 partial output+LSE 在关键路径；payload 随 query rows、gathered heads、c 增长，而非随历史 KV 总长线性增长。
显存访问单请求副本 16→4；每 rank 仍读本组完整 KV，收益主要是容量与并发。主 KV 每 rank 约 ÷c，但 gathered heads ×c，核心读取的理想乘积不变；index-K 与 draft 不同比例下降。
TTFT / TPOT / 吞吐需要足够并发才能兑现独立池收益；低并发不能保证更低 TPOT。长上下文/容量受限更有价值；短序列或小 batch 更可能由归并开销主导。必须实测，不写“更快”。
历史实测的正确读法：Hy r6→r15 的 TPOT 18.2→15.5ms、输出 TPS 21.4→23.6 是组合结果；standalone full 0.179ms 对 DCP compute 0.206ms 也只说明该微基准的归并成本。DCP4 则 TPOT 24.6ms、TPS 18.7、accept 0.4751，明确不适合作为默认配置。

负载变化时的条件判断

  • 并发上升：DP 组更容易填满，kernel/weight 利用改善；同时 KV 占用、MoE 全局 batch、慢组同步与 DCP payload 都增加。
  • 输入/已生成长度上升：DCP 的容量价值上升；但 DSA top-k 达 2048 后核心 sparse attention 近似饱和，indexer 仍随全历史增长。
  • DCP 宽度上升：主 KV 每 rank 约 ÷c、逻辑容量 ×c；Q 复制、partial/LSE 和同步增加。DCP4 已退化，DCP8 超出 attnTP4 的有效布局。
  • NEXTN：verify 行数放大约 draft token 数倍，partial/LSE 与 workspace 同步放大；accept rate 必须单列，不能把最终 TPOT 全归因于 DCP kernel。

04KV 容量与显存公式

普通 MHA 的基线公式

M_request,rank = 2 × Lloc × Hkv,loc × dh × e × S
M_card         = Σrequest M_request,rank + M_page_reserve + M_runtime

2 是 K/V 两份；PP 改本地层数，TP 改本地 head 数，分页把 S 改为 ceil(S/page)×page。GLM/Hy 的 MLA latent KV 不是普通 MHA，不能再机械乘 2。

两套实现的 target 布局

m = 512(FP8 latent) + (512/128)×4(scale) + 64×2(BF16 RoPE) = 656 B
i = 128(FP8 index-K) + 4(FP32 scale) = 132 B

target main / token / rank = 78m = 51,168 B
target index / token / rank = 21i = 2,772 B
NEXTN main+index / token / rank = m+i = 788 B

依据 DSATokenToKVPool 与 IndexKeyCache：78 个 target 层中 21 个 full-indexer 层。MLA latent 由 K/V 共用，所以没有额外 ×2。

单请求、单卡、并行组、整机

S_target = ceil(S/(64×c)) × 64
S_full   = ceil(S/64) × 64

单请求 / rank:
  M_req = 78m×S_target + 21i×S_full + (m+i)×S_full

单请求 / attnTP 组:
  M_group_req = (attn_tp_size/c)×78m×S_target
              + attn_tp_size×21i×S_full
              + attn_tp_size×(m+i)×S_full

target 主 KV 副本因子为 attn_tp_size/c；index-K 与 DCP1 draft 的副本因子仍是 attn_tp_size。

Target main  = (N+64) × 78m
Ibuf         = (N+64)×c - 64
Pidx         = floor((Ibuf+64+1)/64)
Target index = Pidx × 64 × 21i
Draft main   = (cN+64) × m
Pdraft       = floor((cN+64+1)/64)
Draft index  = Pdraft × 64 × i
口径target 容量/占用必须再区分

HiSparse 是另一套修正，不与 DCP 混用

GLM 当前 N=480K、host ratio 3，所以逻辑主池/index 地址空间为 3N=1.44M；每请求热集 16K，长序列其余主 KV 在 host。HiSparseTokenToKVPoolAllocator 同时维护 logical allocator 与 device allocator 及映射。stock DCP guard 拒绝 HiSparse + PD，不能把 Hy 的 DCP2 直接叠上来。

05target KV 构成：DCP 不是同比省

自测

DPAttention 为什么不直接增加单请求上下文长度？
它把不同请求放进不同 DP 池；单请求仍受所属池 N 限制。增加单请求 target 位置空间的是 DCP 的 c，或 GLM 的 HiSparse host ratio。
Hy DCP2 为什么主 KV 是 2 份而不是 1 份？
attnTP4 内有两个 DCP pair。一个 token 在每个 pair 各有一个 owner，所以跨 pair 仍复制一次；只有 DCP4 覆盖整个 attnTP4 时才降到一份。
DCP 为什么不能说“核心 attention FLOPs 降 c 倍”？
gathered Q head 数乘 c，本地 KV 长度除 c，乘积不变。DCP 的确定收益是主 KV 容量/副本效率；partial/LSE、Q 复制和同步还会增加成本。
