# 192k 输入的 P 端：`TP4×PP2×CP4` 与 `TP8×CP4×LayerSplit4` 谁更高效

> 适用版本 SGLang **v0.5.23**。所有时间与容量数字由公式推导，**未做运行时实测**。

## 答案

**选 1（`TP4×PP2×CP4`）**，且 90% 命中下优势比冷启动更大。

原因不是「PP 更快」——两者的理想算力一样 —— 而是两者的**成本随什么缩放相反**：

- **PP 的开销跟「实际算多少 token」走**：bubble = `1/(m+1) × t_chunk`，P2P = `tokens × hidden`。
- **LayerSplit 的开销跟「KV 池驻留多少 token」走**：每前向 `(L − ⌈L/S⌉) × pool × b`。

192k 的池子让后者变成 48 个 chunk 的量级；90% 命中又把前者砍掉 10 倍。

## 口径

- **选项 1** = `--tp 4 --pp 2 --attn-cp-size 4`，`attn_tp = 4//1//4 = 1`。
- **选项 2** = `--tp 8 --attn-cp-size 4 --enable-dsa-cache-layer-split`，`attn_tp = 8//1//4 = 2`，`S = 4`。
- 取 `L = 61`、`b = 708 B`、chunk = 4096、带宽 55 GB/s（PCIe 5.0 x16 量级）。

## 01 决定性的不对称

| | 选项 1 · TP4×PP2×CP4 | 选项 2 · TP8×CP4×LayerSplit4 |
|---|---|---|
| attention 并行度 | CP4 × attn_tp1 = **4 路** | CP4 × attn_tp2 = **8 路** |
| 每卡 KV（192k 池） | 31 层 → 4.31 GB | 17 层 → 2.37 GB |
| 每前向额外成本 | **∝ 算多少 token**：`1/(m+1) × t_chunk` + 一次 P2P | **∝ 池多大**：`45 × 192k × 708B = 6.26 GB` |
| 命中率上升时 | 开销**同比缩小** | 每前向开销**不变**，只是前向次数变少 |
| 有没有旋钮 | 有：`m`、`--chunked-prefill-size`、`--enable-dynamic-chunking` | 基本没有 |

## 02 192k 的账

```text
远程层数       = 61 − ⌈61/4⌉ = 61 − 16 = 45 层
每层广播       = 192k × 708 B  = 139 MB
每前向广播     = 45 × 139 MB   = 6.26 GB
每前向广播时间 = 6.26 GB / 55 GB/s = 113.8 ms
```

最后这个数：**每前向 113.8 ms，与这一向前向算了多少 token 无关**。
换句话说，选项 2 每算一个 chunk（4096 token），就要搬相当于 **48 个 chunk 的 KV**。

> **为什么这么贵？** `_broadcast_tensor_from_owner()` 里 `comm.broadcast(tensor, src=owner_rank)`
> 广播的是 `remote_kv_buffer` 完整张量，形状 `(max_total_num_tokens + page_size, 1, kv_cache_dim)`
> （`memory_pool.py:5283` 的 `DSATokenToKVPool`，`size` 就是 token 数）。
> 集合通信要求所有 rank 传形状一致的张量，所以不能只 gather 本批次命中的 page。
> 池子开到 192k，就把这份成本放大 48 倍。

### 冷启动 vs 90% 命中

| | 冷启动（0% 命中） | 90% 命中 |
|---|---|---|
| 实际计算 token | 192k → 48 个 chunk | 19.2k → 5 个 chunk |
| 选项 1 额外开销 | 47 × `t_chunk/(m+1)`，m 大时 <5% | 5 × `t_chunk/(m+1)`，**同比缩小 10×** |
| 选项 2 额外开销 | 48 × 113.8 ms ≈ **5.3 s** | 5 × 113.8 ms ≈ **569 ms** |
| 占计算时间比例 | 看 `t_chunk`（若 500ms → 23%） | **同一比例** |

选项 2 的**相对**开销不随命中率变（前向次数和计算量同步缩），变的是**绝对浪费**（5.3 s → 569 ms）。
而选项 1 的绝对浪费降得更多（同比 10×）。所以：

- **比相对开销**：两者都不变，选项 1 一直赢。
- **比绝对时延**：90% 命中让选项 2 的浪费掉到 569 ms，但计算本身也只有 19.2k token 的量，
  569 ms 依然是主导项。

## 03 选项 2 唯一的反击：它算得更快

`attn_tp = 2` 对 `attn_tp = 1`，选项 2 的 attention 是 8 路对 4 路。
192k 下 attention 的 FLOPs 占比极高（每 token 的 attention 成本 ∝ 前缀长度），
所以选项 2 的纯计算时间可能只有选项 1 的一半到七成：

```text
选项 1 总时间 ≈ 1.00 × t_compute + bubble
选项 2 总时间 ≈ 0.6~0.8 × t_compute + 113.8 ms/前向

代入 t_chunk = 500 ms, m = 8：
  选项 1 ≈ 500 + 56  = 556 ms
  选项 2 ≈ 350 + 114 = 464 ms      ← 冷启动下选项 2 反而可能略快
```

这也解释了为什么 **90% 命中会把结论翻过来**：`t_compute` 缩到 1/10（50 ms 量级），
选项 2 的 30% 计算优势只剩 ~15 ms，而 114 ms 广播一分不少。此时选项 1 稳定赢。

## 04 什么情况下反过来选 2

| 条件 | 为什么 |
|---|---|
| **池子装不下** | 唯一硬理由。192k 池 × `⌈L/2⌉` 层超过每卡显存时，选项 1 直接起不来 |
| **互连是 NVLink 级** | 广播 ∝ 1/带宽。55 → 450 GB/s 时每前向 113.8 → 13.9 ms，选项 2 的 2× attention 并行度变成净胜 |
| **`m` 压不下去** | 选项 1 的 bubble 是 `1/(m+1)`；并发上不去、`m` 只能到 1–2 时是 33–50% |
| **纯冷启动且 attention 占比极高** | 90% 命中会稀释选项 2 的计算优势；只有每次都满 192k 冷算才吃得满 |

## 05 常见误解

- **「90% 命中等于只算 19.2k，所以两者都变便宜，结论不变。」**
  变便宜的方式不同：选项 1 的 bubble 与 P2P **随计算量缩**（10×）；
  选项 2 的广播**每前向照付**，只是前向次数少了。所以 90% 命中会**放大**选项 1 的相对优势。
- **「LayerSplit 省了 KV，所以长上下文一定更划算。」**
  它在 192k 下省的是 **1.82 倍**（4.31 → 2.37 GB），96 GB 卡上这点余量用不到；
  而它付的广播是 **6.26 GB/前向**。容量不是瓶颈时，这笔交易是亏的。
- **「PP 有 bubble，所以 PP 一定更差。」**
  不一定。bubble 是 `1/(m+1)`，`m` 大时可压到 5% 以下；而选项 2 的广播在 192k 下是
  113.8 ms/前向，对 `t_chunk = 500 ms` 就是 23%。冷启动下选项 2 甚至可能略快 ——
  真正的分水岭是命中率与带宽。

## 06 自测

1. **为什么说选项 2 的广播「与命中率无关」？**
   → 广播的是 `remote_kv_buffer` 整个张量，形状 `(max_total_num_tokens + page_size, 1, kv_cache_dim)`。
   池子要装下 192k 前缀，所以每次广播就是 139 MB/层 —— 哪怕这一向只算了 4096 个新 token。
   命中率只改变**前向次数**，不改变**每次前向的字节数**。
2. **那 90% 命中到底改变了什么？**
   → 改变了「浪费占计算的比例」。冷启动 113.8 ms 占 23%；命中 90% 时 `t_compute` 缩到 50 ms 量级，
   同样的 113.8 ms 就是 200%+。
3. **选项 2 的 attention 并行度为什么是 8 而选项 1 是 4？**
   → `attn_tp = tp // dp // cp`。选项 1：`4//1//4 = 1`，×CP4 = 4 路；选项 2：`8//1//4 = 2`，×CP4 = 8 路。
   两者 CP 相同，差别全在 TP 宽度怎么摊到 attention 上。
4. **带宽从 55 提到 450 GB/s，结论会变吗？**
   → 会。广播时间按 1/带宽 缩到 13.9 ms，选项 2 变成净胜。
   所以「192k 选谁」的真正前置条件是**这块卡的互连是多少**，不是上下文长度本身。
