PP 适配 DFlash：伪造单例 PP 组 + 两条跨阶段数据流

2026-09-16 SGLang流水并行DFlash 投机解码跨阶段通信正确性 bug
速览 前置知识 为什么天生冲突 矛盾与四块改动 为什么选这个方案 正确性 bug 常见误解 自测 延伸阅读

速览 · 30 秒

  • 冲突点：上游 SGLang 用三道断言禁止「投机解码 + 流水并行」共存，因为 DFlash 的数据流假设所有东西都在一个 rank 上——草稿模型、它需要的多层 hidden、以及 LM head。
  • 核心手法：不切分草稿模型，而是给它伪造一个 world_size=1 的 PP 组，让 6 层 draft 以为自己在 PP=1 下运行，整体待在第 0 段。
  • 真正的工作量：设计两条跨阶段数据通道——aux hidden 沿 PP ring 去程累积、投影结果沿 output ring 回程绕回，并把 draft 状态装进信封穿环传递。
  • 代价：草稿计算全部压在 PP0，PP0 明显更忙（busy 25.98s vs 其他段 21.8–23.3s），且 prefill 放弃图捕获。
  • 顺便收获一个教训：投机解码下按「请求数」切片张量是错的，必须按「token 行数」切——同一个坑在 PP+MTP 上已经踩过一次。

前置知识：三个概念

① 流水并行（PP）在做什么

把一个模型的层按顺序切成几段，每段放一组 GPU。第 0 段算完自己的层，把激活值沿一条 ring 传给第 1 段， 依次往后；最后一段算完把结果沿 output ring 传回第 0 段。数据在环上流动，所以叫 pipeline。 关键性质：每一段只持有自己那几层的权重，也只看得见自己那几层的中间结果——这正是下面所有麻烦的根源。

② 投机解码在做什么

用一个小而快的 draft（草稿）模型先一次性猜出后续若干 token，再让目标模型一次前向把这些猜测 全部验证（verify）。猜对的部分直接接受，猜错的位置截断重来。收益来自「一次前向验证多个 token」， 所以 verify 阶段的批内 token 行数 = 请求数 × draft 长度。

③ 为什么这两件事天生冲突

把 draft 的需求逐条摆出来，冲突就很直观了：

draft 需要什么在 PP 下它在哪里
目标模型多个中间层的 hidden state（本例捕获 6 层）散落在 4 个阶段上
LM head（把 hidden 变成词表 logits）只在最后一段
输入 embedding 与下一步的 draft 输入在第 0 段
草稿模型自己（6 层，体积很小）没有归属

上游的选择是干脆不支持：if cfg.pp_size != 1: raise ValueError(...)。 要让它跑起来，必须把这四条需求在 PP 的拓扑上重新安排一遍。

一、要解决的根本矛盾

上游 SGLang 硬性禁止 DFlash 与 PP 共存，三道护栏都在启动期直接报错：

# speculative_hook.py
if cfg.pp_size != 1:
    raise ValueError("Currently DFLASH speculative decoding only supports pp_size == 1.")

# server_args.py
assert (cfg.disable_overlap_schedule and cfg.speculative_algorithm is None), \
    "Pipeline parallelism is not compatible with overlap schedule, speculative decoding"

# layer_setup.py — 推测层的选取条件里没有 DFlash 分支

而即使放开护栏，DFlash 的数据流仍假设「只有一个 rank」：草稿模型是个独立的小模型、需要目标模型多个中间层的 hidden state、还需要 LM head。这些在 PP4 下分散在四个阶段上。

二、改动分四块

A. 放开护栏（全部门控在 DFLASH_PP_INIT_PROBE=1 下）

三个文件各 1~4 行，都是 and os.environ.get("DFLASH_PP_INIT_PROBE") == "1" 形式的条件放宽。没有改算法，只是把禁入改成可入，且保留开关随时可退回。

为什么用环境变量门控，而不是直接删断言

删掉断言等于把这个尚不完整的能力（暂不支持混合微批、TBO/CP）暴露给所有用户；门控成开关则让实验可以推进、 同时保持默认行为不变。改一个上游的「禁止」为「允许」时，给出可退回的开关，比改默认值更负责任。

B. 草稿模型不切分——伪造单例 PP 组

dflash_pp_scope.py（新增，1.5 KB）是整个适配的钥匙：

def create_singleton_pp_group():
    # 每个 rank 建一个 world_size=1 的"PP 组"（集合操作，全 rank 同序参与）
    return ps.init_model_parallel_group(group_ranks=[[rank] for rank in range(world_size)], ...)

@contextmanager
def draft_pp_scope(group):
    ps._PP = group                                  # 临时替换全局 PP 组
    with get_parallel().override(pp_size=1, pp_rank=0, pp_group=group):
        yield                                       # 世界对草稿模型来说退化成 PP=1

worker 侧对应地把 ps 替换后构建，并把 forward 也包进同一个 scope：

self._draft_pp_group = create_singleton_pp_group() if ps.pp_size > 1 else None
with self._draft_scope():
    bundle = build_draft_tp_worker(ps=replace(ps, pp_rank=0, pp_size=1), ...)
...
with torch.inference_mode(), self._draft_scope():
    draft_out = self.draft_model_runner.forward(forward_batch)

关键点：6 层的草稿模型整体跑在 PP0 上，不参与流水切分。构造和 forward 都必须进 scope，因为两者都读并行状态。

C. 两股跨阶段数据流（这是真正的工作量）

sequenceDiagram participant P0 as PP0 · target 层 0-15
＋DFlash draft participant P1 as PP1 · 层 16-30 participant P2 as PP2 · 层 31-45 participant P3 as PP3 · 层 46-61 Note over P0,P3: ① 去程 · aux hidden 沿 PP ring 前向累积 P0->>P1: hidden ＋ dflash_aux_hidden P1->>P2: hidden ＋ 累积后的 aux_hidden P2->>P3: hidden ＋ 累积后的 aux_hidden Note over P3: project_target_hidden() 只在这一段跑
（最终 hidden 只有末段才有） Note over P0,P3: ② 回程 · 投影后的 context 走 PP output ring P3-->>P0: dflash_result/context Note over P0: take_projected_context() 后立刻 del
中间段不再携带这个张量

去程：DFlash 需要 layers_to_capture 这几层的 hidden state，而它们散落在四个阶段。每个阶段只打包本地的捕获：

local_capture_count = (sum(self.start_layer <= i < self.end_layer for i in self.layers_to_capture)
                       if dflash_pp_capture else len(self.layers_to_capture))

然后把 dflash_aux_hidden（形状 [rows, preceding*hidden]）挂进 PP ring 往下传，每段校验 shape/dtype/device 后追加自己那份。

回程：投影必须发生在末段，然后结果沿 output ring 绕回 PP0。所以有了 dflash_pp_result.py——一个带 dflash_result/ 前缀的信封，装 bonus token、seq_len、block_size、commit_len。里面每处都 .clone()，注释说明了原因：

Queued PP outputs must survive subsequent graph/static-buffer reuse.

即 PP ring 会把包跨微批排队，而 worker 的 buffer 会被复用（CUDA graph 静态缓冲），所以必须存快照而非引用。

为什么回程要「用完立刻 del」

投影后的 context 只有 PP0 的 draft 需要。中间段拿到它没有任何用处，却会占着显存、并且每传一段就多一次 ring 上的字节量。跨阶段数据流要显式管理生命周期——这也是为什么 take_projected_context() 之后立刻 释放：让这个张量只活在真正需要它的两个端点。

D. PP0 缺的东西要补

dflash_pp_lm_head.py（新增）——PP0 上没有 LM head（它只在末段），所以直接从 checkpoint 单独加载一份不带量化的、按 TP 切分的 lm_head.weight，注释开头就写明了 "for drafting on the first PP stage"。同时 _resolve_dflash_embedding_module 会优先用这份副本。

三、为什么最终选了「伪造 PP 组」这条路

同样的问题至少有三个解法，选中的这个是最小侵入的：

方案做法代价
A · 把 draft 也切分 6 层按 PP 切成 4 段，每段 1–2 层 draft 本来就小，切完每段只剩一两层，通信与同步开销超过算力收益；而且它要的 6 层 hidden 仍要跨段收集，复杂度反而更高
B · 每段复制一份 draft 四个阶段各放一个完整 draft 显存与加载时间 ×4，但只有 PP0 那份会真正工作（draft 的输入 token 在 PP0 就确定了），纯浪费
C · 伪造 PP=1 单例组
（本次采用）		 用 world_size=1 的 PP 组替换并行状态，draft 整体留在 PP0 PP0 承担全部 draft 计算成为最忙的一段；但改动局限在 scope 与数据流，不碰 draft 内部结构

方案的取舍逻辑值得记住：当一个小模块与主框架的并行假设冲突时，优先让它在「自己以为的单卡世界」里运行， 而不是把它也切碎——前提是这个小模块的计算量相对于主流程足够小。draft 只有 6 层，正好符合。 代价也很清楚：负载会集中到一个阶段上（PP0 busy 25.98s vs 其他段 21.8–23.3s）。

四、一个容易漏掉的正确性 bug

- return PPProxyTensors({k: v[: self.bs] for k, v in output.tensors.items()})
+ return PPProxyTensors({k: v[: self.raw_num_token] for k, v in output.tensors.items()})

投机解码下一条请求产生 block_size 个 token 行，按请求数 bs 切片会丢行。以及 verify 的图预规划：

if pp_proxy_tensors is not None:
    # Verify planning precedes receipt of the preceding PP stage.
    # Refresh its activations now, even when attention metadata is ready.

——这和同项目里 PP+MTP 的 r37 补丁是同一类 bug（pre-planned verify 路径遗漏 pp_proxy 填充，末段 CUDA graph 读到旧缓冲）。同一个坑在 MTP 和 DFlash 上各踩了一次。

这类 bug 的共同形状

「按请求数分配/切片」的假设在非投机场景下永远成立，所以它能活很久；一旦每个请求携带多个 token 行 （verify、block 解码、CUDA graph 预规划），bs 和 num_token 就分道扬镳。 同一类错误在新特性上重复出现，说明它值得被写成一条检查项： 凡是用 bs 切片激活张量的地方，都要问一句「这里是不是该用 token 行数」。

六、明确未接通的部分（能力边界）

if batch.is_extend_in_batch and not batch.forward_mode.is_extend():
    raise RuntimeError('DFlash PP mixed decode/prefill is not connected')
if forward_batch.can_run_tbo or is_cp_v2_active(...):
    raise NotImplementedError("DFlash PP capture requires unsharded eager rows")

混合 decode/prefill 微批不支持、TBO/CP 不支持，加上 --cuda-graph-backend-prefill disabled —— 这些正好对应 profile 里看到的 prefill attention 0% 图覆盖。

把未接通的部分显式写成 raise 而不是「静默走错路径」，是这类适配能被信任的前提： 能力边界在代码里可读，而不是留给下一个调试的人去猜。

常见误解

✗「适配就是删掉那三道断言」
删断言只占改动的几行。真正的工作量在数据流：主文件 +590 行， 加上调度侧的 +94/-22、runner 的形状修正、以及 PP0 缺失 LM head 的补载。 断言是「不许」，而适配要回答「那么该怎么做」。
✗「草稿模型会被切分到各个 PP 段，所以 PP 越大 draft 越快」
恰恰相反——draft 整体留在 PP0，不参与流水。这意味着 PP 段数增加不会加速 draft， 反而让 PP0 相对更忙：draft 的计算全部堆在这一段上（实测 PP0 busy 25.98s，比其他段高 10% 以上）。
✗「折衷方案就是每段都放一份 draft」
看起来简单，实际上只有 PP0 那份会被用到：draft 的输入 token 在 PP0 就确定了。 其余三份纯占显存与加载时间。所以「复制到处都有」在这里不是冗余换安全，而是纯浪费。
✗「按请求数切片和按 token 行数切片是一样的」
在非投机解码下确实一样（一个请求一行）。一旦进入 verify，一条请求就产生 block_size 行——此时按 bs 切会静默丢掉大部分激活值。 这类 bug 不会崩溃，只会让结果悄悄变错，所以最值得警惕。

自测

1. draft 为什么必须整体待在 PP0，而不是可以任意挑一段？
因为它的两个端点都在 PP0：输入是待 draft 的 token（在 PP0 就确定了）， 输出要立刻参与下一轮 verify 的构造（也在 PP0）。把它放在别的段，等于把 draft 的输入输出都变成跨段通信。 另外 PP0 有 embedding，缺的只是 LM head——补一份副本比搬整个 draft 便宜得多。
2. 为什么 aux hidden 沿去程累积，而投影结果要走回程？
因为两者的输入依赖方向不同：aux hidden 是各段「本地」中间层的输出，只能各段自己产出， 所以沿 ring 正向逐段追加；而投影需要最终层的 hidden（只有末段才有），所以只能在末段算， 算完再沿 output ring 送回 PP0 给 draft 用。数据往哪边走，由它的依赖在哪里决定。
3. 信封里每个张量都 .clone()，不加会出什么问题？
PP ring 上的包会跨微批排队，而 worker 的缓冲区（尤其 CUDA graph 的静态缓冲） 会被后续步骤复用。不加 clone 就是把「引用」放进了队列——等接收方真去读时， 同一块内存已经被下一个微批改写，读到的是别人的数据。这类错误往往表现为偶发的、和 batch 组合相关的结果错误。
4. 为什么放开护栏要用环境变量门控？
因为这个能力还不完整（混合微批、TBO/CP 都不支持）。直接删断言会让默认配置也走这条未验证路径， 把风险扩散给所有人；门控成开关则让实验能推进、默认行为不变，而且出问题时能一行退回。 把上游的「禁止」改成「允许」时，保留一个显式的开关比修改默认值更安全。
5. 这个适配明确不支持哪些场景？为什么这些限制是合理的？
不支持混合 decode/prefill 微批、TBO 与 CP，且 prefill 关闭了 CUDA graph。 合理性在于：这些路径都会改变「行」的组织方式（谁和谁在一个微批里、行怎么切分）， 而 aux hidden 的累积与信封传递正是按行组织的。先让主干路径（纯 decode + verify）跑通并用 raise 显式挡住其余路径， 比一次性支持所有组合更可靠。能力边界写进代码，比写在文档里更不容易腐烂。

一句话概括：这次适配没碰 DFlash 的算法，而是（1）放开三道禁入护栏并给了可退回的开关，（2）用一个伪造的单例 PP 组让草稿模型在 PP0 上以 PP=1 的视角独立运行，（3）新设计两条跨阶段数据通道——aux hidden 沿 ring 前向累积、投影 context 沿 output ring 绕回——并把 draft 状态装进信封穿环传递，同时补上 PP0 缺失的 LM head 副本。

代价也清楚：草稿模型集中在一个阶段，PP0 因此比其他段忙（profile 里 PP0 busy 25.98s vs 其他段 21.8~23.3s），且 prefill 放弃了图捕获。
