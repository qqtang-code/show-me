SGLang Router 的调度与 PD 请求生命周期

2026-11-17 sgl-routerPD 分离Radix CacheKV 传输

本文对照 sgl-project/sglang 的 main 分支（commit f534dba，2026-11-17）逐层拆开两件事：router 怎么选出一个（或一对）engine，以及 PD 部署下一条请求如何从 bootstrap_room 走到 KV 传输完成。所有结论都标注了文件与行号；凡是没有在源码里读到的推论，一律标 推断。

术语约定：下面这几个词在全文按此含义使用，不随上下文变化。
router = sgl-router 进程（Rust，sgl-router/src），机群级入口，一个进程服务一个模型。
worker / engine = 一个 SGLang 实例（HTTP 端口 + 内部 Scheduler + TP workers）。
prefill / decode = worker 的角色，启动时由 --disaggregation-mode 固定，不是请求级开关。
room（bootstrap_room）= router 为一次 PD 配对生成的正整数键，是 prefill 与 decode 之间唯一的关联标识。
bootstrap 在仓库里有两个含义：PD 的 KV 引导握手（bootstrap_host/port/room、/route），以及 router 之间的 peer bootstrap（radix tree 快照同步）。本文分别写作 PD bootstrap 与 peer bootstrap，不混用。
结论角色边界调度链策略矩阵 缓存感知PD 配对三种命中对比 超时与故障误解自测

01五条结论

TL;DR

  • Router 是控制面，不是数据面。它选 worker、生成一个 room、把同一份请求体同时发给 prefill 和 decode；KV 由 prefill 直连 decode 传，router 全程不碰（src/server/routes/chat/forward.rs:216-244）。
  • 默认策略不是 cache_aware。legacy 路径默认 round_robin，reorg 路径默认 power_of_two；cache_aware 要显式选，并且必须先有前缀信号（外部 KV indexer 或进程内 radix tree）（src/config/cli.rs:250-258、src/config/cli.rs:884-890）。
  • 选路是一条阶梯，不是一次打分。cache winner → 全局会话亲和 → 按 bucket 的准入 → capacity fallback，每一级失败落到下一级，全部落空才是 503（src/policies/selection.rs:210-330）。
  • PD 下 prefill 与 decode 是两次独立 dispatch，几乎同时发出。prefill 的响应被丢弃（除 input logprobs 一种情况），客户端拿到的是 decode 的流；prefill 先失败会把错误归因给 prefill，并在还有重试预算时排除它（src/server/routes/chat/forward.rs:890-950）。
  • 三种命中情况的差别不在 router 的配对逻辑——PD 下它总是配对——而在三处数字：prefill 要 forward 多少 token、decode 通过 decode_prefix_len 声明自己已有多少、实际 RDMA 传多少页（prefill.py:536-546、decode.py:1809-1830）。

02角色与边界：谁持有什么

把这四类进程各自"知道什么"分清，后面每一步才不会错位。关键点是：router 只持有元数据（哈希、计数、绑定），它既没有 KV 张量，也没有缓存块的 token 内容。

一句话记法：router 认识"哪个 worker 可能有这段前缀"，prefill 认识"这段前缀的 KV 在哪几页"，decode 认识"我要把这些页放到哪几页"。三者之间传递的全部是整数与地址，没有 token 内容。

03Router 内部：一条请求的调度链

Router 没有"队列"和"批处理"——它是 tokio 上的无状态转发器，组批发生在 engine 的 Scheduler 里。Router 侧唯一近似队列的东西，是 decode 准入用的信号量（DecodeGate）和 router 自算的 in-flight 计数。所以下面这条链是每请求一遍的，不存在攒批再发。

两个容易被忽略的细节：

  • tokenize 是可选的。只有当策略需要 token（cache_aware 恒为真）、或者开了 --dp-aware、或者 bucket 路由需要按长度分桶时才做；否则 router 直接把原始 body 转发，省掉一次分词（preparation.rs:1203-1209、policies/mod.rs:538）。
  • --no-tokenizer 会让 cache_aware 静默退化。没有 token 就没有 block hash，lookup_prefix_matches 返回 None，阶梯直接走 load 兜底。这不是报错，是降级。推断（由 chat.rs:691-729 的 zip(tokens) 分支推出）。
PD 模式下的一次请求：router 的两条腿与 prefill→decode 的 KV 通道
实线 = 请求/响应；红线 = PD 内部的握手与 KV 通道，这两步 router 只提供 room 与 bootstrap_host/port，不参与。序号 3/4 之间没有 await：spawn_prefill_request 先起任务，decode 腿紧接着发出。

为什么 prefill 与 decode 可以并发发出

dispatch 先把 prefill 作为一个 tokio::spawn 任务起起来，再构造 decode 的请求并等待它；forward_pd 用 tokio::select! 同时盯两件事：decode 的响应，以及 prefill 的结果（forward.rs:246-330、:905-950）。语义如下：

  • decode 先返回 → 直接把 decode 的流交给客户端，prefill 任务继续在后台完成（held = None 分支）；
  • prefill 先失败 → 立即返回 prefill 的错误，并把这次失败归因给 prefill（Blame），有重试预算时排除它；
  • 需要 input logprobs，或开了 --pd-stream-after-prefill 时，decode 的响应先被 held 住，等 prefill 完成后再合并（wait_for_prefill）。

这也解释了一个常见现象：客户端只看到 decode 的 TTFT，但 prefill 的排队时间其实已经在里面——decode 要等 KV 到达才能出第一个 token。

04策略矩阵：八种 policy 与它们真正读的信号

--policy 是每个模型一份（router 只服务一个模型，所以等价于全局）。legacy 默认 round_robin，--chat-routing reorg 时默认变成 power_of_two（src/config/cli.rs:250-258）。decode 侧是独立的一套：只有 power_of_two 与 legacy_host_affinity 两个取值（src/config/types.rs:151-159）。

power_of_two引擎自报负载快照抽 2 个（--min-load-choices）取较轻者reorg 默认；cache_aware 的兜底；decode 默认

prefill 选的不是"一个 worker"，是一条阶梯

select_prefill_worker 把输入打包成 PrefillSelectionInputs，交给 Selector::run。后者按固定顺序尝试，前一级拿到人就返回（selection.rs:210-330）：

A
cache winner
cache_aware 专属：把候选截断到 --cache-candidate-max-workers，先过队头闸门，再过 KV 容量准入，然后在"未命中 token 近似并列"的集合里按压力决胜。拿到即返回，后面几级不再执行。
B
global affinity
只有 --policy session_aware 且 bucket 模式不是 bucket 时才有：先在全局池里探一次会话绑定，再把绑定落到目标 bucket 的域里。
C
per-domain 准入
按 bucket 切成若干 CandidateDomain，每个域内跑一次策略提案，再过 resolve_prefill 的准入（num_running+1 ≤ max_running 且 num_total_tokens+input ≤ max_total_num_tokens）。
D
capacity fallback
所有域严格准入都失败后，整条阶梯再来一遍，这次允许"容量兜底"：先命中的域胜出。级间是两轮 find_map，不是一轮带 flag。
E
失败
全部落空 → PolicySelectionFailed / NoPrefillWorkersAvailable → 503（src/server/error.rs:218-222）。

decode 侧是同样的两轮结构，但只读负载：select_decode_peer 先对每个 decode 域做严格准入，再统一做 capacity fallback（selection.rs:779-838）。它连"没有负载快照"都不放过——没快照直接返回 None，而不是盲选（selection.rs:782-784）。

负载怎么比：一个向量，逐字段定胜负

引擎通过自己的 ZMQ PUB 口周期发布 LoadStat，wire 形如 [b"load", seq, msgpack]，router 订过来按 URL 存表；超过 5 秒没更新就视为过期，退回 router 自算的 in-flight（python/.../load_publisher.py:1-40、engine_reported_load.rs:294-297）。比较规则（engine_ranking.rs:15-59）：

prefill：estimated_prefill_queue_ms ↑
         → num_waiting_uncached_tokens ↑
         → num_waiting_reqs ↑
         → num_running_reqs ↑
         → router 本地 in-flight ↑
decode ：num_waiting_reqs ↑ → num_running_reqs ↑ → KV 占用率 ↑

逐字段字典序，第一个不等的字段决定胜负，不做加权。这也是为什么 P2 只需要"两个样本里挑一个"：比较是 O(1) 的。

05缓存感知：三份信号、四道闸门

--policy cache_aware 不是"打开 radix cache"，而是"让 router 去问谁有这段前缀"。信号有两个来源，二选一（cli.rs:884-890）：

① 外部 KV indexer（gRPC）

  • --kv-indexer-endpoint 设了就默认用它；router 本地树被整体关掉，只订 load（kv_events/index.rs:607-616）。
  • 请求是 MatchExternalKvPrefix(hashes, max_blocks)，返回每个 worker 的 matched_prefix_blocks（sgl-kv-indexer/proto/kv_indexer.proto:125-163）。
  • worker_address 必须与 router 注册的 URL 逐字节相同，否则静默不命中（policies/cache_aware.rs:45-48）。
  • Indexer 不可达/超时/过载 → 降级为 min-load，请求不失败（chat.rs:754-774）。

② 进程内 radix tree（KV events）

  • engine 侧开 --kv-events-config，router 从 /server_info 的 kv_events 块发现地址并订阅（kv_events/discovery.rs:116-127）。
  • 事件只有三种：BlockStored / BlockRemoved / AllBlocksCleared（wire.rs:49-58）。
  • 节点存 (block_hash, parent, workers{(url,dp_rank): tiers})，不存 token ids、不存 KV（tree.rs:489-507）。
  • 查询按"每个 worker 各自的最长连续深度"返回块数，不是全局最深节点持有者集合（tree.rs:1608-1635）。

块哈希：把 prompt 变成可比对的整数

链式 SHA256：每块的摘要 = SHA256(父块完整 32 字节摘要 ‖ 本块 token 的 4 字节小端)，最后截前 8 字节成 i64（hash.rs:137-163）。三个输入决定"算不算同一段前缀"：

  • block_size：来自 worker 的 page_size，进程级单例，第一个 worker 定调，后来者不一致就拒绝该 worker（block_size_oracle.rs:120-123、index.rs:550-559）。
  • cache_salt：作为链首种子参与哈希，不同 salt 从第 0 块就分叉（hash.rs:68-71）。
  • lora_name / adapter：对每个块哈希再做一次 keying（hash.rs:77-84）。

CacheNamespace 来自请求 body（model: "base:adapter"、lora_path、cache_salt），不来自 header；一个请求里多个值不一致时置 ambiguous，直接返回空哈希——宁可 miss，不猜（preparation.rs:42-84、hash.rs:64-67）。

从"块数"到"token 数"：一次按比例折算

matched_tokens = input_tokens × matched_prefix_blocks / query_blocks
uncached_tokens = input_tokens − matched_tokens          policies/cache_aware.rs:202-217

代码里没有任何 matched_blocks × block_size 的乘法——router 并不知道每块真实有多少 token（尤其最后一块往往是残块），所以按"查询块数"等比折算。同一段逻辑在 reorg 路径里也有一份内联实现（policies_reorg/cache_aware.rs:148-172）。

四道闸门，顺序不能换

闸门判据默认值源码

闸门之后还有两个"软"机制，它们决定"要不要为了负载放弃一点前缀"：

  • 切换余量 --cache-switch-margin-tokens（默认 1024）：只有两个候选的未命中量差超过它，才允许用负载翻盘；否则按"未命中更少"稳定排序（admission.rs:607-648）。
  • 压力守卫（--pressure-abs-threshold-tokens 默认 1024、--pressure-rel-threshold 默认 1.5、可选的 ms 阈值）：在近似并列的集合内，如果 A 比 B 明显更受压，就把 A 排到后面（admission.rs:659-692）。

最后是饱和钉住：如果队头闸门把所有候选都拒了，而全机群没有一个 worker 的队列低于 --saturation-queue-floor，那么"换个地方等"并不能少等，router 反而保留前缀所有者——同样的等待，至少 prefill 是命中而不是冷算（admission.rs:283-345，判决标签 SaturationPin）。这条路径的指标标签是 AllQueued 而不是 CacheHit，两者在监控里必须分开看。

一个反直觉点：cache_aware 的"命中"是块粒度、页对齐的。match_prefix 在 page_size > 1 时会把长度截断到页的整数倍（mem_cache/radix_cache.py:386-387），所以哪怕引擎缓存了全部 token，router 看到的匹配长度也不会超过 floor(L/page)×page。

06PD 配对：room 是唯一的关联键

PD 部署下 router 只说三句话：发给谁（prefill）、发给谁（decode）、你们用这个 room。剩下的握手、寻址、传输、完成确认，全部由两个 engine 自己完成。理解这一点，后面所有"谁发起"的问题都会变得简单。

room 的生成：把 router 的选择编码进一个整数

pub(super) fn generate_room_id() -> u64 {
    rand::random::<u64>() & (i64::MAX as u64)          // 引擎按 int64 存
}

/// A room with `room % dp_ranks == rank`, which is how decode finds the prefill rank.
pub(super) fn generate_room_id_for_rank(rank: u32, dp_ranks: u32) -> u64 {
    let dp_ranks = u64::from(dp_ranks);
    (generate_room_id() >> 1) / dp_ranks * dp_ranks + u64::from(rank)
}                                                       preparation.rs:1264-1272

第二行是整个 PD 配对里最需要注意的一处：decode 默认不被额外告知 prefill 的 DP rank，它自己算 room % dp_size（decode.py:1197-1199）。所以当 router 开了 --dp-aware 并替 prefill 选定 rank 时，它必须反过来约束 room，让这个取模结果正好等于所选 rank——否则 decode 会去错误的 rank 取 KV。兜底的显式通道是请求体里的 disagg_prefill_dp_rank（forward.rs:759-778）。

decode 侧状态机：什么时候算"可以开始解码"

KVPoll 只有五个状态：Failed=0 / Bootstrapping=1 / WaitingForInput=2 / Transferring=3 / Success=4（base/conn.py:141-147）。decode 的推进条件是三件事都到齐：

  1. 所有目标 prefill rank 的状态帧都到（apply_prefill_status 按 prefill_unique_rank 去重计数，够 required_prefill_response_num 才置 Success，conn.py:1053-1076）；
  2. metadata buffer 里确实已经写进了本 room 的首 token（读到 bootstrap_room == 0 就仍算 Transferring，utils.py:339-354）；
  3. 页数据按本轮 kv_indices 收齐（传输层保证）。

第 2 条是防"状态帧比数据先到"的经典竞态：状态帧走 ZMQ/控制面，首 token 走 RDMA/数据面，两者没有共同时钟。所以 decode 用 metadata buffer 里的 room 字段做栅栏——这同时也防了 room 复用导致的串号（不匹配直接 abort，报 Context corruption，decode.py:3420-3466）。

传输本身：谁在搬、怎么并行

  • 不在 scheduler 线程里搬。scheduler 只把 (src_page_indices, dst_page_indices) 入队，prefill 每个 TP rank 有 SGLANG_DISAGGREGATION_QUEUE_SIZE（默认 4）个队列，每个队列一个 worker 线程 + 一个线程池（mooncake/conn.py:354-402）。
  • 分片是确定性的：shard = Σ(目的 session 端口的数字部分) % 队列数，保证同一组目的端的请求落在同一队列（mooncake/conn.py:3440-3450）。
  • 三个层次的并行：rank 间（每 rank 独立进程与端口的 KVManager）／层间（每层一个 executor.submit，mooncake/conn.py:1370-1379）／页间（连续页合并成一次 batch_transfer_sync，group_concurrent_contiguous，:1207-1209）。
  • 与计算的先后：默认"算完再传"（process_batch_result_disagg_prefill 发最后一块）；但缓存命中部分可以在 forward 之前先发——maybe_send_cached_prefix_chunk，开关是 SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX（prefill.py:1627-1666）。这正是"部分命中"能进一步压 TTFT 的地方。

07三种命中情况：完整运转流程

先把记号定下来，后面三个小节只是往同一组公式里代不同的数：

L  prompt token 数
P  page_size（引擎的 KV 页大小，也是 router 的 block_size）
p  prefill 侧 radix 命中长度（page 对齐；0 ≤ p ≤ L）
d  decode_prefix_len：decode 通过 metadata 告诉 prefill "这段我已有"
             （仅当 decode 侧 radix cache 开启时可能 > 0，默认 0）

计算量 = L − p          只有 prefill 的 forward 处理未命中部分
传输量 = L − d          prefill 把 [d, L) 的页写给 decode
router 可见的是 p（决定"发给谁"）；d 由 decode 自己算，router 从不知道

最后一行是这一页最重要的结论：router 的 cache-aware 优化的是"把计算放到有缓存的那台机器上"，它并不会减少 KV 传输量。真正减少传输的是 decode 侧 radix cache（--disaggregation-decode-enable-radix-cache，默认 关，fields/disagg.py:104-110）。

同一段 8192-token prompt 在四种情况下的 token 归属（按比例绘制，P = 64）

0L = 8192

示意图，不是实测。前 3 行对应题目的三种情况；第 4 行是开启 decode 侧 radix cache 后的变体，用来说明"真正缩短传输的是 d"。C 行留出最后一页，是因为 prefill 必须采出第一个 token（prefill.py:1197），而采样要有 logits，logits 要有一次 forward；具体少到多少由 prefill 的 checkpoint 边界决定，这里不逐行展开。

A. 完全未命中（p = 0, d = 0）

  1. Router：lookup_prefix_matches 拿到 PrefixOutcome::Empty 或全 0 匹配，cache_aware 的候选集为空 → 阶梯退回 P2（selection.rs:210-240）；选出 prefill、按容量选 decode，生成 room。
  2. Prefill：match 返回 0，extend_end = L，forward 全量 L 个 token（可能被 chunked prefill 切成多批）；每批 checkpoint 进 radix cache。
  3. Bootstrap：decode 的 metadata 带 decode_prefix_len = 0，prefill finalize_bootstrap 后 start_send_idx = 0、num_pages = ceil(L/P)（prefill.py:536-549）。
  4. 传输：最后一块 send_kv_chunk(last_chunk=True) 把 [0, L) 全部页写给 decode。
  5. 完成：prefill 采样出首个 token 写进 metadata buffer，发状态帧；decode 计数到齐 → Success → 提交首 token → 开始逐 token decode。

开销构成：prefill 算 L、传 L，decode 等 max(自己排队, prefill 算完 + 传完)。这是三种情况里唯一"算与传都满"的。

B. 部分命中（0 < p < L, d = 0）

  1. Router：indexer / radix tree 返回 matched_prefix_blocks > 0；折算成 matched_tokens ≈ L × blocks/query_blocks。过 1024-token 门限后成为 cache 候选，按"未命中最少"排序；若该 owner 队列超 --worker-queue-limit，先尝试换到别的 owner（放弃一部分前缀），换不到且全池饱和则 SaturationPin 钉回原 owner。
  2. Prefill：prefix_len = p，forward 只算 L − p；已在 cache 的 [0, p) 不重算。
  3. Bootstrap：同 A，d = 0 所以 start_send_idx = 0、页数仍是 ceil(L/P)。
  4. 传输：注意——传输量没有减少。decode 没有这段 KV，[0, p) 的页虽然"不用算"，但仍然要从 prefill 的 cache 里读出来发过去。开了 early-send 时，这段可以先发、与 forward 重叠（prefill.py:1627-1666）。
  5. 完成：同 A。

收益全在 prefill 的 L − p 上：TTFT 里"算"的那一段按比例缩短；传输时间不变。所以 B 的加速比大致是 (L + 传输) / (L − p + 传输)——前缀越长、传输占比越高，命中带来的边际收益越小。

C. 全部命中（p ≈ L, d = 0）

  1. Router：命中比接近 1，几乎必然选原 owner；此时它做的唯一有价值判断是"这个 owner 还收不收得下"。
  2. Prefill：extend 只剩最后一页（甚至 0 个新 token）。即便如此，prefill 仍要跑一次 forward 才能采出第一个 token——req.output_ids.append(next_token_id) 发生在 prefill 的结果处理里（prefill.py:1197）。
  3. Bootstrap：仍然要握手。协议上没有"decode 自行完成"的分支：decode 依旧发注册与 metadata，prefill 依旧回状态帧。差别只在传输页数。
  4. 传输：[0, L) 的页仍要发（d = 0）。只有 decode 已持有到 L（d = L）时传输区间才会空：end_idx < start_send_idx 时 _send_kv_chunk 直接 return，相等时也只是零页（prefill.py:1718-1723）。
  5. 完成：同 A。
"全部命中"不等于"prefill 不参与"。它只意味着 prefill 的 forward 退化成最后一段（或一页），而 bootstrap、首 token 采样、KV 传输三件事一件都没少。真正能让传输归零的是 d = L，也就是 decode 自己已经有整段前缀——这需要 decode 侧 radix cache，且该请求此前在同一台 decode 上跑过。

背压的出口只有两个：503 与 504。router 自己不生成 429——ApiError 里没有这个变体；引擎返回的 429/503 会被原样转发，同时被归类为 Backpressure，既不打开熔断器、也不清空已有的失败连击（circuit_breaker.rs:207-238）。这条设计避免了"繁忙的 worker 被误判为坏 worker"。

10四个常见误解

"router 会把 KV 转发给 decode"

不会。router 只传 room 和 bootstrap_host/port；KV 由 prefill 直接 RDMA 写到 decode 注册的地址（forward.rs:216-244、mooncake/conn.py:2048）。这也是为什么 router 的带宽不是 PD 部署的瓶颈——它只承载 token 流。

"cache_aware 看的是引擎 GPU 里的 radix tree"

它看的是块哈希的持有关系：要么来自外部 indexer 的 block_hash → worker，要么来自 router 自己维护的树（由引擎的 BlockStored/BlockRemoved 事件喂养）。router 既没有 KV，也不知道缓存块的 token 内容（tree.rs:489-507）。误判的代价是"发到了一个其实没有这段前缀的 worker"，后果是那次 prefill 退化成全量计算，不是错误。

"全部命中就不用 prefill，也不需要 bootstrap"

两件事都不成立。prefill 至少要跑一次 forward 才能采出第一个 token（prefill.py:1197），而 bootstrap 是 decode 获取"往哪写、写多少、首 token 是什么"的唯一通道，与命中率无关。命中只改变 forward 的长度。

"router 会探测健康状态，失败就摘除"

这个版本里没有主动探测：src/health/ 下只有一个 circuit_breaker.rs，没有任何 --health-* 参数。健康判断完全是被动的：请求失败累计到阈值 → 熔断器打开 → 候选集剔除；冷却后放一个探针。全员打开时还会 fail-open 回全池（registry.rs:200-212）。

11自测

Q1：一个 8192-token 的 prompt，P=64，prefill 全命中。KV 要传多少 token？

仍然传 8192 个 token 的 KV（128 页）——除非 decode 侧 decode_prefix_len > 0。传输量 = L − d，与 prefill 的命中长度 p 无关。

Q2：为什么 generate_room_id_for_rank 要先把随机数对齐到 dp 的整数倍、再加 rank？

因为 decode 默认用 room % prefill_dp_size 推断"该去哪个 prefill DP rank 取 KV"（decode.py:1197-1199）。router 既然已经替 prefill 选了 rank，就必须让 room 的取模结果等于它，否则 decode 会查错 rank；显式覆盖只有 disagg_prefill_dp_rank 一条路。

Q3：cache_aware 选了 A，但 A 的队列已满，B 有同样的前缀且空闲。会发生什么？

--worker-queue-limit 打开时，A 先被队头闸门拒掉，请求转到 B（放弃一部分前缀局部性）；如果全池都在排队且没人低于 --saturation-queue-floor，则触发 SaturationPin，钉回压力最小的 owner——同样的等待，至少 prefill 是命中。指标上分别记 CacheWorkerQueued 与 AllQueued。

Q4：router 返回 503 和引擎返回 503 有什么区别？

router 的 503 是"没有可用的 worker / 全部候选被准入拒绝"（no_healthy_workers、policy_selection_failed 等），属于路由层结论；引擎的 503 是背压，会被原样转发、归入 Backpressure，不打开熔断器，并可能触发重试（若还有重试预算）。
