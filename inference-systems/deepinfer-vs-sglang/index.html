核心结论

  • 同源、不同定位。两者都是 DeepSeek 系深度优化的推理引擎：DeepInfer 是 DeepSeek 生产系统的官方底座；而 SGLang 已反向移植了 V4.1 的关键能力（dsv4 压缩注意力后端、mHC、SWA replay tail、DSpark 变长验证），在 DeepSeek 模型栈上两者高度趋同。
  • 开源完整度是最大分野。DeepInfer 开源的是"引擎内核"——调度、算子、模型、显存管理；KV 分布式存储（3FS）、四级负载均衡、E/P/D 分离编排等生产组件未开源，接口已预留。SGLang 从 HTTP API、Rust 路由到 PD 分离、分层 KV 存储、RL 训推一体全栈可用。
  • 工程路线泾渭分明。DeepInfer 用 C++ 写调度器（nanobind 绑定、进程内运行）、用 TileLang JIT 写全部自研 kernel、把算子库 vendor 进仓库，围绕"一块超节点跑满一款模型"做极致优化；SGLang 用 Python 调度器 + ZMQ 多进程模型、用 Rust 写外围（路由 / gRPC / tokenizer / 树缓存内核）、算子库走 pip 依赖，追求"一套代码跑所有模型与硬件"。

01定位与开源范围

读完这节，你能回答：两个项目各自解决什么问题？开源版本里有什么、缺什么？为什么 DeepInfer 只有一款模型？

两个项目都在解决"把 DeepSeek 级别的 MoE 大模型以最低成本跑进生产"这一个问题，但一个开源的是生产系统的内核，另一个是完整的社区产品。README 的自我描述最能说明定位差异：

  • DeepInfer："DeepInfer is the high-performance inference framework that powers DeepSeek's large-scale production services. This open-source release provides offline inference with the core features needed for serving at scale."（README）——开源的只是"规模化服务所需的核心能力"，且明确列出三大件不在本次发布中：KV cache 系统、VE/Prefill/Decode 分离、跨数据并行副本的负载均衡。
  • SGLang："SGLang is an open-source inference framework for large language, vision-language, and diffusion models, optimized for agentic workloads, large-scale serving, and RL rollouts."——从推理引擎到图像/视频生成（SGLang Diffusion）、音频（sglang-omni）、draft 模型训练（SpecForge）构成完整生态。

02整体架构：同一条请求，两边各走一遍

读完这节，你能回答：谁接收请求、谁决定下一轮执行什么、谁执行、谁把 token 变成文本？两个引擎的进程边界分别画在哪里？

这是两者最直观的分野：SGLang 是"多个平等进程 + 消息总线"的服务架构，DeepInfer 是"单进程引擎 + 从属 worker 守护进程"的内核架构。先沿一条请求把两边的路径并排列出——左边走 DeepInfer 的离线 LLM API，右边走 SGLang 的在线 HTTP 服务：

03调度与异步执行

读完这节，你能回答：两个引擎如何消除 CPU 调度造成的 GPU 空泡？一轮的预算怎么定？为什么同样的输入可能得到不同的输出？

两者都把"消除 CPU 调度造成的 GPU 空泡"作为 decode 性能的关键，思想同源——DeepInfer 官方部署说明 明确写道"参考已有实现（SGLang, Nanoflow）"。但两者的实现深度不同：SGLang 把"结果的批处理"延后一步，DeepInfer 把整个调度流水线重排成三段，并把部分调度决策本身搬上 GPU。

一轮安排多少工作，两个引擎都设有预算。教学抽象写成一道装箱不等式：

∑i ∈ At qi ≤ Bt

At 是第 t 轮准入的请求集合，qi 是本轮为请求 i 安排的位置数，Bt 是 token 预算——SGLang 的 PrefillAdder 与 DeepInfer 的 _schedule_prefill 都在解这道题；qi 不是该请求的最终输出长度（chunk 与 draft 验证轮不满足"每请求一个 token"）。DeepInfer 生产版进一步把 token 预算换成时间预算（生产侧披露）：∑ cost(qi, ci) ≤ T——cost 是对（新增 token 数, 已算前缀）拟合的二次代价模型，T 经 DP 组 allreduce-MIN 收紧，按"时间"而非"token 数"切批。两式均为教学抽象，具体分支以源码为准。

图 3-1 · 异步调度流水线对比。SGLang：schedule(N+1) 与 forward(N) 重叠、结果 N−1 延后处理；DeepInfer ZOS：每步严格"forward 当前步 → post-process 上一步 → launch 下一步"，元数据滞后一步由 GPU kernel 修正（worker/worker.py::execute_model_step、csrc/engine/zos.cpp）。

DeepInfer 的调度器怎么做
  • C++ 单体调度器：FCFS waiting 队列组 prefill 批，容量约束依次为 max_num_prompts → prefill 总 seqlen_k 预算（默认 2^30）→ max_num_batched_tokens；超长 prompt 自动 chunk 切分（开源版 chunked_prefill 默认关），切点避开图片 token 边界。
  • prefill/decode 步型投票：混合引擎下 DP 组内两轮 allreduce 表决——每 70 个 decode 步全员有 prefill 才插（ALL 点）、每 100 步任一 rank 有活就插（ANY 点），且 KV 使用率 ≤ 0.9 水位才允许 prefill，兼顾防饿死与防陪跑。
  • decode 批与抢占：running 按输出长度降序，从队尾（最新请求）准入；块不足时从队首（最长请求）抢占——直接结束或 reset_for_recompute 回队首重算；结构化输出请求不可重算。
  • 生产级调度（未开源，官方口径披露）：Prefill 按 4 个长度分桶（<16K / 16–64K / 64–256K / ≥256K）动态分配引擎；chunk 大小由时间预算反解二次代价模型 cost(q, c)（q=token 数， c=已完成前缀），预算再经 DP 组 allreduce-MIN 收紧——按"时间"而非"token 数"切批。
  • 批不变推理：DEEPINFER_BATCH_INVARIANT=1 切换 DeepGEMM/TileKernels 确定性算法 + FlashMLA batch_invariant 路径；确定性采样用 seq_seed 经 SplitMix64 按 (seed, position) 生成随机数，输出与 batch 组成、行序完全无关。
SGLang 的调度器怎么做
  • Python 调度器（6278 行）+ 策略插件：cache-aware 组（lpm 最长前缀优先 / dfs-weight / hrrn / shortest-prefill-first）与 cache-agnostic 组（fcfs 默认 / lof / random / routing-key），另有优先级调度与抢占阈值。
  • chunked prefill 自适应：预算按显存分档（<20GB→2048 … H100→8192）；PrefillAdder 同时约束 chunk token、输入 token 与总 token（decode 请求按 new_token_ratio 估算占用，schedule_conservativeness 可调）；可开 mixed chunking 把 decode 请求混进 prefill 批。
  • decode 批收缩（retraction）：KV 不足时按 length / priority 策略回退请求，与 DeepInfer 的 preemption 同类但独立调参。
  • overlap 工程化：结果延后一步 + FutureMap/ConfidenceRelay（采样 token 不落 CPU 直接进下一步 forward）+ 连续 prefill 批可临时禁用 overlap 保 TTFT；DP attention 下全局同步决策避免死锁。
  • 确定性推理：独立的 deterministic attention 后端集合与文档（deterministic_inference.mdx），但未像 DeepInfer 那样与投机解码互斥地保证端到端逐 token 一致。

易混淆 "异步/重叠"不等于"这些阶段不再耗时"，也不等于"少做了工作"——它只是把 CPU 逻辑挪进 GPU 忙碌的时间窗。开启投机解码或 chunked 轮次后，"一次 step"与"每条请求加一个 token"也没有对应关系；而 DeepInfer 的确定性输出与置信度驱动的变长验证是互斥选项（第 6 章展开）。

04KV Cache 与显存管理

这是设计哲学差异最大的地方。SGLang 的招牌是 RadixAttention 自动前缀复用 + 多层存储；DeepInfer 的招牌是"为 V4.1 Flash 量身定制的双 KV 结构 + SWA Bounded Replay"，而跨请求的自动前缀复用在开源版中并不存在——生产系统把这件事交给了外部 3FS 存储集群。

06投机解码：DSpark 的两种实现

读完这节，你能回答：为什么固定验证 5 个 draft 是浪费？两边的"置信度"从哪里来？每条请求的验证长度怎么定？

DSpark（DeepSeek 的变长投机验证方案）在两个框架里都有，但实现哲学不同：DeepInfer 让模型自带的 Confidence Head 在线预测接受率，并用实测性能曲线在线求解最优验证长度；SGLang 把接受率与代价做成离线校准表（SPS/STS），在 GPU 上用 planner kernel 排布 ragged 验证。共同的动机：固定验证 5 个 draft 会把算力浪费在低概率 token 上。

两边都要回答"验证多长最划算"。第一步是把每条请求的接受概率估计成前缀累乘（教学抽象）：

accr(k) = ∏j=1..k cr,j

cr,j 是请求 r 第 j 个 draft 的接受率估计——DeepInfer 由模型自带的 Confidence Head 在线预测，SGLang 来自离线校准的 SPS/STS 表。有了 acc(k)，再用"验证 k 个的耗时 vs 期望多收约 k·acc(k) 个 token"权衡验证长度；固定 5 个的做法因此被两边淘汰。

07并行与通信

读完这节，你能回答：两个引擎各自切分什么、不切分什么？DeepInfer 生产为什么不用 TP/PP？专家忙闲不均怎么办？

两者的并行设计都源自 DeepSeek V3 系"attention 数据并行 + MoE 专家并行"的配方，但取向相反：DeepInfer 做减法——生产上直接不用 TP/PP，把 Wide-EP 和 NVL 域内融合做到极致；SGLang 做加法——把每种并行维度都做成可组合的参数，覆盖从单卡到超节点的所有拓扑。

MoE 层的教学抽象，两边语义一致：

yi = ∑e ∈ Si αi,e · Ee(xi)

Si 是 token i 逻辑上选中的专家集合，α 是路由权重。关键区分：token 只知道"逻辑专家"；它被送往哪张卡上的哪个副本，由物理放置（EP 分组 + EPLB 副本布局）决定。本章所有机制改动的都是后半段。

易混淆 EPLB 改的是物理放置（专家副本放哪张卡、放几个），不改逻辑路由（选中哪些专家、权重多少）；重排时物理上移动的是权重，不是 token。另外，Wide-EP"减少访存"不等于"通信消失"——dispatch/combine 依然存在，只是每卡需要驻留的专家权重变少。

DeepInfer 怎么做
  • Attention DP（#DP = #EP）：注意力完全不切分——每个 DP rank 持有完整模型跑自己的请求子集（每 rank 一个 LLMEngine），MoE 部分则全组 EP。官方部署说明 明言"暂未用 TP、CP"。
  • Wide-EP：decode 用 EP64~128（超节点全域），显著减少 per-step MoE 专家权重访存量；prefill 用 EP2~8（显存够就小 EP）。README 基准即"4 卡 prefill / 64 卡 decode，各在一个 scale-up domain 内"。
  • MegaMoE（NVL 域融合）：当 EP 组在单个 NVLink 域内时，dispatch→GEMM1→SwiGLU→GEMM2→combine 整块融成 DeepGEMM 的 fp8_fp4_mega_moe / bf16_mega_moe 单核调用，激活在 NVLink symmetric memory（SymmBuffer）就位；官方结论"无论 EP/batch 大小都显著快于 unfused MoE"。
  • balanced CP（镜像式）：开源版支持的序列维切分：prompt 沿 token 维镜像均分到 CP ranks（chunk 对齐 cp_size×2），层内 DeepEP BucketBuffer all-gather 拼接、层末还原；decode 广播。生产暂未启用。
  • EPLB（开源）：冗余专家（每卡 ≥1 起，向上凑到 ep_size 倍数）+ 滑动窗负载统计 + 周期重排；权重搬运用 NVLink symm_mem IPC 原地 shuffle（NPU 不支持则退化跨网版本）。生产参数：prefill 每卡 4 个冗余专家、窗 100 步、1000 步重排，实测 moe_lb（最慢/均值）= 1.045~1.074；decode 每卡 1 个（EP64 下每卡 7 专家）、窗 1000、10000 步重排，moe_lb = 1.090。
  • 通信栈：DeepEP（vendor 固定 SHA：dispatch/combine + EngramBuffer + CP BucketBuffer）、NCCL（SM 数固定 32）、gloo（CPU 控制面）；PDL 开、NVLS/PXN 关等 worker 环境预设。
SGLang 怎么做
  • 全维度可组合：tp_size / pp_size / ep_size / attn_dp_size / attn_cp_size / dcp_size / moe_dp_size——attention DP 在 TP 组内切（FFN 仍 TP），与 DeepInfer 的"整模型 DP"是同思想不同粒度；DCP 专门解决 decode 长序列（MLA KV 按 p mod c 条带切分，partial attention + LSE 精确合并）。
  • 微批通信-计算重叠：TBO（two-batch overlap）/ SBO（single-batch overlap），token 分布阈值自动判定做 TBO 还是双块；配合 DeepEP 的 normal/low_latency 双模式自动切换（prefill 用 normal、decode 用 low-latency）。
  • MoE 分发后端 11 种：deepep / deepep_v2（ElasticBuffer，direct=单机 NVL / hybrid=多机）/ mooncake / nixl / moriep / pplx / flashinfer / megamoe / ascend_tp…；DeepEP/DeepGEMM 走 sgl-deep-ep / sgl-deep-gemm PyPI fork，另有 FlashInfer TRT-LLM / CUTLASS / cutedsl GEMM 后端可选。

  1. DeepInfer 生产为什么不用 TP/PP？把 Attention DP、Wide-EP、MegaMoE 与 TP/PP 各自解决的问题一一对应。
  2. EPLB 重排时，什么在物理上移动、什么保持不变？为什么搬权重用 NVLink symm_mem 原地 shuffle？

DeepInfer（生产形态）
  • 协议层独立成项目：deepseek-recipe 用 Rust 实现 API 协议转译与 tokenization（special-token 分段并行编码、KMP 增量流式解析、防 token 注入），与引擎解耦。
  • 三段分离：VE / Prefill / Decode 各自独立扩缩容（prefill 看未命中 token 数、decode 看在跑请求数），TTFT 与 TBT 独立控制。
  • 容错靠"配额冗余 + 请求级重路由"而非快速重启：重启是分钟级；大 EP 实例任一卡故障即整实例不可用，恢复时按健康卡重组 EP 规模。
  • 开源版预留了接入点：EngineType 三态、init_pd_split / do_save_kvcache / copy_state 等钩子、SWA 落盘布局都已实现——"most required engine functionality is already implemented"（README）。
SGLang（开箱形态）
  • API 面最宽：OpenAI 全家（chat/completions/responses/embeddings/rerank/classify/score/audio/realtime WS）+ Anthropic Messages + Ollama 兼容 + 原生 gRPC（Rust 内嵌 server）+ LoRA 热加载端点 + 权重热更新端点。
  • Rust 路由器：sgl-model-gateway 提供 cache-aware（前缀命中率路由）、prefix_hash、power_of_two 等策略，PD 专用 gRPC 路由，多 router 间缓存树 mesh 同步，带熔断/限流/重试。
  • PD 分离与复用：prefill/decode 分离（bootstrap server + mooncake/nixl/ascend/mori 传输）+ PDMux 同实例角色切换 + VLM 的 EPD 三级分离。
  • RL / Agent 专项：memory-saver 睡眠唤醒（保 CUDA graph 地址）、R-Fork GPU→GPU 快速起新实例、partial rollout、verl/Miles/slime/AReaL 官方集成；会话式 radix cache、请求 dumper、调度模拟器。
  • 观测与运营：Prometheus 指标（优先级维度）、请求级时间统计、OTel tracing、专家分布 HTTP 端点、KV 一致性巡检（kv_canary）。

选型建议

选 DeepInfer，当：
  • 你的硬件就是 SM100 或昇腾 950，且主力模型就是 DeepSeek-V4.1-Flash——它是这款模型的官方参考实现，FP4 KV、MegaMoE、ZOS、DSpark、Bounded Replay 都是为它调到极限的；
  • 你想要 DeepSeek 生产同款内核（单集群 155 万亿 tokens/天的架构底座），并且自己有（或愿意建）服务层：HTTP/路由/PD 编排/KV 存储需要按 官方部署说明补齐或对接生产设施；
  • 你的场景是离线批量推理、评测复算、确定性输出（batch-invariant + seq_seed）——这些是 DeepInfer 的一等能力。
选 SGLang，当：
  • 你需要在线服务：完整 OpenAI/Anthropic/Ollama API、多 LoRA、会话缓存、观测体系、cache-aware 路由、PD 分离——全部开箱即用；
  • 你的模型谱系或硬件谱系不止一款：255 个模型实现 × 10+ 硬件平台，V4.1 也有预览支持（预览镜像，硬件面比 DeepInfer 宽，含 H200/MI355X）；
  • 你在做 RL 训推一体（verl/Miles/slime 生态）、agent 负载、多模态或扩散模型服务——这些方向 SGLang 的工程化深度无可替代。

一句话：DeepInfer 是"一款模型 + 一种超节点拓扑"的官方最优解，SGLang 是"所有模型 + 所有硬件"的通用最优解；在 DeepSeek V4.1 这个交集上，前者代表生产权威，后者代表社区可得的最近似实现——两者互为参照系，且互相借鉴（ZOS 源自 SGLang overlap，SGLang 的 dsv4/DSpark/mhc/replay_tail 则源自 DeepSeek 的设计）。
