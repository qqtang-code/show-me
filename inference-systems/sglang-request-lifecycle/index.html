速览 · 30 秒

  • 一条请求走五段：接入（分词/模板）→ 排队等待 → 调度（组批 + 分配 KV）→ 前向（78 层 × 【稀疏注意力 + MoE】× TP8 通信）→ 采样输出（流式回传）。
  • 四个进程组：TokenizerManager（收 HTTP）、Scheduler（兼 TP rank0）、7 个 TP worker 进程（每卡一个）、DetokenizerManager。GPU 上真正跑的是后两类。
  • 每轮 decode 的真实代价不在算力，而在访存：读 78 层权重 + 全部 KV + 每层两次 all-reduce。所以这套部署的每个参数都在减少这三项的字节数。
  • 这套部署的三个关键取舍：DSA 把注意力从「看全部 270K 个 key」压到「看 2048 个」；NVFP4 只压在占权重 95% 的专家上；量化 AllReduce 在 16 MB 以上的消息上把通信字节再砍一半。
  • 记住这条链路：参数 → 每轮搬多少字节 → 每轮多久 → 吞吐。任何一个参数都能被追到这条链上。

前置知识：五个词就够读懂后面的流程

① Prefill 与 Decode

Prefill 处理输入的全部 token（一次算很多个，算力受限）；Decode 每步只生成 1 个 token （却要把全部权重和全部 KV 读一遍，访存受限）。两者计算形状完全不同，所以调度器会区别对待： prefill 可以切块，decode 必须每轮都跑。整个推理系统的参数设计，基本都是在调和这两者的冲突。

② 连续批处理（continuous batching）

不等一批请求全部结束才收新的：任何一条请求生成完就立刻退出批次，空出的槽位马上给排队中的下一条。 这是「批处理」在 LLM 推理里的形态 —— 也是为什么批内每条请求的上下文长度各不相同， 所有算子都得按「变长批」来写。

③ 这套模型的两个特殊结构

  • DSA（稀疏注意力）：注意力的 key/value 被压缩成 MLA 的 latent，且每条 query 只挑出 index_topk = 2048 个最相关的历史 key 参与计算。上下文再长，注意力的读取量也不涨（选择成本另算，见 DSA 一节）。
  • MoE（混合专家）：78 层里有 75 层是 MoE，每层 256 个 routed 专家 + 1 个 shared 专家。每个 token 只激活少数专家，所以总参数量很大但每 token 的计算量不大 —— 代价是权重全都要放在显存里。

④ NVFP4 与「量化边界」

NVFP4 是 4 bit 浮点（E2M1）配 fp8 的块级 scale：权重的显存占用约为 bf16 的 1/3.6（每 16 个权重一个 scale 的额外开销）。 这套 checkpoint 只把 routed experts 量化成 NVFP4，attention / shared expert / router / 3 个 dense 层保持 bf16 （checkpoint 的 ignore 列表里有 231 条）。 混精度不是偷懒，而是权衡：专家占权重的大头（量化它省显存最多），而 attention 与 router 对数值精度更敏感（量化它掉点最多）。

⑤ CUDA Graph

Decode 每步的算子序列和形状都一样，于是可以把整个前向录制成一张图，之后一次 replay 而不是逐个 launch kernel —— 省掉的是启动开销（每层几十个 kernel × 78 层，CPU 侧 launch 很容易成为瓶颈）。 代价是形状必须固定，所以要预先为一批批大小（桶）各录一张图。

两个虚线框 = 两组四卡 PCIe 组（无 NVLink）。跨组通信必须过主机桥，这就是通信一节里所有优化的舞台。

为什么要知道进程边界？因为它决定了延迟在哪：分词与模板在 CPU 上（TokenizerManager）， 调度决策也在 CPU 上（Scheduler），GPU 只做前向与采样。所以「TTFT 高」可能是排队久（调度侧）， 也可能是 prefill 慢（GPU 侧），两者的优化手段完全不同 —— 延迟拆解会把这条线拉直。

还有一条容易忽略的拓扑事实：MLA 的 latents 在所有 TP rank 上是复制的（每层每个 token 只有一份 576 维的 latent，所有头共享），代码里 KV 池的形状就是 (size, 1, kv_cache_dim)，头维为 1、不按 TP 切分。 这意味着TP 并不会摊薄 KV 显存：一条请求的 KV 在每张卡上都要占同样多的字节，容量账要按单卡算。

一条请求的完整生命周期

1
接入与分词：HTTP 请求进来，套上对话模板，切成 token id，按解析器配置标记哪些段落算 reasoning / tool call。 这一步是纯 CPU 的，与 GPU 无关，但模板错了会让后面全部白算 —— 前缀缓存也是按 token 序列比对的。 TokenizerManager 进程
2
入队等待：请求进入等待队列（waiting queue），此时不占任何显存。 队列长度 × 单步耗时 ≈ 排队延迟。这就是 --max-running-requests 与 KV 池共同决定吞吐上限的地方。 Scheduler 进程
3
组批与 KV 分配：调度器每轮从队列里挑请求，先在 radix 前缀树上做最长前缀匹配 —— 命中的部分直接复用 KV，不再计算； 未命中的部分按 chunked-prefill-size 切块，并从 KV 池分配页。 这是「同一份系统提示只算一次」的实现位置，也是 TTFT 波动的主要来源。 Scheduler 进程（CPU）
4
前向计算：组好的批被送进模型，78 层依次执行「稀疏注意力 → MoE」，每层穿插两次 TP all-reduce 与两轮专家并行通信； 投机解码时这里一次要验证 5 个 token 行。 GPU 利用率、TPOT（每 token 耗时）几乎全部由这一步决定。 8 个 TP worker 进程 / 8 张 GPU
5
采样与回传：从 logits 采样出下一个 token，去 tokenizer 还原成文本片段，流式推给客户端。 投机解码下这一步会一次接受多个 token；结束条件（EOS / 长度 / stop 串）也在这里判定。 GPU（采样）→ DetokenizerManager → TokenizerManager
6
回收与缓存：请求结束后 KV 页被释放，但 radix 树上的前缀仍然保留（默认开启前缀缓存）， 下一条同前缀请求可以直接命中。 如果开了分层缓存（HiCache），这里还会触发向主机内存的下沉。 Scheduler + 显存池

调度器内部：每一轮它到底在决定什么

Scheduler 是唯一的大脑，它跑在一个 while 循环里（event_loop_normal 或 event_loop_overlap），每轮做四件事：取批 → 前向 → 采样 → 收尾。 关键函数是 get_next_batch_to_run()，它的决策顺序决定了所有请求的命运。 

while True:
    batch = get_next_batch_to_run()        # ① 组这一轮要算的批
    if batch:  run_batch(batch)            # ② 前向 + 采样（GPU）
    process_batch_result(batch)            # ③ 收尾：写回 KV、判定结束、回传 token
                                           # ④ 与下一轮重叠：CPU 组批和 GPU 计算并行

组批时的三个优先级

  1. 先把正在跑的 decode 排上。decode 是延迟敏感的：每条请求每轮都要出一个 token，被跳过就意味着 TPOT 抖动。
  2. 再用剩余预算装 prefill。等待队列按策略排序（默认 LPM 最长前缀匹配，让命中前缀的请求优先，省下最多的算力； 也可以选 FCFS 先来先服务）。装的时候由 PrefillAdder 逐条累加， 超过 max-prefill-tokens = 16384 或 KV 不够就停。
  3. 长请求切块。单条请求的 prefill 超过 chunked-prefill-size = 8192 就只算 8192， 剩下的挂到下一轮（chunked req）。这样长 prefill 不会独占 GPU 几秒钟，decode 的 TPOT 才稳得住。
A
KV 够不够 按「新请求的 chunk + 已有请求还要生成的 token 数」推算。不够就把它留在队列里，或者更激进地抢占（recompute / retract）。
B
前缀命中多少 radix 树上的最长匹配长度决定了要新算多少 token。命中 8000 token 的长系统提示，prefill 预算可以整段省掉。
C
要不要跑投机 decode 批会额外插入 draft 前向 + verify 前向，批内 token 行数变成 请求数 × 5（本部署的 draft 行数）。
overlap 调度：默认开启的 event_loop_overlap 让 CPU（组批、分配、收尾）与 GPU（前向）并行 —— 上一轮的 GPU 还在算，下一轮的批已经在 CPU 上准备好了。这能显著降低小批量的 TPOT， 代价是增加了一轮流水延迟：批的状态要等 GPU 结果回来才能定稿。投机解码与它天然冲突（verify 结果会影响下一轮批的构造），所以这类组合要么关掉 overlap，要么像本部署那样把状态更新改到 ring 上完成。

一次前向到底算了什么

调度器组完批后，会把它变成一次 ForwardBatch；两种模式的准备方式不同：

  • prepare_for_extend()：prefill（含 chunk）。把多条请求的 token 拼成一条长序列，写 KV 到新分配的页，记录每条请求的 seq_lens。
  • prepare_for_decode()：decode。每条请求只喂 1 个 token（投机的 verify 阶段是 5 个），KV 页已经存在，只需按 out_cache_loc 追加写入。

78 层的结构

dense ×3
MoE + DSA 交替 ×75
MTP ×1

前 3 层是普通 dense FFN（保持 bf16），中间 75 层是 MoE（routed 专家 NVFP4），最后 1 层 MTP 被当作 EAGLE 的 draft 模型。

每个 MoE 层内部
  • 输入 norm → DSA 注意力（稀疏 MLA，KV 为 fp8 latent）
  • → 残差 → norm → MoE：router 打分 → 选中 routed 专家（NVFP4 权重）→ 与 shared 专家（bf16）求和
  • → 残差 → 下一层
两次 all-reduce 的位置
  • 注意力输出投影 o_proj 之后（按头切分，需要求和）
  • MLP 下投影 down_proj 之后（按中间维切分，需要求和）
  • 75 个 MoE 层 × 2 ≈ 150 次 all-reduce/轮（dense 层同样有，量级相同）

DSA：270K 上下文为什么没有拖垮注意力

标准注意力的成本随上下文线性增长：每条 query 要对的 key 数量就是历史长度。 270K 上下文下，每层每 token 都要读 270K 份 KV —— 这是任何长上下文服务都过不去的墙。 DSA 把它拆成「先选，再算」两步：

第一步 · indexer 打分（便宜）

用一份低维的 index key（公开口径每层 128 维 fp8）算出每条 query 与所有历史 key 的相关性分数，取 top-2048。

未选中top-2048 入选

成本：O(L) 次低维点积，可融合成一个 kernel（--dsa-topk-backend sgl-kernel），不打分不进 HBM。

第二步 · 稀疏 MLA（省下的大头）

只对选中的 2048 个 key 做 MLA 注意力。KV 本身是压缩 latent，每 token 每层 576 字节（fp8）。

深色 = 真正参与计算的 2048 / 270336 ≈ 0.76%

节省：注意力读取量从 O(L) 变成 O(2048)，上下文越长收益越大，且与 L 解耦。

口径核对：一个 token 的 KV 到底占多少

MLA latent：(kv_lora_rank 512 + qk_rope 64) × 78 层 × 1 B(fp8) = 44.9 KiB / token
DSA indexer：128 维 × 78 层 × 1 B ≈ 9.8 KiB / token
合计 ≈ 54.7 KiB / token —— 264K 上下文的一条请求就要 ≈ 14.1 GiB KV。

这也是为什么 fp8 KV 与 MLA 缺一不可：若用 bf16 的标准 MHA（8 头 × 128 维 × 2 × 78 层）， 每 token 要 312 KiB —— 同样一条请求需要 80 GiB，单卡根本放不下。

MoE 与量化边界：为什么只有专家是 4 bit

一个 token 在 MoE 层里走的路

hidden(6144) → router 打分（bf16）→ 选中 top-k 个 routed 专家 → 各自 NVFP4 矩阵乘 → 按路由权重加权求和 → 与 shared 专家（bf16，独立分支）相加 → 输出

routed experts · NVFP4（权重主体） shared expert + router + attention · bf16
组件精度为什么
routed experts（256 个）NVFP4占权重绝大多数，量化收益最大；专家是「各自独立的查表式」计算，误差不易在整个网络里累积。
shared expertbf16每 token 都会走，任何误差都会被放大；且 checkpoint 里没有 fp4 scale，强行融合会载入失败（本部署显式关掉了融合）。
attention（DSA/MLA）bf16 权重 + fp8 KV注意力对数值误差敏感；但 KV 只是被读取的数据，存 fp8 的精度损失可控，换来 KV 池翻倍。
router 与 3 个 dense 层bf16router 决定 token 去哪，抖动会放大成整层的选路错误；dense 层只有 3 层，量化省的显存可以忽略。

TP8 通信：每轮 150 次 all-reduce 是怎么被压下去的

这台机器没有 NVLink：8 张卡分处两组四卡 PCIe 组，跨组通信要过主机桥。前面算过， 每层两次 all-reduce、75 个 MoE 层 → 每轮 decode 上百次归约，每次的载荷是 行数 × hidden(6144) × 2B。而「行数」在两种阶段差了一个数量级，这决定了它们走完全不同的路径：

三条路径的字节账

① stock CAR / 1-stage bf16（改造前）每 rank 收 (N−1)·P = 7P

NCCL 广播式归约，每张卡收 7 份完整 bf16 载荷。这是本部署最初 57% kernel 时间所在的那条路径（详见另一篇）。

② 2-stage bf16（reduce-scatter + all-gather）1.75P · 4× 更少

把载荷切成 8 份，两个阶段各经手一遍。字节数与 TP 规模解耦 —— 这是 4 倍收益的来源。

③ 2-stage + int8 量化（本部署注入的内核，服务 prefill 大消息）0.875P · 8× 更少

在 ② 的结构上，把每份载荷先本地量化成 int8 再进 ring：字节数再砍一半。两级优化是相乘的：4× × 2× = 8×。

量化 AR 内核的四个守卫（工程上最值得学的部分）

守卫条件为什么必须有
尺寸下界P ≥ 16 MB小消息上 2-stage 要多两个 barrier，延迟主导，量化省下的带宽抵不过同步开销。
尺寸上界P ≤ 100 MB超大消息上手工内核打不过 NCCL 的成熟多 NIC / 多通道实现（实测 96 MiB 时反而更慢）。
向量对齐n % 256 == 0int8 内核按 256 元素向量化读取，不满足就回退 —— 否则会读到越界或触发慢路径。
捕获期拒绝CUDA graph capture 中直接回退最关键的一条：图捕获时内核不会真正执行，barrier 计数器被 replay 会读到陈旧值 → 死锁或算错。所以捕获期一律走 NCCL。

内核本身是「本地量化 → barrier → reduce-scatter → barrier → all-gather」的两阶段结构， 36 个 block × 512 线程，另有一个 tail-safe 变体处理不满向量的尾巴；异常一律兜底回退 NCCL 而不是抛错。 这类改动的价值一半在快，一半在「任何异常都退回到已知正确路径」。

延迟拆解：TTFT 与 TPOT 分别由什么决定

TTFT（首 token 延迟）= 排队 + 前缀匹配 + prefill + 首步采样
  • 排队：并发高、prefill 块小的时候最长。这是 max-running-requests 与准入策略的战场。
  • 前缀匹配：命中越多，这一项越小 —— 命中 100K token 的公共前缀，等于 prefill 工作量归零。
  • prefill：算力受限，约等于 token 数 × 2 × 参数量 ÷ 有效算力（MoE 只算激活的专家）。chunked prefill 会把它切成多块，所以 TTFT 与 chunk 大小正相关。
  • 首步采样：可忽略。
TPOT（每 token 延迟）= 权重读取 + KV 读取 + 通信 + 采样
  • 权重读取：每步都要把激活到的专家权重读一遍 —— NVFP4 的价值就在这里（读的字节少了 3.6 倍）。
  • KV 读取：DSA 把它压到 2048 个 key；fp8 再砍一半。长上下文下这是最大的一项。
  • 通信：每轮上百次 all-reduce，PCIe-only 拓扑下是硬成本 —— 量化 AR 就是把这一项按字节砍。
  • 采样：小批时不可忽略；投机解码正是把「多次采样 + 多次前向」合并成一次的技巧。

常见误解

✗「decode 慢是因为算力不够」
正相反：decode 每步只算 1 个 token（投机的 verify 也只有 5 行），算术强度 ~1–2 FLOP/Byte， 算力大量闲置。瓶颈是把权重和 KV 读一遍的带宽。这也解释了 NVFP4、fp8 KV、稀疏注意力为什么有效 —— 它们都在减少字节。
✗「chunked prefill 让 prefill 变慢了，所以是坏事」
它牺牲的是单条长请求的 TTFT，换来的是所有在跑请求的 TPOT 稳定。 一次 100K token 的 prefill 不切块会独占 GPU 好几秒，期间所有 decode 请求全部卡住。 8K 的块大小就是在这两者之间取的平衡点。
✗「已经用了 CUDA graph，就不需要关心 kernel launch 了」
图只覆盖被捕获的那部分：解码路径、bs ≤ 64、且不含依赖 barrier 的算子。 量化 AR 在捕获期必须回退到 NCCL，prefill 大块完全不在图里 —— 这些路径的 launch 开销仍然是实打实的。
✗「量化 AR 就是把通信量砍一半，收益最多 2 倍」
两层意思都要纠正。第一，它是叠加在 2-stage 之上的：2-stage 先把字节除以 4（N/2）， int8 再除以 2，相对原始 1-stage bf16 是 8 倍。第二，它只在 prefill 的大消息上生效 —— decode 的 verify 载荷只有几 MB，落在 16 MB 起征点之下，走的是 NCCL。同一个优化在不同阶段的有效性完全不同， 这也是为什么守卫要用尺寸窗口来分流，而不是全局打开。
✗「前缀缓存命中率越高，吞吐就一定越高」
还要看命中的是多少 token。命中 20 条请求各 100 token，省下的算力不如命中 1 条 10K token。 另外长前缀命中会把 KV 页留在池子里，可能挤掉并发 —— 命中率与并发之间有取舍。

自测：能答上这六题，说明这套流程你通了

1. 投机解码的 num-draft-tokens = 5 如何影响 all-reduce 的耗时？
verify 阶段一条请求产生 5 个 token 行，批内行数变成 并发 × 5。 64 并发 → 320 行 → 载荷 P = 320 × 6144 × 2B ≈ 3.9 MB。 关键在于这个尺寸落到了哪里：2-stage 之后每 rank 只收约 3.4 MB，低于量化内核 16 MB 的起征点 —— 所以 decode 侧走的是 NCCL / 2-stage，量化 int8 在这里反而是负收益（两次 barrier 的同步开销盖过省下的带宽）。 量化内核真正服务的是 prefill：一个 8192 token 的 chunk 打包成一次归约，载荷约 100 MB，才落进窗口。
2. 一次 100K token 的 prefill，为什么不能一次算完？
会独占 GPU 若干秒，把同时段所有 decode 请求的 TPOT 打到几百毫秒级。 chunked-prefill-size = 8192 把它切成 13 轮，每轮之间还能插 decode。 代价是这条请求自己的 TTFT 变长（要等 13 轮调度），收益是其他请求的延迟稳定。
3. 为什么量化 AR 在 CUDA graph 捕获期间必须回退？
捕获时内核不会真正执行，只记录调用。手写内核里的 barrier 计数器依赖真实执行来推进， 图 replay 时会读到捕获时留下的陈旧值 → 要么死锁、要么算出错误结果。 所以守卫在 capture 阶段一律回退 NCCL —— 这是「宁可慢一点也不能算错」的典型取舍。
4. shared expert 为什么不能和 routed 专家融合成一个 kernel？
两者的量化口径不同：routed 是 NVFP4（带 fp8 块级 scale），shared 是 bf16（没有 scale）。 融合 kernel 期望同一套 dequant 路径，遇到没有 scale 的权重就会载入失败。 所以本部署显式 --disable-shared-experts-fusion —— 量化口径决定了算子能不能融合， 混精度模型的「边界」比想象中更硬。
5. 264K 上下文的一条请求，KV 大约占多少？这对并发意味着什么？
≈ 54.7 KiB/token × 270336 ≈ 14.1 GiB（含 indexer）。 这意味着长上下文与高并发基本不可兼得：KV 预算 20 GiB 时，要么跑 1–2 条满长度请求， 要么跑几十条 8K 的短请求。容量规划必须先确定「典型上下文长度」，而不是看最大值。
6. 如果要把这套部署的吞吐再提高一档，你会先动哪个参数？为什么？
按「改动的收益 ÷ 风险」排序：① 提高前缀命中率（把公共系统提示做成长前缀、复用同一段 RAG 文档）—— 直接减少 prefill，几乎零风险；② 调大 chunk 与批上限，但要盯 TPOT 与 KV 水位； ③ 继续压通信字节（比如把量化 AR 的上下界按实际分布重新标定）； ④ 提高接受长度（换更好的 draft、或按任务调 draft 步数），它直接乘在吞吐上。 ——共同点是：都在减少每轮要搬的字节或要算的 token，没人去动算力。
