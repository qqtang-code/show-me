MoE 的通信：MegaMoE 内核、A2A 开关，与各后端的真实差别

对着 SGLang 与 DeepGEMM 的源码，讲清三件事：MegaMoE 到底把哪些步骤塞进了一个 kernel； --moe-a2a-backend 设与不设之间，跑的不是同一条路；以及「MoE 后端」和「MoE A2A 后端」为什么是两层正交的东西。

一、MegaMoE 是一类「把 EP 通信塞进 GEMM 里」的内核设计，不是某一个内核 SGLang 里有两个同名的实现：DeepGEMM 版（--moe-a2a-backend megamoe，挂在 DeepSeek 系模型自己的 forward 里）和 FlashInfer 版（--moe-a2a-backend flashinfer_megamoe，走标准 FusedMoE 注册表）。 共同点是：没有独立的 dispatch / combine kernel，没有 permute 索引张量，也没有 L2 输出再进 reduce 的那一步。 一个持续占用全网格的 kernel 里，dispatch warp 直接从远端 rank 的对称缓冲区把 FP8 token 拉过来算，算完把 bf16 结果直接推进源 rank 的 combine 槽位。

二、A2A 后端的开关，换的是「怎么把各 rank 的 partial 求和」 不设（none）时，每个 MoE 层尾部有一次稠密 all-reduce：tensor_model_parallel_all_reduce(final_hidden_states)。 设了任意 A2A 后端，这一次 all-reduce 就被 dispatch/combine 取代 —— 而且是被替换掉，不是叠加。 这条替换链还顺手改了七件别的事（强制 ep=tp、关共享专家融合、关 cuda graph、共享专家退化成 tp1 等）， 所以「开 A2A」从来不是一个纯通信选项。

三、「MoE 后端」和「MoE A2A 后端」是两层，靠一张注册表正交起来 runner 后端（--moe-runner-backend）决定专家 GEMM 用谁的 kernel；A2A 后端（--moe-a2a-backend）决定 token 怎么跨 rank 摆布。两者通过 DispatchOutputFormat 对接： 一个 runner 只有在「对应 dispatch 格式」上注册了 permute 或 fused func 才能配对。 结果是 deep_gemm 是唯一能长期配任意 A2A 后端的 runner，而 triton / marlin / hpc_ops / flashinfer_* 系列基本只在 none 下工作 （flashinfer 家族额外支持自家的 flashinfer A2A）。

2MegaMoE 拆开看：四段源码

2.1 权重准备：为了「一遍读完就出 SwiGLU」而重排

GEMM 之前的权重不是原来的形状了。两处重排，都只为了让 kernel 少一次访存：

# layers/moe/mega_moe.py:314-339, 353-410（精简）
def _interleave_mega_moe_gate_up(t, gran=8):
    # [gate | up]  →  [gate:0..7, up:0..7, gate:8..15, up:8..15, ...]
    num_groups, n, *rest = t.shape
    half = n // 2
    gate = t[:, :half].reshape(num_groups, half // gran, gran, *rest)
    up   = t[:, half:].reshape(num_groups, half // gran, gran, *rest)
    if gran == 16:   # MXFP4：打包成偶/奇两组 16 元素块
        result = torch.cat([gate[:, :, 0::2], up[:, :, 0::2],
                            gate[:, :, 1::2], up[:, :, 1::2]], dim=2).reshape(num_groups, n, *rest)
    else:            # FP8：连续的 gran-8 块
        result = torch.stack([gate, up], dim=2).reshape(num_groups, n, *rest)
    return torch.empty_like(t).copy_(result)

def _transpose_mega_moe_sf_for_utccp(sf):
    # 每个 128 元素组内，把 4x32 的 scale 子块转置 —— tcgen05 的 UTCCP 指令要求
    num_groups, mn, packed_sf_k = sf.shape
    return sf.reshape(num_groups, -1, 4, 32, packed_sf_k).transpose(2, 3).reshape(num_groups, mn, packed_sf_k)

def build_mega_moe_experts_weights(experts):
    w13, w13_sf = _interleave_mega_moe_l1_weights((w13, w13_sf), mma_type)
    experts.mega_l1_weights = (experts.w13_weight.data,     _transpose_mega_moe_sf_for_utccp(w13_sf))
    experts.mega_l2_weights = (experts.w2_weight.data,      _transpose_mega_moe_sf_for_utccp(w2_sf))
为什么 gate/up 要交错
切分后的 L1 权重按 N 方向交错存放，kernel 一次 TMA 取到的块里就同时含 gate 和 up， SwiGLU 可以直接在同一份 smem 上算完再写出去 —— 不用把 gate 和 up 分两趟读。
为什么 SF 要转置
UTCCP 是 Blackwell 上给 MMA 搬 scale 的专用通路，它期望的 4×32 子块顺序与常规行主序不同。 转置在权重加载时做一次，之后每层省掉的是逐次搬运的 shuffle。
只多了一份 scale：w13 的权重张量被原地替换成交错布局，同时仍挂在 w13_weight.data 上供普通 deep-ep 路径复用； 只有 scale 走 UTCCP 版本是额外分配的。源码注释明确写了这是刻意的复用（mega_moe.py:389-394）。

2.2 对称缓冲区：八个切片，跨 rank 的同一份地址空间

MegaMoE 的全部通信都发生在这一块显存里。它由 torch.distributed._symmetric_memory 分配， 各 rank rendezvous 后拿到彼此的指针表；kernel 里 sym_buffer.map(ptr, dst_rank) 就是 「把你的指针加到我这份的偏移上」，于是任意 rank 可以直接读写任意 rank 的这块区域，不需要显式通信调用。

2.3 pre-dispatch：只量化、只摊平，不做任何跨 rank 通信

进 mega kernel 之前，SGLang 先用一个 JIT 编译的 CUDA kernel 把 bf16 token 变成 FP8 + UE8M0 scale，并把路由结果摊进缓冲区。 它一个 CTA 一行 token，grid 里多出来的 CTA 负责「补零区」：

三个值得记的细节
  • 补零区必须写死了才有意义。缓冲区是复用的，多出来的槽位若不写 -1，上一轮的脏 token 会被 GEMM 当真算进去。
  • scale 区是行主序、一 group 一字节。但 DeepGEMM 可能为了 TMA 对齐给每行补 padding（源码举的例子：H=2304 时逻辑宽 72B、物理 80B），所以 kernel 用 buf_x_sf_stride_bytes 而不是自己想当然的宽。
  • hidden > 8192 时要求 hidden % 256 == 0。因为分组归约用的是 full-mask 的 warp shuffle，尾部那一次迭代必须由完整的 warp 进入。
FP4 走的是另一个实现

MMA 类型是 mxf4xmxf4 时，改调 DeepGEMM 自己的 mega_moe_pre_dispatch，因为 E2M1 的打包方式不同（两个 FP4 挤一个字节）；SGLang 这个 JIT 版本只发 FP8。 两个实现的分工写在调用点：

这条路径踩过的坑（可作为版本体检项）：FP4 的激活被按 E2M1 打包成宽度 1792（两值一字节）， 但校验仍按未打包的 3584 走，于是 W4A4 启动即报 expected 3584 but got 1792。 修好之前这条 W4A4 路径是拿不到数据的 —— 只能退回 W4A8 评估。这说明两套 pre-dispatch 实现的接口约定必须对齐版本。

它省掉了什么
  • 一次独立的 dispatch kernel、一次独立的 combine kernel
  • permute / unpermute 的索引张量（几分之一个 token 的显存 + 随机访存）
  • L1 输出回全局显存再进 L2 的那趟往返
  • 通信与计算之间的串行点：拉取是按池块细粒度流水推进的，某个专家的 token 一到齐就能开算
它付出了什么
  • 全网格持久内核 + 每层两次跨 rank 屏障，很难和别的 kernel 重叠
  • SM 预算要让出来：调用前把 DeepGEMM 的 num_sms 压到「物理 SM 数 − 保留数（默认 2）」并向下取偶（簇启动要求偶数 CTA）
  • 缓冲区按 M 线性吃显存（见上面的计算器），和 KV 池直接竞争
  • M 超过上限就整层回退，同一进程里可能混着两条路径

实测侧的一个观察：这台 8 卡 B300 上，MegaMoE W4A8 并没有打赢 FlashInfer MXFP4 基线

同一模型、同一 Low-Latency 配置，仅把 MoE 换成 MegaMoE（W4A8；W4A4 因上面那条打包 bug 起不来）， 六个测量点的总吞吐都低于原有 FlashInfer MXFP4 基线，16K→512 场景约低 31%–33%。

但同一批数据里有一个方向性信号：16K 高并发下 TPOT 反而更低（并发 128 时 P50 低 22%）。这和「通信被融合进 GEMM」的预期一致 —— Decode 阶段每 token 的通信占比高，融合的收益体现出来了；而 Prefill 段被 W4A8 的计算开销和排队吃掉了。

怎么读这个结论：这不是一次干净的 backend A/B（量化路径不同、部分点的总请求数也不同），所以只能当方向判断， 不能当「MegaMoE 比 FlashInfer 慢 31%」的定论。要下定论得先把 W4A4 修好，再用相同请求数重跑。

3.4 通信量：A2A 赢的不是字节数

这是最反直觉的一点，值得算一遍。设全局 batch = B 个 token，TP=EP=R，hidden = H，top_k = K。 不设 A2A 时，每个 rank 上被 reduce 的是 DP-gather 后的 B 个 token： ring all-reduce 的每 rank 通信量 = 2·(R−1)/R · (B·H·2)。 设了 A2A，每个 rank 只持有 B/R 个 token，发送量 = (B/R)·K·H·d_disp，收回量 = (B/R)·K·H·2。

5怎么选

1
先问互连 节点内有 NVLink/NVSwitch → DeepEP 类（deepep / deepep_v2）、FlashInfer A2A、MegaMoE 都可能； 只有 PCIe → 优先看 moonlight/mooncake、nixl 这类为弱互连设计的实现，并且务必先做纯通信 smoke（不加载模型）， 再谈接模型。这一步失败的话，后面所有性能数据都拿不到。
2
再问「装不装得下」 A2A 后端会强制 ep=tp、共享专家退化成 tp1（每卡复制），这两条都吃显存。 MegaMoE 还要额外拿一块随 max_tokens_per_rank 线性增长的对称缓冲区。先按上面的计算器把预算算出来，再决定拓扑。
3
然后问 runner 能不能配 检查量化 → runner → A2A 三者是否在矩阵里。这张表里没有的组合，启动期就会给出明确的 ValueError —— 与其改参数硬凑，不如先确认哪一层是真正的约束（经常是量化格式，而不是通信）。
4
最后才谈性能 同一批数据里对比「TTFT / TPOT / 吞吐 / 每层 MoE 耗时 / dispatch+combine 耗时 / 剩余 all-reduce 次数」。 注意 prefill 和 decode 的结论经常相反（MegaMoE 的实测就是 decode 的 TPOT 变好、prefill 段变差）， 所以别只报一个端到端数字。
自测：为什么「A2A 打开了但不能忘了删 all-reduce」这件事不会出错？
因为删除动作是按后端名硬编码的，不是靠数值容错。 对 flashinfer / pplx / flashinfer_megamoe，should_skip_post_experts_all_reduce() 直接返回 True， 源码注释写明理由：dispatcher 的 combine 已经把各 token 的专家输出求和回源 rank， 再做一次 all-reduce 会重复计数并让 bf16 溢出。 对 deepep / mori / nixl / mooncake / deepep_v2，模型层的 _enable_a2a_moe 分支会改走 forward_deepep()，那条函数根本没有层尾 all-reduce。 所以「遗漏删除」在代码层面不可能发生，真正会发生的错误是配错组合 —— 这正好是参数钩子要拦的事。
自测：MegaMoE 的 W4A4 路径为什么在本机起不来，而 W4A8 可以？
两条路走的是两个不同的 pre-dispatch 实现： mxf4xmxf4 走 DeepGEMM 自己的 mega_moe_pre_dispatch，FP8 走 SGLang 的 JIT kernel。 FP4 激活按 E2M1 打包后宽度是 1792（两值一字节），而校验仍按未打包的 3584 检查， 于是 W4A4 在 pre-dispatch 就被尺寸断言挡住。 可迁移的教训：当同一功能有两套实现（一套出 FP8、一套出 FP4）时，接口约定要跟着量化格式一起版本化， 否则「编译通过但跑不起来」的失败会出现在最贵的时刻。

延伸

  • 1-stage → 2-stage AllReduce：为什么省下的是 4 倍字节 理解「none 路径尾部那次 all-reduce」到底花在哪，以及 ring 的延迟为什么随 R 线性增长。
  • CUDA IPC 直推：decode 小消息换的是「固定开销」，不是带宽 小消息时序的直觉，用来判断 A2A 在 decode 阶段的收益来自哪里。
  • SGLang 推理全流程：一条请求从进到出的每一步 本页讲的 MoE 段在整个 forward 里的位置，以及 LayerCommunicator 的 gather/scatter 时机。
  • deepseek-ai/DeepGEMM MegaMoE 的六个内核文件都在这里，csrc/apis/mega.hpp 是最短的入口。
  • deepseek-ai/DeepEP normal / low_latency 两种模式的源实现，以及它对 NVLink + RDMA 的假设。
  • FlashInfer · MoE-EP 架构设计文档 把 EP 明确分成「通信计算分离的 split path」与「融合的 mega path」，本页第 1 节的两分法就来自这套表述。

源码版本为公开的 SGLang 主分支与 DeepGEMM 对应版本。实测数据来自一台 8 卡单机（TP8/EP8）上的内部 A/B 实验； 主机名、内部路径、镜像地址、内部文档链接与模型版本号已做脱敏，测量数值与推导过程保留。

口径说明：计算器里的公式逐条对应源码函数；A2A 的通信量只计 dispatch + combine 的 payload， 不含工作区元数据、屏障和 all-reduce 之外的 gather/scatter 代价。
