L1–L4 缓存 与 LLM 推理的 KV 分层
HiCache / Mooncake 在 SGLang 里各管什么

同一个思想在两个尺度上的外推：离计算越近 → 越贵、越小、越快。硬件层面是 SMEM/L1 → L2 → L3(LLC) → DRAM/NVMe；推理系统层面是 HBM → Host DRAM → 分布式存储。

A · 为什么推理关心缓存层级

逐 token 解码是纯访存瓶颈

decode 一个 token 必须把「全部权重 + 该请求全部 KV」从存储里搬一遍，算术强度只有 ~1–2 FLOP/Byte，而 H100 的 roofline 拐点在 ~295 FLOP/Byte。所以优化只有三条路：少搬字节（量化/GQA/MLA）、少算一次（前缀复用）、把字节放到更近的层（KV 分层）。后两条正是 HiCache / Mooncake 的地盘。

注意两个「L2」不是一回事：GPU 硬件 L2 是片上 40–50 MB SRAM（FlashAttention 关心的那层）；推理语境里的 L2 指主机 DRAM 缓存层。本文其余部分都用后者。

B · SGLang 的三层落地

HiCache：把 radix 树从 HBM 延伸到主机与集群

L1 · GPU HBM

radix_cache.py / hiradix_cache.py · --mem-fraction-static
  • 前缀树节点直接持有设备 KV 页；match_prefix 命中即直接进 prefill 的 extend
  • 容量最小、价值最高：只有这里的数据能真的省算力
▲ load_back（L2→L1，命中后先把页搬进设备再算） ▼ write / demote（L1→L2，写策略决定何时写）

L2 · Host DRAM

pool_host/{mha,mla,dsa}.py · --hicache-ratio / --hicache-size · layout page_first
  • pinned 内存池，按页与设备池一一对应；HiCacheController 用 kernel/direct IO 做整页搬运
  • --hicache-host-memory-mode cache 是真缓存层；buffer_only 只当 L3 的暂存区
▲ prefetch（L3→L2，miss 时异步预取，best_effort / wait_complete / timeout） ▼ backup（L2 淘汰时回写 L3）

L3 · 共享存储（可插拔后端）

hicache_storage.py 接口 · --hicache-storage-backend mooncake|hf3fs|nixl|file|aibrix|mori|eic|simm|shm
  • 统一 get/set/exists/batch_* + 分组语义；实现零拷贝注册缓冲区（Mooncake 用 RDMA 直取）
  • 跨实例共享：同一份系统提示 / RAG 文档在集群里只算一次

命中路径（省算力）

match_prefix L1 命中 → 直接 serve，零搬运 L1 未命中 → 查 L2 前缀 ├ L2 命中 → load_back 到 L1（PCIe 页级搬运） └ L2 未中 → prefetch L3→L2 → load_back 剩余未命中部分才算 prefill

写入 / 淘汰路径（保容量）

cache_finished_req write_through → 立刻写 L2（可再 backup 到 L3） write_back → 只写 L1，等淘汰再下沉 write_through_selective→ 短前缀不写，够长才写 evict L1 淘汰 → 已 backup 的降级到 L2，未 backup 的按策略补写或直接丢弃 L2 淘汰 → backup 线程回写 L3

一串具体数字：8B 级 GQA 模型约 131 KB/token 的 KV，10K token 的系统提示 ≈ 1.3 GB；从主机 DRAM 经 PCIe Gen5 搬回约 20 ms，而重算这 10K token 的 prefill 约 0.2–0.5 s。跨层搬运之所以成立，是因为它永远比重新计算便宜。

C · 职责边界

HiCache 是策略层，Mooncake 是数据面

HiCache —— SGLang 进程内的缓存层级管理器

  • 决定哪份 KV 该在哪一层：提升、降级、预取、回写
  • 与 RadixAttention 树耦合：key 是前缀哈希 / chunk 哈希，节点带 lock_ref，淘汰必须尊重树结构
  • 与调度器耦合：prefetch 与 batch 重叠、超时终止、命中长度影响本轮的 extend 长度
  • 对外只暴露 L3 的抽象接口，后端可替换（Mooncake 只是其中一种）

Mooncake —— 集群级的 KV 存储与传输基础设施

  • 决定东西在哪台机、怎么最快搬过去：聚合全网 DRAM/SSD 成共享池
  • Transfer Engine（RDMA / GPUDirect / 多网卡零拷贝）+ Master（元数据、租约、淘汰）
  • 不理解前缀树，也不感知 batch；只认 key → 对象
  • 可脱离 HiCache 独立使用：PD 分离的 KV 搬运默认就走 Mooncake
维度HiCacheMooncake
层次策略 / 编排层（进程内）数据面 / 资源层（集群级）
管的层L1、L2 的拥有者，L3 的定义者L3 的实现者之一（也可做 PD 传输、embedding store）
地址空间单实例：HBM + 本地 DRAM跨实例：全网 DRAM/SSD
核心算法前缀匹配、写策略、预取策略、树形淘汰对象放置、副本、一致性、RDMA 传输调度
换成别人行不行可以：L3 换成 hf3fs / nixl / file / aibrix 等可以：PD 传输换 nixl，L3 换 3FS
共同点都以 KV 对象为粒度做 key-value 复用；都靠 RDMA / 零拷贝打通主机与远端；目标都是「让别人算过的前缀不再算」；都有淘汰与命中统计

一句话：HiCache 回答「这份 KV 现在最该待在哪一层」，Mooncake 回答「这些 KV 在哪个节点的哪块内存/盘上，怎么几毫秒搬过来」。前者像 CPU 的 cache 替换策略 + 页缓存逻辑，后者像分布式内存设备加一台 DMA 引擎。
