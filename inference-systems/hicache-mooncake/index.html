速览 · 30 秒

  • 为什么关心缓存层级：decode 每生成一个 token，必须把「全部权重 + 该请求全部 KV」完整读一遍，算术强度只有 1–2 FLOP/Byte，远低于 GPU 的 roofline 拐点 —— 推理是被访存带宽钉死的。
  • 于是只有三条路：少搬字节（量化/GQA/MLA）、少算一次（前缀复用）、把字节放到更近的层（KV 分层）。HiCache 和 Mooncake 做的是后两条。
  • HiCache 是 SGLang 进程内的缓存层级管理器：决定哪份 KV 待在哪一层（GPU / 主机 / 远端），负责提升、降级、预取、回写。
  • Mooncake 是集群级的 KV 存储与传输基础设施：把全网 DRAM/SSD 聚合成共享池，是 HiCache 可选的 L3 后端之一，同时还是 PD 分离的默认传输后端。
  • 记住这一条：跨层搬运之所以成立，是因为它永远比重算便宜——10K token 从主机搬回约 20 ms，重算约 500 ms。

前置知识：四个必须先站稳的概念

如果下面四点你都清楚，可以直接看 层级阶梯。

① KV Cache 是什么

自回归生成第 t 个 token 时，注意力需要这个请求前面所有 token 的 Key 和 Value。如果每步都重算， 生成 N 个 token 就是 O(N²) 次投影。KV Cache 就是把这 N 步算出来的 K/V 存下来复用—— 代价是显存，收益是每步只算 1 个 token 的投影。 它的大小只跟层数、KV 头数、精度和上下文长度有关，与模型参数量无关（下一节给出公式）。

② Prefill 与 Decode 是两种完全不同的负载

  • Prefill（处理输入）：一次算很多 token，矩阵乘很大 —— 算力受限（compute-bound），GPU 利用率高。
  • Decode（逐字生成）：一次只算 1 个 token，却要把全部权重和全部 KV 读一遍 —— 访存受限（memory-bound），算力大量闲置。

两个阶段对缓存的需求也不同：prefill 关心「能不能不重算」，decode 关心「KV 放不放得下、读不读得动」。HiCache 的价值主要落在前者。

③ 算术强度与 roofline：为什么说是被带宽钉死的

算术强度 ≈ 1–2 FLOP / Byte  （decode 每读一个字节只做一两次乘加）
H100 拐点 ≈ 295 FLOP / Byte  （bf16 989 TFLOPS ÷ HBM 3.35 TB/s）
→ 差两个数量级：算力在 decode 阶段基本闲置，真正的天花板是 HBM 带宽

补充：批处理能提高算术强度——一次读权重服务多条请求。但KV 的读取量随 batch 线性增长， 所以长上下文高并发下，KV 流量本身会变成新的墙。

④ 前缀复用为什么天然成立

因果注意力下，一个 token 的 K/V 只由它自己及其之前的 token 决定，与后面接什么无关。 所以两个请求只要开头一段 token 完全相同（同一个 system prompt、同一份 RAG 文档、同一段多轮对话）， 这段前缀的 KV 就逐字节相同，可以互相复用。这就是 RadixAttention / 前缀缓存的物理基础。 它带来一个和普通缓存很不一样的性质：命中不是一个 key 命中与否，而是一棵前缀树上的最长匹配。

A · 为什么推理关心缓存层级

decode 一个 token 必须把「全部权重 + 该请求全部 KV」从存储里搬一遍，算术强度只有 ~1–2 FLOP/Byte，而 H100 的 roofline 拐点在 ~295 FLOP/Byte。所以优化只有三条路：少搬字节（量化/GQA/MLA）、少算一次（前缀复用）、把字节放到更近的层（KV 分层）。后两条正是 HiCache / Mooncake 的地盘。

推导：一个 token 的 KV 到底占多少字节

这个公式值得背下来，它决定了 L1 能装多少上下文、以及 L2/L3 值不值得开。

MHA / GQA
KV 字节/token  =  2 × n_kv_heads × head_dim × n_layers × dtype_bytes
（2 是 K 和 V 各一份；GQA 的 n_kv_heads 是分组后的 KV 头数，不是注意力头数）
MLA（DeepSeek 系）
KV 字节/token  =  (kv_lora_rank + qk_rope_dim) × n_layers × dtype_bytes
（压缩成一份 latent：512 + 64 = 576 个元素/层，K 和 V 共享）

三个算例

模型配置KV / token100K 上下文
Llama-3-8B32 层 · 8 KV 头 · 128 dim · bf16128 KiB≈ 12.5 GB
Llama-3-70B80 层 · 8 KV 头 · 128 dim · bf16320 KiB≈ 31.3 GB
DeepSeek 系 MLA61 层 · 576 元素 · fp8≈ 34 KiB≈ 3.4 GB

最后一行解释了 MLA 为什么是个大突破：同样 100K 上下文，KV 从 12.5 GB 降到 3.4 GB， 相当于把 L1 的有效容量放大约 3.7 倍。在此之前，长上下文服务里最先撞墙的从来不是算力，而是 KV 把显存吃满。

为什么 L2/L3 值得存在：跨层搬运 vs 重新计算

搬回来 时间 ≈ KV 字节数 ÷ 层间带宽
10K token × 128 KiB = 1.31 GB ÷ 64 GB/s ≈ 20 ms
重算 时间 ≈ 2 × 参数量 × token 数 ÷ 有效算力
2 × 8e9 × 1e4 = 1.6e14 FLOP ÷ 3e14 FLOPS ≈ 530 ms

20 ms 对 530 ms，差 26 倍。这就是 KV 分层的全部经济性来源：只要命中的前缀足够长， 从哪怕最慢的一层搬回来，都比重新算一遍便宜。反过来也界定了它的边界—— 只有被复用的前缀足够长时才算得过来：几十个 token 的前缀，搬运的固定开销（建连、同步、启动） 就超过重算了。

命中路径（省算力）

match_prefix L1 命中 → 直接 serve，零搬运 L1 未命中 → 查 L2 前缀 ├ L2 命中 → load_back 到 L1（PCIe 页级搬运） └ L2 未中 → prefetch L3→L2 → load_back 剩余未命中部分才算 prefill

写入 / 淘汰路径（保容量）

cache_finished_req write_through → 立刻写 L2（可再 backup 到 L3） write_back → 只写 L1，等淘汰再下沉 write_through_selective→ 短前缀不写，够长才写 evict L1 淘汰 → 已 backup 的降级到 L2，未 backup 的按策略补写或直接丢弃 L2 淘汰 → backup 线程回写 L3

写策略的选择本质是在带宽和容量之间做交换：write_through 保证被淘汰的前缀都还在 L2/L3（换来一次额外写），write_back 省带宽但淘汰时没备份的就真丢了。所以「前缀会被反复复用」的在线服务更适合默认的 write_through。

C · 职责边界：HiCache 是策略层，Mooncake 是数据面

HiCache —— SGLang 进程内的缓存层级管理器

  • 决定哪份 KV 该在哪一层：提升、降级、预取、回写
  • 与 RadixAttention 树耦合：key 是前缀哈希 / chunk 哈希，节点带 lock_ref，淘汰必须尊重树结构
  • 与调度器耦合：prefetch 与 batch 重叠、超时终止、命中长度影响本轮的 extend 长度
  • 对外只暴露 L3 的抽象接口，后端可替换（Mooncake 只是其中一种）

Mooncake —— 集群级的 KV 存储与传输基础设施

  • 决定东西在哪台机、怎么最快搬过去：聚合全网 DRAM/SSD 成共享池
  • Transfer Engine（RDMA / GPUDirect / 多网卡零拷贝）+ Master（元数据、租约、淘汰）
  • 不理解前缀树，也不感知 batch；只认 key → 对象
  • 可脱离 HiCache 独立使用：PD 分离的 KV 搬运默认就走 Mooncake

一句话：HiCache 回答「这份 KV 现在最该待在哪一层」，Mooncake 回答「这些 KV 在哪个节点的哪块内存/盘上，怎么几毫秒搬过来」。前者像 CPU 的 cache 替换策略 + 页缓存逻辑，后者像分布式内存设备加一台 DMA 引擎。

常见误解

✗「推理里的 L1/L2 就是 CPU/GPU 的 L1/L2 硬件缓存」
两套命名只是借用了同一套直觉（越近越快越小）。推理里的 L1 = GPU 显存、L2 = 主机内存、L3 = 远端存储， 按「数据要跨几种介质才能到 SM」划分；而 GPU 片上那个 40–50 MB 的硬件 L2 是另一回事。 同一份文档里出现「L2」时，先看它在说带宽还是说容量——说容量时基本就是主机内存那一层。
✗「HiCache 和 Mooncake 是一回事，都是 KV 缓存方案」
它们是正交的两层：HiCache 是 SGLang 内部的策略层，Mooncake 是外部的数据面。 证据很直接——HiCache 的 L3 后端可以换成 hf3fs / NIXL / 本地文件而不改上层逻辑； Mooncake 也可以完全不参与缓存层级，只做 PD 分离的 KV 搬运。把两者当作「一个东西的两种叫法」是最常见的误解。
✗「KV 放到主机内存就能提升吞吐」
要看命中率和访问模式。用 L2 的 KV 服务 decode 是亏的——PCIe 64 GB/s 对比 HBM 3.35 TB/s， 每步都要读全部 KV 会把 TPOT 拖垮。L2/L3 的真正价值在 prefill 复用： 用一次 20 ms 的搬运换掉 500 ms 的重算。搞错这一点，就会得出「开了 HiCache 反而更慢」的结论。
✗「命中率就是命中的请求比例」
前缀缓存里命中是最长前缀匹配：一次请求命中 8000 token 后又分叉，剩下的部分仍要重算。 所以有效指标不是「多少请求命中」，而是命中的 token 数占总 token 数的比例—— 一个 90% 请求命中、但每次只命中 100 token 的系统，收益接近于零。

自测：能答上这五题就算懂了

1. 用公式估算：40 层、8 个 KV 头、head_dim 128、bf16 的模型，64K 上下文的 KV 占多少显存？
2 × 8 × 128 × 40 × 2 B = 163840 B ≈ 160 KiB/token。 64K 上下文 = 65536 × 160 KiB ≈ 10.5 GB。一张 80 GB 卡上，权重之外能留给 KV 的空间就是这么被吃掉的。
2. MLA 和 GQA 都在「把 KV 变小」，思路差在哪？
GQA 是让多个注意力头共享同一组 K/V（在头维度上做减法），MLA 是把 K/V 压缩成低秩 latent （在特征维度上做减法，用时再投影回来）。两者可以叠加，但代价不同：GQA 几乎不增计算， MLA 的投影要在每层做矩阵乘——它把成本从「显存带宽」搬到了「算力」，而算力恰恰是 decode 阶段闲着的那部分。
3. 一个请求命中了 8000 token 的前缀，为什么还可能比不命中更慢？
如果这 8000 token 在 L2/L3 上，加载要走 PCIe/RDMA：8000 × 128 KiB = 1 GB，按 64 GB/s 要 15.6 ms。 若此刻这批请求重算成本本来就不高（小 batch、算力空闲），或者预取没赶上调度（请求在等 IO）， 这笔搬运就白花了甚至更贵。所以 HiCache 要配 prefetch 策略与超时终止—— 超时后放弃预取、直接重算，正是为了防止慢速 L3 拖垮调度。
4. write_through 和 write_back 分别在什么场景下更优？
write_through：写完立刻下沉到 L2/L3，任何时刻被淘汰都不丢——适合前缀会被跨请求反复复用、且 PCIe/RDMA 带宽有余量的在线服务。 write_back：只写 L1，等淘汰时再下沉——省写带宽，但淘汰时来不及备份的节点就真丢了，适合复用概率低的一次性长上下文。 write_through_selective 是折中：短前缀不写（写了也不值），足够长的才写。
5. 如果集群里所有实例共享同一个 Mooncake 池，命中率会怎么变？代价是什么？
命中率显著上升——缓存边界从单个实例扩大到整个集群，同一份 system prompt 在整个集群里只需付一次 prefill。 代价：① 命中延迟变高（RDMA 往返，需要预取来掩盖）；② 网络成为共享资源，KV 流量会和 MoE 的 all-to-all 抢带宽； ③ 要处理一致性与故障（对象过期、节点掉线），这正是 Mooncake 里 Master/租约机制存在的原因。
