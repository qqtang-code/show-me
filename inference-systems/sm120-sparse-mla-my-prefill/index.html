SM120 上的 sparse-MLA prefill 内核：直接读 656 B/key 的布局

2026-11-16 SM120 sparse MLA kernel KV 布局 prefill

这套部署的 KV 不是「一个张量」，而是三种东西交织在一起的 656 B/key：FP8 的主 KV、块级的 scale、BF16 的 RoPE 段。通用注意力内核不认识这种布局，得先把 KV 反量化、重排成自己的形状再算 —— 这一步在 prefill 上是实打实的读写。专用内核做的事只有一件：就按原样读，不重排。换来的是 kernel 级 1.32×、端到端 3 个点上下，代价是一条很窄的形状门和「你永远不知道它今天有没有生效」。

术语约定：key、layout、scale、RoPE、skip_softmax、T、fallback 保留英文。T 指单次调用能吃的 token 行数，不是整段序列长度 —— 16K 输入会按 tile 切成多次调用，所以「16K prefill」与「T≤64 才走」并不冲突。本文讲的是四机 PD 线 D 端的 sparse-MLA prefill 内核（P 侧不开）；稀疏选择本身的机制见 prefix cache 的三类注意力。

01速览

TL;DR

  • 它的全部卖点是「不重排」。 通用内核要先反量化、再重排成自己的形状；专用内核直接按 656 B/key 的原布局读，省掉这一步的读写。
  • 数字：kernel 级 1.32×；16K 的 c8/c16/c32 三档端到端 +2.9–3.3%。 精度仍在原有的 stock numeric band 内 —— 也就是说它没有改变数值路径的类别。
  • 五条形状门，任一不满足就逐调用回退 FlashInfer。 不是整段关闭，是这一调用退一步 —— 所以「配置对了但没生效」是常态。
  • 必须看统计行才能确认它在用。 只看 flag 等于没验证。
  • 换 KV 布局或换 SM 架构，这条要整条重验。 它是为「656 B/key + SM120」这一对定制的。

02通用路径要先重排，专用路径直接读

通用路径（FlashInfer）
1
读原布局656 B/key：FP8 + scale + BF16 RoPE
2
反量化 / 拆分把三段拆开、按通用形状拼
3
算通用 sparse MLA
4
回写结果再转回输出布局
专用路径（本页）
1
读原布局同一个 656 B/key
2
算专用 sparse-MLA prefill，dequant 折进读
—
省掉 2 与 4没有中间张量，没有额外一趟读写

原来那两步（拆分重排 + 回写）的代价，随 被选中的 key 数量 × 每次调用的 T × 调用次数 增长。prefill 的总行数大、调用次数多，这笔账就重；decode 一步只有很少的 query 行，省下的绝对量有限 —— 同样是省一趟读写，分母不同。

为什么它可以「就按原样读」：因为它不追求成为通用内核。通用内核要同时支持多种 KV 布局，只能把布局转换放在调用方；专用内核把「这套布局」写死进实现，于是 dequant 可以直接折进读取指令，中间张量整个消失。

03656 B/key 是什么

这个数字不是 KV 的「大小」，是一个 key 在一层里占的字节数，而且里面混了三种不同精度的东西（同一套 656 B/key 的行/字节口径见 P 端 CP4 那篇的 KV guard；那边还有另一个「每行 6336 B」，那是 hidden 行、不是 key 行，别混）：

FP8 主 KV
scale
RoPE
FP8 主 KV（latent） 块级 scale（FP32） RoPE 段（BF16）

三段等宽画，不是因为它们等大，而是因为原始记录只给了 656 B/key 这个总数、没给三段的字节拆分 —— 任何按比例画的条都会变成编造。三段的存在是记录里写明的（「656B/key 的 FP8 KV + scale + BF16 RoPE 布局」），比例不是。

这条布局事实有三个直接后果：

  • 「KV 是 FP8 的」这句话只说对了两段。 RoPE 那段是 BF16，任何「把整块 KV 当 FP8 读」的假设都会读错。
  • scale 是跟着 key 走的，不是跟着 tensor 走的。 所以任何重排都必须把 scale 和它的数据块绑在一起搬，这正是通用路径容易出错的点。
  • 656 这个数一旦变了，专用内核的前提就没了。 换 KV dtype、换 RoPE 维度、换 scale 块度，都会改这个数。

04逐调用回退的条件

专用内核不是「整段开 / 关」，而是在每一次调用判断能不能走。不满足就这一调用退回 FlashInfer：

条件为什么卡它
形状对得上tile 与并行度是对这套 head / hidden 组合选的
dtype 对得上FP8 主 KV + BF16 RoPE 混排是写死的
布局是 656 B/key换布局就没有「不重排」这个前提了
T ≤ 64超过就走通用路径。记录原文这句写的是「T≤64 decode」—— 一个短语里混了两个词，本页按「单次调用的 token 行数门」理解，原始记录没有进一步解释
skip_softmax 不成立这条快路径在特定 softmax 形态下才成立
「逐调用回退」是个双刃剑。 好处是永远不会算错；代价是你无法从配置判断它是否生效 —— 一次压测里可能 90% 的调用走了专用、10% 回退，而日志安静得像什么都没发生。所以要确认，只能靠统计行。

三个数字要分开读：1.32× 是 kernel 自己的；2.9–3.3% 是端到端的三个并发档，它已经把「这个 kernel 在整条 prefill 里占多少」折进去了；精度那句是定性的 —— 意思是它和通用路径的数值差异落在原有的波动范围内，不构成一个新的质量门。

这三档都是 16K 输入。更长输入的收益取决于「被选中的 key 数 × T」有多大 —— 但那部分原始记录没有给数，这里不补。

07换布局、换架构必须整条重验

  • 换 KV 布局。 656 B/key 一变，「不重排」这个前提就消失了 —— 此时它要么直接回退，要么算错。
  • 换 SM 架构。 tile 与 wave 是按 SM120 选的；换架构不是「重新编译」的问题，是要重新选 tile。
  • 换并行度。 head 数随 TP 变，形状门跟着变；同一个内核在别的 TP 下可能全在回退。
  • 换镜像 / 换 KV dtype。 dtype 一变，那五个回退条件里的第二条就挂了。

08常见误解

①「开了 flag 就是开了」

最典型的一类错。它是逐调用判断的，形状/dtype/布局/T/skip_softmax 任一不满足就回退。没有统计行，你就没有证据。

②「1.32× 的 kernel 应该带来 32% 的端到端」

不会。端到端里这个 kernel 只占一段，实测是 2.9–3.3%。任何「kernel 加速比 ≈ 端到端加速比」的推断都忽略了占比。

③「它和通用路径结果一样，所以可以随便切」

「精度在原有 band 内」不等于「逐位一致」。混着跑（一部分调用专用、一部分回退）在数值上是允许的，但做逐位对比验收会失败 —— 这是预期内的。

④「P 侧也有 prefill，一起开」

P 侧不开。这条是为 D 端的 sparse-MLA prefill 写的（D 端也有 prefill 段：接收 P 传过来的 KV 后要处理），P 端的注意力形态不同，不能照搬。

09自测

这个内核到底省掉了哪一步？

省掉了「把 656 B/key 的三段拆开、重排成通用内核的形状，算完再回写」这一整趟。它直接按原布局读，dequant 折进读指令，中间张量不存在。

为什么说「省一趟读写」在 prefill 上值、在 decode 上未必？

因为省下的量随「被选中的 key 数 × 每次调用的 T × 调用次数」增长。prefill 的总行数与调用次数都大；decode 一步只有很少的 query 行，省下的绝对量有限，而固定成本不会跟着变小。

「逐调用回退」带来的最大工程风险是什么？

配置看起来对、实际全在回退，而日志没有异常。判断只能靠统计行里的专用/回退计数，不能靠 flag 是否设置。

什么情况下它就不再成立了？

KV 布局变化（656 B/key 不成立）、换 SM 架构、换并行度导致 head 数变化、换 KV dtype —— 任一条都会让形状门对不上。

如果我的 T 常年大于 64 呢？

那这条基本对你无效：T ≤ 64 是五条门之一，超过就回退。此时应当去看通用路径的调优，而不是继续在这里找收益。
