KV 预取与预测：该不该提前搬，以及提前搬什么

速览 · 30 秒

  • 先分清两件事：该不该提前搬（策略问题，靠系统层信号）与提前搬什么（预测问题，可以下沉到模型内部）。前者不改模型，后者要改。
  • SGLang 现有的 prefetch 是需求驱动的：请求来了、发现 L2 缺 L3 有，才去搬。它不是预测，所以它的命中率天然接近 100%，衡量它要看的是来得及吗。
  • 真正的失败模式只有两个：来不及（白搬还占带宽）、抢带宽（在跑的请求 TPOT 被拖长）。判断标准是提前量 ≥ 传输时间，提前量 ≈ 排队深度 × 单轮耗时。
  • 模型层预测有两种切面：SparDA 用层间相关性预测下一层要哪些 KV block（提前量 ≈ 一层）；DualDecoder 用投机解码已经猜出来的 token 预测下一个 decode step 的检索索引（提前量 ≈ 一步，KV 预测准确率 88%）。
  • 评测的关键：必须跨并发梯度测（低压没排队、没收益；高压才可能变负），报「固定 TTFT p99 下的吞吐」而不是裸吞吐，并且把预取精度、浪费字节、辅助状态显存一起报出来。

前置：三个时间量，和一句话定义

prefetch（预取）= 在数据被真正需要之前，把它从慢层搬到快层。这里"慢层"是主机 DRAM 或远端存储（L2/L3），"快层"是 GPU 显存（L1）。 和普通缓存命中不同，预取是主动制造命中，所以它一定伴随一个风险：搬的东西可能没人要，或者要得太早还没到。

传输时间 = 字节 ÷ 有效带宽 提前量 lead time = 从发起到被需要 等待 wait = 被需要时还没到位的部分（纯损失）

利用率 = 传输时间 ÷ 提前量。提前量给得再大也不加分，但小于传输时间就一定会出现 wait —— 而 wait 是加在请求的关键路径上的。 预取的全部工程价值，就是把 wait 压到 0，同时不把带宽抢光。

现状：SGLang 的预取是需求驱动的，而且限流只看容量

先把已有机制的边界讲清楚——很多"要不要做预测"的讨论其实卡在这里。

请求到达
  └─ match_prefix 在 radix 树上做最长前缀匹配
       ├─ L1（GPU 显存）命中 → 直接用
       ├─ L2（主机 DRAM）缺失，但 L3（远端存储）有
       │    └─ hiradix_cache.prefetch_from_storage()
       │         └─ HiCacheController.prefetch() → PrefetchOperation 入队
       │              └─ prefetch_thread / prefetch_io_aux / prefetch_sync 三个线程
       │                   异步搬运，与 batch 计算重叠
       └─ 都没命中 → 重算
已有能力现状意味着什么
触发时机请求到达时才发起（需求驱动）它把"L3 有但我们还没搬"变成"现在搬"，不预测未来。命中率天然 ≈ 100%，只有及时率有意义。
策略best_effort / wait_complete / timeout（默认 timeout）就是在回答"等不等"：等满会阻塞调度，超时放弃则退化为重算。这是推迟问题的第一道闸。
限流prefetch_rate_limited() 只看主机池占用；源码里留着 TODO：还没有基于后端带宽/队列深度的限流它防的是"把主机内存塞满"，不防"把 PCIe/RDMA 抢光"。高并发下后者才是伤害来源。
竞态处理--hicache-storage-prefetch-retry-poll-interval / -max-attempts处理"备份还没落地就去查存在性"的假缺失——这是负载升高后最容易出现的坑。
廉价信号buffer_only 模式下有一份本地 LRU「存在性缓存」，并用预取查不到的 shortfall 反向失效值得借鉴的模式：花很小的代价维护"某段 KV 大概在哪"的近似信号，省掉每次的远端往返。

所以"加预测"要解决的并不是"命中率不够高"——需求驱动的命中率本来就高——而是把提前量从 0 变成正数， 以及决定在带宽紧张时该牺牲谁。前者是预测，后者是准入控制，两件事都要做。

值不值：不是"搬运 vs 重算"，而是"来得及吗、抢不抢带宽"

先说结论：在长上下文 LLM 服务里，"搬运 vs 重算"这笔账永远是压倒性的，讨论它没有意义。用本库部署口径算一遍 （KV 54.7 KiB/token、8 卡 PCIe 单机、MoE 活跃参数按 ~35B 估、有效算力 300 TFLOPS）：

比值≈ 270×≈ 270×

差两个数量级——所以只要命中，搬就是对的。真正的失败模式只有两个：

失败模式 ①：来不及
  • 预取完成时请求早被调度，wait 照样吃满
  • 代价 = 白搬的字节 + 被挤掉的带宽
  • 根因：提前量 < 传输时间
失败模式 ②：抢带宽
  • 预取与 load_back、MoE all-to-all 抢同一条 PCIe/RDMA
  • 表现为「总吞吐微升、p99 明显恶化」
  • 根因：没有带宽维度的准入控制

提前量从哪来：排队深度 × 单轮耗时

刚到的请求（想预取它） 正在跑的（占着 GPU） 排队的（它们的时间就是提前量）

刚到的请求前面还有 8 条在跑、7 条在排队。若单轮 decode 耗时 20 ms，轮到自己之前大约有 8×20 = 160 ms 的提前量—— 足够把 100K 前缀（86 ms）搬完。反过来：排队浅的时候，预取救不了 TTFT，只能靠 load_back 拼带宽。 这也是为什么评估预取必须跨并发梯度：低压区根本没有提前量可用。

系统层四类信号：不改模型就能做

这四类都只动调度器与缓存管理层，不碰模型权重。按 ROI 排序，第一类最重要。

右上角最好做：提前量大（好藏）、精度高（不浪费）。左上角是「高精度但窗口极小」——SparDA 与 DualDecoder 都在这一侧， 但它们的提前量足够盖住分层搬运的传输时间（一层的数据量本来就不大），所以依然成立。 系统层信号的提前量以「排队周期」计，代价是它只知道"这段前缀会被用到"，不知道"其中哪些条目现在就要"。

① 队列可见性（最高 ROI，而且不是预测）

调度器的等待队列里已经躺着请求了，它们的 token 序列是确定的。组批时抽样对队首若干条做一次 match_prefix， 命中 L3 而缺 L2 的立刻发起预取——精度 100%，提前量是整个排队周期。 实现落点在调度器组批之后、run_batch 之前，注意别在调度线程上做重活（抽样即可）。

② 会话延续（高 ROI）

多轮对话 / agent 的下一轮请求，前缀 = 上一轮的全部 token（含模型回复）。所以请求结束、往 L3 备份的同时， 按 session 预热并钉住（pin/lease）这段时间。精度取决于会话返回率，秒级间隔通常 70–90%。 前提是有 session 标识；退一步可以用前缀哈希近似。

③ 频率重击（中 ROI）

给前缀根节点挂命中计数器（或 TinyLFU 近似），窗口内第 k 次命中就把整段提升到 L2 并 pin—— 把缓存的准入从"LRU on access"换成轻度 LFU，治的是"热点第一次命中还得排队等"的长尾。

④ 静态先验（低 ROI 但最稳）

系统提示、工具 schema、RAG 文档集是静态已知的：启动时或首次出现后主动下沉 L2/L3 并常驻。 这不是预测，是 cache priming，收益最稳、风险最低。

通用前提：预测性预取必须配 pin/lease + 准入控制。没有 pin，你搬进来的东西可能在被用之前就被淘汰（纯浪费带宽）； 没有准入控制，带宽紧张时预取会反过来伤害在跑的请求。而且 prefetch 的优先级必须低于 load_back——已经在等的请求优先。

模型层预测：两篇工作是怎么作用的

系统层信号赌的是"这段前缀会被复用"；模型层预测算的是"下一步会读哪些内存"。后者把命中率从概率变成接近确定的数。

SparDA：预测下一层要读哪些 block（空间维度）

SparDA（arXiv 2606.04511） 在 Q/K/V 之外给每层加了第四个投影 Forecast：它不算注意力，只预测下一层需要哪些 KV block。 有了提前一层的选择结果，就能把 CPU→GPU 的预取压在当前层计算之下——提前量 = 一整层的时间。 可行性来自相邻层稀疏选择的高度相关：同一批 token 在相邻层往往被同样关注（这条观察在更早的 IndexCache（跨层索引复用） 里已被单独利用）。

机制：Forecast 把"选择"提前一层，预取压进计算里

层 l+1 计算时数据已就位

代价控制有两处设计：只训 Forecast（<0.5% 参数），用 KL 散度对齐原 selector 的 block-attention 分布，基座不动； 因为 Forecast 与 query 解耦，GQA 下每个 GQA 组只要一个 forecast head，比原来的多头 selector 更省。 实现上是 persistent UVA kernel 做异步预取，外加 batch-adaptive CTA allocation：小 batch 时层执行是瓶颈、少量 CTA 就够； 大 batch 时传输量线性增长而层执行次线性，越过交叉点后就要多分 CTA（哪怕略微拖慢主 kernel）。

报告的数字：1.25× prefill / 1.7× decode（对照稀疏+offload 基线），并且因为能开更大 batch， decode 吞吐再拿到 5.3×。作者在 Limitations 里说得很克制，也很关键：SparDA 不是新的稀疏注意力，只是加法件，精度上限由基座决定； 并且明确表示这套 lookahead 思路同样适用于 token 级稀疏（DSA，已被 DeepSeek-V3.2 与 GLM-5 采用）以及 DeepSeek-V4 的 CSA 路径，留作 future work。

DualDecoder：用投机 token 预测下一个 decode step 要读哪些条目（时间维度）

DualDecoder（arXiv 2607.26475） 先挖出一个被忽视的真问题：现有"动态稀疏 KV + host offload"的系统为了做检索，必须在 GPU 里常驻辅助状态 （KV landmarks、检索索引元数据），而这份状态随 深度 × batch × 上下文 × hidden × 稀疏预算 × chunk 一起长， 把 offload 本来要省下的 HBM 又吃回去了，高并发下自己变成新瓶颈。

显存账：offload 省下的 vs 辅助状态吃掉的

现有动态稀疏 + offload 系统
GPU 常驻的稀疏 KV + 选中状态aux 状态（landmarks/索引）权重 / 运行时缓冲
DualDecoder：预测取代存储
GPU 常驻的稀疏 KV + 选中状态省下的 aux 状态（改为预测）权重 / 运行时缓冲

它的价值主张不是"省传输"，而是省掉为了传输而存在的那份元数据——这份账在常规评测里几乎总是被漏掉。

关键洞察：一个 decode step 的检索索引由「当前 token + 常驻 landmarks」算出，而下一个 token 已经有投机草稿了—— 所以下一个 step 的关键 KV 集合可以提前一步算出来。测到的数很有说服力： token 预测准确率可以很低，但 KV 预测准确率平均 88%。因为它预测的是"内存访问"而不是"正确答案"，容错度高得多。 三个部件：dual-token decoding pipeline（低开销算出下一 token 的关键 KV）、 speculative KV cache transfer schedule（layer-aware，把预取与计算重叠）、layer-scoped memory management（压缩 GPU 运行时缓冲）。 结果是对照 SOTA 最高 2.62× decode 吞吐，延迟与质量不降。

  • 报固定 SLO 下的吞吐（如 TTFT p99 ≤ 2s 时的 QPS），而不是裸吞吐——否则可以靠牺牲延迟"赢"。
  • 三条基线同图：no-cache、demand-prefetch（现状）、predictive-prefetch。
  • 把代价一起报：预测精度、浪费字节、aux 状态显存（后者常被漏掉，却是 DualDecoder 的核心卖点）。
  • 你这套的两个特有注意点：投机解码的 verify 5 行会污染 TPOT 分布，要把"在等预取的请求"和普通请求分开统计；长前缀走 L3→L2→L1 是两跳（各 86 ms 量级），direct-L3 拓扑值得单测。

常见误解

✗「预取命中率高就说明预取有效」
需求驱动的预取命中率天然接近 100%——你搬的正是被请求的。它只说明"有活干"。 真正要看的两个数是及时率（来得及吗）和浪费字节（有没有白搬）。
✗「预取越多越好，反正带宽闲着」
带宽从不闲着：它和 load_back、MoE all-to-all 共用同一条 PCIe/RDMA。 现有 prefetch_rate_limited() 只看主机池占用、不看带宽，所以"多预取"在高并发下是
典型的负优化—— 表现为总吞吐微升、p99 明显恶化。而且没有 pin 的预取会自我淘汰。
✗「用低并发测预取就能看出效果」
低压下没有排队 → 提前量 ≈ 0 → 请求本来就不用等，测不出差别； 高压下预取又可能变负。结论必须来自跨并发梯度的整条曲线，而不是某一个点。
✗「模型层预测（SparDA / DualDecoder）是系统层预取的替代品」
是互补：系统层决定"要不要提前搬、搬哪一段前缀"，模型层决定"这段前缀里的哪些条目现在就要"。 两者作用的尺度差三个数量级（一层 ~50 μs vs 一个排队周期 100 ms+）， 而且模型层预测需要 offload 场景才划算——全 HBM 部署拿不到它的收益。
✗「offload 省下的就是 KV 那部分显存」
漏掉了辅助状态：为了让稀疏检索跑起来而常驻 GPU 的 landmarks 与索引元数据，随深度 × batch × 上下文 × 稀疏预算增长。 DualDecoder 的出发点正是这份账——它把"存储"换成"预测"，才真正把显存还回去。

自测

1. 为什么说"需求驱动的预取命中率接近 100%，但只有及时率有意义"？
因为它预取的正是被请求的那段前缀——命中是构造保证的，不是预测对了。 但它可能在请求已经被调度之后才搬完，那段时间就变成阻塞在关键路径上的 wait。 所以衡量它的是：预取在多少比例的请求上赶在需要之前完成。
2. 10K 前缀、TPOT 20 ms、前方排队 8 条，预取来得及吗？100K 呢？
可用提前量 = 8 × 20 ms = 160 ms。 10K 前缀 547 MB ÷ 64 GB/s = 8.5 ms → 绰绰有余； 100K 前缀 5.5 GB ÷ 64 GB/s = 86 ms → 仍然够（160 > 86），但余量只剩一半， 一旦带宽掉到 32 GB/s 或排队变浅就不够了。这就是"提前量 ≥ 传输时间"这条判据的用法。
3. SparDA 的提前量只有一层（几十微秒），为什么还能藏住 PCIe 传输？
因为它是分层搬的：每一层需要的是那一层的 KV，而不是整段上下文。 decode 时一层的数据量并不大，传输时间被压到与单层计算同量级甚至更短。 对这套部署做个量级核对：一层 2048 个 token 的 fp8 latent ≈ 1.18 MB，PCIe 上约 18 μs，而一层计算在几十 μs—— 藏得住。反过来 prefill 时一层的数据量大得多，收益就小了。
4. DualDecoder 为什么能把 GPU 辅助状态"省掉"，而不是"搬走"？
因为它改变了信息的获取方式：aux 状态（landmarks / 索引）原本是为了快速算出检索索引而缓存的中间结果。 既然下一个 token 的检索索引可以由「当前 token + 投机草稿」提前算出来，就不必把这套索引常驻在显存里—— 需要用的时候算一遍即可。用算力换显存，而 decode 阶段最闲的恰恰是算力。
5. 为什么必须按并发梯度测预取，而不能只测一个高并发点？
两个方向的效应都在并发上： ① 提前量 = 排队深度 × TPOT，低压时提前量为 0，预取无从发挥； ② 负载升高后带宽成为共享资源，预取开始抢占在跑请求的带宽，收益转负。 所以曲线通常是倒 U 形，拐点位置才是要报告的结论。
6. 如果只能改一处，先做哪个？为什么？
队列感知预取（扫描等待队列、对已排队请求的前缀提前发起预取）。 理由：它把"预测"变成"已知"，精度 100%；提前量直接取一个排队周期； 实现上只是调度器里加一次抽样匹配，不碰模型、不碰 kernel； 而且它天然和现有 prefetch 链路复用同一套线程与策略。 —— 相反，模型层预测（SparDA 类）需要训练新投影，收益还依赖 offload 场景，应该放在后面。

延伸阅读

  • SparDA: Sparse Decoupled Attention for Efficient Long-Context LLM Inference 本页"空间维度预测"的原作：Forecast 投影、层间 lookahead、persistent UVA 预取内核、batch-adaptive CTA 分配。其 Limitations 明确点名 DSA / CSA 是尚未做的方向。
  • DualDecoder: Accelerate Long Context LLM Inference by Predictive Prefetch "时间维度预测"的原作：用 speculated token 预测下一 decode step 的检索索引（KV 预测准确率 88%）、layer-aware 传输调度、layer-scoped 显存管理。
  • IndexCache: Accelerating Sparse Attention via Cross-Layer Index Reuse SparDA 的直接前作，把"相邻层选择高度相关"这条观察单独做成了系统优化——想理解 SparDA 为什么能成立，先读它。
  • InfLLM-V2: Dense-Sparse Switchable Attention SparDA 的基座（块级稀疏选择 + 三段压缩表示），"统一稀疏注意力"的代表实现之一。
  • Native Sparse Attention (NSA) · MoBA 可训练稀疏注意力的两条主线：NSA 用可学习门控融合压缩/稀疏/滑窗分支，MoBA 做块级混合。想理解 SparDA 与基座的关系必读。
  • InfiniGen · ShadowKV KV offload + 预取的早期代表作：前者用下一层注意力近似来预取，后者把 KV 放低秩/低精度影子存储。SparDA 的预取思路与它们一脉相承。
  • Quest: Query-Aware Sparsity for Long-Context Inference "按 query 选关键页"的经典做法，理解稀疏选择成本与收益的起点。
  • SeerAttention 把稀疏模式学出来的另一条路线（可学习 gate + 自蒸馏），与 SparDA 的"只训选择器"形成对照。
  • LiteTopK: Fused Indexer-TopK Kernel for Long-Context · HISA: Hierarchical Indexing for Fine-Grained Sparse Attention 顺着"选择开销本身"这条线的最新工作——与你正在用的 top-k 后端（sgl-kernel）直接相关。
  • SGLang · HiCache 设计文档 · Mooncake 论文 本页"现状"一节的官方口径；分层缓存与本页的预取是同一套机制的两面（参见另一篇）。
