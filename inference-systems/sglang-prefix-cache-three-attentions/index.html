速览 —— 五条结论

  • 不是三套缓存，是同一棵树上的三类组件。UnifiedTreeNode 每个节点带一份 component_data[ct]，ct ∈ {FULL, SWA, MAMBA}。线性注意力落在 MAMBA； 滑动窗口是 SWA；稀疏注意力没有组件身份，它的 indexer K 寄生在 FULL 的同一批 token slot 上。
  • 同一个 .value 字段，三种粒度。FULL/SWA 存 per-token 的池索引（len(value) 就是覆盖的 token 数）； MAMBA 存 一个 slot id（len(value)==1），因为状态里根本没有 token 轴。
  • 命中是「合取」。_all_valid(validators, node) 要所有组件同时通过，边界才前进。 但 Full 命中长度 full_kv_hit_length 独立于校验器先行累加，所以「KV 命中、辅助组件没命中」不会浪费， 而是变成 branching_seqlen 交回调度器。
  • SWA 的复用是尾窗「全有或全无」。一条已解码过的 5000-token 缓存序列，查询前缀长度 L < 4999 时可复用 0 个 token，只有 L ≥ 4999 才能拿到完整的 L。 不是「复用最后 128 个」，而是「凑不满一窗就一个都不复用」。
  • 稀疏注意力缓存的是 indexer K，不是 top-k 模式。模式每步用当前 query 重算， 因此「上下文不同 / 前缀长度不同 / 稀疏配置不同」在结构上都不可能让旧模式失效 —— 它从没被留下来。

01共同底座：一棵树，三类组件

key 里有什么，没有什么

RadixKey 只描述「这段 token 是谁」：

要点：key 里没有注意力配置。没有 sliding_window_size，没有 index_topk，没有稀疏模式。 这条事实后面会直接决定稀疏注意力那条路径为什么「不会失效」。粒度由 page_size 决定， 匹配长度一律 page_aligned（radix_cache.py:139-143）。 比较本身是「指数搜索 + 二分」而不是逐 token Python 循环，长共享前缀不会退化成 O(n) 次解释器循环 （radix_cache.py:186-210 match_at()）。

命中判定：合取 + 两个独立进度

这是三类机制共用、也是最容易被读漏的一段。走查从 root 向下，每个节点过一遍所有组件的校验器：

# python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py:932-970（重排为逻辑序）
def _all_valid(validators, node):
    return all([v(node) for v in validators])       # ← 合取：所有组件都点头

def _update_best_if_valid(node):
    if _all_valid(validators, node):
        best_match_node = node                      # ← 边界只在这里前进

while key_offset < len(key) and child_key in node.children:
    child = node.children[child_key]
    if child.evicted and not child.backuped:
        break                                       # ← FULL 缺失：整条匹配直接断
    prefix_len = child.key.match_at(key, key_offset, page_size=self.page_size)
    full_kv_hit_length += prefix_len                # ← 先累加，早于任何校验器
    if prefix_len < len(child.key):
        node, action = self._split_node(child.key, child, prefix_len)
        _update_best_if_valid(node); break
    node = child
    _update_best_if_valid(node)
    key_offset += prefix_len
两个进度必须分开看
  • best_match_node —— 最后一个「所有组件都通过」的节点，决定辅助组件复用到哪（LRU 提升、加锁、COW 源）。
  • full_kv_hit_length —— 纯 token 比较的进度，不受校验器影响，可以比 best_match_node 更深。
  • device_prefix_len 由前者派生（unified_tree_core.py:1041），是调度器实际采用的 token 数。
于是总有 full_kv_hit_length ≥ device_prefix_len
  • 差额不能被静默吞掉，否则每次都会白白重算一段长前缀。
  • 两个辅助组件把它包装成建议：SWA 出 swa_branching_seqlen， MAMBA 出 mamba_branching_seqlen——「这里本来可以命中，但我没有状态」。

02Linear Attention：一个 checkpoint = 一个节点的状态

线性注意力（Gated DeltaNet、Kimi Delta Attention / KDA、Mamba2）把整条历史折进一个固定大小的循环状态里， 于是缓存的对象不再是「每个 token 一份 KV」，而是「某些位置上的整条状态」。这一句话决定了后面所有细节。

先归并：所有线性注意力家族都收敛到同一个组件。Qwen3-Next 的 GDN、Kimi-Linear 的 KDA、glm5_next 的 Glm5NextLinearAttention、nemotron_h、gigachat35、bailing_hybrid 全部走 uses_ssm_state() → registry.py:166-169 → ComponentType.MAMBA。 不同家族之间只差状态形状参数（KimiLinearStateShape vs Mamba2StateShape：卷积轴 (K-1, dim) 还是 (dim, K-1)、是否 per-K gate），缓存层一行都不用改。

2.2 复用判定：条件就是「这个节点有没有状态」，但合法边界只有网格点

校验器短到可以直接整段贴出来 —— 没有任何长度运算：

# python/sglang/srt/mem_cache/unified_cache/components/mamba.py:149-160（完整函数）
def create_match_validator(self, match_device_only: bool = False):
    ct = self.component_type
    if match_device_only:
        return lambda node: node.component_data[ct].value is not None

两个方向都被显式命名了。一个方向是「状态比 key 走得远」，另一个是「key 比状态走得远」：

  • 完整跑完后，最新状态可能超出要发布的 key 长度。
  • 此时回退到 ping-pong 的另一个 slot：它一定存着张量，只有 mamba_prev_track_seqlen 能说明它对应哪个长度。
  • 两个都超了就返回 None，即「什么都不捐」（docstring：None means donate nothing）。
mamba_branching_seqlen —— 往前补
  • Full KV 命中得比任何状态都深 ⇒ 那个位置本来可以有状态。
  • 取 full_kv_hit_length 内最后一个网格对齐点，作为「分支点」交回调度器。
  • 它的语义是「请你在这里补一个快照」，不是「你可以复用到这里」。

06三类机制的主要区别

把四个问题逐行摊开。左列是问题，三列是答案 —— 这张表可以直接当查找表用。

问题Linear（MAMBA）SWA（SWA）Sparse（无组件）
① 存什么 树上一个 slot id（shape (1)）；指向 MambaPool 的 conv + temporal 两块状态。成本 O(1)/序列 per-token 的 SWA 池索引（需经翻译表）；窗口外的节点是 tombstone。metadata["uuid"] 记窗口锁边界 indexer K + scale（uint8，约 132 B/token/层），与主 KV 同 loc 空间；树上没有独立字段
② 怎么判命中 校验器等价于 value is not None；合法边界由 lcm(chunk, page) 网格 + insert 时截断保证 累加 len(node.key)，遇 tombstone 归零；边界合法 ⟺ 连续 live 段 ≥ W 复用 FULL 的校验器。index-K 存在性不被检查，靠同 loc 空间的结构不变量
③ 怎么更新 decode 在 ping-pong 两 slot 间轮转；结束 donate、未完成 fork；命中后 COW（记录 + 前向流执行） 滑窗推进游标 → insert 在游标处切节点（父 tombstone / 子 live）→ 新叶 SWA 上限一窗；tombstone 可被更短请求恢复 与 KV 同一次 forward、同一批 loc 写入；复用后 top-k 重算；无独立淘汰

逐出优先级0，不触发级联 1，级联 MAMBA 跟 FULL（2）同生共死
粒度单位状态（slot） token（page 对齐） token（page 对齐，随 KV）

三条最本质的差异

1. 负载有没有 token 轴
  • KV 与 index-K 有 token 轴 → 任何 token 下标都是合法切点，可以按需截断共享。
  • 循环状态没有 → 只有网格对齐的位置才是合法边界，所以引入 branching_seqlen 这种「建议补快照」的机制。
2. 负载是可变还是只增
  • KV append-only → 命中前缀可被任意多请求只读共享。
  • 状态被 decode 原地改写 → 命中必须 COW。并发成本是 O(并发请求数)，不是 O(1)。
3. 「值」是连续的还是离散的
  • SWA 的值会随窗口滑动大片消失，于是需要 tombstone 表达「节点在、值没了」。
  • 稀疏的值与 KV 同生共死，不需要第三种状态 —— 这也是它不需要组件身份的原因。
为什么稀疏不能走组件化
  • 组件化的前提是「这份数据有独立的生命周期」：要能单独分配、单独逐出、单独加锁。
  • index-K 的生命周期完全被 KV 决定，独立成组件只会带来一致性成本而没有收益。
  • 反过来，真正需要独立生命周期的 DSV4 C128 sidecar 就确实拿到了自己的 ComponentType。

08常见误解

「SWA 的 prefix cache 就是复用最后 128 个 token。」
不是。链上的复用边界是一个整数 device_prefix_len，不能一半一半。 一条已解码的 5000-token 序列，长度 4000 的前缀请求拿到的是 0，不是 128。 要复用，前缀必须落进最后不到一个 page 的窄带里。
「稀疏注意力会把 top-k 选择缓存下来，命中时要检查模式是否兼容。」
不存在这个检查，因为模式从来没被保存过。 缓存的是 indexer K（每个 token 自己的投影），top-k 每步用当前 query 重算。 mem_cache/ 整个目录搜 topk_indices 是 0 命中。
「线性注意力的状态也占 KV 池的槽位，命中长度就是 token 数。」
状态挂在 HybridReqToTokenPool 的 MambaPool 上， value 是 shape (1) 的 slot id，len(value)==1。 「能省多少 token」与「从哪个状态起步」是两个独立的数，组件把两个都留着。
「三类机制各有一套独立的缓存树。」
只有一棵树。UnifiedTreeNode.component_data 是 按 ComponentType 下标索引的 list，一份 key、多条 value 线。 稀疏干脆连这条线都不占 —— 它和 FULL 共用同一批 token slot。
「命中失败就等于这部分完全白算。」
不一定。full_kv_hit_length 早于校验器累加， 所以「KV 命中但辅助组件没命中」会被包装成 branching_seqlen， 让本次前向顺手在那个位置落一个状态快照，后来的兄弟分支就能命中。 这一次仍然要重算，但下一次不用。

09自测题

Q1 · 一个 hybrid full+SWA 模型，W=256、page_size=16。已缓存并解码过一条 8000-token 序列。现在来一个 3000-token 的严格前缀请求，SWA 侧能复用多少？
0。Wp = ceil_align(max(256,16),16) = 256，稳态游标 B = pre_len − Wp = 7999 − 256 = 7743。判据是 L − B ≥ W， 这里 3000 − 7743 < 0，落点本身就在 tombstone 里。 通式 max_reusable = 0 if L < B + W else L，阈值 T = C − 1 − (Wp − W) = 8000 − 1 − 0 = 7999。
Q2 · 同一个请求，若只让 FULL 组件参与判定、SWA 不 gate（ring 模式），能复用多少？
3000。回落到 Full 语义 —— 每个 page 对齐的 token 下标都是合法边界。 这正是 swa_gates_prefix_match=False 的效果（kv_cache_builder.py:341-347）： 当 SWA 由请求自己的 ring 重建时，让它 gate 只会误伤 Full 命中。
Q3 · 一条 KDA 层与 full-attention 层混排的模型，为什么 prepare_for_caching_req 的返回值要取 min()？
因为它决定「树能发布到多长」。MAMBA 返回的是状态实际加密的 seqlen （受 mamba_checkpoint_grid 约束和 mamba_last_track_seqlen 截断）， FULL 返回 None（表示不限制）。取 min() 保证了 节点深度与状态 seqlen 是同一个数 —— 这是 2.2 那三条约束里的第一条。 不这么做，节点就会声称自己在某个深度有状态，而实际上没有。
Q4 · index-K 的布局从 fp8 换成 fp4，同一份 L3 缓存还能命中吗？
不能，而且代码不会拦住你。布局不写进 key，注释只提醒 「a persisted cache written under the other one must be cleared before switching」 （deepseek_v4_memory_pool.py:583-586）。 页数和形状都没变，但字节语义变了 —— 命中会读到错位的数据。这是这份实现里少数需要运维纪律兜底的地方。
Q5 · 为什么 MAMBA 内部节点的逐出优先级是 0，而且不触发级联？
因为状态只在匹配边界节点上被消费。内部节点上的状态对任何路径都没有贡献， 删掉它不影响别人读 —— 影响的是「以后还能不能从那个深度起步」，而这已经由 branching_seqlen 这套补快照机制在管理了。 反过来 FULL 是 2：它一死，整条路都读不了（break），所以必须最后死。
Q6 · 如果一个请求的前缀在树里同时命中 FULL 与 SWA，但 MAMBA 只到一半深，会发生什么？
不是「三选一」，而是合取 + 差额建议： best_match_node 停在 MAMBA 还能命中的深度（FULL、SWA 会跟着这个边界一起加锁、提升 LRU）， full_kv_hit_length 继续记录到更深的位置， mamba_branching_seqlen 把「本可以命中的网格对齐点」交回调度器， 由 schedule_batch.py:3210-3225 在本次前向补一个 track 点。 这样本次多算了一点，但下一个同前缀的请求能命中得更深。
