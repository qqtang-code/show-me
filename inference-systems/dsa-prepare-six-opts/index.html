DSA 的准备阶段六项小优化：条件窄、净值小，还有一项是负向

2026-11-16 DSA 稀疏注意力 元数据 prefill 小优化

DSA（稀疏注意力）的大头是「先选再算」。但在开始选之前还有一段活：切 page table、切 query、拼 metadata、做 batch plan、给 indexer 分块、对齐 SM wave。这六件事都不改变算法，只减少分配、拼接与重复的元数据工作 —— 全部加起来，192K 的 TTFT 只降了约 1.5%。这一页的价值不是「六个开关」，而是它们的生效条件为什么这么窄，以及其中一条为什么会掉吞吐。

速览 准备阶段在哪 六项逐条 条件为什么这么窄 净值与那条负向 该不该开 常见误解 自测

术语约定：indexer、top-k、page table、metadata、batch plan、wave、singleton、eager 保留英文。本文讲的是四机 PD 线 P 端 DSA 的 prefill 准备阶段；选 top-k 与稀疏 MLA 的机制本身见 SGLang 推理全流程 与 prefix cache 的三类注意力。

01速览

TL;DR

  • 六项都在「选 top-k 之前」。 分块、对齐、复用布局、单页表视图、单 query 元数据、单请求批计划 —— 全是减少元数据与分配的工作，不动算法。
  • 条件极窄，而且不是同一条。 ③⑤⑥ 挂在 singleton（批里只有一条请求），④ 挂在 eager（非图捕获），①② 挂在大行数 + SM120 —— 每个都有自己的前提，缺一条那项就不走。
  • 净值约 −1.5%。 80 请求冷 C1 下，indexer 分块 + Q 布局复用两项合起来把 192K 的 TTFT 拉低约 1.5%。
  • 其中一条是负向。 单请求批计划单项曾出现 TTFT 只降 12 ms、而吞吐掉 3.94% —— 这是全页最该记住的一行。
  • 正确读法：这是「保留的小幅组合优化」。 不是六项各自都有正收益，更不能当作六条独立开关去逐条 A/B。

02准备阶段在哪

DSA 的 prefill 主流程是「先选后算」。准备阶段就是在开始选之前必须把一批一次性工作做完：

③PAGE TABLE把本次请求要读的页拼成视图
④QUERY 准备对齐到最终的 absorbed-Q 布局
⑤METADATA每条 query 的长度/偏移
⑥BATCH PLAN这一批怎么排
▼
①②INDEXER 打分按行块切（1024 行）+ 对齐 SM wave
TOP-K选出要读的页（不改）
SPARSE MLA只算选中的部分（不改）

六项里有四项（③④⑤⑥）改的是「怎么把同一份信息组织成内核能直接吃的形状」。它们的共同收益机制是一样的：让下游内核少做一次拼装、少读一遍元数据。所以每一项的收益都很小，而且都只在「元数据占比最高」的形状下才显出来 —— ③⑤⑥ 对应的形状是 singleton，④ 对应的是非图捕获。

03六项逐条

#项做了什么生效条件
①indexer 行块logits 按固定行块（1024 行）切，避免超大行数一次铺满大行数 + SM120
②SM wave 对齐块大小取 wave 的整数倍，减少最后一批 SM 空转SM120 + 大行数
③单页表视图singleton 时给一个 unit page-table view，不再每次重拼批里只有一条请求
④Q 布局复用直接产出 absorbed-Q 的最终布局，省一次搬运/转换非图捕获
⑤单 query 元数据unit-query 的 metadata 快路径单 query
⑥单请求批计划singleton batch plan 快路径批里只有一条请求

编号按数据流的先后排（不是原始记录里的编号）：①② 在 indexer 打分这一步，③⑤⑥ 是「批里只有一条请求」时的快路径，④ 与图捕获互斥。

04生效条件为什么这么窄

六项的前提不是同一条，这是最容易记错的地方：③⑤⑥ 挂 singleton，④ 挂 eager（非图捕获），①② 挂大行数 + SM120。下面先讲最主流的那个前提（singleton），再讲另外两个为什么也收得这么紧。

singleton 那条的原因是经济学的：这三项省的是「把 N 条请求的元数据拼起来」这笔开销。批里只有一条请求时，拼接逻辑退化成「包装一层」，快路径能整段跳过；一旦批里有两条以上，就得走通用路径 —— 而通用路径本身已经在为吞吐优化了，快路径插不进去。

「只在 singleton 生效」意味着什么？意味着你的压测必须包含并发 1 的场景，否则这几项在你的数据里等于没开。反过来，如果你的线上几乎没有 singleton 流量（大并发常驻），它们对你就没有价值 —— 这不是「配置没调对」，是场景不匹配。

另外两个条件也各有来由：eager（非图捕获，这是 ④ 的前提）是因为这些快路径改变的是元数据的组织方式，录进 CUDA graph 之后形状必须固定，快路径的「按需跳过」就没了；SM120 是因为 wave 大小与 SM 数量绑定，①的块大小与②的对齐都是按这套硬件选的。

那 −1.5% 是怎么来的，值得看清楚：它不是六项相加，而是「indexer 分块 + Q 布局复用」两项在 80 请求冷 C1 上的合计读数。其余四项没有独立的干净对照 —— 也就是说，「六项都有收益」这句话没有证据支持。

那条负向为什么最值得记。 单请求批计划单项：TTFT 只降了 12 ms（噪声级），吞吐却掉了 3.94%。这正是「小优化叠多了会互相打架」的典型形态 —— 快路径为了省一次拼接，牺牲了通用路径上已经做好的批内合并；在并发场景下，省下的那点时间远不抵批处理效率的损失。结论不是「这项错了」，而是「它只该在它声称的场景里开」。

① 你的流量里有 singleton 吗

没有就别开。③⑤⑥ 这三项只在批里一条请求时生效，并发常驻的服务开了等于没开。

② 你的长输入是否走 eager

开了图捕获，快路径的「按需跳过」就不成立。

确认 prefill 是否禁用图
③ 你能接受「整体保留、逐条不承诺」吗

它们是一组小幅组合优化，没有逐项收益证据；验收只能按组合读。

按 192K TTFT 的整体读数验收

如果三个问题的答案都指向「该开」，也不要逐条 A/B —— 直接按组合开关，用「192K 冷 C1 的 TTFT + 吞吐」两个数一起验收，把负向那项排除在外。

07常见误解

①「六项是六个独立可调的开关，可以逐条找收益」

不是。只有「indexer 分块 + Q 布局复用」这一组有干净的合计读数（≈ −1.5%），其余没有独立对照；逐条 A/B 在噪声级上找不到信号，只会白跑一轮。

②「单项不亏就都开上」

反例就在这张表里：单请求批计划单项 TTFT −12 ms、吞吐 −3.94%。只看 TTFT 会把它判成「无害」，看吞吐才知道它在并发场景下是负的。

③「既然叫准备阶段，应该对所有形状都有用」

恰恰相反。它省的是元数据拼接这笔开销，而元数据的相对占比只有在 singleton + 大行数时才高。批一大，通用路径的批内合并效率反而更高。

④「−1.5% 太小，不值得进知识库」

值得记的不是 1.5%，而是两个判断：①哪些优化只在 singleton 下存在（决定你要不要压并发 1）；②小优化叠加会互相打架（那条负向）。这两条会反复用到。

08自测

这六项为什么都叫「准备阶段」？它们改的是算法吗？

都不是算法。它们改的是「在开始选 top-k 之前，把页表、query、metadata、批计划组织成内核能直接吃的形状」的工作量 —— 省的是分配、拼接与重复读元数据。

为什么 ③⑤⑥ 只在 singleton 生效，而 ④ 不是？

③⑤⑥ 省的是「把 N 条请求的元数据拼起来」这笔开销，只有一条请求时拼接退化成包装，快路径能整段跳过。④（Q 布局复用）省的不是拼接而是一次布局转换，所以它的门是「没录进 CUDA graph」—— 图捕获之后形状必须固定，这个「跳过转换」的自由度就没了。

那条约 −3.94% 吞吐的负向告诉了我们什么？

小优化会互相打架。快路径为了省一次拼接牺牲了批内合并效率，在并发场景下净亏。所以判断这类优化的标准不是「单项快不快」，而是「在它声称的场景里快不快」。

验收这组优化应该看哪两个数？

192K 冷 C1 的 TTFT（看它省了多少）和同一批的吞吐（看它有没有把批处理拖垮）。只看 TTFT 会把负向项判成无害。

如果你的线上没有 singleton 流量，这页还有用吗？

有用，但不是用来开的：它告诉你这类「单请求快路径」在你的场景里没有价值，省得以后看到别人的收益数字又回头试一遍。
