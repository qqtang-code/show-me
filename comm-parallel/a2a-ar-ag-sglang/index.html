结论

  • 1 · 三者不是并列关系。 allreduce 在数学上等于 reduce_scatter 接 allgather —— 这条恒等式在 SGLang 里是字面成立的：layer_boundary/ops.py 的 tp_reduce_scatter() 把层尾的求和切成 reduce_scatter_tensor，下一层入口的 attn_tp_gather_input() 再用 attn_tp_all_gather_into_tensor 把行拼回去。 all2all 与这条恒等式无关，它是另一类操作。
  • 2 · 区分三者的判据是输出布局，不是「走哪张网」。 allreduce 和 allgather 的输出在每个 rank 上完全相同（冗余复制）， all2all 的输出每个 rank 都不同（置换）。而且只有 allreduce 做算术： 输入必须是 partial，输出是这些 partial 的和。
  • 3 · SGLang 里三者落在完全不同的层。 allreduce 走「模型层 → layer_boundary 的契约 → communication_op → GroupCoordinator.all_reduce」这条稠密路径； allgather 除了同一条路径，还有一条只在词表并行处出现的专用路径 （vocab_gather.py）； all2all 在 MoE 里根本不经过 communication_op.py —— 它是 token_dispatcher 的 dispatch() / combine() 这一对语义， 而 dispatch() 底下可能是 DeepEP、FlashInfer、Mooncake、NIXL、pplx 中的任意一个。
  • 4 · GLM-5.3 在 H200 上那份配方里，一条 forward 看不到 all2all。 官方用例 test/glm53_flash_common.py 只给了 --tp-size 8，没有给 --moe-a2a-backend；none 之下 MoE 走 TP，层尾是一次 all_reduce，而不是 dispatch/combine。按源码调用点数下来，一次 text forward 是 91 次 all-reduce + 1 次 all-gather + 0 次 all2all（45 层 × 2 次边界求和 + 1 次 embedding； 末尾一次 logits 拼接）。
  • 5 · 但 all2all 一开，allgather 会回来。 glm5_next.py:1191 里，只有当 --moe-a2a-backend 取 deepep / deepep_v2 / mooncake 时 enable_a2a_moe 才为真，随后 capture_output() 对 aux hidden state 做一次 attn_tp_group.all_gather(..., dim=0) —— 因为 A2A 把 token 打散到了 EP rank 上， 要还原一条完整序列只能 all-gather。

01三个原语：四个维度逐一拆

下面三张图用同一个约定：行 = rank，列 = 数据块，颜色 = 这块数据由哪个 rank 产出，N = 4。 三张图的输入格子数不同，输出格子数也不同 —— 差异全在布局里，不在"带宽"这种模糊说法里。

同一个 N = 4 的 group。左：每个 rank 交一份 partial，输出处处相同。 中：每个 rank 只交一格，输出拼成整行。右：每格都要发出去，输出是输入矩阵的转置。 右图的字节数和中图相同 —— 都是 (N−1)/N·n，区别只在"发给谁"。 窄屏上这张图可横向滑动。

allreduce —— 求和后人人有份

通信目标

把 N 个 rank 上同 shape 的 N 份 partial 逐元素相加， 再把完整的和放回每一个 rank。它的目标里同时包含"归约"和"广播"两件事。

参与方数据变化

每份输入都覆盖全部元素，但只是部分和（例如 o_proj 在本 rank 那 1/8 个 head 上算出的贡献）。输出仍是全部元素， 数值变成 Σ，且 N 份完全相同。

典型输出

所有 rank 上的张量逐字节相同。冗余是它的定义，不是副作用 —— 下游每个 rank 都要独立继续算，所以必须人手一份。

常见场景

TP 的 RowParallelLinear（o_proj、 down_proj）之后；词表并行 embedding 之后；DP attention 上 attention 的 partial 求和； 层尾那次"把 FFN 的 partial 收拢"。

allgather —— 拼起来后人人有份

通信目标

每个 rank 持有一个互不重叠的切片，把它们按顺序拼接成完整张量， 让每个 rank 都拿到这份拼接结果。不做任何算术。

参与方数据变化

输入只有 n/N（列切则宽度是 1/N，行切则行数是 1/N）。输出是 n： 每个 rank 从"我这一片"变成"所有人那几片都在我这"。数据被复制，而不是被求和。

典型输出

所有 rank 上相同，且等于 [s0 | s1 | … | sN-1]。 SGLang 里这一步是显式写出来的：先 all_gather_into_tensor， 再 reshape((world_size,) + input_size) + movedim(0, dim) + reshape， 拼的语义就落在 movedim 这一行。

常见场景

词表并行的 lm_head 之后拼 logits；A2A 打散 token 之后还原完整行； TP 切分的 KV 需要凑齐时；MTP / aux hidden state 需要全序列时。

all2all —— 每对之间交换的块都不一样

通信目标

每个 rank 把自己的 buffer 切成 N 段，第 j 段只发给 rank j， 同时从每个 rank 收一段。它是 N 个"点对点、且每对内容不同"的交换， 而不是 N 次广播。

参与方数据变化

输入是"按目的 rank 切好的块"，输出是"按来源 rank 排好的块"。 总字节基本不变（balanced 时严格不变），每 rank 仍是 n，但内容被重排： rank r 的输出恰好是输入矩阵的第 r 列。

典型输出

每个 rank 都不一样。这正是它与前两者的分界： allreduce / allgather 的产物在 rank 之间可以互换，all2all 的产物不能 —— 换过去就是错的。

常见场景

MoE 的 dispatch（token 按路由结果搬到专家所在 rank）与 combine（算完搬回原 token 所在 rank）；以及 SGLang 里 TP lm_head 把"all-gather + DP scatter"合并成一次 all_to_all_single 的那条路。

03与其余五种集合通信的区别

把另外五个放进来一起看，三者的特殊性才明显：只有这三个是"无 root、全员参与、全员拿到结果"的。 broadcast / scatter / gather / reduce 都有一个 root 或一个单点接收方；reduce_scatter 虽然全员参与， 但输出只有 n/N，不给全量。

读这张表有两个捷径：

  • 看有没有 root。 有 root 的四个（broadcast / scatter / gather / reduce）里，root 或 dst 是一个"特权 rank"，其余人要么只发、要么只收。三原语没有特权 rank，所有 rank 的地位对称 —— 这是它们必须全互通、必须做满 N 份收发的根本原因。
  • 看输出是不是"全量"。 只有三原语保证每个 rank 结束时都持有全量数据。 reduce_scatter 是唯一"全员参与但不给全量"的那个，所以它永远只能作为中间步骤出现， 不能单独承担一层的数据交换。

04两条恒等式：三者怎么互相造出来

恒等式一：allreduce = reduce_scatter ∘ allgather

allreduce(x₀, x₁, …, x_{N-1})            
  ≡  reduce_scatter(x)   → 每 rank 拿到 Σ 的 1/N 个切片
  ∘  allgather(那一片)    → 把 N 个切片拼回来，人人一份

字节账也对得上：reduce_scatter 搬 (N−1)/N·n，allgather 再搬 (N−1)/N·n， 合计 2·(N−1)/N·n，与一次 ring allreduce 的代价相同。所以"把 allreduce 拆成两段"在带宽上不是免费的， 它换的是别的东西：中间那一步的数据量只有 n/N，可以做在更小的行数上、可以和下一层的 norm 融合、可以和计算重叠。

SGLang 里这条恒等式是字面实现的，不是类比。layer_boundary/ops.py 里两个函数直接对应两段：

恒等式二：allgather = N 次 broadcast

allgather 可以看成"rank 0 广播 s₀、rank 1 广播 s₁…… rank N−1 广播 s_{N-1}"。ring 实现就是这个思路的流水化。反过来， all2all 不是 N 次 broadcast —— 因为 rank r 发出去的那 N 块内容互不相同， 收端也不能共享。所以 all2all 的实现必须是双向的、逐对的，SGLang 里它落在 DeepEP / FlashInfer / NIXL 这些专门的 transport 上，而不是 GroupCoordinator 的通用集合通信通路。

all2all 也不是"all-to-all 版的 allgather"。 两者字节数一样，但 allgather 的每个接收者都得到同一份完整张量； all2all 的每个接收者得到的是自己那一列。把 allgather 换成 all2all， 结果不是"慢一点"，而是布局错了 —— 下游拿到的张量形状和内容都不对。

05SGLang 的五层落点

在 SGLang 里找一次集合通信，要沿着五个层往下走。三原语在这五层里的"存在感"完全不同 —— allreduce 和 allgather 走第 2 到第 5 层，all2all 直接从第 1 层跳到第 5 层， 中间两层它不经过。

L1 模型层
models/glm5_next.py

声明这一层的 attention / FFN 用哪个 stage，以及少数"就地决定"的通信 （例如 capture_output() 里的 all_gather、MoE 前的 token 广播）。 它不决定原语，只声明契约。

L2 边界层
layers/layer_boundary/ ＋ layers/dp_attention.py

真正决定"这一次求和现在做、留到下层做、还是用 reduce-scatter 顶掉"的地方。 ops.py 把选择翻译成具体的 all_reduce / all_gather_into_tensor / reduce_scatter_tensor / scatter 调用。

L3 API 层
distributed/communication_op.py

12 个具名函数（其中 8 个是 all-reduce 入口、2 个是 gather、2 个是广播），全部是一行转发：tensor_model_parallel_all_reduce()、 tensor_model_parallel_all_gather()、attention_tensor_model_parallel_all_reduce()…… 名字里的前缀（tensor_model_parallel / attention_… / moe_…） 决定选哪个 group。

L4 组层
distributed/parallel_state.py · class GroupCoordinator

按 dtype、size、是否对称内存、是否在 torch.compile 下，在 msCCL++ / custom all-reduce / pynccl / FlashInfer / quick-all-reduce / torch-symm-mem / NCCL 之间选一个后端。这一层是"同一条 all_reduce 调用，落在不同 kernel 上"的全部来源。

L5 内核层
distributed/device_communicators/ ＋ layers/moe/token_dispatcher/

前者是 custom_all_reduce.py、quick_all_reduce.py、 torch_symm_mem.py、triton_symm_mem_ag.py、vocab_gather.py； 后者是 deepep.py、deepep_v2.py、flashinfer.py、 mooncake.py、nixl.py、pplx.py、standard.py。 all2all 只在这一层。

07边界层：这一层的 allreduce 到底在哪儿发生

一句话答案：GLM-5.3 的 decoder layer 里，attention、MoE、dense MLP 四个模块全部用 reduce_results=False 构造 —— 它们自己不发起 all-reduce。 求和被记成数据流上的一个"欠账"，由 layer_boundary 在层与层的交界处兑现。 兑现方式有三种（就地 all-reduce / 延后 all-reduce / reduce-scatter）， 由 --boundary-reduction 与当前 batch 的行布局共同决定。

为什么能换？因为两边的输出布局需求不同：

做法每个 rank 最后拿到冗余
all-gather全部 T 行 × 完整 V（[T, V]） TP 倍冗余：每个 rank 都存了所有人的 logits
all-to-all本 rank 负责的那 1/TP 行 × 完整 V 零冗余：每行只存在一个 rank 上

触发条件写在 _can_use_tp_lm_head_all_to_all()（logits_processor.py:1179）， 而默认值由部署形态决定（overrides.py:1405）：

enable = (
    view.disaggregation_mode == "decode"
    and view.attn_dp_size > 1
    and view.tp_size == view.attn_dp_size
    and view.attn_cp_size == 1
    and not view.enable_dp_lm_head
)

即：PD 分离里的 decode 节点、且是纯 DP attention 时默认开启。 函数里还有一个必须满足的布局契约 —— logits.shape[0] == local_rows * tp_size； 不满足就退回 all-gather（batches without an equal padded row count fall back to the existing all-gather path）。

这一小节直接回答"allgather 和 all2all 到底差在哪"：数学结果不同，代价可以相同。 两者都搬 (N−1)/N·n 字节，但 all-gather 之后每个 rank 都持有全量（冗余 N 倍）， all-to-all 之后每个 rank 只持有自己那一片（无冗余）。当"全量"是下游所需时（例如 embedding 之后人人要算）， 冗余是必要成本；当"全量"没人要时（例如 sampling 之后每 rank 只处理自己的行）， 冗余就是纯粹浪费 —— 这就是这里能换的原因。

12常见误解

all2all 就是"更通用的 allgather"，因为两者字节数一样的。

两者字节数相同（都是 (N−1)/N·n），语义完全不同。

allgather 之后每个 rank 都持有全量、且内容一致，产物可以在 rank 之间互换； all2all 之后每个 rank 持有的是输入矩阵的一列，互换就是错的。 第 09 节第 5 小节那处 _tp_lm_head_all_to_all 能换来换去，是因为那里 下游只需要自己那一片，不是因为两者等价。

既然 allreduce = reduce_scatter + allgather，那拆开肯定更快。

拆开不会降低总线字节数 —— 两段加起来正好等于一次 ring allreduce。

收益只能来自别的地方：中间那一步只有 n/N 的行，norm 与残差可以做在更小的张量上； 这一段可以和下一层的计算重叠；还能被融合进一个 kernel。 --boundary-reduction 的 help 里写的是 ar uses all-reduce then token redistribution —— "token redistribution"就是拆开之后必须补的那笔开销，说明拆开是有代价的。

开了 EP / A2A 之后，MoE 层就没有 allreduce 了。

要看 reduce_results 与 moe_tp_size / moe_ep_size。

layer.py:1612 那一行是 if self.reduce_results and (self.moe_tp_size > 1 or self.moe_ep_size > 1): —— 条件成立时 combine 之后仍然会有一次 tensor_model_parallel_all_reduce。 GLM-5.3 之所以没有，是因为它在构造时传了 reduce_results=False（glm5_next.py:758）， 把这次求和交给了边界层，不是因为它开了 A2A。

给了 --ep-size 8 之后 MoE 走专家并行，那 42 次 MoE 的 allreduce 就没了。

次数不变，变的只是它落在哪个 group、叫什么名字。

moe_tp_size = tp_size // moe_ep_size // moe_dp_size （runtime_context.py:154）。--ep-size 8 把它从 8 变成 1，于是 moe/utils.py:878-885 的两个分支对调：reduce_ep 为真走 moe_expert_parallel_all_reduce，reduce_tp 为假不再走 moe_tensor_model_parallel_all_reduce —— 还是一层一次。 真要消掉它，只能开 A2A 后端，让求和并进 dispatch/combine；代价是每层多出两次变长 all2all。

--boundary-reduction 对 GLM-5.3 解析成 rs+rsv， 所以它的层尾根本不是 allreduce，是 reduce-scatter。

解析成 rs+rsv 只是允许 reduce-scatter；走不走还要看布局。

_select_exit_move() 在 produced.layout == residual 时直接 返回 ExitMove(keep_output)（boundary.py:724-726）。纯 TP8、行没被切开时 条件成立，求和因此延后到下一层入口，以 all-reduce 兑现（prepare.py:163-170）。 reduce-scatter 只在行真的被切开（SP / INPUT_SCATTERED）时才启动。 "配置允许"和"这次请求走了"是两件事。

13自测

N = 8 的 TP 组上，一次 all_reduce 搬多少字节？换成 reduce_scatter + all_gather 呢？

两者都是 2·(N−1)/N·n = 1.75n。 all_reduce 一次搬 1.75n；拆开是 0.875n + 0.875n。 总额一样，差别在于中间那一步只有 n/8 的数据量可以做别的事。

为什么 VocabParallelEmbedding 用 all_reduce，而 lm_head 之后的 logits 用 all_gather？

因为输出布局不同。embedding 的输出是 [T, H]，hidden 维没切， 每个 rank 算出来的是"只有自己词表分片那几行非零"的 partial —— 求和即真值。 logits 是 [T, V/P]，V 维被切了，每列都是独立值 —— 只能拼接。 同一份词表并行布局，两个出口、两个原语。

在 GLM-5.3 的默认 H200 配方里，MoE 层会不会出现 all2all？为什么？

不会。配方只给了 --tp-size 8，--moe-a2a-backend 取默认 none，create_moe_dispatcher() 于是返回 StandardDispatcher —— 它的 dispatch / combine 不做跨 rank 交换，MoE 在 TP 上切专家。 要出现 all2all，必须显式给 --moe-a2a-backend deepep 之类的值。

为什么开了 A2A 之后，capture_output() 里反而多了一次 all_gather？
