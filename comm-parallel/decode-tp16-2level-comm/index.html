D 端 TP16 分层通信：把 16 卡集合通信拆成「跨机配对 + 机内 8 卡」

4 机 32 卡 · 1P1D · D 端 TP16 横跨两台机 · 隐宽 6,144、每 rank 1–4 行时生效

2026-11-04集合通信AllGatherReduceScatter TP16PD 分离投机解码SLO

这一版改的不是「少搬字节」，而是把 16 卡全组集合通信的依赖链从 15 轮压到 8 轮， 并把跨机段从「2 跳串行」变成「8 对并行」。收益因此高度集中在 TPOT 一处， 而 TTFT 在短输入档上是变差的 —— 这两件事必须一起讲。

速览 部署约束 动机 方法 为什么起作用 算一算 证据链 代价与边界 常见误解 自测
术语约定：rank、AllGather、ReduceScatter、TP/DP/PP/CP、 verification round（一次投机验证轮次，产出一批被验证的候选 token）按部署侧原文保留。 机内 = 一台机 8 卡之间走机内高速互连；跨机 = 两台机之间走 IB 链路。 本页出现的「耗时」除非特别说明，都是 GPU kernel 时间（含到达不齐与依赖等待）， 与端到端 TTFT / TPOT 是两套口径。
沿用团队自己的叫法：这条路径叫「D 端分层通信」、表格行名「分层 BF16」； 机制词是「同位置 rank 跨机配对」「机内八卡集合通信」「跨机全组 AllGather／ReduceScatter」； 它要解的问题叫「decode 通信墙」「D 侧跨机 AR 墙」；基线叫「镜像原路径 / 原生路径」。 两个坑：①「分层」在团队文档里至少三个所指 —— P 端 PP 的层划分（18/21/21/18）、本条通信分层、 分级 KV 缓存 —— 本页只在第二种意义上用它；②团队 9 月做过一版「机内分层 AllReduce」，实测无收益、路线作废， 与本页这条不是同一件事（见 08 节）。

速览 · 30 秒

  • 1 · 改的是依赖链长度。原来一次 16 卡 AllGather／ReduceScatter 要 15 轮才走完， 拆成两级后是「1 轮跨机（8 对 rank 并行）+ 7 轮机内」= 8 轮。字节数几乎不变，轮数少了 47%。
  • 2 · 它是一条形状门。只在 BF16 隐宽 6,144、每 rank 1–4 行时改走两级路径，其余形状仍走镜像原路径。 这条门不是拍的：团队在这条链上的惯例是先做「形状 × 原生/自研」算子对照、只给获益形状开准入、其余保持原生。
  • 3 · 收益落在两个算子身上。D 端每验证轮的 AllGather+ReduceScatter 由 37.79 → 29.44 ms（−22.11%，2K 冷前缀）与 34.45 → 20.77 ms（−39.72%，64K/85% 共享前缀）； 占全部 kernel 时间的比例 54.11% → 46.90%、46.17% → 33.40%。
  • 4 · 端到端只动 TPOT。2,048／1,024 档 TPOT P50 21.41 → 18.67 ms，把这一格从「唯一未通过项就是它」翻成通过； 达标并发从不到 5 提到 8，该档可用总 TPS 634.76 → 1,069.27。
  • 5 · 代价同样成立。短输入档 TTFT P50 变差（首测 +65.35%、复测 +19.96%），P90 反而变好； AllReduce 完全没动；trace 里残留的长 AllGather 是早到 rank 在等，不是算子本身慢。

01先看部署：这条 D 端为什么天生跨机

一句话答案：16 卡的单组并行度超过了单机 8 卡，所以 D 端的TP16组必然横跨两台机； 而 decode 每步的批量小到每个 rank 只有 1–4 行，于是每一次集合通信都是「小消息 + 远链路」， TPOT 的瓶颈就只能落在通信的固定开销上。

角色机器 / 卡并行策略关键配置
P（prefill） 2 机 / 16 卡 TP4 × PP4 + CP4 层分配 18/21/21/18（合计 78 层）；CP 通信走 FP4；8K chunk；分级 KV 缓存
D（decode） 2 机 / 16 卡 TP16 + Attention DP4 全部 78 层；EP1（无专家并行，所以没有 all2all）；稀疏 KV 分池（GPU 主池 480K token、每请求热集 16K、逻辑槽配置上限 1.44M = 480K×3，实测逻辑池 70–74 万）；投机解码 3 步、top-k 1、draft 4

P 与 D 各占两台机。D 侧的 TP16 组 = 机 C 的 ranks 0–7 + 机 D 的 ranks 8–15， 所以 D 端每一层 MLP/MoE 的张量并行集合通信都要跨一次机界 —— 这不是偶发路径，是主路径。
而 attention 不跨机：D 端是 attn_tp4 × attn_dp4 = TP16， 4 个 DP 组各 4 个 rank，每组整体落在一台机内（每 rank 16 头；代价是 MLA KV 在组内复制 4 份）。 跨机的只有 MLP/MoE 那一段 gather。

行的来源：并发决定行数

一次验证轮次的 token 数 S = 5 × 在途并发 —— 每请求每轮验 draft 4 个位置 + 1 个 bonus，共 5 个位置。按 TP16 切开就是每 rank 的行数： S = 16–64 对应 1–4 行， 也就是在途并发大约 3–13 档。这条推导有两处用处：

  • 它把门和前沿对上了：本轮 14 组里的达标并发取值全部落在 1–12（最高一档 12）， 而 4 行的上沿是并发 12.8 —— 门与达标前沿落在同一档附近。反过来，扫参里 C16 的测点（5 行）已经掉出门外、 走的是原路径，它们也正好都是未通过的点。这是观察，不是因果，但值得继续追。
  • 它解释了为什么这条优化只对 decode 有意义：prefill 的一次 forward 动辄上千行， 同样的两级拆解在那里是带宽问题，不是轮数问题。

02动机：三个观测把矛头指向两个集合通信

一句话答案：D 端每跑一步都要跨机同步 78 层 × 2 次，而每次只搬 12–48 KB —— 这是一个纯延迟问题；恰好这一档 SLO 唯一没过的那一项就是 TPOT P50， 而 TPOT 就是「每轮时间 ÷ 每轮 token 数」，所以拿下通信的固定开销，就等于直接拿下 SLO。

观测 1 · 占比：两个算子吃掉一半以上的 kernel 时间

在同一发布镜像、同一组 P 容器上补采两份 trace（2K 冷前缀、64K／85% 共享前缀，端到端并发 5）， D 端 16 个 rank、每 rank 6 个原生验证轮次，共 64 份 rank trace。按「通信 kernel 时间之和 ÷ 全部 kernel 时间之和」算：

场景（并发 5）AllGather+ReduceScatter 占比全部通信占 GPU 活跃时间
2,048／1,024，冷前缀54.11%57.67%
65,536／1,024，85% 共享前缀46.17%51.61%

观测 2 · 形态：小到不该被带宽解释

窄端形状是「每 rank 1–4 行、宽 6,144、BF16」，一份 12–48 KB。这个量级在机内链路上是微秒级的事， 但 trace 里一次快的机内 8 卡 AllGather 实测也要 32.7–42.5 μs； 按 242 μs 的平均值算，绝大多数调用还远高于此。也就是说单次调用的耗时里，传输占不到 5%， 剩下是 kernel 启动、同步与到达不齐 —— 前者只与「调用次数」有关，后者只与「链有多长」有关。

观测 3 · SLO：只差一项，而且是 TPOT

2,048／1,024 冷前缀这一档的阈值是 TTFT P50 1,789 ms / P90 3,500 ms、TPOT P50 20.69 ms / P90 37.20 ms、ITL P95 70 ms。 发布原配方在并发 5 上：TTFT、ITL、成功率全部通过，唯一未通过项是 TPOT P50 = 21.41 ms（阈值 20.69）。

这一步把动机锁死了：既然 TPOT = 每轮时间 ÷ 每轮 token 数，而在途并发固定时 token 数由投机解码决定、 不会因为改通信而变化，那么把每轮时间里的通信固定开销削掉 8 ms，TPOT 就掉 8 ÷ 3.2 ≈ 2.5 ms —— 刚好够跨过阈值。 事后实测 21.41 → 18.67 ms（−2.74），与这条估算对得上（见 对账）。

这条链上其实已经改过一轮

「镜像原路径」不是从来就有的：更早的版本里，attn_dp < tp_size 时的 MLP 同步走的是 gloo CPU 组 —— 把每层都要做一次的跨机集合通信放到 CPU 上做。 团队先把这一跳换成了 NCCL 全组集合通信，本轮的分层通信是在那之上做的第二层。 这点很要紧：本轮对比的基线已经是「改过一轮的 NCCL 路径」，不是 CPU 组那种显而易见的坏路径； 还能再省 22%–40%，说明原路径的问题在分解方式，不在实现质量。

同族文档对这件事还有另一种量法：D 端 16 卡跨双机、每步 MoE-gather 跨 16 rank， 另一处实测把 decode 通信记到了 58% 的量级（与本节 trace 的 54.11% 同量级、不同测点）。 团队把这条结构性劣势写成一句话：对手是 TP8×PP2、TP 组全在节点内、归约走机内， 而自己是 TP16 跨双机 —— 这就是「D 侧跨机 AR 墙」。

为什么不能换别的杠杆

  • P 端已经压过一轮：CP4 的通信走 FP4、8K chunk、分级 KV 缓存 —— 本轮保留不动。
  • D 端的 attention 不发生跨机通信：attn_tp4 × attn_dp4 = TP16，4 个 DP 组各 4 rank、 每组整体落在单机内（每 rank 16 头；代价是 MLA KV 在组内复制 4 份）。这一层已经把通信压在机内了。
  • 剩下的就是 MLP／MoE 那条 TP16 路径：每层一次前向 AllGather、一次反向 ReduceScatter， 形状固定、频率最高、且正好全部跨机。可动的只剩「这次集合通信怎么分解」。
  • 降批量不在选项里：并发本身就是被测的量，降并发等于放弃吞吐。
假设 每轮时间 ≈ 计算项 + 集合通信轮数 × 单轮固定开销
可检验 若假设成立，缩小轮数应当只在通信项上体现，计算项纹丝不动； 且算子级（16 rank、1／2 行）的最大 rank 耗时应当同比例下降
若不成立 即字节是瓶颈 —— 那么两级方案的多一次 stage 边界只会更慢

03方法：把 16 卡全组集合通信拆成两级

一句话答案：给每个 rank 找一个「同位置的跨机搭档」（机 C 的第 i 张卡 ↔ 机 D 的第 i 张卡）， 把原来 15 轮的全组集合通信改成「跨机配对 1 轮 + 机内 8 卡集合通信 7 轮」， 8 对配对同时进行，跨机只走一跳。

第一层：形状门与回退

两级路径不是无条件启用的。它只在窄端形状命中时接管，其余形状照走镜像原路径。 这条门的来历有据可查：团队在这条链上做自研通信的惯例是先跑「形状 × 原生/自研」算子对照， 只给明显获益的形状开准入，未获益形状保持原生，接入后再做服务级 A/B（同族的机内 IPC AllGather 就是按这套筛的： 9 个形状里只准入 3 个，其余「保持原生」）。11.4 的「隐宽 6,144 + 1–4 行」就是这套流程筛出来的准入形状集合。 为什么要这么小心，见 04 节。

// 集合通信入口的分流 if dtype == BF16 and hidden_width == 6144 and 1 <= rows_per_rank <= 4 two_level_allgather(16 ranks, shard) // 8 轮：1 跨机 + 7 机内 two_level_reducescatter(16 ranks, partial) // 8 轮：7 机内 + 1 跨机 else original_path(16 ranks, x) // 镜像原路径，一行不改

第二层：AllGather 怎么拆

先把 16 份数据按机器分成两半：机 C 持有 s0…s7、 机 D 持有 s8…s15，同位置的两张卡 (C, i) 与 (D, i) 结成一个搭档。 AllGather 的窄端在入口 —— 每个 rank 手里只有自己那一份 —— 所以跨机放在第一段。 「8 对」指的是 8 组 rank 之间的点对点交换，不等于 8 条独立物理链路（见 04 节量 2）。

// AllGather：窄端在入口 → 跨机在前 two_level_allgather(rank = (m, i), shard): // shard: [rows_i × 6144] BF16 # stage 1 跨机，1 轮，8 对并行 peer = sendrecv(shard, partner=(m^1, i)) // 每对互搬 1 份 = 12–48 KB # stage 2 机内，7 轮，NVLink full = allgather_local(my_machine, [shard, peer]) // 8 卡 × 2 份 = 16 份 return full // [Σrows × 6144]
同一个 rank 眼里的三级快照（以搭档 i = 0 为例，16 个槽 = 16 份数据）

起点 · (D,0)

三个阶段对应三类开销：第一段只有 1 次跨机往返（8 对搭档同时做，互不阻塞）， 第二段是 7 轮机内 NVLink 累加式拼接。原路径则是 15 轮一路走到底， 其中 2 轮要跨机 —— 而且这 2 轮串在链中间，任何一轮慢，后面全部等着。

第三层：ReduceScatter 的顺序是反的

同样的两级，但顺序反过来：先在机内做 8 卡 ReduceScatter 把宽张量收窄， 再跨机配对把那 1 份部分和相加。原因是窄端位置不同： ReduceScatter 的窄端在出口（最后每个 rank 只要自己那一份），所以跨机放到最后一段。

// ReduceScatter：窄端在出口 → 跨机在后 two_level_reducescatter(rank = (m, i), partial): // partial: [Σrows × 6144] 部分和 # stage 1 机内，7 轮，NVLink mine = reducescatter_local(my_machine, partial) // 8 卡先归约，再收窄到 1 份 # stage 2 跨机，1 轮，8 对并行 peer = sendrecv(mine, partner=(m^1, i)) // 每对互搬 1 份 = 12–48 KB return mine + peer // 16 卡完整归约的 1 份

如果 ReduceScatter 也先跨机，那么第一段就要在两台机之间互搬完整的宽张量 （16–64 行，是窄端的 16 倍），机间链路立刻成为瓶颈 —— 那个方案在本轮的数据上不成立。 文档给的门是「窄端 1–4 行」而不是「宽端 16–64 行」，与这个顺序一致 （推断：文档没有逐行写出实现顺序，这里是从门的形状反推）。

AllGather 跨机配对（1 轮，8 对并行） 机内 8 卡 AllGather（7 轮，NVLink） 15 → 8 1 份（12–48 KB）

两段的分工是「跨机只搬 1 份，多跳的累加全交给 NVLink」。 注意每份的字节数在配对两端可以不同 —— 各 rank 行数本身不等（1–4 行），配对是点对点，不要求对称。

数值上发生了什么

  • AllGather 逐位一致：它只拼接、不做算术，换顺序不改变任何 bit。这一条在 16 rank 算子对照里直接验证过。
  • ReduceScatter 不再逐位一致：两级求和是 (A+B)+(C+D)， 原路径是链式 (((A+B)+C)+D)，BF16 下加法不满足结合律，结果会在最低几位上分叉。 实测最大 NRMSE 0.419%，参考值是同一组 BF16 输入以 FP64 累加。
  • 所以端到端另做验收：因为归约顺序变了，除了 SLO，还必须验完整输出比对、1M 长输入与 D 端自动回收 —— 这一步不能省，压测通过 ≠ 输出没变。

04为什么起作用：三个可算的量

一句话答案：把这次集合通信看成一个有 15 个串行环节的链条，两级拆解把环节数降到 8 个， 同时把「要跨机的环节」从 2 个（一条链上顺序出现）改成 1 个（8 对搭档同时进行）。 省下来的东西不是字节，是串行环节数与跨机环节的并发度。

量 1 · 串行轮数：15 → 8

先说口径：原路径 16 个 rank 究竟用哪种算法（ring / tree / 混合）、几轮，文档没有写 —— 这是本页最主要的推断值，下表按最常见的环形算：N−1 = 15 轮。 两级拆解是 1 + (8−1) = 8 轮。若「机内一轮」记为 1 个单位、「跨机一跳」记为 k 个单位， 则原路径 13 + 2k、两级 7 + k，比值：

rounds 原路径 = 13 + 2k　两级 = 7 + k
ratio (7 + k) / (13 + 2k)
k = 1 8 / 15 = 53.3%（−46.7%）　 k = 5 12 / 23 = 52.2%（−47.8%）　 k = 10 17 / 33 = 51.5%（−48.5%）

注意这个结果对 k 不敏感：k 从 1 变到 10，预测变化只从 −46.7% 走到 −48.5%。 原因很直白 —— 两种方案里跨机跳都只占少数环节，比值主要由「13+7」这组机内环节决定。 于是得到一个可以拿去和实测对的预测：算子级耗时应该下降 47% 左右，而不是 90%、也不是 20%。 16 rank 算子对照在 1／2 行上测到 −37% ~ −47%（中位最大 rank 耗时）—— 方向与量级都对，略低于模型上界，差额来自多出来的那一次 stage 边界（见「量 3」）。 即使原路径不是环形、15 这个数要改，结构性的那条结论也不变：轮数变少、跨机跳变少， 实测区间 −37% ~ −47% 不依赖 15 这个具体取值。

量 2 · 跨机环节的并发度：2 条链 → 8 对并行

这条更隐蔽。按 ranks 0–7 在机 C、8–15 在机 D 的放置，环上只有 2 条边跨机， 其余 13 条都在机内。也就是说：环形算法在任何时刻只用得上 2 条机间链路， 而且这 2 次跨机还被串在链的中间 —— 任何一次跨机往返变慢，后面的所有环节都要等。

两级方案的第一段是 8 对搭档各自点对点交换：8 个跨机配对同时发起，一次往返结束。 跨机环节从「链上出现两次、每次 2 条链路」变成「链上出现一次、8 个配对同时走」。

但「8 对」不等于「8 条链路」。这台部署的启动配置里只暴露了 4 条机间 HCA， 所以最可能是 2 对 rank 共享 1 条 HCA —— 物理层面的并发度提升是 2 → 4 条，不是 2 → 8。 真正的大头仍然是量 1 的轮数。（推断：HCA 条数取自同族部署的启动配置；11.4 这一轮的 D 启动命令未随文档披露。）

量 3 · 字节账：几乎没省，反而多了一次 stage

把两边的「份」数逐项列出来，就能看出这次优化不是省字节 —— 这也是它和常见的「1-stage → 2-stage AllReduce」那类改动最本质的区别（那类改动省的是 4 倍字节，见文末延伸阅读）。

06证据链：算子 → trace → 端到端 → 前沿

7.2 唯一没达标的档位与口径差异

14 组里唯一没拿到达标并发的是 16,384／1,024：逐档表里它只在 C ≤ 2 通过（C2 总 TPS 1,823.55）， 再往上 TTFT P50 就超过 1,715 ms 的阈值。汇总表把它记为「未达标」， 说明前沿判定与逐档单点通过不是同一套规则 —— 读这种表时要把两套口径分开看。

7.3 AllReduce 一行没动

两次采集里，每个 rank 在 6 个验证轮次内都记录了 48 次 AllReduce（= 8 次/轮）， 走的是原有 TP 归约路径。它是下一步的候选：既然两级拆解能把 15 轮压到 8 轮， 同样的思路对 AllReduce 是否也成立，取决于它现在的分解方式与消息形状 —— 本页不下结论。

7.4 残留的长 AllGather：是等待，不是传输

优化后 trace 里仍能看到一块 1.613 ms 的机内 AllGather（rank 0）。同一验证轮次、同一调用序号下： rank 0–3 比 rank 4–7 提前约 1.58 ms 进入，八个 rank 几乎同时结束；而 rank 4–7 的这次调用只持续 32.7–42.5 μs。 也就是说那块长条几乎全是早到 rank 在等 —— 下一个杠杆是「到达时间」（负载分配与前序跨机配对依赖）， 不是集合通信算子本身。

7.5 会话回放：收益从 +12% 缩到 +2.3%

代表点是固定长度 + 固定并发，天然偏向「通信项占比高」的形态。换成更接近线上的混合负载： 回放同一组五条多轮任务轨迹 900 秒，根并发 8，两轮都用同一发布镜像、同样的 KV 缓存策略。

7.6 三件必须一起验收的事

  • 数值：归约顺序变了，AllGather 逐位一致但 ReduceScatter 不是 —— 端到端必须验完整输出，不能只看 SLO。
  • 长输入与回收：1M 输入档与 D 端自动回收单独验收，因为两级路径改变了每层的同步点。
  • 门的覆盖范围：每 rank 行数超过 4（在途并发约 13 以上）就退回原路径。要推向更高并发，门必须先重新划。
  • CUDA graph：decode 走 CUDA graph，换集合通信实现必须在图捕获下工作。同族部署已经踩过这个坑： 某一版在 decode graph 内换实现后退化成 eager，慢约 2×，因此被默认关闭。11.4 的实现方式未披露， 但这必然是接入时的主要工程风险。

08常见误解

「分层通信省的是字节。」
不是。跨机段每对仍然只搬 1 份（12–48 KB），份数一模一样；省的是串行轮数（15 → 8） 与跨机环节的并发度（2 条链 → 8 对并行）。真要省字节，两级拆解反而让机内份数从 13 涨到 14。
「只要是「分层」，就一定会更快。」
团队自己的反例就摆在那儿。9 月他们试过一版机内分层 AllReduce（把跨 socket 的流量拆开）， 实测 PIX 与 SYS 带宽无差异、无收益，路线作废。所以本轮的收益来源不是「分层」这个形式， 而是「把跨机环节从多跳压成 1 跳」—— 机内分层没有可省的跨机跳，自然没有收益。 这也是本页坚持说「两级」而不是「hierarchical」的原因：同名不同命。
「8 对 rank 配对 = 8 条独立链路，跨机带宽直接 ×8。」
只有 4 条机间 HCA。8 个配对要共享这 4 条，最可能是 2 对共用 1 条。 物理链路的并发提升是 2 → 4 条，不是一个数量级；所以这一节的收益不能记在「带宽变宽」上， 要记在「环节数变少」上。
「这是通信库按消息大小自动选的算法。」
不是自动的。文档写得很清楚：一组形状（隐宽 6,144、每 rank 1–4 行）走新的两级路径， 其余形状走镜像原路径 —— 这是一条应用侧显式的形状门，不是库内部启发式。
「改了通信，所有指标都会一起变好。」
不会。2,048／1,024 档 TTFT P50 变差 +65%（首测），P90 变好 7%； 900 秒会话回放里 TTFT P50 更是 +31%。收益只落在 TPOT／TPS 这一侧，而且恰好是那一格唯一的未通过项。
「trace 里那块 1.6 ms 的 AllGather 说明这条路径还是慢。」
那块是等待。同一调用序号下 rank 4–7 只花 32.7–42.5 μs，rank 0–3 早到 1.58 ms 后干等。 kernel 时间包含到达不齐与依赖等待 —— 不把「传输」和「等」分开，就会把偏差读成算子性能。
「通信占比降了 7 个百分点，所以通信快了 7%。」
占率的分母也在变。54.11% → 46.90% 的同时，总 kernel 时间从 68.37 降到 61.30 ms； 通信项自身是 37.79 → 29.44 ms（−22.11%）。比率永远要配绝对量一起读。

09自测

1. 为什么 ReduceScatter 的两级顺序和 AllGather 相反？反了会怎样？
因为窄端的位置不同：AllGather 的窄端在入口（每 rank 只有自己那一份），所以跨机放在第一段； ReduceScatter 的窄端在出口（最后每人只要自己那一份），所以跨机放在最后一段。 反过来做，ReduceScatter 的第一段就要在两台机之间互搬完整的宽张量（16–64 行，是窄端的 16 倍）， 机间带宽立刻成为瓶颈 —— 这也解释了为什么文档给的门是「窄端 1–4 行」。
2. 门从「1–4 行」放宽到「1–32 行」，最先坏的是哪一项？
最先坏的是跨机段字节：每对要搬 32 × 6,144 × 2 B = 384 KB， 是原来的 8 倍，而跨机一跳的带宽项开始压过延迟项 —— 此时「少轮数」省下的固定开销不再占主导， 多出来的 stage 边界变成纯成本。第二个坏的是机内段：8 卡集合通信每轮要搬 2 份，带宽项同样抬升。
3. 为什么 AllGather 能逐位一致，ReduceScatter 不能？
AllGather 只做拼接，不做算术，换顺序只是换拼接次序，bit 不变。 ReduceScatter 要做求和，两级是 (A+B)+(C+D)、原路径是链式 (((A+B)+C)+D)，而 BF16 加法不满足结合律，中间结果每次舍入的位置不同 —— 实测最大 NRMSE 0.419%。
4. 「每轮 156 次、单次平均 242 μs、最快 33 μs」这三个数放在一起说明了什么？
说明单次调用的时间几乎全不是传输：12–48 KB 的搬运是微秒级，33 μs 已经是「快」的下限， 而平均 242 μs 是它 7 倍 —— 中间那部分只能是启动、同步与等待。所以在这一档上， 改轮数（把等待点变少）比改带宽（把传输变快）有效得多。
5. 并发从 8 提到 32，这条优化还能吃到收益吗？
按本页的推导，先掉出门外：32 并发 × 每请求 5 个候选位置（draft 4 + bonus 1）= 160 token， 除以 16 卡 = 10 行 > 4，直接走镜像原路径。即使把门放宽，收益也会被跨机段的带宽项吃掉。 这也提示一件更要紧的事：门是随并发档位画的，要推向更高并发，得先重划门。
