P 端 CP4 的量化通信三件套：MoE 先量化再 AllGather、quant-RS、CP KV 的 FP8 gather

2026-11-16PD 分离Context Parallel量化通信 AllGatherReduceScatterFP4 / FP8Prefill

P 端（prefill）在 CP4 下每层要过五处跨卡搬运，它们的共同点是：都在搬残差流或 KV，都可以用精度换线上字节。三个落点各有各的门限 —— 一个门是「gather 之前就压成 4 bit」，一个门是「1024 行以下必须回退」，还有一个根本不需要转换（KV 本来就是 FP8 的）。这一页把三个落点、它们的守卫，以及「所有 rank 必须一致」这条最容易在多机调试时踩的硬约束讲清楚。

术语约定：rank、group、wire、payload、block、chunk、gateway 保留英文以便和源码 / 日志对齐；P = prefill 角色，D = decode 角色。本文只讲四机 PD 线的 P 端（tp=4 / pp=4 / cp=4 / ep=4、权重是 4 bit 格式）。单机那条线（tp=1 的 CP8 prefill、BF16→FP8）是另一篇，两边的 flag、门限、收益都不能互抄。

01速览

TL;DR

  • 三个落点，一条原则：在 gather 之前把精度降下来。 先量化再搬，比「搬完再量化」少一趟读写；KV 那条更彻底 —— 它本来就是 FP8 存的，gather 时不需要转换。
  • 门限决定它是否生效，而且门限各不相同。 MoE 的 FP4 路要求登记的拓扑与权重格式组合（当前是 TP4/CP4 + EP1/EP4）；RS 的 FP8 路要求行数 ≥ 1024；KV 路要求 EP4 / 8192 行 / eager / 656 B 的 KV 布局同时对得上。
  • 最硬的约束不是性能，是一致性。 集合通信的形状由开关决定：一个 group 里必须同开同关，否则不是变慢，是形状不匹配。
  • 量级：组合之后 P 端 16K/384 冷前缀的 Prefill TPS +29.5%、64K +27.4%，请求延迟 −21.5～−22.8%。 单看 quant-RS 一项，一次 prefill_forward 从 8.40 s 到 8.05 s。
  • 证据强度不一样。 FP4/RS 三件套里 MoE 那两项给了强证据（有激活回执 + 多份 GPU probe + 19 档 SLO 全过），attention 边界的 qcomm 只给中证据 —— 因为统一镜像的清单没有覆盖所有调用点文件，逐字节生效证据弱于历史 overlay。

02五处搬运，四类机制

「三件套」这个名字容易让人以为是三个开关。实际上一层里有五处跨卡搬运，归成四类机制 —— 前三类是这一页的主线（也就是常说的「三件套」），第四类是同一思路在 attention 层边界上的版本：

① attention 层边界

hidden 的 AllGather / ReduceScatter，按行 6336 B 的 FP8+scale 走

qcomm · cp_ag / cp_rs
② attention 内 KV

gather 的 key 本来就是 FP8 NoPE + scale，RoPE 保 BF16

KV FP8 gather · 零转换
③ MoE 之前

把 MoE 输入压成 4 bit 再 AllGather

CP-FP4 AllGather
④ MoE 之后

ReduceScatter 走 FP8 wire，本地 FP32 累加

quant-RS · ≥1024 行

它们不是同一件事的四个副本：①和③④都在改 wire 上的位宽，但①搬的是 attention 层边界的 hidden，③搬的是 MoE 的输入（并且多一步「先压成 4 bit」），④改的是归约的位置；②根本不做转换，只是把已有的 FP8 字节直接拼起来。理解这一点，后面每个门限为什么长那样就都顺了。

03① MoE 之前：先压成 4 bit 再 AllGather

MoE 的输入在 CP4 下要先收齐（本卡那份专家权重必须见过全部 token），这次 AllGather 的载荷就是 MoE 的输入。既然反正要搬一遍，那就先把它压成 4 bit 再搬 —— 线上字节直接掉到 BF16 的四分之一量级，剩下的开销是随数据带的 scale。

// 形状差别（伪代码）
// 改之前：把 BF16 的 MoE 输入直接 gather 出去
gathered = all_gather(moe_input_bf16)

// 改之后：先量化成 4 bit（连带 scale），wire 上只有 4 bit
q, s     = quantize_to_fp4(moe_input)
gathered = all_gather(q, s)          // 收到后在本地反量化
moe_out  = moe(gathered)
为什么这条要求 moe_tp 是登记过的值。 4 bit 那条路绑定的是「权重本来就是 4 bit 格式 + 对应的 MoE 内核」，两者必须成对。这也是最容易踩的坑：开关存在 ≠ 生效，比如当前 TP4 的 P 端，某个 4 bit prefill 路径的内核要求 moe_tp_size == 8，于是它虽然被设成 1，实际一次都没跑 —— 这类空转项要单独记成一份清单 —— 因为「env 设了」和「路径跑了」是两件事，后者只能靠激活回执证明。

04② MoE 之后：quant-RS 与那道 1024 行的门

MoE 算完要把结果散回各卡自己的 token。这一步的改法比「压精度」更深一层：把归约从 wire 里搬出来 —— 线上只跑各 rank 的 FP8 partial，收到之后在本地用 FP32 累加。

收益是两层：线上 1 字节/元素（而不是 2），以及误差只来自「量化成 FP8」这一次、不来自「用 FP8 反复加」。代价同样明确：数值路径变了。

1024 行这道门不是保守，是踩出来的。 实测里这条线一旦在小批量上强行开，2K / 16K 的并发档位会掉档 —— 量化的固定成本在消息很小时盖过了省下的带宽。所以门限必须留在那儿，别因为「大 batch 有效」就在通用配置里打开。

05③ KV：一次不需要转换的 gather

KV 这条和上面两条性质不同：它不做任何精度转换。

这套部署的 KV 本来就是「FP8 的 NoPE 分量 + 每块一个 scale + BF16 的 RoPE 分量」交织存放的（每 key 每层 656 B 量级）。CP4 下注意力层边界要把 KV 收齐，如果按 BF16 收，就得先把已有的 FP8 反量化、搬完再量化 —— 一来一回全是白费的精度损失和带宽。正确做法是直接把已有的 FP8 字节拼起来，RoPE 段保持 BF16：

// 改之前：反量化成 BF16 传过去，再量化回来
buf_bf16 = dequant(kv_fp8, kv_scale, rope_bf16)
gathered = all_gather(buf_bf16)          // 2x 字节 + 两次转换

// 改之后：按原布局直接拼，RoPE 段单独走 BF16
gathered = all_gather_concat(kv_nope_fp8, kv_scale, rope_bf16)

这条的守卫最细：EP4、8192 行、eager 模式、656 B 的 KV 布局 —— 四个条件要同时对得上才走。换句话说，它是「按布局定制的通道」，不是一个通用开关。

为什么同一个家族里，一个给强证据、一个只给中证据。 这不是谨不谨慎的问题，是能不能核到。cp_ag/cp_rs 的量化通道分散在多个调用点文件里，而当前统一镜像的清单没有覆盖全部这些文件，所以「逐字节真的走了新通道」这件事只能靠历史 overlay 的证据推断，不能宣称在当前镜像上重新验过。审计里这种差别要保留，别为了好看统一升级成「强」。

08数值代价：rel-L2 2–3%

  • qcomm 不是无损的。 attention 边界这条通道的典型相对 L2 误差在 2–3% 量级。它不是「足够小所以可以忽略」，而是「要单独做质量门」。同家族的 attention 投影量化、shared expert 量化都要跟着做门。
  • FP4 与 FP8 改的是数值路径，不是打包方式。 累加顺序也变了（本地 FP32 vs wire 内累加）。任何逐位对比的验收都会失败，这是预期内的。
  • P 端专属。 这些开关在 D 端要么不生效、要么直接判负：D 侧的同类量化通信（dp_ag / dp_rs）在 decode CUDA graph 内退化成 eager，16K 的 TPOT P95 从 21.1 ms 变成 46.6 ms。所以 D 端保持关闭是正确配置，不是「还没来得及开」。
  • 不能外推到别的拓扑。 收益绑定已测的四机与那条 gateway 链路；换机器、换互联、换网关都要重测。

09动手算：每行 6336 B 是怎么来的

6336 这个数不是拍出来的：它等于「hidden 个 FP8 字节」加上「按 block 块度每块 4 字节的 FP32 scale」。反过来解，当 hidden = 6144、block = 128 时正好是 6144 + 48×4 = 6336 —— 这是唯一能让三个数都是整数的组合，所以可以合理反推这条通道用的是 128 列一个 scale。

10常见误解

①「三个开关都是同一个东西的三个副本」

不是。①搬 attention 边界的 hidden、②改归约位置、③根本不做转换（KV 本来就是 FP8）。它们的门限、失败模式、证据强度都不一样，改一个不影响另一个。

②「大 batch 有效，那通用配置里就打开」

错。quant-RS 的 1024 行门是踩出来的：小批量上强行开会掉档（2K / 16K 并发档位实测掉）。门限是配置的一部分，不是可以调的保守值。

③「既然 P 端能省，D 端照搬就行」

不行。D 侧的同类量化通信在 decode CUDA graph 内退化成 eager，16K 的 TPOT P95 从 21.1 ms 涨到 46.6 ms —— 已经是判负项。D 端保持关闭是正确配置。

④「开了 env 就等于生效」

不等于。4 bit 的那条 prefill 路径要求 moe_tp_size == 8 一类条件，当前 TP4 下它被设成开却一次都不跑 —— 这类「env 还在但路径不生效」的空转项，正是要单独记清单的原因。

11自测

为什么 MoE 输入要「先量化再 AllGather」，而不是「先 Gather 再量化」？

因为 gather 搬的就是这份数据。先量化，线上就只有 4 bit；先 gather 再量化，线上仍是 BF16，省不到任何带宽，反而多一趟读写。

quant-RS 的 1024 行门为什么必须留？

量化的固定成本（转换 + 出 scale + 额外的一次本地归约）与消息大小基本无关。行数少时消息很小，省下的带宽盖不过这笔固定开销；实测里小批量强行开会让 2K / 16K 并发档位掉档。

KV gather 为什么不需要「转换」？

因为 KV 本来就以 FP8 的 NoPE + scale + BF16 的 RoPE 交织存着。按原布局把字节拼起来即可，反量化再量化只会白丢精度、白搬带宽。

四个落点里，哪一个不满足条件时是「失败」而不是「回退」？

attention 边界的 qcomm。它的开关决定集合通信的形状，一个 group 里配置不一致就会形状不匹配直接失败；其余三个不满足时都是回退到保守路径（变慢但正确）。

为什么同一个家族里，attention 边界那条只给中证据？

因为它分散在多个调用点文件里，而当前统一镜像的清单没有覆盖全部这些文件 —— 「逐字节真的走新通道」只能靠历史 overlay 推断，不能在当前镜像上宣称重新验过。证据强度取决于能不能核，不取决于重不重要。

这套东西能直接搬到别的机器上用吗？

不能。收益绑定已测的四机拓扑与 gateway 链路；换机器、换互联、换网关都要重测。而且它需要「权重 4 bit + 对应内核 + 登记的并行组合」同时成立。
