CP 边界的 FP8 通信：AllGather 先量化、ReduceScatter 把求和移出 wire

2026-11-16Context Parallel量化通信AllGather ReduceScatterFP8PCIePrefill

CP 边界每层有两次大块搬运：MoE 之前把 token 收齐（AllGather），MoE 之后把结果散回去（ReduceScatter）。这两次搬的都是残差流，BF16，每个 MoE 层都来一遍，而单机 PCIe 的带宽就那么点。把精度换成线上字节：AG 在 gather 之前先量化，RS 干脆把「求和」这件事从线上搬到本地 FP32 里做 —— 线上字节约减一半。

术语约定：并行维度沿用 SGLang flag 的写法（tp_size / attn_cp_size）；rank、group、wire、payload、block、chunk 保留英文——它们要在源码、日志和命令行里 round-trip。本文只讲单机 8 卡、tp=1 的 CP8 prefill 形态；四机 PD 线 P 端的同类做法（多一层 FP4 预量化）在另一篇里，两条线的配置不能互抄。

01速览

TL;DR

  • 省的是线上字节，不是通信次数。 CP 边界的两次集合通信一次都没少，改的是每次搬多少 —— BF16 2 字节/元素变成 FP8 1 字节/元素，外加每 block 一个 FP32 scale。
  • RS 的改动比 AG 更本质。 AG 只是「先压再搬」；RS 是把归约的位置从 wire 里挪到本地 FP32 累加里 —— 线上只跑各 rank 的 partial，收到之后自己加。
  • 量级是个位数，不是减半。 线上字节约 50.2%，但通信只占 prefill 墙钟的一部分：实测端到端 +8.39%（16K→512）与 +9.93%（长输入冷前缀），RS 在此之上再 +8.55% / +10.48%。
  • 两道门决定它会不会生效。 行数少于 256 一律回退 BF16（固定量化成本吃掉收益）；block 必须是能整除 4096 的 2 的幂。另有一条反向门：确定性推理关掉 RS 新路径。
  • 不是逐位无损，且当前镜像没有重做单变量消融。 数值路径变了，质量验收仍挂着。引用这些数字时必须标「历史同方案」。

02这两次通信从哪来

先把位置说清楚，否则后面所有字节数都没法对账。

TP8 prefill 里，每张卡只有 8 个注意力头，所以注意力输出必须跨卡求和 —— 每层一次 AllReduce。切到 CP8 之后，每个 token 的全部注意力头都在同一张卡上，那次 AllReduce 直接消失，token 的输出在卡内就是完整的。

但 MoE 切的是权重，不是 token：本卡负责的那份专家权重，必须见过这一批里的所有 token 才有意义。于是重心从「按头求和」换成了「按 token 收齐 / 散回」：

① 注意力输出

CP8 下 token 在卡内完整，无跨卡求和

省掉一次 AllReduce
② MoE 之前

把 8 张卡各 1024 行的 token 收齐成 8192 行

新增一次 AllGather
③ MoE 之后

把全量行的结果 散回各卡自己的 token

新增一次 ReduceScatter
④ 残差回到本卡

下一层从本卡的 1024 行接着算

回到 CP 布局

这两次搬的东西一样：残差流（hidden_states），宽度是 hidden，行数是全量 chunk 的行数，dtype 是 BF16，每个 MoE 层各来一遍 —— 层数越多，这两笔账越沉。用一台 8 卡 PCIe 单机的 GLM 系列 MoE 部署实测，切换前 TP8 的通信是 349.51 ms、CP8 重构后是 275.71 ms —— 注意变少了，因为消失的那次 AllReduce 比新增的 AG+RS 更贵；但剩下的 275.71 ms 里，这两次搬运就是最大的两块。

为什么这两块偏偏是 PCIe 的痛处：它们不是小消息。一个 8192 行的 chunk、hidden 数千，单次就是百 MB 量级（8192 × 6144 × 2 B ≈ 100 MB），正好落在「带宽决定一切」的区间里。而 PCIe 单机没有 NVLink，8 张卡还分处两个四卡组、跨组要过主机桥。

03先算搬多少字节

AllGather 和 ReduceScatter 在「每 rank 收多少」这件事上是同一个数：

// 一次集合通信，每 rank 收到的字节（N = 组内 rank 数）
每 rank 收 = (N − 1) / N × P        // P = 这次通信的载荷
P         = rows × hidden × bytes_per_elem

// BF16：bytes_per_elem = 2
// FP8 + scale：bytes_per_elem = 1，另加每个 block 4 字节的 FP32 scale

所以「省多少」只有两个乘数：元素位宽和scale 的块度。按 block = 1024 列算，scale 的开销是 4 / 1024 = 0.39% 的载荷，几乎可以忽略：

BF16 线上字节（基准）100%
2 字节 / 元素
FP8 payload + FP32 scale（block = 1024）50.2%
FP8 payload 50%
省下 49.6%
FP8 payload FP32 scale（每 1024 列一个，占 0.39%） 省下的字节 BF16 原始

这张条是按 block=1024 推出来的算术，不是实测读数。block 越小 scale 开销越大：block=128 时是 3.1%，仍然值得做；block=32 时升到 12.5%，就该重新算这笔账了（计算器里可以直接拖）。

别把这个 50% 当端到端收益。 线上字节减半 ≠ 墙钟减半：通信只占 prefill 时间的一部分，而且量化本身要花算力。第 06 节的实测是个位数。

04AG：量化发生在读地址上

AllGather 改起来直白：在 gather 之前先把本地那份压成 FP8，wire 上就只有 FP8 payload 和每 block 的 FP32 scale。

关键在于「先」字落在哪。如果实现是 把 BF16 复制进一块缓冲区 → 再扫一遍做量化 → 再 gather，那多出来的读写会把省下的带宽又吃回去。这里的做法是把量化折进 gather 的读地址：内核按目标布局去读本地 BF16 源数据时顺手转换，写进 wire 缓冲区的就已经是 FP8 —— 元素只被读一次、写一次，没有中间那一趟。

// 形状差别（伪代码，不是源码）
// 改之前：gather 直接搬 BF16
wire[r] = local_bf16[shard_indices]

// 改之后：读的时候顺手量化，并按 block 吐出 scale
wire[r], scale[r] = quantize_on_read(local_bf16, shard_indices, block)
gather(wire, scale)        // wire 上只有 1 字节/元素

为什么这条对 prefill 特别值：prefill 的行数是 chunk 决定的（一个满 chunk 8192 行），载荷大、量化摊得薄；而 decode 的载荷只有几 MB 量级，固定成本吃不住 —— 这也是为什么同一族的量化思路在 decode 上普遍不划算。

05RS：把求和移出 wire

ReduceScatter 的改法不一样，也是这一页真正值得记的一点。

常规的 reduce-scatter，求和发生在通信内部：数据在 ring 上转，每跳把收到的段累加上去，最后每个 rank 手上是一段「已经加好的」BF16。这么做省事，但有两个后果：

  • 线上搬的每一段都必须保持足够精度 —— 因为它已经是求和结果的一部分，误差会被后续累加放大；
  • 累加发生在 wire 上，你无法选择用什么精度做加法。

这里的做法是把这两件事拆开：线上只搬各 rank 的 FP8 partial，不做任何加法；收到之后在本地用 FP32 累加。

常规 RS（BF16）

ring 上每跳累加，wire 上搬的是「部分和」

2 字节/元素 · 累加在 wire 里
本地求和 RS（FP8）

wire 上只搬各 rank 的 partial，落盘后在本地 FP32 相加

1 字节/元素 · 累加在 FP32 里

这样做的收益有两层，而且只有第一层是带宽：

层次改了什么量级
字节wire 上每元素 2 字节 → 1 字节，另加 0.39% 的 scale≈ 50.2%
精度预算误差只来自「量化成 FP8」这一次，不来自「用 FP8 反复加」；加法的舍入留在 FP32误差不随 N 放大
但这不等于「无损」。 每个加数本身已经带了 FP8 的量化误差（e4m3 只有 3 位尾数，相对误差 6% 量级）；FP32 累加只是保证误差不叠加，不会把已经丢掉的信息找回来。所以它仍然是「改变数值路径」，仍然需要质量门。

AG 与 RS 各自独立开关（SGLANG_CP_AG_FP8 / SGLANG_CP_RS_FP8），但在同一个 group 里必须全体一致：集合通信的形状取决于它，一半开一半不开会直接形状不匹配。

08数值代价与不可用的场合

  • 不是逐位无损。 AG 在 gather 前把 BF16 压成 FP8，RS 在发送前压成 FP8 —— 两处都改变了数值路径。下游任何对数值敏感的验收（GSM8K、质量对比）都要重新做。
  • 确定性推理会关掉 RS 新路径。 需要可复现结果时，RS 退回常规路径；AG 不受这条影响。
  • 小批量场景不划算。 行数掉到 256 以下就回退，别指望在 decode 或小 chunk 上看到收益。
  • 换机器要重验。 收益正比于「这次通信在墙钟里的占比」；换了网络（NVLink、跨机 IB）之后占比会变，收益可能消失甚至转负。

10常见误解

①「FP8 通信 = 通信时间减半」

错。减半的是字节。墙钟取决于这次通信在关键路径上暴露了多少；实测端到端是个位数。而且量化本身要花算力，行数少的时候这笔账会反过来。

②「它和 decode 端拆分轮数是同一件事」

不是，是两条正交的轴。TP16 分层通信那篇省的是串行轮数（15 → 8），页内明确写了「字节几乎没省，反而多了一次 stage」；这一页省的是字节，轮数一次没动。两条改动的收益不能相乘，也不能互相替代。

③「AG 和 RS 的收益可以相加」

不能。RS 的两档是在 AG 已经打开的基础上测的增量。真要报一个总数，只能报「AG + RS 全开 vs 都不开」的那一组对照。

④「它是无损的优化」

不是。它改的是数值路径。唯一能说的是：误差只来自一次量化，不会因为 8 个 partial 相加而放大 —— 但已经丢掉的精度找不回来。

11自测

为什么 CP 边界是 AllGather + ReduceScatter，而不是一次 AllReduce？

因为 CP 切的是 token（按位置交错分片），每个 token 的注意力输出在卡内就是完整的，不需要跨卡求和；真正需要跨卡的是 MoE —— 专家按权重切，本卡那份权重必须见过全部 token。所以是「收齐 token → 算 MoE → 把结果散回去」，正好是 AG + RS。

AG 说「量化折进读地址」，省掉的是哪一步？

省掉的是「先把 BF16 复制进一块中转缓冲区、再整体扫一遍做量化」这一趟。折进去之后元素只被读一次、写一次，写进 wire 的就已经是 FP8。

RS 把求和移出 wire，改的到底是什么？

把「加法」从通信内部（ring 上逐跳累加）挪到接收端本地（FP32 累加）。线上只搬各 rank 的 FP8 partial。收益是字节减半 + 误差不随 N 叠加；代价是数值路径改变、确定性推理要关掉新路径。

为什么 block 必须是能整除 4096 的 2 的幂？

实现按 4096 列切 tile，block 要能整除它才不会出现跨 tile 的最后一块。所以合法取值是 128 / 256 / 512 / 1024 / 2048 / 4096，3000 这类不是 2 的幂的数不合法。

线上字节减半，为什么端到端只有 8–10 个百分点？

因为通信只占 prefill 墙钟的一部分（另一部分是 GEMM 与按 token 重复的算子），而且量化本身要花算力、要出 scale。8–10 个百分点是「字节减半」经过占比折算之后的结果。

什么情况下这套东西不该开？

行数长期低于 256（小 chunk、decode）、需要确定性推理（RS 那条）、以及换了更高带宽的互联之后通信占比大幅下降的场景。换机器要重新测，不能沿用这台机器的结论。
