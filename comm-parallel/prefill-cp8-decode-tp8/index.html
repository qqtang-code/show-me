Prefill CP8 / Decode TP8：为什么 CP 能拿到收益

从 SGLang 的 CP 策略实现出发，拆开 TP8 prefill 里被重复计算的那部分，以及 CP8 用哪次通信把它换掉

TL;DR

  • CP 省的不是注意力 FLOPs。TP8 每卡是 8192 行 × 8 头，CP8 每卡是 1024 行 × 64 头 —— 每卡 query×head 完全相同（都是 65,536）。注意力那 46 ms 的收益来自形状（64 个真头 vs 补到 64 的 8 个头），不是来自算得少。
  • 真正的收益来自「每卡行数」。凡是按 token 重复、TP 切不动的算子 —— 超连接 mHC、LayerNorm、量化、indexer —— 在 CP8 下每卡只做 1/8 的行。hc_combine 的 kernel 网格是 (m, …)，m 就是行数：实测 mHC 136.77 → 13.06 ms，与行数 8 倍差同比例。
  • 通信不是变多，是换了形态。TP8 每层必须有注意力输出的 AllReduce（每卡只有 8 个头，必须跨卡求和）；CP8 每个 token 的输出在卡内就是完整的，那次 AllReduce 消失，只在 MoE 前换成一次 AllGather、MoE 后一次 ReduceScatter。实测通信 349.51 → 275.71 ms。
  • 按权重算的部分一点没变。MoE GEMM 55.14 → 54.98 ms：MoE 前把 token 收齐（deepseek_v4.py 里的 dsa_cp_gather_hidden_states），每卡仍然把全部 8192 行喂进自己那份专家。CP 重排的是 per-token 工作，动不了 per-weight 工作。
  • 代价是显存和一次运行时切片。CP 模式下 tp=1，注意力权重整份复制到每卡（静态显存比例提到 0.74），decode 侧靠 cp_decode_attn_tp.py 现场切权重 + 重算 MXFP8 swizzled scale 换回 TP8 行为。
  • 换来的数字：相对切换前一步，C8 输入吞吐 +27.1%、TTFT −34.5%、TPOT −15.8%；C32 输入 +37.9%、TTFT −35.5%、TPOT −24.3%（相对本轮起点分别为 +56.85% / +70.03%）。

01TP8 prefill 里谁在被重复算

TP 切的是头和隐藏维，切不掉 token 维。于是每一层里「逐 token 但不必分片」的算子，在 8 张卡上各算了一遍同一批 8192 行；只有真正的矩阵乘、以及按头切分的注意力，才享受到了分片。

Prefill TP88192-token chunk · 每卡处理同一批全部 token，只算本卡的 8 个头
8192 行 · 8 头8192 行 · 8 头8192 行 · 8 头8192 行 · 8 头 8192 行 · 8 头8192 行 · 8 头8192 行 · 8 头8192 行 · 8 头
Prefill CP88192-token chunk · 按位置交错分片，每卡 1024 行、全部 64 个头
1024 行 · 64 头1024 行 · 64 头1024 行 · 64 头1024 行 · 64 头 1024 行 · 64 头1024 行 · 64 头1024 行 · 64 头1024 行 · 64 头

两种布局的总 query×head 都是 8192 × 64 = 524,288。差别在于：TP8 每卡把 20480 宽的超连接输入（4 路 × 5120）读 8192 遍，CP8 只读 1024 遍。

这也是本轮优化清单里那条判断的由来：

「TP8 Prefill 中，每卡处理同一批 8192 个 token 的残差流，并计算本卡的 8 个注意力头。mHC、输入投影及多次 hidden-state AllReduce 占据较多时间。单遍 mHC 与注意力均可随输入序列分片，MoE 继续使用已有的 TP2×EP4。」

02源码：CP 切在哪、怎么切

2.1 入口是「按行交错」，不是按头

--cp-strategy interleave 对应 InterleaveCPStrategy。它做的是取模取行：第 r 张卡拿 r, r+8, r+16… 这些行，注意力头一个不切。

# srt/layers/cp/interleave.py · _interleave_shard
if tokens % cp_size != 0:
    indices = torch.arange(cp_rank, tokens, cp_size, device=input_.device)
    return input_[indices]
return input_.view(-1, cp_size, *input_.shape[1:])[:, cp_rank].contiguous()

分片发生在模型入口，由 split_before_forward 统一处理 —— input_ids、positions、input_embeds 都按同一套索引切：

# srt/layers/cp/base.py · ContextParallelStrategy.split_before_forward
if input_ids is not None:
    forward_batch.cp_v2_input_ids = self.shard_hidden_states(input_ids, forward_batch)
forward_batch.positions = self.shard_position_ids(positions, forward_batch)

shard_position_ids 切的是「每个 token 的 KV-cache 槽位」：所以每张卡只为自己那 1024 行写 KV，KV 池没有重复写。

2.2 通信形态变了，不是变多了

TP 版和 CP 版的 communicator 在同一个位置做同一件事，但一个要 AllReduce、一个不要：

# TP：srt/layers/communicator.py · _gather_hidden_states_and_residual
if context.attn_tp_size > 1:
    hidden_states = attention_tensor_model_parallel_all_reduce(hidden_states)
hidden_states, residual = layernorm(hidden_states, residual)

# CP：srt/layers/communicator_dsa_cp.py · 同名方法
if hidden_states.shape[0] != 0:
    hidden_states, residual = layernorm(hidden_states, residual)
if dsa_use_prefill_cp(forward_batch) or mla_use_prefill_cp(forward_batch):
    hidden_states = dsa_cp_gather_hidden_states(hidden_states)   # 没有 all_reduce

原因很直白：TP8 里每个 token 只有 1/8 个头在本卡算出来，输出必须跨卡求和才完整；CP8 里每个 token 的 64 个头都在拥有它的那张卡上算完，不需要求和。层内这样收口之后，MoE 前把行收齐、MoE 后把结果散射回去即可：

# srt/layers/communicator_dsa_cp.py
# After using cp, the communication mode of this part changes.
# The three parts of prepare_attn, prepare_mlp, and postprocess_layer
# no longer require additional communication for reduce, scatter, etc.

def dsa_cp_reduce_scatter_hidden_states(hidden_states):
    hidden_states = hidden_states.tensor_split(cp_size)[cp_rank]   # 先切好目标槽位
    attn_cp_reduce_scatter_tensor(hidden_states, input_hidden_states)
    return hidden_states

ReduceScatter 的目标切片提前 tensor_split 好了，所以归约的结果直接落在本卡那一行区间里，顺带把残差加也吃掉一次。

2.3 MoE 前把 token 收齐 —— 这决定了 MoE 不受益

# srt/models/deepseek_v4.py · forward（CP 分支）
_use_cp = self.dsa_enable_prefill_cp and dsa_use_prefill_cp(forward_batch)
...
if _use_cp:
    moe_a2a_backend = get_moe_a2a_backend()
    if moe_a2a_backend.is_none():
        hidden_states = dsa_cp_gather_hidden_states(hidden_states)

专家是「按权重切、不按 token 切」的：本卡负责的那份专家权重，必须见过请求里的所有 token 才有意义。所以 MoE 之前一定要回到全量 8192 行，每卡的专家 GEMM 工作量与 TP8 时一模一样 —— 实测 55.14 → 54.98 ms，差 0.3%，也就是没变。CP 只重排 per-token 工作，动不了 per-weight 工作。

2.4 为什么这样切是无损的

Sparse MLA 要先用 indexer 在全上下文里选 top-k 候选。如果每张卡只在自己那 1024 行上打分，选出来的候选就和 TP8 不是同一批了。所以 indexer 的 key 必须收齐再用：

# srt/layers/attention/dsa/dsa_indexer.py · _maybe_rotate 之后
# Gather the full key on alt_stream so the CP all-gather overlaps
# with the query rotate above on the current stream.
if is_cp_v2_active(forward_batch):
    key = get_cp_strategy().materialize_full_indexer_k_cache(key, forward_batch)

注意这个 gather 是挂在另一条 stream 上、和 query 的 rope 旋转重叠跑的 —— 通信被算力盖住，而不是排在关键路径上。注意力本体需要的 KV 同理，按 MLA 的 latent 收（materialize_full_mla_kv，每 token 只有 kv_lora_rank + qk_rope = 512 + 64 = 576 个元素），不是按头收 64 × head_dim。

代价换的是同一套算术、不同的分布：候选集一致、注意力对每个 token 仍看全上下文，所以完整模型 25 项质量检查通过。

2.5 切到 CP8 之后，decode 侧要补一张票

CP 模式下 tp_size=1 —— 注意力权重不切了，每卡一份完整副本。decode 不需要行分片，于是要现场把这副本切回 TP8 的样子用：

# srt/layers/cp/cp_decode_attn_tp.py
"""CP Decode Attention TP context.
When CP sets tp_size=1 (repeat weights), decode can partition attention
weights across CP ranks matching normal TP behavior."""

self.use_decode_attn_tp = not is_cp_v2_active(forward_batch) and not dsa_use_prefill_cp(forward_batch)
...
radix_attn.tp_q_head_num = orig_tp_q_head_num // self.decode_tp_size   # 64 → 8 头

切权重的同时还得重算量化 scale：CUTLASS 用的 weight_scale_inv_swizzled 布局依赖矩阵形状，切片后必须重新生成并按 rank 缓存（cp_mxfp8_scale.py：block_fp8_scale_to_mxfp8_e8m0 → block_scale_interleave）。这段是 CP 的纯开销，TP8 下不存在。

  • mHC 136.77 → 13.06 ms。逐 token 的超连接合并，每卡行数掉 8 倍，它就掉 8 倍多一点 —— 这是 CP 收益的最大一块（占总收益 45%）。
  • Sparse MLA 79.77 → 33.55 ms。FLOPs 没变，变的是每卡头数 8 → 64：一把 GEMM 从 8 头变成 64 头，KV 读一次分摊给更多头；TP8 那条路径还得把 8 个真头补齐到 64。
  • 通信 349.51 → 275.71 ms。省掉每层注意力输出的 AllReduce，加上 MoE 前后的 AllGather / ReduceScatter。仍然是最大的一块，占 CP8 窗口的 52%。
  • MoE GEMM 55.14 → 54.98 ms。两把梯子一样高 —— 这是「CP 动不了权重类算子」的直观证据，也是它必须保持 TP2×EP4 的原因。

04代价与边界

  • 显存。tp=1 意味着注意力权重（含 scale）整份复制，静态显存比例从 0.68 提到 0.74，full pool 2,404,864 token / SWA pool 601,088 token；实测每卡最少仍余 4,664 MiB。CP 的算力收益是要用显存买的。
  • decode 侧的运行时切片。每个非 prefill 的 forward 都要切权重、改 tp_q_head_num、必要时重算 swizzled scale（有缓存，但首次要生成），退出时再恢复。
  • 部分 TP8 优化直接失效。切换 CP8 后，原本针对「每卡 8 个真头」做的优化不再可用（原生 8 头 Sparse MLA 的补头裁剪、以及按 TP8 形状调的 mHC / AllReduce 重叠），所以上面那 +56.85% 是扣掉这些损失之后的净值。
  • chunk 不能随便放大。把 chunk 提到 32768 反而更低：C8 −1.90%、C32 −3.07%，346 次显存采样里最低空闲只剩 2 MiB，最终保留 16384。CP 是「在固定 chunk 下换一种切法」，不是「把 chunk 做大」。

05判据与计算器

一句话判据：如果一层的耗时里，按 token 重复的算子占大头，CP 有收益；如果按权重算的 GEMM 占大头，CP 没收益。这个模型里 per-token 那部分（mHC 124 ms + 注意力形状 46 ms）贡献了 278 ms 中的 170 ms，通信重构又贡献 74 ms，MoE 一分未动 —— 余下约 34 ms 落在 trace 未单列的算子上。
