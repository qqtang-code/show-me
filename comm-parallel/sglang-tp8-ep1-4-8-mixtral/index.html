速览 —— 六条结论

  • 三种写法在默认 backend 下通信完全相同。MoE 段最后只有一次 _TP(8) 上的 all-reduce， 注意力段也只有一次 _TP(8) 上的 all-reduce，载荷都是 [T, 4096] BF16； _MOE_EP/_MOE_TP 在三种配置下要么等于 _TP，要么在归约前被合并回 _TP。 源码
  • --ep 1 不是「专家不切」。8 个 rank 各存全部 8 个专家、每个专家只存 intermediate 的 1/8 （1792 列）：w13=[8,3584,4096]、w2=[8,4096,1792]。 每个专家都切了 8 份，只是切的方向是「专家内 intermediate」。源码
  • --tp 8 --ep 4 得到的是 moe_tp=2，不是 2 份专家副本。 每个 rank 拿 2 个专家、每个专家的 intermediate 再切 2 份（7168）； EP 组是 {0,2,4,6} / {1,3,5,7}，MoE-TP 组是 {0,1} / {2,3} / … 源码
  • --ep 8 是每 rank 一个完整专家。_MOE_EP 直接复用 _TP， _MOE_TP 退化成 8 个单例；归约走 moe_expert_parallel_all_reduce，但组还是同一个 _TP。 源码
  • 每 rank 的专家参数恒定。三种配置都是 176.16M 参数/层 = 5.64B/全模型， 因为 (E/ep) × (I/moe_tp) = E×I/tp，与 ep 无关； 变的是形状：[8, 3584] → [2, 14336] → [1, 28672]（w13 的后两维）。源码
  • 真正出现 all-to-all 的是 a2a backend，而且它把 ep 强制成 tp。 deepep/mooncake/nixl/mori/flashinfer/megamoe 等后端会把 --ep 1/4/8 三种写法统一改成 ep=8；此时 MoE 段才是 dispatch + combine 两次 all-to-all，载荷从 14.3 KiB 降到约 4 KiB/token/层（按 rank 计）。源码字节为推导

01参数语义：--ep 改的是哪个宽度

先把三个宽度分开：tp_size 是一个 model replica 的进程总数，注意看源码注释 —— 「tp_size is the world size, not the real tensor parallel size」；注意力真正用的宽度是 attn_tp_size， 专家内部真正用的宽度是 moe_tp_size。

# python/sglang/srt/runtime_context.py:137-157（derive_parallel_widths）
attn_tp_size = tp_size / (attn_dp_size × attn_cp_size)   # 注意力 TP 宽度
moe_tp_size  = tp_size / (ep_size × moe_dp_size)         # 每个专家内部的 TP 宽度
world_size   = tp_size × pp_size                          # 一个 replica 的进程数
num_dp_ranks = dp_size × attn_dp_size                     # 调度器数量

把本页的三个配置代进去（pp=dp=attn_dp=attn_cp=moe_dp=1）：

命令行ep_sizemoe_tp = tp//ep//moe_dp每 rank 专家数 = E/ep每专家 intermediate = I/moe_tpEP 组大小world
--tp 8 --ep 118817921（单例）8
--tp 8 --ep 4422716848
--tp 8 --ep 88111433688

E=8（专家数），I=14336（专家 intermediate），H=4096（hidden）。 moe_tp 的公式在 runtime_context.py:154；ep_size 字段在 arg_groups/fields/parallel.py:281-288，默认值 1。

约束一：整除关系 源码ep | tp 为推断

FusedMoE.__init__ 显式断言 num_experts % ep == 0 （layers/moe/fused_moe_triton/layer.py:414）与 intermediate_size % moe_tp == 0（同文件 :427）。 moe_tp = tp // ep 是整除，组构造假设 ep × moe_tp × moe_dp == tp； 因此实际可用的整齐布局要求 ep | tp，但源码在默认 moe_dp=1 时没有为它单独写断言。若 ep=3, tp=8， moe_tp=2 只覆盖 6 个 rank，不要这样配。

约束二：moe_dp 参与时的等式 源码

只有在 moe_dp_size > 1 时才进入这段校验： ep × moe_dp ≤ tp，且当 ep > 1 时要求 ep × moe_dp == tp（arg_groups/parallel_hook.py:170-183）。 另外 attn_cp_size != moe_dp_size 时只允许 moe_dp == 1（同文件 :189-192）， 所以「moe_dp=2」不是给普通 TP 部署用的旋钮。

约束三：a2a backend 强制 ep = tp 源码

overrides.py:1578-1592 列出 _A2A_EP_SPANNING_BACKENDS： megamoe、deepep、deepep_v2、mooncake、nixl、ascend_fuseep、flashinfer、flashinfer_megamoe、mori。 _a2a_ep_size()（:1609-1619）对它们统一返回 {"ep_size": view.tp_size}， 并打印「The expert parallel size is adjusted from X to the tensor parallel size」。

数据并行 / world 源码

dp_size 是独立的 replica 数，不是 TP 组内的一个维度： num_dp_ranks = dp_size × attn_dp_size（runtime_context.py:202-207）， replica 之间没有 MoE 集合通信（每个 replica 一套 WORLD，见 distributed/bootstrap.py:304-340）。本页三个配置 dp=attn_dp=1，所以 world = tp × pp = 8（runtime_context.py:173-178），没有 DP 组。

所以 ep=4 的专家布局是「连续块 × 列切片」：rank 0/1 都拿专家 0、1，rank 0 拿列 [0:7168]、rank 1 拿列 [7168:14336]；rank 2/3 拿专家 2、3，以此类推。 EP 组 {0,2,4,6} 合起来是全部 8 个专家的前半列，{1,3,5,7} 是后半列。 这解释了为什么下面会出现「EP 组 4 个 rank + MoE-TP 组 2 个 rank」的混合归约。

3.1 attention：固定按 8 个 head 切，和 ep 无关

MixtralAttention 只读 get_parallel().tp_size，没有引用 ep： models/mixtral.py:137-153 把 32 个 q 头除以 8 得 4 头/rank；8 个 kv 头除以 8 得 1 头/rank， 正好不需要复制。权重形状由 QKVParallelLinear（layers/linear.py:1075， 头数除法在 :1121-1136）和 RowParallelLinear（:1553）决定。 o_proj 在 Mixtral 里显式传 reduce_results=False（mixtral.py:166-173）， 所以它的求和不在 linear 内完成，而是交给后面的 stage boundary（见 04 节）。

3.2 专家：每 rank 的预算恒定，变的是「几个专家 × 多宽的列」

FusedMoE.__init__ 先算本地专家数，再算本地 intermediate 宽度：

# python/sglang/srt/layers/moe/fused_moe_triton/layer.py:404-428
self._num_global_routed = num_experts - num_shared_slots        # Mixtral: 8
assert self._num_global_routed % storage_ep_size == 0            # :414
self._num_local_routed = self._num_global_routed // storage_ep_size   # :415
self.num_local_experts = self._num_local_routed + num_fused_shared_experts

assert intermediate_size % self.moe_tp_size == 0                 # :427
self.intermediate_size_per_partition = intermediate_size // self.moe_tp_size  # :428

于是每 rank 的专家参数是：

paramsexpert = (E / ep) × 3 × H × (I / moe_tp)
          = 3 × H × I × E / tp   （当 ep × moe_tp = tp）
          = 3 × 4096 × 14336 × 8 / 8 = 176,160,768

参数形状落在 UnquantizedFusedMoEMethod.create_weights： w13 = [num_local_experts, 2 × intermediate_size_per_partition, hidden]（layers/quantization/unquant.py:796-813）， w2 = [num_local_experts, hidden, intermediate_size_per_partition]（同文件 :815-839）。 num_experts 传进去的是 self.num_local_experts（fused_moe_triton/layer.py:561-574）， 所以三种配置分别得到表中三种形状，但元素总数相同。

专家 id 到 rank 的映射是连续块：

# python/sglang/srt/layers/moe/fused_moe_triton/layer.py:1153-1161
def _map_global_expert_id_to_local_expert_id(self, expert_id: int) -> int:
    start_idx = self._expert_storage_rank * self._num_local_routed
    end_idx = start_idx + self._num_local_routed
    if start_idx <= expert_id < end_idx:
        return expert_id - start_idx
    ...
    return -1

权重加载时再按 moe_tp_rank 切列：_load_w13 用 narrow(shard_dim, shard_size * moe_tp_rank, shard_size)（:856-859）， _load_w2 对输入维做同样的切片（:948-951）。 于是 ep=4 的 rank 0/1 拿到同一对专家、不同列；ep=8 的 rank r 拿到专家 r 的完整权重。 源码

3.3 router：唯一整份复制的权重

MixtralMoE.gate 是 ReplicatedLinear（mixtral.py:85-92）， 形状 [8, 4096]，每个 rank 一份，不做 TP 切分。它的输出 router_logits 形状 [T, 8]，在每个 rank 上完全相同；TopK（layers/moe/topk.py:674）在本地算出 [T, 2] 的 topk_ids/topk_weights，仍然完全相同。router 的重复计算量是 8×4096 的小 GEMM， 可以忽略；它的意义是让每个 rank 都能独立决定「这个 token 该去哪个专家」，为后面的本地掩码服务。

3.4 embedding / lm_head：vocab 维切 8 份，输入侧 all-reduce，输出侧 all-gather

VocabParallelEmbedding 每 rank 存 32000/8 = 4000 行 （num_embeddings_per_partition，layers/vocab_parallel_embedding.py:327）， forward 里对本 rank 的 embedding 结果做一次 tensor_model_parallel_all_reduce （:515-534），把「只有本 rank 负责的 token 行非零」的稀疏结果加起来。 ParallelLMHead（同文件 :546）同样切 8 份；生成时每个 rank 算 [T, 4000] 的 logits， 再由 LogitsProcessor 做 all-gather 拼成 [T, 32000] （layers/logits_processor.py:479-488 决定开关，:1024-1035 执行）。 这两处都不读 ep。

3.5 KV cache：按 kv head 切，Mixtral 恰好 1 头/rank

model_config.get_num_kv_heads(tp) 返回 max(1, total_kv_heads // tp) （configs/model_config.py:1700-1711），Mixtral 是 8 // 8 = 1； pool 的每 token 字节数按 head_num × (head_dim + v_head_dim) × dtype 计算 （model_executor/pool_configurator.py:704-709）。所以每 rank 每 token 每层是 2 × 1 × 128 × 2 B = 512 B，32 层共 16 KiB/token。 KV 也不读 ep；它只跟 attn_tp_size（本页等于 8）有关。

3.6 激活与 token 路由：没有 token 搬移，只有本地掩码 + 最后求和

attention 是 TP，8 个 rank 各算 4 个 q 头，o_proj 求和后每个 rank 都拿到完整的 [T, 4096] hidden state；所以 MoE 开始时 8 个 rank 的 token 集合完全相同。 MoE 内部不做 dispatch：StandardDispatcher.dispatch()（token_dispatcher/standard.py:156-286） 只做一件事 —— 当 moe_ep_size > 1 时，把全局 topk_ids 用 local_expert_mapping 映射成本地 id，非本 rank 的专家映射成 -1（:225-278）， runner 看到 -1 直接跳过。于是每个 rank 只算自己的专家，对全部 token 都「看一遍」； 最后靠一次 all-reduce 把各 rank 的偏和加起来。这就是默认 backend 的 EP 实现方式： 专家切权重，不切 token。

# python/sglang/srt/layers/moe/utils.py:881-897
def _post_experts_sum(hidden_states, *, reduce_ep, reduce_tp):
    if reduce_ep and reduce_tp and can_merge_post_experts_all_reduce():
        return tensor_model_parallel_all_reduce(hidden_states)   # ep=4 走这里：合并成一次 _TP AR
    if reduce_ep:
        hidden_states = moe_expert_parallel_all_reduce(hidden_states)  # ep=8：_MOE_EP = _TP
    if reduce_tp:
        hidden_states = moe_tensor_model_parallel_all_reduce(hidden_states)  # ep=1：_MOE_TP = _TP
    return hidden_states

can_merge_post_experts_all_reduce() 的条件是 moe_ep_size > 1 and moe_tp_size > 1 and moe_dp_size == 1（:837-848）， 注释写明「the two groups are an orthogonal decomposition of _TP」。也就是说 ep=4 本来要分别做 EP(4) 和 MoE-TP(2) 两次 all-reduce，但因为两个组正交且 moe_dp=1，等价于一次 8-rank all-reduce， 于是被合并了。这是 ep=4 最容易被忽略的一处源码行为。

为什么三种分支最终都是同一个 _TP？ ep=1 时 _MOE_TP = _TP（parallel_state.py:2923-2924）； ep=8 时 _MOE_EP = _TP（:2894-2895）； ep=4 时走合并分支，直接调用 tensor_model_parallel_all_reduce → get_tp_group()。 三个 wrapper 分别定义在 distributed/communication_op.py:21-23、132-139， 但落到的 device group 是同一个 _TP（8 个 rank）。源码

05通信对照：ep 从 1→4→8，通信量不变

这是本页最反直觉的一条：三种配置的通信原语、通信组、字节数完全相同。 不是「差不多」，而是落在同一个 _TP device group 上的一次 all-reduce。 下面把每个通信点拆开，先给结论表，再给证明与反例。

5.1 为什么没有 token all-to-all

因为默认 backend 的 dispatch 根本不搬 token。回看 StandardDispatcher.dispatch()： 它只处理 topk_ids 的本地映射（standard.py:225-278），然后返回 StandardDispatchOutput（:282-286）；combine() 只把 hidden_states 原样返回（:288-300）。整个 MoE 层没有跨 rank 的 token 交换， 所以 _MOE_EP 这个组对象在默认路径下几乎只被 moe_expert_parallel_all_reduce （communication_op.py:137-139）使用；DeepEP dispatcher 的通信组来自 tp_group.device_group（fused_moe_triton/layer.py:163-173），EPLB 走 expert location，不用这个组。 这也是为什么 ep=4 的 EP 组虽然是 4 个 rank，通信表里却看不到 4-rank 集合通信。

5.2 一个反例：如果 ep=4 的合并被关掉

can_merge_post_experts_all_reduce() 还有两个并列条件：moe_tp > 1 与 moe_dp == 1。假设由于某种配置（例如显式把 moe_dp 调大，或路径上不允许合并）， ep=4 的求和拆成 EP(4) + MoE-TP(2) 两次 all-reduce，则每 rank 字节变成 2×(4−1)/4×P + 2×(2−1)/2×P = 1.5P + 1.0P = 2.5P，而合并版是 1.75P， 多 43%。这就是 _post_experts_sum 里那个合并分支的价值。

5.3 换到 a2a backend：三种写法收敛成 ep=8

真正的 all-to-all 只出现在 --moe-a2a-backend 非 none 时。 这时配置解析会先改写 ep_size：_a2a_ep_size() 对 _A2A_EP_SPANNING_BACKENDS 里的后端返回 {"ep_size": tp_size} （arg_groups/overrides.py:1609-1619）。tp=8 时， --ep 1、--ep 4、--ep 8 全部变成 ep=8， 只有日志里那行 adjustment 不同。此时：

  • dispatcher 从 StandardDispatcher 变成 MaybeTboDeepEPDispatcher （fused_moe_triton/layer.py:194-213）。注意 Mixtral 的 MixtralMoE 直接 new 了 FusedMoE（models/mixtral.py:100），所以类仍是 FusedMoE，换的是 dispatcher； DeepEPMoE 是给调用 get_moe_impl_class() 的模型用的子类（layers/moe/ep_moe/layer.py:352-365）。
  • 每层多两次通信：dispatch + combine 的 all-to-all，分别落到 buffer.dispatch()（token_dispatcher/deepep.py:668）与 buffer.combine()（:723）。
  • MoE 段的主通信从 1 次 all-reduce 变成 dispatch + combine 两次 all-to-all；combine 在源 rank 上按 top-k 权重汇总专家输出。 是否还残留一次收尾 all-reduce，由 stage boundary 的 complete 判定决定（moe/utils.py:761-794），本页不展开。

载荷估算（理想均衡、只计 token 数据、BF16）：每 token 被送到 top_k=2 个专家， 平均 2/8 落在某个 rank；dispatch 出 + combine 回，按 rank 计 2 × (2/8) × 4096 × 2 B = 4 KiB/token/层，对比 all-reduce 的 14.3 KiB， 约 1/3.5。32 层加起来，整条 forward 的通信量从约 0.94 MiB/token 降到约 0.63 MiB/token。 推导

但这不是「ep 越大越省」的故事：a2a 下只有一个 ep=8 布局， --ep 4 根本没有机会生效；而且 all-to-all 有固定延迟、需要 handle 同步、 decode 低延迟模式还会 padding，小 batch 下未必比一次 8-rank all-reduce 快。收益要在 「专家数多、top-k 远小于 EP 宽度、跨机 NVLink/RDMA 可用」时才成立。推断

5.4 那 reduce-scatter / send-recv 在哪里

它们不在本页三种配置里，但理解边界有用：reduce_scatter 出现在 attention-DP （dp_attention.py 的 reduce_scatterv）和 LayerNorm-SP （layers/linear.py:1774 的 row_parallel_gbar_matmul）路径； send/recv 出现在 PP 的 send_tensor_dict/recv_tensor_dict （parallel_state.py:1783-1898）与 mooncake/nixl 这类 RDMA dispatcher。 只要 attn_dp_size=1、pp_size=1、默认 backend，这三类原语都不会出现。

5.5 瓶颈：ep 变了，哪一段真的动了

默认 backend 的瓶颈与 ep 无关。每层 2 次 all-reduce（attention 后、MoE 后）是同步点： decode 小 batch 下是固定延迟，prefill 大 batch 下是带宽，两者都只随 tp、T 与网络变化。 ep 只改 grouped GEMM 的 M/N 形状与每 rank 的专家数，不改变这两个同步点。 源码延迟/带宽判断为推断

ep=8 的新瓶颈是负载均衡，不是通信。每 rank 只有 1 个专家，路由热点会直接变成 rank 间的 straggler；ep=1 的每 rank 都参与全部专家，计算天然均衡，但每 rank 的 grouped GEMM 要处理 8 个 小 N 的专家。这是「通信相同、性能不一定相同」的来源。推断

a2a 把 MoE 段载荷降到约 1/3.5，但引入新的固定开销。dispatch/combine 的 kernel 启动、 handle 同步、decode 低延迟模式的 padding，以及跨机 RDMA 的带宽，都会变成瓶颈的一部分； 收益大小取决于 top_k / ep_size 这个比值与网络拓扑。换句话说，真正的分水岭是 --moe-a2a-backend 的选择，而不是 --ep 的数字。推断

08常见误解

误解 1：--ep 1 表示专家不切分，每个 rank 有一份完整专家。
纠正：每个 rank 有全部 8 个专家的 1/8 列（w13=[8,3584,4096]）。 「不切专家」只在 tp=1 时成立；tp=8 时切的是每个专家的 intermediate 维。 ep 和 moe_tp 是同一根预算的两个乘数：ep × moe_tp = tp。
误解 2：--tp 8 --ep 4 是 2 份 EP 副本，专家权重复制 2 份。
纠正：默认 moe_dp=1 时它是 moe_tp=2：4 个 ep rank 各拿 2 个专家， 每个专家的列再切 2 份。要得到「2 个 EP 副本」需要显式 --moe-data-parallel-size 2， 而当前校验要求配套 attn_cp_size=2（parallel_hook.py:189-192）， 用户给的命令没有这个 flag。
误解 3：ep 越大，通信越多（或越少）。
纠正：默认 backend 下三种 ep 的通信完全相同：同一个 _TP(8)、 同一次 all-reduce、同样的载荷。真正改变通信模式的是 --moe-a2a-backend； 而它会先把 ep 强制成 tp，所以三种写法在 a2a 后端下只有一种布局。
误解 4：--ep 4 --moe-a2a-backend deepep 会得到 4 路 EP。
纠正：_a2a_ep_size() 会把 ep_size 从 4 改成 8 （overrides.py:1609-1619），日志里会有一行 adjustment。deepep 的组宽就是 tp_size。
误解 5：既然通信一样，ep 就完全没有意义。
纠正：通信一样不代表布局一样。整专家（ep=tp）是 a2a 后端、per-expert 量化 scale、EPLB 专家迁移、弹性 EP 的前提；ep=1 的细粒度列切分则在计算均衡上更好。 选择 ep 是在权重粒度 / 负载均衡 / 后端兼容性之间选，不是在选择通信量。

09自测

Q1：--tp 8 --ep 4 的 rank 0 和 rank 1 各持有哪些专家权重？
答：两者都持有专家 0、1；rank 0 是每个专家 intermediate 的 [0:7168]， rank 1 是 [7168:14336]。rank 2/3 换成专家 2、3，以此类推。 它们同属一个 MoE-TP 组 {0,1}，归约时两半列相加。
Q2：三种配置里，MoE 后的 all-reduce 分别由哪个函数发起？落在哪个组？
答：ep=1 走 moe_tensor_model_parallel_all_reduce （_MOE_TP，等于 _TP）；ep=4 走合并分支的 tensor_model_parallel_all_reduce（_TP）；ep=8 走 moe_expert_parallel_all_reduce（_MOE_EP，等于 _TP）。 三个 wrapper 不同，device group 相同。
Q3：为什么 ep=4 的 EP 组是 {0,2,4,6} 而不是 {0,1,2,3}？
答：组构造按 moe_tp 步长取 rank： for moe_tp_idx in range(moe_tp): range(st, en, moe_tp)（parallel_state.py:2897-2908）。 moe_tp=2 时偶数 rank 组成一个 EP 组、奇数 rank 组成另一个； 这样每个 EP 组内的 rank 共享同一个 moe_tp_rank，各自持有不同专家块的同一列切片。
Q4：如果只把 --ep 8 改成 --ep 4，哪一项通信字节会变？
答：都不变。MoE 段仍是每层一次 8-rank all-reduce、[T,4096] BF16； attention、embedding、logits 也不受影响。变化的是每 rank 的专家形状（[1,28672] → [2,14336]）、 EP 组/MoE-TP 组对象，以及负载均衡与量化粒度。
