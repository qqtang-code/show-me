CUDA IPC 直推：decode 小消息换的是「固定开销」，不是带宽

8 卡 PCIe 服务器（无 NVLink）· TP8 · 与「1-stage → 2-stage」是同一条成本式上的两项，按载荷尺寸分流，不是叠加

速览 · 30 秒

  • 问题：decode 每一步的归约只有 10 KB 量级。这个尺度上带宽不是瓶颈，固定开销才是——NCCL 每次 collective 都要把数据拷进通道缓冲、由 proxy 侧完成会合与握手，这套开销与消息大小基本无关。
  • 改动：把归约换成 CUDA IPC 直推。每个 rank 的 workspace 用 IPC 句柄导出、被所有 peer 映射进各自地址空间，kernel 一条 st.global 就写进对端显存；同步也改成 workspace 内的 device 侧 flag 自旋，不再有 host 参与的会合。
  • 和「1-stage → 2-stage」的关系：不是叠加。1-stage / 2-stage 是同一套 IPC 内核里的 Variant 选择（源码里的 seed 交叉点是 32 KiB），按载荷尺寸二选一；decode 小消息上它选的正是 1-stage——恰好是 2.1 的反方向。两条改动作用在成本式的不同项上，各自负责不同的尺寸区间。

如果「2.1 Custom AllReduce：1-stage → 2-stage」那篇讲的是搬多少字节，这一页讲的是每次归约的固定开销。两件事经常被当成两个可以相乘的百分比，其实它们是同一条成本式上的两项，而且落在不同的尺寸区间。下面把这条式子拆开，再用源码对上。

01一次归约的时间拆成两项

把单次 all-reduce 的耗时写成两项，后面所有讨论都挂在这条式子上：

T  ≈  α  +  Peff / BW
α    = 固定开销：launch、通道拷贝、proxy 会合、握手 —— 与消息大小基本无关
Peff = 每个 rank 实际经手的字节数（≠ 载荷 P，差一个算法倍数）
BW  = 链路有效带宽（这台机器上反推得 ≈ 35.5–39 GB/s）
改动砍的是哪一项手段主导的尺寸区间
1-stage → 2-stage 字节项 P_eff 广播式搬法 → reduce-scatter + all-gather，TP8 上字节降到 1/4 大载荷（verify 4.6 MB、prefill 84 MB）
换 CUDA IPC 直推 固定项 α 对端显存直接映射进本进程；去掉通道拷贝与 proxy 会合 小消息（decode 单步 10 KB–数百 KB）
一句话：2.1 是「通信变少了」，IPC 是「通信变便宜了」。前者受带宽墙约束（省字节越多越赚），后者受固定开销约束（消息越小越赚）。所以它们在 decode 这个尺度上方向相反：小消息上字节项本来就小，把算法换成 2-stage 反而要多付几轮相位屏障。

02两条轴：谁砍 α，谁砍 Peff

把「传输层」和「算法」当成两条独立的轴看，可选的组合只有三种是真实存在的：

传输层算法每 rank 经手字节固定开销 α谁在用
NCCL ring 结构性等价于 2-stage 2(N−1)/N · P 大（通道 + proxy 会合） 兜底；IPC 未覆盖形状的回落
CUDA IPC 直推 Variant::kUnstaged（1-stage） (N−1) · P 小（无通道、无会合、无相位屏障） decode 小消息
CUDA IPC 直推 kStaged / kStagedRing（2-stage） 2(N−1)/N · P 小 + 多轮相位屏障 verify / prefill 大载荷

这张表里最值得注意的一点：NCCL 的 ring 本来就搬 2(N−1)/N · P，它已经是字节最优的。所以「省下 4 倍字节」这件事在 NCCL 上根本不存在——如果某次实验测到一条路径每 rank 收 7P，那必然是某个 one-shot 实现，不是 NCCL。这也顺手说明：2.1 的收益和 IPC 的收益不可能是同一份，因为 2.1 的字节节省只可能发生在 IPC 内核的 variant 之间。

03源码对照：variant 枚举与分派顺序

3.1 「1-stage / 2-stage」在源码里就叫 Variant

kernel 头文件里这个枚举，就是那条算法轴的原文（注释是源码自带的）：

// flashinfer …/comm/pcie_ipc_all_reduce.cuh
enum class Variant : int {
  kUnstaged    = 0,  // push to every peer at once  ← 1-stage
  kStaged      = 1,  // staged pushes; island-decomposed at world_size 8
  kStagedRing   = 2,  // staged pushes in neighbour order  ← 我们那次命中的
  kFlatStaged   = 3,  // staged pushes without the island decomposition
};

内核名字直接标着算法：rsag = reduce-scatter-all-gather，也就是 2-stage。而我们 84 MB prefill 那一次实测里站上榜首的内核是：

flashinfer::comm::pcie_ipc::ipc_topo_rsag8_ring_push_param_kernel<bf16>
4,106 次调用 × 3.758 ms，载荷 84 MB，按算法搬 1.75 S = 147 MB ⇒ 39 GB/s
对比 NCCL 同载荷 4.64–4.90 ms（30–31.5 GB/s）：IPC 路径快 24–30%

而 1-stage 的内核是 push_oneshot_param_kernel<T,4>（world 4）和 ipc_topo_rsag8_push_param_kernel<T>（world 8）——同一个 FI_PCIE_IPC_SELECT 宏按 (world_size, variant) 分发。选哪个 variant 由 seed 策略给出兜底、由实测调优表逐形状决定：

# pcie_ipc_policy.py
# Payload above which reduce-scatter/all-gather beats pushing to every peer.
_SEED_STAGE_BYTES = 32 * 1024   # 32 KiB：字节项开始压过相位屏障成本

# 其余分支（节选，注释为源码原文）：
world 2 → UNSTAGED   # “staging moves the same bytes it would have pushed”
world 4 → STAGED     # “the all-to-all form pays only two barriers”
world 8 → 载荷 ≥ 32 KiB ? STAGED_RING : UNSTAGED
         # “the island-partitioned push has no barriers, which is what the staged path's
         #  six island barriers must beat”
关键点：seed 只是兜底。真正生效的是 autotune 跑出来的实测表（每个形状一行 tactic），seed 只负责没测过的形状。所以「decode 到底走了 1-stage 还是 2-stage」不能只按 32 KiB 猜，要读服务启动日志里的逐形状 tactic 打印（instrumentation 会对 rows = 1/4/8/16/32/64/128/512/8192 各打一行）。

3.2 分派是互斥的：一个张量只走一条路

// parallel_state.py —— 返回单一方法名，先匹配者胜
ca       → CustomAllreduce（本机被硬性禁用，见下）
pcie_ipc  → PCIe-IPC 直推（本机第一个真正生效的加速分支）
qr       → QuickAllReduce（需 NVLink/multicast）
pymscclpp → 需自有 fabric
torch_symm_mem → …
pynccl   → …
None     → 回落到 NCCL

ca 排在 pcie_ipc 前面，看起来像「先试 CustomAllreduce，不行再 IPC」。但这台机器上 CustomAllreduce 是被硬性禁用的，不是「效果差」：

# custom_all_reduce_utils.py
if world_size > 2 and not full_nvlink:
    "…is disabled because it's not supported on more than two PCIe-only GPUs"
    return  # → full_nvlink = None

# custom_all_reduce.py → should_custom_ar()
if self.world_size == 2 or self.full_nvlink:
    return inp_size <= self.max_size
return False   # ← TP8 无 NVLink：对**所有**形状返回 False

所以在 8 卡无 NVLink 的 TP8 上，classic CustomAllreduce 对每一个形状都拒收（启动时会打一条 warning），另一个 CustomAllReduceV2 也没有接进 parallel_state。这也解释了一个容易被忽略的事实：当 IPC 不可用时，回落目标是 NCCL，而不是 CustomAllreduce——因为后者在这台机器上根本不工作。

05源码侧：采用 CUDA IPC 之后改变了什么

5.1 「直推」指的是数据不再经过通道缓冲

先把两条通路并排画出来（r0 的视角，N = 8）：

── NCCL 通路（固定开销 α 大）：数据必须先进通道缓冲 ────────────── r0 计算出的部分和 │ ├─▶ 拷贝进 NCCL 的 send channel 缓冲 ← 与消息大小无关的成本 │ ├─▶ proxy / host 侧会合，按 ring 顺序 send/recv ← 每次 collective 都要重来一遍 │ ├─▶ PCIe（经过 CPU root complex） │ └─▶ 落到本地 recv channel 缓冲 ─▶ 再拷出到输出张量 ─▶ 本机归约 ── CUDA IPC 直推（固定开销 α 小）：对端显存是本进程里的一个合法指针 ── 启动时一次性： cudaMalloc slab → cudaIpcGetMemHandle → all_gather 句柄 → cudaIpcOpenMemHandle 把每个 peer 的 slab 映射进本进程 → make_peer_views() 算出 per-peer 指针（偏移此后固定不变） 运行时（kernel 内部）： r0 计算出的部分和 │ └─▶ st.global 直接写进对端 slab ← 没有通道，没有拷贝，没有 host 参与 │ └─▶ 同步也在这个 slab 里：device 侧 flag 自旋 + __threadfence_system()

所谓「直推」（push），就是发送方的 kernel 直接往接收方的显存里写，而不是把数据交给一个通信库去搬运。能做到这一点，唯一的前提是那个地址在本进程里合法——这正是 cudaIpcOpenMemHandle 给的。

5.2 改变了四件事

维度NCCL / 通道语义CUDA IPC 直推
地址空间 每个 rank 只有自己的显存是合法地址，所以必须有 channel 缓冲承载「别人的数据」 对端 slab 的每一个区域都映射为本进程里的合法指针（ipc_ptrs[]），可以直接寻址
谁发起传输 ring 语义：每个 rank 往邻居发自己那一份（send/recv），带宽最优但要走库的调度 push 语义：自己那一份直接推进对端（st.global），发起方就是算完的那个 kernel
怎么同步 per-collective 的会合/握手，涉及 proxy 与 host 侧进展 带内同步：同一个 slab 里划出 signal 区（epoch 槽 / barrier 相位 / barrier flag 三段互不相交），kernel 自己写 flag、自旋等待
拓扑是否烘死 库在运行时按拓扑选算法 workspace 在首次归约时一次性分配，peer 偏移烘进 handle，此后不可增长

5.3 没有改变的两件事（这是最容易被误读的地方）

  • 物理链路与带宽上限没变。还是那根 PCIe，还是过 CPU root complex。「直推」省掉的是软件层的通道与会合，不是链路本身。所以它抢不到任何带宽红利——大载荷上它能赢，靠的仍然是 variant 换了算法（省字节），不是 IPC 让链路变快了。
  • staged 变体的字节数也没变。源码注释写得很直白：“Total bytes are unchanged, only the order.”——kUnstaged 在无 switch 的机器上 all-to-all 写会塌，所以 staged 变体把推送重排成「任意时刻每个 rank 恰好一个出站流、一个入站流」。字节数相同，只是次序变了。

06代价：workspace 是一块一次性、不可增长的显存

直推要求 buffer 常驻且被所有 peer 映射，所以必须提前申请。布局函数把它的构成写得完全确定：

// compute_workspace_layout()
signal_bytes  =  align128(4B × (epoch 槽 + 相位屏障槽 + flag 槽 + scratch 状态))
payload_bytes =  align128(max_numel × elem_size)
scratch_bytes =  align128(2 × world_size × payload_bytes)  ← epoch 双缓冲 × world_size 个 peer 槽
total_bytes  =  signal_bytes + 2 × scratch_bytes
⇒ 量级上 total ≈ 4 × world_size × max_numel × elem_size

末行那个 2 × 是两套协议族（sentinel 内核与 barrier 内核）各占一份 scratch。max_numel 由服务侧传入（默认取 decode 宽度 × hidden，可用 env 覆盖到 prefill 规模）。把它代进我们的实际配置可以验一下账：

实测印证：max_numel = 41,943,040（= 8192 × 5120）、bf16、N = 8 时算得 2.68 GB/卡，与启动日志观测到的「显存 +2.7 GB/卡」一致——这条式子可以直接用来估任何配置的代价。

两条硬约束：
① 不能增长。偏移在 init() 时就烘进 handle，超过 max_numel 的形状会让 supports() 返回 False 并回落 NCCL，而不是报错——所以「要不要开大」是在显存与覆盖率之间做取舍。
② 不能跨主机。数据面是 CUDA IPC，句柄只在同一台主机内有效，代码里对跨主机的 process group 直接抛错。而且回落是整组粒度的：一个 TP 组里只要出现两台主机，节点内那几对 rank 也一起退回 NCCL——这个实现不提供「跨节点 slow + 节点内 fast」的混合模式。

07为什么两个收益不能相乘

  • 分派层互斥。_resolve_outplace_all_reduce_method() 返回的是一个方法名，一个张量只会走一条路，不存在「两条路的收益都拿到」。
  • 两条轴在同一套内核里。「1-stage ↔ 2-stage」不是外挂在 IPC 之外的第二个开关，它就是 IPC 内核的 Variant。所以对 decode 而言，「换 IPC」与「换回 1-stage」是同一个动作的两面。
  • Amdahl 是加权，不是乘法。端到端收益 = 归约时间在总时间里的占比 × 局部加速比。不同形状的占比不同（prefill 高的场景里归约占比低），所以两个局部加速比不会以乘积形式传导到端到端。
  • 一台机器上只有一份「省字节」的空间。TP8 的最优字节下界是 2(N−1)/N·P，谁先到谁拿走；NCCL 的 ring 本来就在这个下界上，所以 2.1 的 4 倍节省只能来自 IPC 内核内部的 variant 切换。
正确的说法：两条改动是同一个决策表的两个维度，按载荷尺寸与TP 规模分流。要判断某个配置该拿多少收益，先问「这个形状落在哪个格子」，再取那个格子的路——而不是把两个百分比加起来。

08自测

decode 小消息上，2-stage 明明省 4 倍字节，为什么反而更慢？
因为小消息上字节项不是主导项。以 N=8、P=10 KB 为例：1-stage 收 7P = 70 KB，2-stage 收 1.75P = 17.5 KB，按 36 GB/s 折算差 1.5 μs；而 2-stage 要多付数轮相位屏障。我们 84 MB 那次实测把 0.579 ms 残差归因到 7 个相位（≈ 83 μs/相位，含 __threadfence_system），相位成本是固定量级、不随载荷缩小，所以小消息上它直接吃掉全部字节收益还倒亏。源码里那句「the island-partitioned push has no barriers, which is what the staged path's six island barriers must beat」讲的就是这个取舍。
为什么说「省 4 倍字节」这件事不可能发生在 NCCL 上？
NCCL 的 ring 结构本身就是 reduce-scatter + all-gather，每 rank 经手 2(N−1)/N·P，已经在字节下界上。所以任何测到「每 rank 收 7P」的路径都必然是一个 one-shot（广播式）实现，不是 NCCL。这条推理的用处：它能在不看实现的情况下，判断一次「省字节」的改动是在哪个后端上发生的。
这台机器上 CustomAllreduce 是「效果差」还是「被禁用」？后果是什么？
被硬性禁用。world_size > 2 and not full_nvlink 直接 return，should_custom_ar() 对所有形状返回 False，启动时还会打一条 warning。后果是：当 PCIe-IPC 不可用时（显存不够、形状超界、跨主机），回落目标是 NCCL，而不是 CustomAllreduce——后者在这台机器上本来就不工作。所以测「IPC 关掉会掉多少」时，对照组是 NCCL 基线，不是 ca。
workspace 为什么必须一次性申请、且不能增长？
因为 peer 的偏移量在 init() 时就烘进了 kernel 的 handle 并分发给所有 rank，运行期不能再重新分配（重新分配需要所有 rank 在「所有 peer 解除映射」与「各自 cudaFree」之间做一次集体屏障，析构函数表达不了）。代价是必须按「模型会发出的最大归约」来定尺寸：decode 宽度 × hidden，或直接用 env 覆盖到 prefill 规模。超出即 supports() = False 静默回落。
为什么这页的三条实测都反推出「同一个带宽量级」是重要证据？
因为它排除了「换了算法但其实走了别的路径」这类误判。verify 4.6 MB：32.2 MB ÷ 907 μs = 35.5 GB/s；2-stage：8.05 MB ÷ 222.6 μs = 36.2 GB/s；prefill 84 MB 的 rsag：147 MB ÷ 3.758 ms = 39 GB/s；独立微基准 push/pull/双向 = 39.1/38.6/41.1 GB/s。四处同量级 ⇒ 这些路径都是纯带宽受限的 PCIe 交换，差别只在「搬了多少」与「固定开销付了几次」。
