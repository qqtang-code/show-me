1-stage → 2-stage AllReduce：省下的是 4 倍字节

8 卡 PCIe 服务器（无 NVLink）· TP8 · 单次归约 kernel 907 → 222.6 μs，端到端 1k/4k C64 847.82 → 1358.47 tok/s

2026-09-15AllReduce张量并行通信优化 PCIe投机解码Amdahl

速览 · 30 秒

  • 问题：8 卡跨 PCIe 交换做 AllReduce，一条 4.6 MB 的消息，单次归约要 907 μs，占 Decode 累计 kernel 时间的 57%。
  • 改动：把「广播 + 本机相加」换成「reduce-scatter + all-gather」。没有换硬件，没有提带宽，只是每个 rank 从收 7 份完整载荷变成收 1.75 份。
  • 结果：kernel 907 → 222.6 μs（4.07×），端到端 +60.2%。做到 91% 的 Amdahl 上限。
  • 记住这一条：字节倍数恰好是 TP/2。所以 TP 越大收益越大，TP2 上收益为零。
一次 AllReduce 的载荷 P：高并发 verify 消息 ≈ 4.6 MB。 它等于 行数 × hidden(6144) × 2B，行数由 并发 × 投机 draft 长度决定 —— 并发越高，消息越大，这条优化的收益也越大。 八卡分处两个四卡 PCIe 组（无 NVLink），归约必须走 PCIe 交换。

前置知识：这次归约到底在传什么

如果下面三个概念你都已经清楚，可以直接跳到 搬多少字节。

① AllReduce 做什么

每个 rank 手里有一份形状相同、内容不同的张量（这里是各卡算出的部分和）。AllReduce 结束后， 每个 rank 都拿到所有 rank 之和。注意它和 ReduceScatter、AllGather 的关系： AllReduce = ReduceScatter + AllGather —— 这正是本次改动的全部数学内容， 两个阶段拼起来的结果与一步到位完全一样。

② 张量并行（TP）里为什么到处都是 AllReduce

张量并行把一层的权重按列/行切到多张卡上。以 Transformer 的一层为例，两个地方会产生「部分和」：Attention 的输出投影 o_proj 之后、MLP 的 down_proj 之后。

  • 列并行（q/k/v_proj、gate/up_proj）输出按列切，各卡结果互不重叠，不需要通信；
  • 行并行（o_proj、down_proj）需要把输入按行切、结果相加，必须 AllReduce。

所以每层 2 次 AllReduce，64 层就是 128 次 —— 单次省下的微秒数会被层数放大，这就是它对端到端能有 60% 影响的原因。

③ 载荷 P 是怎么长出来的

投机解码的 verify 阶段，一条请求要一次性验证 draft 长度个 token，所以这一批参与计算的「行」数远大于请求数。 行的宽度就是 hidden size。于是：

P  =  行数 × hidden × dtype 字节数
本轮实测：4.6 MB ≈ 374 行 × 6144 × 2B
行数 ≈ 并发批大小 × draft 长度（并发越高、draft 越长，消息越大）

这就是为什么这条优化在高并发 verify 场景收益最大：P 越大，PCIe 越是瓶颈，省字节的价值越高。 而 8 卡分处两个四卡 PCIe 组、且没有 NVLink，意味着跨组流量必须过主机桥 —— 归约天然是带宽墙上的活。

01两种算法真正做的事：搬多少字节

两者的数学结果完全一样，区别只在「每个 rank 要从网络上收多少字节」。这是本次提升的全部来源。

1-stage：广播 + 本机归约

broadcast everyone's P, then sum locally
r1P
r2P
⋮每个 rank 都把自己完整的 P 发给其他 7 个
r7P
▼ 7 份完整载荷全部落到本地
r0 读 7 份 + 自己 1 份 → 相加 → 写出完整 P
每 rank 接收 7P = 7 × 4.6 MB = 32.2 MB，与 TP 规模成正比

2-stage：reduce-scatter + all-gather

split P into N chunks, then two passes
阶段1reduce-scatter：切成 8 份 (每份 P/8)，各自只归约属于自己的一份
阶段2all-gather：把归约好的那一份广播回去，拼回完整 P
▼ 两个阶段各收 7 份，每份只有 P/8
2 × (7/8)P  →  每 rank 恰好各经手一遍
每 rank 接收 1.75P = 1.75 × 4.6 MB = 8.05 MB，与 TP 规模无关（趋近 2P）

02为什么倍率恰好是 N/2

一次 all-reduce 的字节下界是每 rank 2(N−1)/N · P：每个 rank 至少要把「别人的贡献」和「所有人的结果」各过一遍。 1-stage 是广播式搬法，收的是 N−1 份完整载荷，比下界多出 N/2 倍。

TP 规模 1-stage 每 rank 收 2-stage 每 rank 收 字节节省 对应观测
TP2 1.00 P 1.00 P 1.00×（无） TP2PP4 通信补丁 +0.76% / −0.12%
TP4 3.00 P 1.50 P 2.00× TP4PP2 通信补丁 +9.44%
TP8 7.00 P 1.75 P 4.00× 本轮主实验（2-stage 自定义 AllReduce）

TP2 时两个算法搬的字节数完全相同，只多出一轮同步开销 —— 所以凡是以省字节为目标的通信改动，在小 TP 域上都应当预期接近零收益。

把倍率算出来

1-stage 每 rank 收 (N − 1) · P
2-stage 每 rank 收 2 · (N − 1)/N · P
比值 = (N − 1) ÷ [2(N − 1)/N] = N / 2
N = 8 → 4×；N = 4 → 2×；N = 2 → 1×（无收益）；N = 16 → 8×

注意两个式子的量级差异：1-stage 是 O(N·P)，随 TP 线性膨胀； 2-stage 是 O(2P)，与 TP 规模无关。这是「TP 越大越该用 2-stage」的根源， 也是它成为带宽最优算法的原因 —— 下界是 2(N−1)/N·P，N 很大时趋近 2P。

03对账：907 → 222.6 μs 是不是同一堵带宽墙

如果提升真的来自「少搬字节」，那么两次 kernel 反推出的有效带宽必须相等。

1-stage
32.2 MB ÷ 907 μs  =  35.5 GB/s
2-stage
8.05 MB ÷ 222.6 μs  =  36.2 GB/s
独立微基准（push / pull / 双向扫描） =  39.1 / 38.6 / 41.1 GB/s
→ 三者同量级，残差 1.9%；时间比 4.07× ≈ 字节比 4.00×
→ 结论：没有换硬件、没有提带宽，只是换了「搬多少」

kernel 时间与接收字节数几乎完全成正比，说明这条路径是纯带宽受限的（PCIe 交换）， 而不是延迟或计算受限。这也解释了为什么同一改动在 16k/512 上只有 +7.8%～+13.4%： 那里 allreduce 在整轮耗时里的占比本来就低。

这个「反推带宽」的手法值得单独记住

面对一个性能改动，判断它是否真的按你设想的那条路径起作用，最有力的证据不是「变快了」，而是 两条独立路径反推出的物理量一致：字节数 ÷ 时间 ≈ 外部微基准测得的带宽。 一旦它们在 2% 内吻合，就可以排除「换了算法但其实走了别的路径」「编译器把某段优化掉了」这类解释。

怎么理解这个提升：它不是「通信变快了」，而是「通信变少了」。 单次归约的延迟/带宽特性没有任何改善，改的是数据搬运量 —— 所以收益上限由两件事决定：归约在总时间里的占比（决定能否传导到端到端），以及 TP 域有多大（决定能省多少字节）。两者都已知时，+60% 这个数字就是可预测的，不是运气。

05边界：什么时候这条改动不成立

  • TP 域小。TP2 时 1-stage 与 2-stage 搬的字节完全相同，2-stage 只多一轮 kernel + barrier，理论上应略慢 —— 与 TP2PP4 上观测到的 −0.12% 一致。
  • 消息极小。1-stage 只需 1 个 kernel + 1 次同步，延迟最优；2-stage 要 2 个 kernel + 2 次同步。延迟主导的小消息上 1-stage 反而更快 —— 这也是为什么还要为 1–64 行的小张量单独做 IPC 路径。
  • 大消息也不该继续加码。96 MiB 上 IPC 候选比参考路径慢（3.71 ms vs 参考路径），所以大消息保留原路径；本轮最终配方是按消息尺寸分流，而不是全量替换。

常见误解

✗「2-stage 的通信更快」
两阶段的单跳带宽、链路、协议全都没变。变的是需要搬的字节数。所以正确的说法是「通信变少了」—— 这也意味着：如果链路本身没到饱和（比如延迟主导的小消息），这条改动不会带来收益。
✗「省了 4 倍字节，所以端到端快 4 倍」
被 Amdahl 定律拦住了。归约只占 57.2% 的 kernel 时间，即使它缩到 0，上限也只有 1/(1−0.572) ≈ 2.34×； 缩到 1/4 则上限 1.76×。加速比是「占比」和「局部加速比」的函数，不是后者本身。
✗「那所有 AllReduce 都该换成 2-stage」
反例就在同一份数据里：TP2 上字节完全相同却多一轮同步，实测 −0.12%；小消息上 1-stage 反而更快。 正确做法是按 N 和消息大小分流（N ≥ 4 且消息够大才换），而不是全局替换。
✗「kernel 快了 4 倍，那吞吐应该也快 4 倍」
kernel 时间 ≠ wall time。真实一轮里还有 prefill、还有 kernel 之间的空隙与同步。 兑现率 91% 已经是很好的结果，剩下的 9% 就来自这些没被加速的部分。

自测：能答上这五题就算懂了

1. N = 16、P = 1 MB 时，两种算法每 rank 各接收多少字节？
1-stage：(N−1)·P = 15 MB；2-stage：2(N−1)/N·P = 1.875 MB。 比值 8×，正好是 N/2。注意 2-stage 已经非常接近理论上限 2P = 2 MB。
2. 为什么这条改动在 TP2 上不但没收益，还可能略慢？
N = 2 时两个式子的值相同：1-stage 收 (2−1)P = P；2-stage 收 2(1)/2·P = P。 字节数完全一样，而 2-stage 需要两个 kernel、两次同步，纯属额外开销 —— 所以实测 −0.12% 是符合预期的，不是噪声。
3. 如果 AllReduce 只占 kernel 时间的 20%，缩到 1/4，端到端上限是多少？
1 ÷ (0.8 + 0.2/4) = 1 ÷ 0.85 ≈ 1.18×（+18%）。 对比本次 57.2% 占比下的 1.76×：同样一个优化，占比决定了它值不值得做。
4. 有人报告 2-stage 的单次耗时从 222 μs 变成 300 μs，能断定「带宽变差了」吗？
不能。必须先算 字节数 ÷ 时间 反推有效带宽：如果消息变大导致字节数也涨了， 300 μs 可能仍然是同一堵带宽墙。只有「有效带宽显著低于微基准」才说明链路或实现出了问题 —— 这正是 03 节那套对账方法的用处。
5. 为什么说 1-stage 是 O(N·P)、2-stage 是 O(2P)？后者为什么与 TP 无关？
1-stage 每个 rank 要收齐其他所有人的完整载荷，(N−1) 份，随 N 线性增长。 2-stage 把载荷先切成 N 份，每个 rank 在 scatter 和 gather 两阶段各只经手 (N−1) 份小块， 合起来是 2(N−1)/N·P —— N 变大时 (N−1)/N → 1，总量趋近 2P，与 N 无关。
