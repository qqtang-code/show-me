主机侧的四项：NCCL 的 SYS 路径、NUMA 绑定、CPU governor、host 分词

2026-11-16 NCCL NUMA CPU governor 主机侧 口径

这四项都不改 GPU 上的任何一个 kernel。它们改的是四件更底层的事：集合通信的 ring 走哪条链路、进程的显存与 CPU 落在哪个 NUMA 节点、CPU 会不会被节能策略降频、prompt 在哪台机器上分词。共同点是：收益看起来零散、容易被记成「调参玄学」，而实际的判据只有一条 —— 这台机器的拓扑事实。这一页把四项放在一起讲，因为它们同属一类错误：把拓扑事实当通用配方抄走。

术语约定：ring、rail、socket、NUMA node、governor、PIN、tokenizer 保留英文；P = prefill 角色、D = decode 角色。本页不做数据图：四项的单位分别是 ms、百分比、NUMA 编号和行数，画在同一张图上只会伪造可比性 —— 该说的地方用表和量纲明确的数值说。

01速览

TL;DR

  • NCCL 的 SYS 路径买的是「ring 不走错链路」。 双 socket / 双 PCIe 组的机器上，默认策略可能让 ring 混用快慢链路，一次 128 MB all-reduce 从 7.60 ms 降到 5.75 ms；对应到 16K/512 的 C8 档，端到端 +10.4%。
  • NUMA 绑定是拓扑事实，不是调参。 每张卡绑到它物理最近的 CPU node；这套机器上是 0,0,0,0,2,2,2,2，换机器必须用 numactl -H 重新查，抄数字没有意义。
  • CPU governor 的坑在「恢复」而不是「设置」。 要显式 apply，停服务不会自动 restore —— 一次没恢复干净，下一次测量的基线就变了。验收记录里是 128 项 governor/EPP 精确回读。
  • host 分词只有几十毫秒。 单项 8162.897 → 8131.237 ms，约 −0.39%；它的价值是「别把它算成 GPU 收益」，以及知道边界不安全时必须回退。
  • 四项都不能「上次有效这次照抄」。 它们全部以本机拓扑、宿主权限、tokenizer 配置为前提；换机器/换镜像/换模板都要重新确认。

02为什么这四项要单独一页

因为它们有一个共同的失败模式：看起来像通用参数，实际是本机事实。

NCCL_P2P_LEVEL=SYS 写进配置很容易，但它在单 socket 机器上可能什么都没变、在别的拓扑上还可能变慢；NUMA 那串数字抄错两位，性能会悄悄掉一半却没人报错；CPU governor 忘了恢复，第二天所有对比实验都不可信；分词加速更是典型的「改对了没感觉、改错了看不出」。

所以这一页的写法是：每项先给判据（什么情况下它才成立），再给数字（有多大的量级），最后给回退/恢复责任（谁负责把它还原）。照着顺序读，就不会出现「抄了参数、不知道为什么快」的情况。

03NCCL 的 SYS 路径：让 ring 不走错链路

先看这台机器的形状。它没有 NVLink，8 张卡分处两个四卡 PCIe 组，跨组要过主机桥：

NUMA node 0 · 四卡组 A
GPU0GPU1GPU2GPU3
NUMA node 2 · 四卡组 B
GPU4GPU5GPU6GPU7
组间通信过主机桥（socket 间互联）— 带宽与延迟都差一档

默认的 ring 构造可能在两个组之间来回跳：rank0→rank1（组内快）→rank2（组内快）……一旦排布跨了组，每一圈都有一跳走慢链路，而集合通信的耗时由最慢那一跳决定。

NCCL_P2P_LEVEL=SYS 的作用是让 P2P 走系统级路径（经主机），而不是让它误以为可以走更快的点对点；配套再关掉组内网络路径。这样 ring 的连通性选择和实际拓扑对齐，不会出现「以为在走组内、其实在绕桥」的错配。

D 侧还有一件同族的事：decode 端的集合通信还额外开了 PCIe-IPC 直推（小消息换成固定开销更低的内核），并且 P / D 两侧都设 SYS。那件事的原理在 CUDA IPC 直推 那篇，这里只记一句配置事实，避免两处各讲一半。

04NUMA 绑定：0,0,0,0,2,2,2,2 是怎么来的

绑定的目的只有一个：让进程读写的显存和它跑的 CPU 在同一个 node 上。跨 node 访问内存要多走一跳 socket 互联，在 decode 这种每步都要同步、每步都有小规模主机侧工作的负载上，这一跳会以抖动和 P99 的形式还回来。

所以绑定表的来源只能是拓扑查询，不是经验值：

# 先查这张卡属于哪个 node，再定绑定
numactl -H | grep -E 'available|node [0-9]+ cpus'
nvidia-smi topo -m                  # 看 GPU 之间的连接方式（SYS / PIX / PHB …）

# 查完才写进 inventory：前四张卡绑 node 0，后四张绑 node 2
NUMA_NODES=0,0,0,0,2,2,2,2

为什么是 0 和 2 而不是 0 和 1？因为这台机器上 CPU 侧的 node 编号本来就不连续（有未暴露的插槽/内存域），这是它的事实，不是规律。同一份配置搬到 2 socket 的普通机器上很可能直接绑错 —— 绑错了不会报错，只会变慢。

这类配置最危险的地方是「静默」。 NUMA 绑错、绑到不存在的 node、或者忘了加亲和 —— 三种情况都不会让服务起不来，只会让延迟和抖动慢慢变差。所以它是必须写进部署清单、并在换机器时逐条复核的那一类。

05CPU governor：设置容易，恢复才是关键

第三项是把 CPU 从节能策略拉到性能策略（performance governor / EPP）。目的是去掉降频带来的抖动 —— 它不是让计算变快，而是让主机侧的等待时间变得可预期。

坑有两个：

① 必须显式 apply

不会因为「服务起来了」就自动生效，要单独执行一次策略应用

cpu-apply
② 必须显式 restore

停服务不会自动恢复；没恢复的机器会一直跑在 performance 上

cpu-restore
③ 需要宿主权限

容器内通常改不动，要宿主机配合，且要能读回原值

先快照，再改
④ 要能回读验

验收不是「我设了」，而是「逐项回读等于原值」

128 项精确恢复

为什么「恢复」比「设置」重要：下一次测量的基线是上一轮留下的状态。如果一台机器上残留了 performance governor，之后所有「默认配置」的对照都不是默认配置。这类污染不会报错，只会让数字缓慢漂移。

06host 分词：两项、几十毫秒、不是 GPU 加速

第四项最容易记错性质。它是主机侧的优化：长 prompt 的分词在主线程上做，CPU 一慢就挡在 GPU 前面。

09常见误解

①「TCP / NCCL 参数是一套可以复用的调优经验」

不是。这一页四项里有三项（SYS 路径、NUMA、PCIe-IPC）本质是拓扑描述：它们之所以有效，是因为这台机器的卡分处两组、跨组过桥。换一台单组机器，同一份配置可能毫无变化。

②「host 分词加速也算推理优化，可以并进 GPU 收益」

不行。它省的是 GPU 空等的时间，量级是几十毫秒、约 0.4%。把它算进「模型变快了」会让收益归因错位，之后再做 GPU 侧的 A/B 就分不清谁的功劳。

③「CPU governor 设一次就行」

设一次可以，但恢复要单独做。停服务不会自动把它改回去；残留的 performance 状态会让后来所有「默认配置」的对照组失效。

④「NUMA 那串数字照抄就好」

那串 0,0,0,0,2,2,2,2 是这台机器的实测拓扑（CPU 侧 node 编号本身就不连续）。换机器不查 numactl -H 就抄，是绑错还查不出来的典型。

10自测

为什么 NCCL_P2P_LEVEL=SYS 能提升集合通信？它到底改了哪一步？

改的是 ring / 连通性的路径选择：让 P2P 走系统级路径，避免 ring 在双组拓扑上误用更快但实际会绕桥的通路。耗时由最慢那一跳决定，所以把错配的那一跳纠正过来，整次通信就跟着降。

NUMA 绑定为什么必须现场查，而不能照抄？

因为它描述的是「这张卡物理上离哪个 CPU node 最近」。这套机器上编号是 0 和 2（不连续），换机器就可能完全不同；绑错不会报错，只会让延迟与抖动慢慢变差。

CPU governor 的两个动作是什么？为什么「恢复」更重要？

apply 与 restore，两个都要显式执行。恢复更重要的原因是：下一轮测量的基线是这一轮留下的状态，残留的 performance governor 会让之后所有「默认配置」的对照都失真。

host 分词值不值得单独记一条？

值，但不是因为它快 0.4%。值得记的是两条判断：别把主机侧收益算成 GPU 收益；换 tokenizer / 模板后必须重新核对 token ID 与数据集是否对齐。

这四项里有哪一项「失败时不会报错」？

四项都不会报错。SYS 路径失效只是没加速；NUMA 绑错只是变慢；governor 残留只是污染基线；分词回退只是少了 0.4%。所以它们只能靠「实测 A/B + 逐项回读」验证，不能靠配置看起来对不对。
