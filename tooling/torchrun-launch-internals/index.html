torchrun 是怎么把一次命令变成 N 个训练进程的

2026-10-13torchruntorchelasticrendezvousDDP源码走读

你敲下 torchrun --nproc-per-node=8 train.py，最后跑起来的是 8 个各自持有一张卡的 Python 进程，它们能互相发现、组成 process group、失败后还能被重新拉起。中间发生的事全部在 torch.distributed.run 和它下面的 torchelastic 里：解析参数 → 每台机器起一个 agent → agent 通过 rendezvous 为每个节点分配 GROUP_RANK → agent 按分配结果给每个 worker 生成一份环境变量 → 用 subprocess.Popen 拉起进程 → 循环监控，失败则重启整个 worker group。这一页把这条链路拆开，每个结论都指到源码里的那一行。

01结论

TL;DR

  • torchrun 自己不跑训练，也不做通信。它只是一个 launcher：进程里跑的是 elastic_launch → LocalElasticAgent，agent 再 Popen 出真正的训练进程。torchrun 退出 = agent 退出 = 所有 worker 被 killpg 终止。
  • 真正的 rank 不是参数算出来的，是 rendezvous 排出来的。每台机器的 agent 以 (min_nodes, max_nodes, nproc_per_node) 参与 rendezvous，拿到 GROUP_RANK（本节点在 group 内的编号）与 GROUP_WORLD_SIZE（本轮节点数），然后 global_rank = group_rank × local_world_size + local_rank。所以 rank 在重启后会变。
  • --master-addr/--master-port/--node-rank 只在 --rdzv-backend=static（默认）下有效；--rdzv-backend=c10d 下会被忽略甚至告警，MASTER_ADDR/MASTER_PORT 改由 rendezvous 现场商定。
  • 注入给 worker 的是完整的环境变量字典（RANK/WORLD_SIZE/LOCAL_RANK/MASTER_ADDR/MASTER_PORT/…），不是命令行参数。脚本里 dist.init_process_group() 无参就能跑，靠的就是它默认走 env://。
  • --max-restarts 重启的是「整个 worker group」，不是坏掉的那个 worker：任一 worker 失败 → 所有节点的 worker 全部被终止 → 重新 rendezvous → 全部以新的 RANK 重启。不存 checkpoint 就等于丢弃这段计算。

术语约定：凡是翻译成中文会产生歧义的词，本页一律保留英文原词，不做意译 —— rank（不译「序号/座次」）、group（不译「组」以外的含义）、store、 rendezvous、agent、worker group、elastic、 quorum、complete、heartbeat、communicator、 watchdog、client / server、slow path、checkpoint。 变量名、函数名、参数名同样保持原样，以便与源码和报错信息逐字对照。

02谁是谁：六个角色

先分清这几个东西，后面所有细节才挂得住。torchrun 是 torch.distributed.run 的 console script，两者完全等价（python -m torch.distributed.run 也行）。它启动后，进程里做的第一件正事是构造 LaunchConfig 并调用 elastic_launch。

03启动流程：从命令行到 8 个进程

下面九步对应源码里从 run(args) 到 Popen 的真实顺序。第 5 步的 monitor_interval 和 start_method 用的是默认值 0.1s / spawn。

1
解析参数，并用 PET_* 环境变量提供默认值 每个 --flag 都注册了 action=env：命令行未提供时读取 PET_FLAG（大写、下划线）。因此 PET_NNODES=2 torchrun train.py 等价于 --nnodes=2。 run.py: get_args_parser() · torch/distributed/argparse_util.py: class env
2
为未提供的参数填默认值，决定 rendezvous 怎么走 ① --standalone → 强制 c10d / localhost:0 / uuid4；② 未提供 endpoint 且 --nnodes 最大值为 1 → 同样改为 c10d / localhost:0；③ master_port 为 None 时填 29500。 run.py: run() — 因此单机单节点即使不写任何 rdzv 参数也不会占用 29500
3
解析节点数与每节点进程数 parse_min_max_nnodes("1:4") → (1,4)；determine_local_world_size 支持 auto/cpu/gpu/xpu/int，gpu 取 torch.cuda.device_count()。若 nproc_per_node > 1 且未设置 OMP_NUM_THREADS，torchrun 会将其设为 1 并输出一条警告。 run.py: parse_min_max_nnodes / determine_local_world_size / config_from_args
4
构造 LaunchConfig 与 worker 的启动命令 命令 = sys.executable -u train.py <剩余参数原文>（-u 保证日志不缓冲；PYTHON_EXEC 可覆盖解释器；-m 走模块）。注意：此处不含任何 rank 相关参数，rank 全部通过环境变量传递。 run.py: config_from_args 末尾 — 仅当旧式 use_env=False 才追加 --local-rank=
5
构造 RendezvousHandler 与 LocalElasticAgent get_rendezvous_handler(params) 按字符串查注册表（static/c10d/etcd/etcd-v2，可通过插件扩展），再与 WorkerSpec 一起传给 LocalElasticAgent。 launcher/api.py: launch_agent() · elastic/rendezvous/registry.py
6
等所有节点到齐 —— rendezvous 每台机器一个 agent 参与 rendezvous。static 模式即连接 rank 0 的 TCPStore；c10d / etcd 模式则是一轮一轮 join，参与者数量达到 min_nodes 且到达 deadline 后才 complete。返回的是 GROUP_RANK 与 GROUP_WORLD_SIZE。 agent: _rendezvous() → handler.next_rendezvous()
7
把 group 内的分配结果展开为每个 worker 的 global RANK global_rank = group_rank × local_world_size + local_rank。默认（未设 TORCH_ELASTIC_WORKER_IDENTICAL=1）走 store 的 slow path：各 agent 写 torchelastic/role_info/<group_rank>，GROUP_RANK 0 计算完成后写回 assigned_ranks/<i>，其余 agent 阻塞在 get 上等待结果。 agent: _assign_worker_ranks() — 快路径需 TORCH_ELASTIC_WORKER_IDENTICAL=1
8
为每个 worker 生成一份独立的环境变量字典 一次写全全部变量（见下一节），其中 LOCAL_RANK、RANK、WORLD_SIZE、MASTER_ADDR/PORT 是分布式初始化的全部输入。存在 CUDA_VISIBLE_DEVICES 时原样继承，不做切割。 agent: _start_workers() 的 worker_env 构造 + _set_local_rank_env()
9
真正 spawn 出进程并进入监控循环 entrypoint 为字符串 → SubprocessContext → 每个 rank 一个 subprocess.Popen(args, env=父环境+worker_env, start_new_session=True)，退出时用 os.killpg 终止整个进程组。（只有通过 Python API 传函数时才会走 torch.multiprocessing，此时 --start-method 才生效。） elastic/multiprocessing/__init__.py: start_processes → SubprocessContext → SubprocessHandler._popen

一个容易误解的点：--start-method（spawn/fork/forkserver）对 torchrun 的命令行路径不生效。start_processes 只看 entrypoint 的类型：字符串 → SubprocessContext（Popen），只有函数才 → MultiprocessContext（torch.multiprocessing）。torchrun 传进来的永远是解释器路径这个字符串。

04rendezvous：rank 是谁定的

--rdzv-backend 决定使用哪个 RendezvousHandler 实现，三者的差别在于 rendezvous 由谁承载，以及是否支持 elastic 成员变更：

模式触发方式谁承载 rendezvous合适场景
static默认值由你指定：--node-rank 与 --master-addr/--master-port 直接作为参数传入，rank = node_rank、world_size = max_nodes；rank 0 创建 TCPStore(is_master=True)，其余节点作为 client 连接节点数固定、脚本化调度（k8s Job / Slurm）
c10d--rdzv-backend=c10d --rdzv-endpoint=host:portrendezvous store 自身（TCPStore / FileStore）。支持 min:max 弹性、动态成员变更，--standalone 也用它多机、需要容错与弹性扩容
etcd / etcd-v2--rdzv-backend=etcd-v2 --rdzv-endpoint=...外部 etcd（必须启用 v2 API）。功能与 c10d 等价，etcd 已进入维护模式已有 etcd 集群的存量环境

三种模式下 MASTER_ADDR / MASTER_PORT 从哪来

static--master-addr+--master-port→handler 直接使用该值→env: MASTER_ADDR/PORT
c10d / etcdrendezvous complete→rank0 在 store 里写 MASTER_ADDR/MASTER_PORT→所有 rank 读到同一份→env
端口易错点rank 0 会另找一个空闲端口给训练用的 store，并通过 store 广播≠rdzv-endpoint 的 29400

这就是「c10d 模式下你改 --master-port 没用」的根源：那两个值在 c10d 路径里由 rendezvous 现场商定并写进 store（RendezvousStoreInfo.build()，rank0 用 get_free_port() 或共享 TCPStore 的真实端口），--master-addr/--master-port 只被 spec.master_addr or rdzv_info.bootstrap_store_info.master_addr 这一行当作可选的覆盖项读取。

c10d 一轮 rendezvous 里到底发生了什么

a
先执行上一轮的 exit op每轮开始先执行一次 exit op，把自己从上一轮的 participants 中移除。节点的存活由 heartbeat 判定，heartbeat 过期的节点会被判定为退出。dynamic_rendezvous.py: next_rendezvous → _RendezvousExitOp
b
再 join 本轮，等待 quorum参与者数量 ≥ min_nodes 且 ≤ max_nodes，并到达 deadline 后才 complete。--rdzv-conf=timeout=... 控制这个等待窗口。参与者已满时，后来的节点先进入 wait_list；等待过久则转入 redundancy_list 作为替补。dynamic_rdzv.py: _RendezvousJoinOp
c
complete 之后拿到自己的 rankrank, world_size = self._get_world() —— 这就是前面的 group_rank 与 group_world_size。dynamic_rdzv.py: next_rendezvous 末尾
d
同时把训练所用 store 的地址广播出去rank 0 创建（或复用）一个 TCPStore，把 MASTER_ADDR/MASTER_PORT 写入 store；所有 rank 读到同一份 → 即 RendezvousStoreInfo。有了它，每个 worker 不必再自行启动 store server。rdzv_api.py: RendezvousStoreInfo.build

elasticity 的语义就在这里：节点数写成 --nnodes=1:4 时，多来的节点进入 wait_list，等待下一轮 rendezvous；处于 HEALTHY 状态时，agent 每次轮询都会检查 rdzv_handler.num_nodes_waiting()，只要有人在等待，就主动重启整个 worker group（成员变更不计入 restart 次数）。

代价说明写在官方文档里：成员一变，所有存活的 worker 立即被终止，新一轮以新的 RANK 与 WORLD_SIZE 重启。因此 world_size 会变化、不能写死，rank → 数据的映射也必须在重启后重建。

05注入给 worker 的环境变量

这是整条链路里最值得记住的一张表 —— 它就是 _start_workers() 中构造的 worker_env 字典，逐字对应。另有几个只在特定开关下出现、容易出错的变量，单列在后面。

变量取值 / 含义谁在使用
LOCAL_RANK本机第几个 worker，0..nproc-1。配 torch.cuda.set_device / device_ids 用你的脚本；DDP
RANK全局编号 = GROUP_RANK × LOCAL_WORLD_SIZE + LOCAL_RANKenv:// rendezvous
WORLD_SIZE全局进程总数 = 节点数 × nproc_per_nodeenv:// rendezvous

几个例外，都不是 torchrun 主动设置的

OMP_NUM_THREADS

仅当 nproc_per_node > 1 且父环境未设置时，torchrun 才会在 config_from_args 里设置 os.environ["OMP_NUM_THREADS"]="1"，随后经 Popen 的环境继承传递下去（_start_workers 中再显式拷贝一次）。

N 张卡跑 N 个进程时若不设置，每个进程默认创建大量线程，会争抢 CPU、反而降低吞吐。

TORCHELASTIC_TIMER_FILE

只有显式设置 TORCHELASTIC_ENABLE_FILE_TIMER=1，agent 才会创建一个命名管道作为本地 watchdog 判断 worker 是否存活，并把管道路径写入 worker 环境。

适用场景：NCCL 集合通信 desync —— 进程仍存在但不再推进。

VT_ / PET_ / MASTER_* 的继承

worker 的环境 = 父进程环境全量拷贝 + 上表覆盖（env_vars = os.environ.copy(); env_vars.update(env)）。

所以 shell 里 export 的 NCCL_*、CUDA_VISIBLE_DEVICES、PYTHONPATH 都会带进去；反之，父进程中过期的 MASTER_ADDR 会被正确覆盖，但过期的 LOCAL_RANK 只会在 worker 自己 fork 子进程时造成干扰。

PYTHON_EXEC

cmd = os.getenv("PYTHON_EXEC", sys.executable)：需要强制使用其他解释器（例如带特定 CUDA 版本的 venv）时，设置这个变量比修改 PATH 更可靠。

注意 --no-python 会跳过解释器直接执行脚本，此时再传 --module 会直接报错。

细节：CUDA_VISIBLE_DEVICES 到底有没有被改？

传统模式（默认）不做切割：_set_local_rank_env 只把父进程的 CUDA_VISIBLE_DEVICES 原样拷贝给 worker，LOCAL_RANK 给实际序号。因此 8 卡机器上 8 个进程都能看到 8 张卡，依靠 torch.cuda.set_device(LOCAL_RANK) 各自绑定到正确的卡 —— 这也是「忘记 set_device 时 8 个进程都用 GPU 0」的原因。

--virtual-local-rank 是另一套语义：每个 worker 的 LOCAL_RANK 均为 0，并把 CUDA_VISIBLE_DEVICES 收窄为它对应的 GPU（ROCm 下同时设置 HIP_VISIBLE_DEVICES）。适合写死 cuda:0 的既有代码，但要注意它会破坏「LOCAL_RANK 等于物理卡序号」这一假设。

06进程管理与容错：谁在看着谁

agent 的主循环 _invoke_run() 如下（省略了日志与指标）：

# elastic/agent/server/api.py: SimpleElasticAgent._invoke_run()
_initialize_workers(worker_group)          # rendezvous + 拼 env + Popen
while True:
    time.sleep(monitor_interval)           # 默认 0.1 s
    run_result = _monitor_workers(worker_group)
    state = run_result.state

    if state == SUCCEEDED:
        _exit_barrier()                    # 等其它节点的 agent 也跑完
        return run_result
    elif state in {UNHEALTHY, FAILED}:
        if self._remaining_restarts > 0:
            self._remaining_restarts -= 1
            _restart_workers(worker_group) # 停全组 → 重新 rendezvous → 全组重开
        else:
            _stop_workers(worker_group)
            return run_result              # 交给上层抛 ChildFailedError
    elif state == HEALTHY:
        if rdzv_handler.num_nodes_waiting() > 0:
            _restart_workers(worker_group) # 弹性：有人排队 → 成员变更，不计次
终止流程Popen(start_new_session=True)→os.killpg(pid, SIGTERM)→等待 shutdown_timeout（默认 30s）→SIGKILL
整组语义本节点用 killpg；跨节点依赖 store 中的共享状态→任一节点重启，其它节点观察到 rendezvous 变化后随之重启
退出全部 worker 成功→_exit_barrier()→在 store 上执行 barrier，等待所有 agent 到齐（默认 300s）

root cause 是怎么被识别出来的

子进程启动时会设置 TORCHELASTIC_ERROR_FILE 指向一个临时 JSON 文件；只要 main 被 @record 装饰，异常与 traceback 就会被写入其中。agent 收集各 rank 的错误文件，按时间戳取最早的一个作为 root cause，汇总成一条错误报告，并把该错误文件的内容复制到 launcher 自己的错误文件上 —— 因此最终看到的是最早真正出错的 rank，而不是一串级联失败。

失败模式（对应官方文档的 Failure Modes）：worker 失败 → 停止并重启整个 worker group，最多 max_restarts 次；agent 失败 / 节点掉线 → 等同于本节点 worker group 失败，由 job manager 决定是终止整个作业（gang 语义）还是替换节点；重启后 RANK 不稳定，本节点的 worker 可能被分到完全不同的 rank 区间，因此「只有 RANK 0 才存盘」这类假设在重启后会失效；标准做法是每个 rank 都保存，或只由 RANK==0 保存但保证幂等。

07worker 侧：init_process_group 怎么接上这份环境变量

dist.init_process_group(backend="nccl") 不传 init_method 时默认就是 env://，于是走 _env_rendezvous_handler：读 RANK、WORLD_SIZE、MASTER_ADDR、MASTER_PORT 四个变量（缺任何一个都直接抛「environment variable X expected, but not set」），创建或连接 TCPStore，然后由 backend 创建 communicator。

dist.init_process_group(backend="nccl")
  └─ init_method 为空 → 默认 "env://"                distributed_c10d.py
       └─ _env_rendezvous_handler()                   torch/distributed/rendezvous.py
            ├─ rank       = int(os.environ["RANK"])
            ├─ world_size = int(os.environ["WORLD_SIZE"])
            ├─ master_addr=     os.environ["MASTER_ADDR"]
            ├─ master_port= int(os.environ["MASTER_PORT"])
            └─ _create_c10d_store(master_addr, master_port, ...)
                 ├─ TORCHELASTIC_USE_AGENT_STORE=True 且就是 agent 自己的 addr:port
                 │     → 所有 rank 都只做 client（server 由 agent 承包）
                 └─ 否则 rank0 建 TCPStore(is_master=True, multi_tenant=True)
       └─ ProcessGroupNCCL(...)  ← 这里才真正建 NCCL 通信域、开始 all-reduce

由此可以推出几个实践结论：

agent 的 store ≠ 训练用的 store

rendezvous 使用的 store 负责参与者登记与 rank 分配；训练使用的是同一个 TCPStore server（多租户命名空间隔离，PrefixStore 前缀为 torch.rendezvous.<run_id>），也可能由 rank 0 的 worker 另起一个端口。

因此「MASTER_PORT 被占用」与「rdzv-endpoint 被占用」是两回事，报错位置也不同。

为什么建议传 device_id=

init_process_group(device_id=torch.device("cuda", LOCAL_RANK)) 会让 NCCL communicator 立即初始化（而不是在第一次集合通信时惰性初始化），错误在初始化处就暴露，而不是在第一个 all-reduce 上表现为超时。

PyTorch 2.6 起，不传 backend 时也会用 device_id 推断 backend（cuda → nccl）。

08命令行示例与常用参数

单机 8 卡

torchrun --standalone --nnodes=1 --nproc-per-node=8 train.py --bs 32 --lr 1e-4

最省事的一种：--standalone 让 torchrun 自动选择一个空闲端口（localhost:0）并生成 uuid 作为 rdzv_id。等价的显式写法是 --rdzv-backend=c10d --rdzv-endpoint=localhost:0。不写 --standalone 且 nnodes 最大值为 1 时，torchrun 也会自动走到同一条路径。

多机 4 节点 × 8 卡（static，节点数固定）

# 在 node0 上（node_rank=0 是 rank0 所在节点，必须能被其它节点访问到）
torchrun --nnodes=4 --nproc-per-node=8 \
         --node-rank=0 --master-addr=10.0.0.1 --master-port=29500 \
         train.py --bs 32

# node1 / node2 / node3：只有 --node-rank 不同
torchrun --nnodes=4 --nproc-per-node=8 \
         --node-rank=1 --master-addr=10.0.0.1 --master-port=29500 \
         train.py --bs 32

static 模式下每个节点的 --node-rank 必须互不相同且从 0 连续；--master-addr 填 node0 的地址（FQDN 或 IP，IPv6 使用 [::1] 形式）。所有节点的其余参数与脚本参数必须完全一致。

多机 + 容错（c10d，最多重启 3 次）

torchrun --nnodes=4 --nproc-per-node=8 \
         --rdzv-backend=c10d --rdzv-endpoint=node0.example.com:29400 \
         --rdzv-id=my-job-20261013 --max-restarts=3 \
         train.py --bs 32

所有节点执行同一条命令（没有 node_rank 之分）。--rdzv-id 必须在同一作业的所有节点上一致 —— 它是 store 中的命名空间，不一致会导致两个作业互相看不见或互相干扰。--rdzv-endpoint 省略端口时默认 29400。

弹性（节点数 1..4，成员变更属于正常语义）

torchrun --nnodes=1:4 --nproc-per-node=8 \
         --rdzv-backend=c10d --rdzv-endpoint=node0.example.com:29400 \
         --rdzv-id=my-job-20261013 --max-restarts=3 \
         train.py --bs 32

同一台机器并行跑多个作业

torchrun --rdzv-backend=c10d --rdzv-endpoint=localhost:0 \
         --nnodes=1 --nproc-per-node=4 train.py     # 端口 0 = 让内核挑

两个作业若共用同一个 MASTER_PORT，会被对方当作同一组的成员 —— 这是最难排查的一类故障，症状是 world_size 对不上或 RANK 重复。应使用 :0，或为每个作业分配不同端口。

09训练脚本要改什么：最小可运行示例

脚本侧只有三件事必须做对：读取 LOCAL_RANK 并绑定 device、不带参数调用 init_process_group、用 DDP 包装模型并让 DataLoader 按 rank 分片。

# train.py —— torchrun 直接跑这个文件
import os, torch, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, DistributedSampler
from torch.distributed.elastic.multiprocessing.errors import record

# 1) 每个进程一张卡：用 DDP 包装模型
def setup():
    # LOCAL_RANK 由 torchrun 注入；单卡调试时回退为 0
    local_rank = int(os.environ.get("LOCAL_RANK", 0))
    torch.cuda.set_device(local_rank)          # ← 漏了这句，8 个进程都会用 GPU 0

    # 2) 不带参数初始化：RANK/WORLD_SIZE/MASTER_ADDR/MASTER_PORT 全部由 torchrun 注入
    dist.init_process_group(
        backend="nccl",
        device_id=torch.device("cuda", local_rank),   # 立即初始化 communicator，错误尽早暴露
        timeout=__import__("datetime").timedelta(minutes=30),
    )
    # 或者显式：dist.init_process_group("nccl", init_method="env://")
    return dist.get_rank(), dist.get_world_size()

@record                                    # 让 root cause 带完整 traceback
def main():
    rank, world_size = setup()
    is_main = rank == 0

    model = MyModel().to(rank)
    model = DDP(model, device_ids=[rank])   # device_ids=LOCAL_RANK，output_device 同理

    dataset = MyDataset()
    # 3) 数据分片：由 sampler 保证各 rank 看到互不重叠的子集
    sampler = DistributedSampler(dataset, num_replicas=world_size, rank=rank, shuffle=True)
    loader = DataLoader(dataset, batch_size=32, sampler=sampler,
                        num_workers=4, pin_memory=True)

    for epoch in range(NUM_EPOCHS):
        sampler.set_epoch(epoch)            # ← 漏了这句，每个 epoch 的分片顺序都相同
        for x, y in loader:
            x, y = x.to(rank, non_blocking=True), y.to(rank, non_blocking=True)
            loss = model(x, y)
            loss.backward()
            optimizer.step(); optimizer.zero_grad(set_to_none=True)

        # 4) 容错：任何 rank 都可能被重启，checkpoint 必须可重复写入
        save_checkpoint_atomic(model, optimizer, epoch, path=CKPT)
        dist.barrier()

    if is_main:
        print("done", rank, world_size)
    dist.destroy_process_group()

if __name__ == "__main__":
    main()

为什么不要在脚本里手写 MASTER_ADDR

常见做法是在脚本里写 os.environ["MASTER_ADDR"]="127.0.0.1" 作为「方便单机调试」的默认值 —— 在多节点上这会让每个节点的 rank 0 都去连自己的 localhost，形成若干个互不可见的独立分组，最典型的表现是 torchrun 阻塞在 init_process_group 直到超时。

正确的单卡调试方式是：python train.py 时用 getenv 返回默认值，而不是覆盖环境变量。

rank → device 的映射规则

torchrun 不会替你设置 current device，只提供 LOCAL_RANK。是否调用 set_device 完全由脚本决定，这也是「device 不对」（NCCL 报 invalid device / 显存占用集中在 GPU 0）最常见的原因。

推荐写法：device = torch.device("cuda", int(os.environ["LOCAL_RANK"]))，之后所有 .to(device) 都使用它。

PyTorch 2.0 起的 --local-rank 变化（旧脚本会在此处报错）

2.0 之前 torchrun 会向命令行追加 --local_rank=N（下划线）；2.0 起改为 --local-rank=N（连字符），并且只在 use_env=False 的旧路径下才注入 —— 如今默认全程走环境变量，不再追加该参数。

如果 argparse 只注册了 --local_rank，而某个环境注入了连字符版本，就会报 unrecognized arguments: --local-rank=N。兼容写法：parser.add_argument("--local-rank", "--local_rank", type=int)。新脚本建议只使用环境变量。

10常见故障与排查

每条都给出典型报错原文的关键片段（括号内为它出现在哪一层）与排查顺序，按「观察到什么 → 先排查什么」组织。

① 端口占用 / 两个作业被识别为同一组

Address already in use · The server socket on ...:29500 has failed to bind (TCPStore, rank0) · Timed out after 300 seconds waiting for clients. 4/8 clients joined.

  • 先确认是哪个端口：MASTER_PORT（训练用 store）与 --rdzv-endpoint（29400，rendezvous store）都可能被占用。
  • 用 lsof -i :29500 / ss -ltnp | grep 29400 确认是否为上一次作业未完全退出；pkill -f torchrun 后重试。
  • 同机多作业：用 --standalone 或 --rdzv-endpoint=localhost:0 让内核选择端口，不要手工分配。
  • 「clients joined 停在中途」通常与端口无关，而是节点间网络问题：某些节点根本没连上 store。先在各节点执行 nc -vz <master_addr> <port>。

② rendezvous 超时 / 节点无法满足 quorum

RendezvousTimeoutError · The node 'xxx' has failed to join the rendezvous 'none' in 900 seconds · RendezvousConnectionError: The connection to the C10d store has failed.

  • 先确认各节点是否都在运行、参数是否一致：--rdzv-id 不同 → 各自创建新作业；--nnodes 不同 → 永远无法满足 quorum。
  • rank 0 地址不可达：--master-addr/--rdzv-endpoint 用了容器内的 127.0.0.1，或用了无法反向解析的短主机名。应使用 IP 或 FQDN，并在每台机器上验证可达性。
  • 时钟不同步（NTP）会导致 heartbeat 判定异常，表现为随机节点被移除；多机环境应先确认时钟同步。
  • 可调大等待窗口：--rdzv-conf=timeout=1800。注意影响 complete 时机的是 rdzv timeout，而不是 --monitor-interval。

③ 环境变量缺失 → 初始化直接失败

ValueError: Error initializing torch.distributed using env:// rendezvous: environment variable RANK expected, but not set (或 WORLD_SIZE / MASTER_ADDR / MASTER_PORT)

  • 这是「脚本不是由 torchrun 启动」的典型信号：直接 python train.py 时不存在这些变量。
  • 脚本中不要用 os.environ[...] = ... 覆盖；确实需要调试时用 os.environ.setdefault 并配 WORLD_SIZE=1。
  • 缺少 LOCAL_RANK 时，脚本里直接写 os.environ["LOCAL_RANK"] 会抛 KeyError，建议用 getenv 取默认值 0。
  • 自定义 launcher 或二次 fork 时最常见：父进程环境未透传。检查 env_vars = os.environ.copy(); env_vars.update(worker_env) 这条链路是否被中断。

④ RANK 分配与「由谁写 checkpoint」的假设冲突

现象：重启后 TORCHELASTIC_RESTART_COUNT 增加，但 checkpoint 目录被另一个 rank 覆盖，或恢复时 world_size 对不上

  • RANK 在重启与成员变更后不稳定；官方明确要求不要假设 RANK 的稳定性，也不要假设 RANK 与 LOCAL_RANK 之间存在固定关系。
  • 启用 elastic 后 WORLD_SIZE 会变化，checkpoint 中应记录 world_size 与 shard 方案，恢复时按新的 world_size 重新切分。
  • 只在 RANK==0 写 checkpoint 时必须配原子写（先写临时文件再 os.replace），否则写了一半的文件会被当成有效 checkpoint。
  • 在日志中打印 TORCHELASTIC_RESTART_COUNT 与 TORCHELASTIC_RUN_ID，很多「数据重复」问题由此即可定位。

⑤ hang 住：初始化完成但集合通信不返回

NCCL timeout / Watchdog caught collective operation timeout · ProcessGroupNCCL is aborting · 或完全没有输出、torchrun 一直阻塞

  • 先判断是「组内少了一个 rank」还是「网络异常」：用 nvidia-smi 确认每张卡上都有进程；用 --tee 3 --log-dir 把各 rank 日志写入文件，观察哪个 rank 停止推进。
  • 集合通信的次数或顺序不一致（某个 rank 进入了不同的 if 分支）是最常见的根因 —— 检查是否存在依赖数据的控制流，以及是否正确调用 DistributedSampler 的 set_epoch。
  • NCCL 的两种等待策略：TORCH_NCCL_BLOCKING_WAIT=1（阻塞等待）或 TORCH_NCCL_ASYNC_ERROR_HANDLING=1（异步中止，torchrun 会透传）；配合 TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC 可以更早得到报错。
  • 多网卡机器：NCCL_SOCKET_IFNAME=eth0 / NCCL_IB_HCA=... 指定错误网卡时，会表现为「连不上但也不报错」的阻塞。
  • 可用 torch.distributed.breakpoint()，或设置 TORCHELASTIC_ENABLE_FILE_TIMER=1 的文件 watchdog 来捕获「进程存在但不再推进」的情况。

⑥ worker 崩溃 → 整组被终止，看起来像「无故重启」

[default0]: exitcode: 1 (pid: 12345) · [default2]: exitcode: -9 · ChildFailedError: torchrun failed with 1 ... (附各 rank 时间戳与 traceback)

  • 被内核 OOM killer 终止 = exitcode -9，查看 dmesg | tail；显存不足则表现为 CUDA OOM 的 Python 异常。
  • 任何一个 rank 抛出未捕获异常，torchrun 都会停止整个 worker group（这是设计行为，不是 bug）。因此看到「8 个 rank 全部失败」时，应按时间戳找最早的那个 —— torchrun 已经标注了 root cause。
  • 未加 @record 时，错误摘要里只有 exitcode 而没有 traceback —— 这是官方推荐使用的装饰器，建议直接加上。
  • 被 SIGKILL 后处于 D 状态（不可中断睡眠）的进程会拖住重启；新版 agent 会把卡住的 worker group 标记为 UNHEALTHY 并放弃重启，此时应查看日志中的 D-state 提示。

12四个常见误解

误解 1：torchrun 只是多了一层循环的 python -m torch.distributed.launch

launch 是旧 API，只负责启动 N 个进程并传入 --local_rank；torchrun 走的是 torchelastic 的 agent + rendezvous：多机拓扑由 rendezvous 决定，具备成员变更语义、重启预算与 root cause 汇总。launch 时代的 --use-env/--node-rank 行为只作为兼容参数保留在 --node-rank 上。

误解 2：--max-restarts=3 是每个 worker 可重启 3 次

实际是 worker group 级 3 次。任何一次失败都会停止全部 worker、重新 rendezvous、全部重启，且不按 monitor 的失败计数累计 —— elastic 成员变更甚至不消耗这个额度。

误解 3：rdzv 与 init_process_group 是两套东西，可以各自配置

两者确实各自独立（rdzv endpoint 29400 与训练用 store），但在 c10d 模式下，训练 store 的地址由 rendezvous 决定并广播，手工修改 MASTER_PORT 无效。只有 static 模式下才由你直接指定。

一句话区分控制面与数据面

控制面：torchrun / agent / rendezvous / store，负责参与者登记、rank 分配与失败处理，走 TCP + KV。
数据面：worker 之间的 NCCL / NCCL-IB，负责梯度等张量的集合通信，走 NVLink/IB/RoCE。两者的日志、报错与调优参数互不通用。

自测题：4 个节点 × 8 卡，node2 上 local_rank=5 的进程，它的 RANK / WORLD_SIZE / GROUP_RANK 各是多少？

LOCAL_WORLD_SIZE = 8、GROUP_WORLD_SIZE = 4 → WORLD_SIZE = 32；GROUP_RANK = 2（static 下即 --node-rank=2）；RANK = 2 × 8 + 5 = 21。

追问：如果第 3 个节点在训练中途掉线、--nnodes=1:4 的 elastic 语义生效，重启后这个进程的 RANK 还是 21 吗？不一定 —— 新一轮 rendezvous 会重新分配 RANK，WORLD_SIZE 也可能变为 24。
