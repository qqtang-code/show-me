torchrun 是怎么把一次命令变成 N 个训练进程的

2026-10-13torchruntorchelasticrendezvousDDP源码走读

你敲下 torchrun --nproc-per-node=8 train.py，最后跑起来的是 8 个各自持有一张卡的 Python 进程，它们能互相找到、能组成一个 process group、挂了还能被拉起来。中间发生的事全部在 torch.distributed.run 和它下面的 torchelastic 里：解析参数 → 每台机器起一个 agent → agent 用 rendezvous 给所有节点排座次 → agent 按座次给每个 worker 拼一份环境变量 → 用 subprocess.Popen 把它们生出来 → 循环监控、失败就整组重启。这一页把这条链路拆开，每个结论都指到源码里的那一行。

结论 谁是谁 启动流程 9 步 rendezvous 环境变量 守护与重启 init_process_group 命令行示例 脚本适配 踩坑排查

01结论

TL;DR

  • torchrun 自己不跑训练，也不做通信。它只是一个 launcher：进程里跑的是 elastic_launch → LocalElasticAgent，agent 再 Popen 出真正的训练进程。torchrun 退出 = agent 退出 = 所有 worker 被 killpg 收走。
  • 真正的 rank 不是参数算出来的，是 rendezvous 排出来的。每台机器的 agent 带着 (min_nodes, max_nodes, nproc_per_node) 去 rendezvous 报到，拿到一个 group_rank（节点的座次）和 group_world_size（本轮节点数），然后 global_rank = group_rank × local_world_size + local_rank。所以 rank 在重启后会变。
  • --master-addr/--master-port/--node-rank 只在 --rdzv-backend=static（默认）下有效；--rdzv-backend=c10d 下会被忽略甚至告警，MASTER_ADDR/MASTER_PORT 改由 rendezvous 现场商定。
  • 注入给 worker 的是完整的环境变量字典（RANK/WORLD_SIZE/LOCAL_RANK/MASTER_ADDR/MASTER_PORT/…），不是命令行参数。脚本里 dist.init_process_group() 无参就能跑，靠的就是它默认走 env://。
  • --max-restarts 重启的是「整个 worker group」，不是坏掉的那个 worker：任一 worker 挂掉 → 所有节点的 worker 全被杀 → 重新 rendezvous → 全部用新 rank 重开。不存 checkpoint 就等于白丢。

02谁是谁：六个角色

先分清这几个东西，后面所有细节才挂得住。torchrun 是 torch.distributed.run 的 console script，两者完全等价（python -m torch.distributed.run 也行）。它启动后，进程里做的第一件正事是构造 LaunchConfig 并调用 elastic_launch。

03启动流程：从命令行到 8 个进程

下面九步对应源码里从 run(args) 到 Popen 的真实顺序。第 5 步的 monitor_interval 和 start_method 用的是默认值 0.1s / spawn。

1
解析参数，并用 PET_* 环境变量兜底 每个 --flag 都注册了 action=env：命令行没给就看 PET_FLAG（下划线转连字符、大写）。所以 PET_NNODES=2 torchrun train.py 等价于 --nnodes=2。 run.py: get_args_parser() · torch/distributed/argparse_util.py: class env
2
给默认值兜底，决定 rendezvous 怎么走 ① --standalone → 强制 c10d / localhost:0 / uuid4；② 没写 endpoint 且 --nnodes 最大值是 1 → 同样悄悄换成 c10d / localhost:0；③ master_port 为 None 时填 29500。 run.py: run() — 所以单机单节点不写任何 rdzv 参数也不会撞 29500
3
算出节点数与每节点进程数 parse_min_max_nnodes("1:4") → (1,4)；determine_local_world_size 支持 auto/cpu/gpu/xpu/int，gpu 取 torch.cuda.device_count()。若 nproc_per_node > 1 且 OMP_NUM_THREADS 未设，torchrun 会替你设成 1 并打一条大告警。 run.py: parse_min_max_nnodes / determine_local_world_size / config_from_args
4
拼出 LaunchConfig 和 worker 的启动命令 命令 = sys.executable -u train.py <剩余参数原文>（-u 保证日志不缓冲；PYTHON_EXEC 可覆盖解释器；-m 走模块）。注意：这里没有 rank 相关参数，rank 全走环境变量。 run.py: config_from_args 末尾 — 仅当老式 use_env=False 才追加 --local-rank=
5
构造 handler 与 agent get_rendezvous_handler(params) 按字符串查注册表（static/c10d/etcd/etcd-v2，插件可扩展），再连同 WorkerSpec 一起塞进 LocalElasticAgent。 launcher/api.py: launch_agent() · elastic/rendezvous/registry.py
6
等所有节点到齐 —— rendezvous 每台机器一个 agent 去 rendezvous 报到。静态模式就是「连 rank0 的 TCPStore」；c10d/etcd 模式是「一轮一轮 join，凑够 min_nodes 且到 deadline 就成团」。回来的是 group_rank 与 group_world_size。 agent: _rendezvous() → handler.next_rendezvous()
7
把座次摊成每个 worker 的 global_rank global_rank = group_rank × local_world_size + local_rank。默认（非 identical）走 store 慢路径：各 agent 写 torchelastic/role_info/<group_rank>，group_rank 0 算好后写回 assigned_ranks/<i>，其余 agent 阻塞 get 等结果。 agent: _assign_worker_ranks() — 快路径需 TORCH_ELASTIC_WORKER_IDENTICAL=1
8
为每个 worker 生成一份环境变量字典 13 个变量一次写全（见下一节），其中 LOCAL_RANK、RANK、WORLD_SIZE、MASTER_ADDR/PORT 是分布式初始化的全部输入。有 CUDA_VISIBLE_DEVICES 就原样继承，不切割。 agent: _start_workers() 的 worker_env 构造 + _set_local_rank_env()
9
真正 fork/exec 出进程并进入监控循环 entrypoint 是字符串 → SubprocessContext → 每 rank 一个 subprocess.Popen(args, env=父环境+worker_env, start_new_session=True)，退出时 os.killpg 整组杀。（只有当你用 python API 传函数时才会走 torch.multiprocessing，那时 --start-method 才生效。） elastic/multiprocessing/__init__.py: start_processes → SubprocessContext → SubprocessHandler._popen

一个容易误解的点：--start-method（spawn/fork/forkserver）对 torchrun 命令行路径不起作用。start_processes 只看 entrypoint 的类型：字符串 → SubprocessContext（Popen），只有函数才 → MultiprocessContext（torch.multiprocessing）。torchrun 传进来的永远是解释器路径这个字符串。

04rendezvous：rank 是谁定的

--rdzv-backend 决定用哪个 RendezvousHandler 实现，三者的差别只在「谁当裁判」和「能不能弹性」：

模式触发方式裁判是谁合适场景
static默认值你自己：--node-rank + --master-addr/--master-port 直接喂进去，rank=node_rank、world_size=max_nodes，rank0 起一个 TCPStore(is_master=True)，别人连它节点数固定、脚本化调度（k8s Job / Slurm）
c10d--rdzv-backend=c10d --rdzv-endpoint=host:port一个 rendezvous 存储本身（TCPStore / FileStore）。支持 min:max 弹性、动态成员变更、--standalone 也用它多机、需要容错与弹性扩容
etcd / etcd-v2--rdzv-backend=etcd-v2 --rdzv-endpoint=...外部 etcd（必须开 v2 API）。功能等价 c10d，etcd 已进维护模式已有 etcd 集群的存量环境

三种模式下 MASTER_ADDR / MASTER_PORT 从哪来

static--master-addr+--master-port→handler 直接用→env: MASTER_ADDR/PORT
c10d / etcdrendezvous 成团→rank0 在 store 里写 MASTER_ADDR/MASTER_PORT→所有 rank 读同一份→env
端口的坑rank0 会另找一个空闲端口给训练用 store，并在 store 里广播≠rdzv-endpoint 的 29400

这就是「c10d 模式下你改 --master-port 没用」的根源：那两个值在 c10d 路径里由 rendezvous 现场商定并写进 store（RendezvousStoreInfo.build()，rank0 用 get_free_port() 或共享 TCPStore 的真实端口），--master-addr/--master-port 只被 spec.master_addr or rdzv_info.bootstrap_store_info.master_addr 这一行当作可选的覆盖项读取。

c10d 一轮 rendezvous 里到底发生了什么

a
先参加上一轮的「离场」每轮开始先跑一次 exit op，把自己从上一轮的 participants 里摘出去。心跳（heartbeat）决定一个节点是否还活着；心跳过期的节点会被判定退出。dynamic_rendezvous.py: next_rendezvous → _RendezvousExitOp
b
再 join 本轮，等 quorum人数 ≥ min_nodes、≤ max_nodes，且到达 deadline 才「成团」（complete）。--rdzv-conf=timeout=... 控制这个等待窗口。已经满员的后来者先挂 wait_list，满太久就进 redundancy_list 等着替补。dynamic_rdzv.py: _RendezvousJoinOp
c
成团后拿到自己的号rank, world_size = self._get_world() —— 这就是前面的 group_rank 与 group_world_size。dynamic_rdzv.py: next_rendezvous 末尾
d
顺带把训练用的 store 地址广播出去rank0 建（或复用）一个 TCPStore，把 MASTER_ADDR/MASTER_PORT 写进 store；所有 rank 读同一份 → 这就是 RendezvousStoreInfo。它的存在让每个 worker 不必自己再起一个 store server。rdzv_api.py: RendezvousStoreInfo.build

弹性（elasticity）的语义就藏在这里：节点数写成 --nnodes=1:4 时，多来的节点排进 wait_list，等下一轮成团；HEALTHY 状态下 agent 每次轮询都会看 rdzv_handler.num_nodes_waiting()，只要有人排队，就主动重启整个 worker group（成员变更不计入 restart 次数）。

代价说明写在官方文档里：成员一变，所有存活的 worker 立刻被杀，新的一轮用新的 RANK 和 WORLD_SIZE 重开。所以 world_size 会变，不能写死，rank→数据的映射也必须在重启后重建。

05注入给 worker 的环境变量：13 个 + 例外

这是整条链路里最值得背下来的一张表 —— _start_workers() 里那个 worker_env 字典就是它，逐字对应。此外还有几个只在特定开关下出现、容易踩坑的变量，单列在后面。

三个例外，都不是 torchrun 主动设的

OMP_NUM_THREADS

只在 nproc_per_node > 1 且父环境没设时，torchrun 会在 config_from_args 里把 os.environ["OMP_NUM_THREADS"]="1"，然后经由 Popen 的环境继承传下去（_start_workers 里再显式拷一次）。

N 卡跑 N 个进程时如果不设，每个进程默认起满线程 → 争抢 CPU，吞吐反而掉。

TORCHELASTIC_TIMER_FILE

只有你显式设了 TORCHELASTIC_ENABLE_FILE_TIMER=1，agent 才会建一个命名管道做「worker 还活着吗」的本地看门狗，并把管道路径塞进 worker 环境。

用得上它的场景：NCCL 卡死的集合通信（desync），进程还在但不推进。

VT_ / PET_ / MASTER_* 的继承

worker 的环境 = 父进程环境全量拷贝 + 上表覆盖（env_vars = os.environ.copy(); env_vars.update(env)）。

所以你在 shell 里 export 的 NCCL_*、CUDA_VISIBLE_DEVICES、PYTHONPATH 都会带进去；反过来，父进程里 stale 的 MASTER_ADDR 会被正确覆盖，但 stale 的 LOCAL_RANK 之类只会在 worker 自己 fork 子进程时添乱。

PYTHON_EXEC

cmd = os.getenv("PYTHON_EXEC", sys.executable)：想强制用别的解释器（比如带特定 CUDA 版本的 venv），设这个变量比改 PATH 更可靠。

注意 --no-python 会跳过解释器直接执行脚本，此时 --module 会直接报错。

细节：CUDA_VISIBLE_DEVICES 到底有没有被改？

传统模式（默认）不切割：_set_local_rank_env 只把父进程的 CUDA_VISIBLE_DEVICES 原样拷给 worker，LOCAL_RANK 给真实序号。所以 8 卡机器上 8 个进程都能看到 8 张卡，靠 torch.cuda.set_device(LOCAL_RANK) 各就各位 —— 这也是「忘了 set_device 时 8 个进程全挤在 GPU0」的原因。

--virtual-local-rank 是另一套：每个 worker 的 LOCAL_RANK 都设成 0，并把 CUDA_VISIBLE_DEVICES 收紧成它那一张卡（ROCm 下同时设 HIP_VISIBLE_DEVICES）。适合那些写死 cuda:0 的老代码，但注意它和 LOCAL_RANK 语义假设会打架。

06进程管理与容错：谁在看着谁

agent 的主循环 _invoke_run() 长这样（去掉了日志和指标）：

# elastic/agent/server/api.py: SimpleElasticAgent._invoke_run()
_initialize_workers(worker_group)          # rendezvous + 拼 env + Popen
while True:
    time.sleep(monitor_interval)           # 默认 0.1 s
    run_result = _monitor_workers(worker_group)
    state = run_result.state

    if state == SUCCEEDED:
        _exit_barrier()                    # 等其它节点的 agent 也跑完
        return run_result
    elif state in {UNHEALTHY, FAILED}:
        if self._remaining_restarts > 0:
            self._remaining_restarts -= 1
            _restart_workers(worker_group) # 停全组 → 重新 rendezvous → 全组重开
        else:
            _stop_workers(worker_group)
            return run_result              # 交给上层抛 ChildFailedError
    elif state == HEALTHY:
        if rdzv_handler.num_nodes_waiting() > 0:
            _restart_workers(worker_group) # 弹性：有人排队 → 成员变更，不计次
kill 语义Popen(start_new_session=True)→os.killpg(pid, SIGTERM)→等 shutdown_timeout（默认 30s）→SIGKILL
「全组」本机是 killpg；跨节点靠 store 里的集体状态→任一节点重启，其它节点看到 rendezvous 变化后跟着重启
退出worker 全成功→_exit_barrier()→在 store 上 bar，等所有 agent 到齐（默认 300s）

Root cause 是怎么被找出来的

子进程启动时设了 TORCHELASTIC_ERROR_FILE 指向一个临时 json；只要你的 main 被 @record 装饰，异常与 traceback 就会被写进去。agent 收集各 rank 的错误文件，按时间戳取最早的那个当 root cause，汇总成一条错误报告，并且把这份错误文件的内容复制到 launcher 自己的错误文件上 —— 所以最后你看到的是「第一个真正出错的那个 rank」，而不是一串级联失败。

失败模式对照（官方文档的原话翻译）：worker 失败 → 全组停、重启，最多 max_restarts 次；agent 失败 / 节点掉线 → 等于本机 worker group 失败，由 job manager 决定是 kill 整个作业（gang 语义）还是换节点；重启后 rank 不稳定，本地 worker 可能被分到完全不同的 rank 区间，所以「rank 0 才存盘」这种假设在重启后会错乱，标准做法是每个 rank 都存、或者只按 RANK==0 存但保证幂等。

07worker 侧：init_process_group 怎么接上这份环境变量

dist.init_process_group(backend="nccl") 不传 init_method 时默认就是 env://，于是走 _env_rendezvous_handler：读 RANK、WORLD_SIZE、MASTER_ADDR、MASTER_PORT 四个变量（缺任何一个都直接抛「environment variable X expected, but not set」），建/连 TCPStore，然后由 backend 建通信域。

dist.init_process_group(backend="nccl")
  └─ init_method 为空 → 默认 "env://"                distributed_c10d.py
       └─ _env_rendezvous_handler()                   torch/distributed/rendezvous.py
            ├─ rank       = int(os.environ["RANK"])
            ├─ world_size = int(os.environ["WORLD_SIZE"])
            ├─ master_addr=     os.environ["MASTER_ADDR"]
            ├─ master_port= int(os.environ["MASTER_PORT"])
            └─ _create_c10d_store(master_addr, master_port, ...)
                 ├─ TORCHELASTIC_USE_AGENT_STORE=True 且就是 agent 自己的 addr:port
                 │     → 所有 rank 都只做 client（server 由 agent 承包）
                 └─ 否则 rank0 建 TCPStore(is_master=True, multi_tenant=True)
       └─ ProcessGroupNCCL(...)  ← 这里才真正建 NCCL 通信域、开始 all-reduce

几个由此推出的实践结论：

agent 的 store ≠ 训练用的 store

rendezvous 用的 store 承担「谁来了、你是几号」；训练用的是同一个 TCPStore 服务器（多租户命名空间隔离，PrefixStore 前缀 torch.rendezvous.<run_id>），也可能由 rank0 的 worker 另起一个端口。

所以「MASTER_PORT 被占用」和「rdzv-endpoint 被占用」是两件不同的事，报错位置也不同。

为什么 device_id= 值得带

init_process_group(device_id=torch.device("cuda", LOCAL_RANK)) 会让 NCCL 通信域立刻初始化（而不是第一次集合通信时懒加载），错误在初始化处就暴露，而不是在第一个 all-reduce 变成超时。

PyTorch 2.6 起，不传 backend 时也会用 device_id 推断后端（cuda→nccl）。

08命令行示例与常用参数

单机 8 卡

torchrun --standalone --nnodes=1 --nproc-per-node=8 train.py --bs 32 --lr 1e-4

最省心的一种：--standalone 让 torchrun 自动选一个空闲端口（localhost:0）并生成 uuid 作 rdzv_id。等价的显式写法是 --rdzv-backend=c10d --rdzv-endpoint=localhost:0。不写 --standalone 且 nnodes 最大值为 1 时，torchrun 也会自动走到同样的路径。

多机 4 节点 × 8 卡（static，节点数固定）

# 在 node0 上（node_rank=0 是 rank0 所在节点，必须能被其它节点访问到）
torchrun --nnodes=4 --nproc-per-node=8 \
         --node-rank=0 --master-addr=10.0.0.1 --master-port=29500 \
         train.py --bs 32

# node1 / node2 / node3：只有 --node-rank 不同
torchrun --nnodes=4 --nproc-per-node=8 \
         --node-rank=1 --master-addr=10.0.0.1 --master-port=29500 \
         train.py --bs 32

static 模式下每个节点的 --node-rank 必须互不相同且从 0 连续；--master-addr 写 node0 的地址（FQDN 或 IP，IPv6 用 [::1] 形式）。所有节点的其它参数、脚本参数必须完全一致。

多机 + 容错（c10d，最多重启 3 次）

torchrun --nnodes=4 --nproc-per-node=8 \
         --rdzv-backend=c10d --rdzv-endpoint=node0.example.com:29400 \
         --rdzv-id=my-job-20261013 --max-restarts=3 \
         train.py --bs 32

所有节点跑同一条命令（没有 node_rank 之分）。--rdzv-id 必须同一个作业一致 —— 它是 store 里的命名空间，写错会让两个作业互相看不见或互相串味。--rdzv-endpoint 省略端口时默认 29400。

弹性（节点数 1..4，成员变更也算作业的一部分）

torchrun --nnodes=1:4 --nproc-per-node=8 \
         --rdzv-backend=c10d --rdzv-endpoint=node0.example.com:29400 \
         --rdzv-id=my-job-20261013 --max-restarts=3 \
         train.py --bs 32

同一台机器并行跑多个作业

torchrun --rdzv-backend=c10d --rdzv-endpoint=localhost:0 \
         --nnodes=1 --nproc-per-node=4 train.py     # 端口 0 = 让内核挑

两个作业若共用同一个 MASTER_PORT，会出现「互相当成同一组的成员」这种最难查的故障 —— 症状是 world_size 对不上或 rank 重复。用 :0 或给每个作业分配不同端口。

09训练脚本要改什么：最小可运行示例

脚本侧只有三件事必须做对：读 LOCAL_RANK 并选卡、无参 init_process_group、用 DDP 包模型并让 DataLoader 按 rank 分片。

# train.py —— torchrun 直接跑这个文件
import os, torch, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, DistributedSampler
from torch.distributed.elastic.multiprocessing.errors import record

# 1) 分布式训练必须用 DDP：每个进程一张卡
def setup():
    # LOCAL_RANK 由 torchrun 注入；单卡调试时回落到 0
    local_rank = int(os.environ.get("LOCAL_RANK", 0))
    torch.cuda.set_device(local_rank)          # ← 漏了这句 8 个进程全挤 GPU0

    # 2) 无参初始化：RANK/WORLD_SIZE/MASTER_ADDR/MASTER_PORT 全部来自 torchrun
    dist.init_process_group(
        backend="nccl",
        device_id=torch.device("cuda", local_rank),   # 立即建通信域，错误早暴露
        timeout=__import__("datetime").timedelta(minutes=30),
    )
    # 或者显式：dist.init_process_group("nccl", init_method="env://")
    return dist.get_rank(), dist.get_world_size()

@record                                    # 让 root cause 带完整 traceback
def main():
    rank, world_size = setup()
    is_main = rank == 0

    model = MyModel().to(rank)
    model = DDP(model, device_ids=[rank])   # device_ids=LOCAL_RANK，output_device 同理

    dataset = MyDataset()
    # 3) 数据分片：sampler 负责让每个 rank 看到不重叠的子集
    sampler = DistributedSampler(dataset, num_replicas=world_size, rank=rank, shuffle=True)
    loader = DataLoader(dataset, batch_size=32, sampler=sampler,
                        num_workers=4, pin_memory=True)

    for epoch in range(NUM_EPOCHS):
        sampler.set_epoch(epoch)            # ← 漏了这句每个 epoch 的分片顺序都一样
        for x, y in loader:
            x, y = x.to(rank, non_blocking=True), y.to(rank, non_blocking=True)
            loss = model(x, y)
            loss.backward()
            optimizer.step(); optimizer.zero_grad(set_to_none=True)

        # 4) 容错：任何 rank 都可能被重启，checkpoint 必须可重复写
        save_checkpoint_atomic(model, optimizer, epoch, path=CKPT)
        dist.barrier()

    if is_main:
        print("done", rank, world_size)
    dist.destroy_process_group()

if __name__ == "__main__":
    main()

为什么不要手写 MASTER_ADDR

很多人习惯在脚本里 os.environ["MASTER_ADDR"]="127.0.0.1" 兜底「方便单机调试」—— 这在多节点上会让每个节点的 rank0 都去连自己的 localhost，于是形成若干个互相看不见的孤岛，最典型的症状是 torchrun 卡在 init_process_group 直到 timeout。

正确的单卡调试方式是 python train.py 时用 getenv 返回默认值，而不是覆盖 env。

rank → 卡 的映射规则

torchrun 不帮你设 current device，只给 LOCAL_RANK。是否调 set_device 完全由脚本决定，这也是「设备不对」（NCCL 报 invalid device / 显存爆在 GPU0）最常见的原因。

习惯写法：device = torch.device("cuda", int(os.environ["LOCAL_RANK"]))，之后所有 .to(device) 都用它。

PyTorch 2.0 起的 --local-rank 变化（老脚本会在这里炸）

2.0 之前 torchrun 会往命令行里塞 --local_rank=N（下划线）；2.0 起改成 --local-rank=N（连字符），并且只在 use_env=False 的老式路径下才注入 —— 现在默认全程走环境变量，压根不加这个参数。

如果你的 argparse 只注册了 --local_rank，而某个环境又注入了连字符版本，会报 unrecognized arguments: --local-rank=N。兼容写法：parser.add_argument("--local-rank", "--local_rank", type=int)。新脚本建议直接只用环境变量。

10踩坑与排查

下面每一条都给了典型报错原文的关键片段（括号里是它出现在哪一层）和排查顺序，按「看到什么 → 先查什么」排列。

① 端口占用 / 两个作业串成一组

Address already in use · The server socket on ...:29500 has failed to bind (TCPStore, rank0) · Timed out after 300 seconds waiting for clients. 4/8 clients joined.

  • 先分清是哪个端口：MASTER_PORT（训练 store）与 --rdzv-endpoint（29400，rendezvous store）。两者都可能被占。
  • lsof -i :29500 / ss -ltnp | grep 29400 看是不是上个作业没退干净；pkill -f torchrun 后重试。
  • 同机多作业：用 --standalone 或 --rdzv-endpoint=localhost:0 让内核挑端口，别手工分配。
  • 「clients joined 卡在中途」通常不是端口，是节点之间的网络：某些节点根本没连上 store。先在每台机器上 nc -vz <master_addr> <port>。

② rendezvous 超时 / 节点对不齐

RendezvousTimeoutError · The node 'xxx' has failed to join the rendezvous 'none' in 900 seconds · RendezvousConnectionError: The connection to the C10d store has failed.

  • 先看每个节点是否都在跑、参数是否一致：--rdzv-id 不同 = 各自开新作业；--nnodes 不同 = 永远凑不齐 quorum。
  • rank0 地址不可达：--master-addr/--rdzv-endpoint 用了容器内的 127.0.0.1、或用了没做反向解析的短主机名。用 IP 或 FQDN，并在每台机器验证可达。
  • 时间不同步（NTP）会让心跳判定错乱，表现为随机节点被踢出；多机环境先确认时钟同步。
  • 调大等待窗口：--rdzv-conf=timeout=1800；排查阶段把 --monitor-interval 调小没关系，但真正影响成团的是 rdzv timeout。

③ 环境变量没设对 → 初始化直接失败

ValueError: Error initializing torch.distributed using env:// rendezvous: environment variable RANK expected, but not set (或 WORLD_SIZE / MASTER_ADDR / MASTER_PORT)

  • 这是「脚本没被 torchrun 启动」的经典信号：直接 python train.py 就没有这些变量。
  • 脚本里不要自己 os.environ[...] = ... 覆盖；确需调试就 os.environ.setdefault + WORLD_SIZE=1。
  • 缺 LOCAL_RANK 时脚本若写了 os.environ["LOCAL_RANK"] 会 KeyError，建议 getenv 兜底为 0。
  • 自定义 launcher / 二次 fork 时最常见：父进程的环境没透传，检查 env_vars = os.environ.copy(); env_vars.update(worker_env) 这条链路是否被你自己打断。

④ rank 分配与「谁来存盘」假设冲突

现象：重启后 TORCHELASTIC_RESTART_COUNT 涨了，但 checkpoint 目录被另一个 rank 覆盖 / 恢复时 world_size 对不上

  • rank 在重启与成员变更后不稳定，官方明确要求不要对 rank 的稳定性、以及 rank 与 local_rank 的相关性做任何假设。
  • 弹性开启时 WORLD_SIZE 会变，checkpoint 里要记录 world_size 与 shard 方案，恢复时按新 world_size 重切。
  • 只在 RANK==0 存盘要配原子写（写 tmp + os.replace），否则半个文件会被当成有效 checkpoint。
  • 在日志里打印 TORCHELASTIC_RESTART_COUNT 与 TORCHELASTIC_RUN_ID，很多「数据重复」的问题一打印就现形。

⑤ 卡死：初始化完成但集合通信不返回

NCCL timeout / Watchdog caught collective operation timeout · ProcessGroupNCCL is aborting · 或者干脆没有任何输出，torchrun 一直挂着

  • 先判断是「组里少了一个 rank」还是「网络坏了」：nvidia-smi 看每张卡上是否都有进程；--tee 3 --log-dir 把每个 rank 的日志落盘，看谁的进度条停住了。
  • 集合通信次数/顺序不一致（某个 rank 进了 if 分支）是最常见的根因 —— 检查是否有依赖数据的控制流、以及 DistributedSampler 的 set_epoch。
  • NCCL 的两种等法：TORCH_NCCL_BLOCKING_WAIT=1（阻塞等待）或 TORCH_NCCL_ASYNC_ERROR_HANDLING=1（异步中止，torchrun 会透传）；配 TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC 能拿到更早的报错。
  • 多网卡机器：NCCL_SOCKET_IFNAME=eth0 / NCCL_IB_HCA=... 指错网卡时，会以「连不上但也不报错」的方式卡住。
  • 用 torch.distributed.breakpoint() 或 TORCHELASTIC_ENABLE_FILE_TIMER=1 的文件看门狗抓「进程还在但不推进」。

⑥ worker 挂掉 → 全组被杀，看起来像「莫名其妙重启」

[default0]: exitcode: 1 (pid: 12345) · [default2]: exitcode: -9 · ChildFailedError: torchrun failed with 1 ... (附各 rank 时间戳与 traceback)

  • OOM 被内核杀 = exitcode -9，看 dmesg | tail；显存 OOM 则是 CUDA OOM 的 Python 异常。
  • 任何一个 rank 抛未捕获异常，torchrun 就停掉全组（这是设计，不是 bug）。所以看到「8 个 rank 全崩」时，要按时间戳找最早那个，torchrun 已经帮你标了 root cause。
  • 没加 @record 时错误摘要里只有 exitcode 没 traceback —— 这是官方点名推荐的修饰器，直接加。
  • 被 SIGKILL 卡在 D 状态的进程会拖住重启；新版 agent 会把卡住的 worker group 标成 UNHEALTHY 并放弃重启，此时看日志里的 D-state 提示。

12三个高频误解

误解 1：「torchrun 就是多了个循环的 python -m torch.distributed.launch」

launch 是老 API，只管「起 N 个进程、给 --local_rank」；torchrun 走的是 torchelastic 的 agent + rendezvous：多机拓扑由 rendezvous 决定、有成员变更语义、有重启预算、有 root cause 汇总。launch 里那些 --use-env/--node-rank 的旧行为只作为兼容参数留在 --node-rank 上。

误解 2：「--max-restarts=3 是每个 worker 3 次」

是 worker group 3 次。任何一次失败都停掉全部 worker、重新 rendezvous、全部重开，且不计入 monitor 的失败计数 —— 弹性成员变更甚至不消耗这个额度。

误解 3：「rdzv 和 init_process_group 用的是两套东西，所以能各配各的」

两者确实各有一套（rdzv endpoint 29400 vs 训练 store），但 c10d 模式下训练 store 的地址是由 rendezvous 决定并广播的，手工改 MASTER_PORT 无效。只有在 static 模式下才是「你说了算」。

一句话记住控制面与数据面

控制面：torchrun/agent/rendezvous/store，管「谁参加、你是几号、挂了怎么办」，走 TCP + KV。
数据面：worker 之间的 NCCL/NCCL-IB，管「梯度怎么换」，走 NVLink/IB/RoCE。两者的日志、报错、调优参数完全不通用。

自测题：4 个节点 × 8 卡，node2 上 local_rank=5 的进程，它的 RANK / WORLD_SIZE / GROUP_RANK 各是多少？

LOCAL_WORLD_SIZE = 8、GROUP_WORLD_SIZE = 4 → WORLD_SIZE = 32；GROUP_RANK = 2（static 下即 --node-rank=2）；RANK = 2 × 8 + 5 = 21。

追问：如果第 3 个节点在训练中途掉线、--nnodes=1:4 弹性生效，重启后这个进程的 RANK 还是 21 吗？不一定 —— 新一轮 rendezvous 会重新排座次，WORLD_SIZE 也可能变成 24。
