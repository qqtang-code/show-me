show-me 知识库体检：改了什么，以及为什么这么改

对 18 篇条目做的一轮实测审查，以及随后的落地。结论跟直觉相反：不需要重做视觉或技术栈，问题集中在发布契约、检索排序和状态语义上——而且其中一项功能从来没真正生效过。

结论01 保留什么02 发布契约03 搜索04 首页与卡片05 标签与状态06 一个真 bug07 还没做的

范围：线上门户、19 份 meta.json、文章外壳、搜索与构建脚本。数字来自本地复算、headless Chrome 与 verify_site.py；未逐条核验各文章的技术结论。

TL;DR · 六项判断

  • 视觉不用推倒重来。改动后完整验收 70 PASS / 0 FAIL / 1 SKIP，六档宽度无整页横向溢出。
  • 锚点是坏的，而且检查器看不见。23 处分类链接指向不存在的 id；旧的链接检查只判断文件存在，锚点写错照样全绿。
  • 标签筛选从来没生效。.card 自带的 display:flex 盖掉了浏览器对 [hidden] 的默认 display:none，实测点标签前后都是 19 张卡片。
  • 搜索按归档顺序返回。没有相关度排序、没有词边界；TP 复算出 44 处结果，all-reduce 与 AllReduce 是两组不同结果。
  • 发布语义糊在一起。visibility 一个字段同时承担「原料多敏感」和「能不能公开」，5 篇公开页面上写着 internal。
  • 卡片摘要更像 abstract。平均 262 字符、最长 475，同一行两张卡无法横向比较。

02发布契约：让检查器真的能拦住问题

一句话：先修「检查器看不见」和「一个字段两种含义」，否则后面的规则都建在沙上。

问题处理验证
分类锚点失效shell.py 与正文里手写的面包屑统一改为 index.html#cat-<category>；check_links.py 开始解析 #fragment 并与目标页面的 id 集合比对。已修 先在 23 处上失败，修完 20 个页面 0 失效。
发布语义混用一个字段拆成两个：visibility 记原料敏感度，publish 记是否已批准公开；publish:false 不进门户、不进 README、不参与上一篇/下一篇。旧的 public-ok 归一到 public。已修 5 篇 internal 保留原料标记、publish:true 明确公开。
脱敏没覆盖元数据构建期把 cwd 的绝对路径改写为仓库相对路径；其余字段若仍有本机绝对路径或完整 session id，直接中止构建（不打印原值）。已修 4 份被自动改写，公开元数据里 0 条绝对路径。
同步允许带病发布sync.sh 在链接检查失败时中止且不提交；push 失败改为返回非零。已修 故障注入：坏锚点会阻止提交。
一条判断留给你：visibility: internal 不等于「正文没脱敏」，所以我没有批量把 5 篇下线——那会把公开内容凭空拿掉。现在的读法是「原料来自内部，已脱敏并批准公开」。若某篇其实不该公开，把它的 publish 改成 false 即可，构建会自动把它从站点里摘掉。

04首页与卡片：先帮读者做选择

1
hero 改成读者视角。原来首屏在讲 index.html / notes.md / meta.json 怎么组织——那是维护者视角，已移到页脚；首屏改成「写给做推理与多卡部署的实践者」。
2
去掉没有兑现的模板承诺。门户原写「每篇都按速览 → 机制 → 实测 → 常见误解 → 自测」，实际并非每篇都有。改成「常见结构，具体小节以页面为准」。
3
压缩卡片摘要。one_liner 平均 262 → 186 字符，最长 475 → 234，超过 240 字符的从 9 篇降到 0 篇，关键数字一个没删。
4
加「最近更新」，并让漏收录自己冒出来。审查时路线只覆盖 12/18 篇，且 curation.json 自 2026-10-21 起没再改过——之后发布的 6 篇一篇都没被考虑。现在路线覆盖 17/19，构建期还会对「既不在 routes 也没登记进 unlisted」的条目告警。

05标签、路线与「已打开」

标签：从自由累加改为受控词表

新增 taxonomy.json，构建期把同义写法归并到规范写法，各篇 meta.json 保留作者原词。结果：唯一标签 95 → 92，只出现一次的 75 → 69；AllReduce 从 3 篇变 5 篇（allreduce / all-reduce 合并），DSA 与 GLM 系列 同样收敛。

代价说清楚：归并会让某些具体写法在标签列表里消失（例如 GLM-5.3），它们仍保留在各自的 meta.json 与正文里，只是不再各自占一个标签位。

路线：区分 path 与 collection，并补上漏收录

curation.json 增加 kind：path 表示前一篇是后一篇的前置，collection 表示同方法合集、可挑读。门户按 kind 显示「路线 · N 篇」或「合集 · N 篇」。

补成员时发现「多卡通信」一条路线塞不下（DESIGN.md 约定每条 3–5 篇），于是按问题拆成两条：集合通信怎么省时间（原语 → 少搬字节 → 砍固定开销 → 藏进计算 → MoE 的 A2A 内核）与 并行切分与跨机通信（CP 换算子 → EP 改权重排布 → TP16 跨机分层）。stream-interval 移入「源码走读与实践」——它本来就是对着一个开关走源码。

清单改成了对象形态：routes 之外新增 unlisted，显式登记「确认不进路线」的两篇（横向对比、站点自身的体检页）。否则构建期会一直把它们当漏收录，告警噪声一多就没人看了。

「已打开」：把记账点从卡片挪到目的地

原来唯一写入 showme:opened 的地方是门户卡片的点击监听，从推荐路线、搜索结果、上一篇/下一篇或外链进来都不记录。现在文章页 shell 加载时按 <cat>/<slug>/ 自己落一次盘，门户只负责展示；门户侧也改成按 data-dir 统一监听，路线与最近更新的链接一并覆盖。

06过程中挖出来的真 bug：标签筛选从未生效

给搜索命中行加折叠时，我用 hidden 属性切换可见性，顺手验了一下现有代码——结果发现门户的标签筛选一直是坏的：

实测（headless，:root 未改）
  隐藏 2 张卡片后可见卡片数   19 → 19      ← hidden 没起作用
  点 SGLang 标签后可见卡片数   19 → 17      ← 只隐藏了空分类，同分类内的不匹配卡片仍在
  修复 [hidden]{display:none!important} 后
  隐藏 2 张卡片后可见卡片数   19 → 17
  点 SGLang 标签后可见卡片数   19 → 11      ← SGLang 确实对应 11 篇

原因是 .card{display:flex} 属于作者样式，会盖掉浏览器 UA 样式表里 [hidden]{display:none} 的默认值——这不是本项目特有的坑，任何「先用 hidden 属性切换、又给元素写了 display」的列表都会踩。原来的探针没抓到，是因为它只检查 computed display，而分类页签恰好靠隐藏 .cat 容器生效，看起来「筛选能用」。

教训：交互验收要断言「数量确实变少且等于预期」，而不是「数量变了」。类别筛选和标签筛选看起来是同一个功能，实际一条走容器、一条走卡片，只有后者坏了。

07还没做的，以及为什么

级别事项判断
P2给源码型文章加 applies_to / verified_at，区分写作日期与源码版本。有价值但要逐篇回填，且需要先确定「版本对齐到什么粒度」，不如等下次内容更新时顺带补。
P2拆内联搜索索引、按需加载。门户现在约 600 KiB / gzip 约 240 KiB，19 篇仍可接受，而且内联才能离线搜。等内容翻倍、首屏成本成为实测问题时再做。
P2opened 的「已读进度」是否也要在文章列表高亮。当前只标卡片。路线与最近更新用的不是卡片结构，加标记需要另一套样式，收益不明显。

明确没做：换肤、深色模式、React/Vite 重构、服务端搜索、为分类齐全而拆空分类。这些都不解决本轮暴露的问题。

这份记录没有断言什么？
没有断言各篇文章的技术结论正确或错误。也没有把 internal 直接等同于「正文该不该公开」——那是维护者按原始材料判断的事，这里只把两个含义拆成两个字段，让判断变得可表达。
为什么锚点问题之前一直是绿的？
因为链接检查把 # 之后的部分直接丢掉了，只验证 index.html 这个文件存在。读者点过去不会 404，只是停在页首——这种「看起来能用」的坏链接，只有真的去解析 fragment 才会暴露。
